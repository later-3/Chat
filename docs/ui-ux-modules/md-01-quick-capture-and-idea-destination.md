## 1. 本轮只解决什么

用户正在任意 Chat 页面工作时，突然想到一句尚未分类的话：

1. 不先选择 Project、Work、Note 或日期，也能把原始表达留下。
2. 明确区分草稿、保存中、已保存、保存失败和“已接受为正式 Idea”。
3. 保存后能撤回候选或在稳定位置重新找到。
4. 以后关联已有对象或升级为 Note、Work、Project 时，原话和来源不丢。

本轮不设计 Personal Home 本身、Today 排序、Calendar、日终复盘、Personal Workspace、Project Dossier、
Workflow Run View，也不把原型壳误记为后端已经实现。

## 3. Chat 怎样吸收

| 结论 | 采用或改造 | 原因 |
|---|---|---|
| 全局捕获是动作，不是新一级页面 | 采用；桌面为顶栏动作与快捷键，手机为底部浮动动作 | 用户不应为了先记一句话离开当前工作 |
| 先进入统一待整理区 | 改造；落为“类型未定的 Idea 候选”，不是 Task，也不是正式 Idea | 降低当下分类成本，同时避免模型替用户作决定 |
| 解释放在输入附近 | 采用；明确写出“保存原文与来源、不发模型、不自动建 Project/Work” | 让用户看到这次动作的真实后果 |
| 捕获后再归类 | 采用；在待整理区提供“保留为 Idea / 关联已有 / 升级为…” | 保存和分类是两个事实，任一步失败都不应丢原话 |
| 保存结果可重新找到 | 改造；成功 Toast 给“查看”，稳定入口为 Garden 的待整理区 | Toast 是短反馈，不承担长期找回 |
| 失败时保留输入 | Chat 自主补齐；显示未保存、重试和复制出口 | Routine 公开材料没有证明这一保证 |
| 普通撤销不等于删除 | Chat 自主补齐；撤回候选/关系，原始 Message 来源仍保留 | 删除来源是另一个高影响动作 |

明确拒绝：裸文本静默变成 Task、把本地草稿冒充已保存、保存后立即强迫填写对象表单、用 Delete 或
Won't do 冒充 Undo，以及在没有证据时声称支持离线队列或跨端恢复。

## 4. 候选交互合同

这不是正式 Schema，只固定用户可见语义：

```text
Input Draft
→ 零模型、零 Agent Run 的 Interaction / User Message 被接纳
→ 类型未定的 Idea 候选
→ 用户接受
→ Note(kind=idea)
→ 以后关联已有对象或升级为 Note / Work / Project
```

其中 3 个事实必须分开：

1. **原话已保存**：权威 Message 已被接纳，可重新找到。
2. **候选已接受为 Idea**：此时才成为正式 `Note(kind=idea)`。
3. **已经关联或升级**：目标 Owner 成功提交，并留下稳定目标 ID 与来源回链。

同一次技术重试必须通过稳定 Command ID 幂等返回同一结果；用户后来再次输入相同文字属于新的真实输入，
只能提示可能重复，不能自动合并。升级回执丢失时必须先查询或对账，不能再创建第二个目标对象。

## 5. 原型中的主路径与风险态

### 5.1 正常主路径

1. 用户从任意页面点“捕获”，或在桌面按 `⌘/Ctrl + Shift + K`。
2. 桌面打开居中轻量层；手机打开底部 Sheet，不离开当前页面。
3. 输入层预告落点为“待整理 · 类型未定”，并解释不会启动模型或自动创建正式对象。
4. 保存成功后关闭输入层，Toast明确“原话已保存到待整理”，提供“撤销”“查看”“关闭”，并在10秒后自动消失。
5. “查看”进入 Garden 的待整理区；“保留为 Idea”可完整演示，关联已有对象与升级入口禁用并明确标为待实现，
   避免用可点击假按钮冒充后端合同已经存在。
6. 接受为Idea后，界面才显示“正式Idea”；撤销接受会退回待整理，并把成功Toast替换为“已撤销接受”。
7. 撤回待整理不会删除原始Message：捕获层明确显示`MSG-01`仍已保存、当前只是可编辑副本；重新放入待整理
   会继续引用同一来源，不创建第二份Message。

### 5.2 最高风险态

离线或保存失败时：

1. 不关闭输入层，不清空文字。
2. 明确写“尚未保存到 Chat”，不能显示成功 Toast。
3. 同时提供“重试”和“复制原话”。
4. 原型只演示反馈；离线队列、跨刷新草稿恢复、幂等写入和对账仍待后端实现。

## 6. 桌面、手机与视觉取舍

1. 继续使用已批准的暖中性色、青绿色主色和珊瑚色风险强调，不引入 GitHub Actions 式开发者流水线或紫色 AI 渐变。
2. 桌面输入层保持单一主动作，背景保留空间定位；不把捕获做成完整编辑器。
3. 手机使用底部 Sheet，主按钮全宽，浮动捕获按钮位于五项底部导航之上。
4. 正常、已保存、待整理、正式 Idea 和保存失败使用不同文案与视觉层级，不只靠颜色区分。

## 7. 用户已批准的4项决定

| 决定 | 当前建议 | 如果不这样做的主要代价 |
|---|---|---|
| D1 入口形态 | 全局动作 + 桌面快捷键；不是一级页面 | 独立页面会打断当前上下文，也增加导航负担 |
| D2 默认落点 | 保存为 Garden“待整理”中的类型未定候选；不直接成为正式 Idea | 直接建 Idea 会把系统推断冒充用户决定；只留本地草稿又不可靠 |
| D3 分类时机 | 先保存，之后再“保留 / 关联 / 升级”；捕获时不展开表单 | 当场分类会把低成本捕获变成对象创建流程 |
| D4 反馈与撤销 | 成功Toast提供“查看/撤销/关闭”并自动消失；失败保留文字并给“重试/复制”；普通撤销显示稳定来源ID且不删除原始Message | 只给“保存成功”会让找回和恢复不明确；撤销即删除会破坏证据链 |

2026-08-01用户看过可操作原型及本地单文件呈现后，明确认可当前模块整体效果与交互逻辑。该结论批准本表
`D1`—`D4`当前revision，`IU-104`、`IU-105`进入交互设计已批准记录；若后续改变默认落点、分类时机、撤销语义
或来源保留合同，必须重新提交受影响决定。代码实现状态仍保持待实现。
