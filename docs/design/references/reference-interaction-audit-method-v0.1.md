# 参考产品交互审计方法 v0.1

## 1. 结论

参考产品不能再以“产品名 + 1 张截图 + 3 条 Take”结束。它必须成为一份可以约束 HTML 原型的**交互证据包**：看清对象层级、入口、下钻、返回、状态变化和设计理由，再决定 Chat 取、改或拒绝什么。

Basecamp 是第一份样板，并已于 2026-08-08 通过用户审核。Things、Linear、Heptabase、HEY Calendar 和 Microsoft Agent Feed 使用同一模板重做。

## 2. 每个锚点产品的最低证据

每个锚点产品至少覆盖：

1. 1 张全局/账户级入口界面。
2. 1 张主对象空间，例如 Project、Today 或 Feed。
3. 1 张工具/列表视图。
4. 1 张对象详情。
5. 1 张返回、关闭或跨空间跳转后的状态。
6. 1 张异常、空态、通知或需要介入状态。

不是为了凑满 6 张图，而是至少证明 1 条完整路径和 1 条恢复/例外路径。外部截图只放在仓库外研究包；仓库内只记录官方来源、观察结论和可审核的产品翻译。

## 3. 七层审计框架

### 3.1 产品对象与作用域

先画清楚对象，不从组件开始：

```text
Account / Workspace
  → Project / Personal scope
    → Tool / View
      → Item / Thread / Run / Artifact
```

每个界面必须注明当前作用域、主对象和返回到哪里。若同一名词在不同作用域含义不同，单独记录。

### 3.2 页面职责

每个页面只回答 1 个主问题，例如：

- Home：我现在去哪里？
- Project：这个项目有哪些稳定协作场所？
- Activity：刚发生了什么？
- New for you：什么是明确送到我这里的？

若一个页面同时声称解决 3 个以上主问题，标记为高风险拼盘。

### 3.3 可点击对象

每个关键点击记录：

| 字段 | 要回答的问题 |
|---|---|
| Trigger | 点击、键盘、拖拽还是系统事件？ |
| Precondition | 权限、选择或当前状态是什么？ |
| Surface | 原位变化、Popover、Peek、整页、标签还是新窗口？ |
| Result | 哪个对象或状态发生变化？ |
| Persistence | 刷新、返回、跨设备后是否保留？ |
| Recovery | Esc、关闭、浏览器返回后回到哪里？ |
| Feedback | 动效、焦点、文案、徽标如何确认动作？ |
| Evidence | 截图观察、官方说明、实际操作或推断？ |

### 3.4 信息与动作层级

分别标注：

1. 全局导航。
2. 当前作用域导航。
3. 个人聚合入口。
4. 管理/低频动作。
5. 当前对象主动作。
6. 次级动作和危险动作。

空间位置本身也是设计决定，不能只记录按钮名称。

### 3.5 状态与反馈

至少验证 default、hover、focus、pressed、loading、success、empty、error、disabled。若官方证据不足，不把推断写成事实；在 HTML 实验中把它变成待验证假设。

### 3.6 设计理由

每个模式必须回答：

1. 它降低了哪一种认知或操作成本？
2. 它牺牲了什么？
3. 它依赖什么对象模型或使用频率才成立？
4. 复制外观但没有复制底层模型时，会坏在哪里？

### 3.7 Chat 翻译

对每个模式做三分法：

- `Take`：可直接作为交互原则。
- `Adapt`：保留职责，改写对象、作用域或状态。
- `Refuse`：与 Chat 的产品不变量、可访问性或长期规模冲突。

必须写出映射对象，例如 `Basecamp Activity item → Chat Project/Work/Run 的事件投影`，不能只写“参考时间线”。

## 4. 证据强度

所有判断使用以下标签：

| 标签 | 含义 |
|---|---|
| `O` Observed | 从当前截图或实际操作直接观察 |
| `D` Documented | 官方帮助/文档明确说明 |
| `I` Inferred | 根据结构推断，尚需实测 |
| `C` Chat hypothesis | Chat 自己的产品翻译，不归因于参考产品 |

`I` 不能进入正式交互合同；它只能进入待验证列表。

## 5. HTML 原型前的新完成门

UL1 开始前必须满足：

1. Basecamp 深审计样板通过。状态：**已完成，2026-08-08 用户确认**。
2. 其余 5 个锚点产品各完成 1 条完整路径。
3. 每个 Chat 核心场景有明确的主参考、辅助参考和反参考。
4. 至少 10 个关键交互已经写出触发、结果、返回和状态反馈。
5. UI Lab 的每个实验被定义为“行为切片”，不是静态页面复刻。

## 6. 审计产物

每个产品交付 3 个结果：

1. 仓库内审计文档：事实、推断、设计理由和 Chat 翻译。
2. 仓库外可视参考页：真实截图、热点与状态路径，供用户直接标注。
3. HTML 行为切片任务：只实现改变 Chat 设计判断的关键交互。
