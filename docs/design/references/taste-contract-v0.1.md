# Chat Taste Contract v0.1

> **设计命题：安静的项目系统，鲜活的 Agent；严肃的事实，轻巧的交接。**

这份合同解决的不是“把页面做漂亮”，而是让 Chat 在每次设计取舍中保持同一种判断。它是待审核提案，不覆盖现有的 [`design-guidelines.md`](../../product/design-guidelines.md)；批准后的新增规则应提炼进正式规范，而不是长期维护第二套规范。

## 0. 适用边界

### 0.1 这次要解决

1. 项目、会话、Today、工作台、Agent 动态之间的视觉人格与交互连续性。
2. AI 规划、决定、执行、验证、正式提交之间的真实状态表达。
3. “有趣、有个性”如何落到结构、节奏、文字、声音和动作，而不是贴装饰。
4. 草图与 HTML 原型的统一验收标准。

### 0.2 这次不解决

1. 不先画完整设计系统或组件库。
2. 不为尚未进入产品范围的社交功能写生产组件。
3. 不从参考项目复制布局、品牌资产或像素。
4. 不用视觉稿改写已经冻结的产品事实、状态机和权限边界。

### 0.3 目标态 8 状态故事板

这是包含长期 Project/Work、Context Package 与后续能力的**目标态设计故事板**，不是当前仓库已实现能力清单。当前实现范围仍以 [`PROJECT_STATE.md`](../../../PROJECT_STATE.md) 为准。

| 状态 | 主要问题 | 视觉重心 |
|---|---|---|
| 1. 项目落点 | 这个项目现在在哪里，我该接哪件事？ | 目标、阶段、活动 Work、需要介入 |
| 2. 工作立约 | 这次工作要交付什么，明确不做什么？ | 期望结果、验收条件、范围 |
| 3. 上下文装配 | 本轮究竟采用了哪些项目事实？ | Context Package、来源、采用/排除 |
| 4. 规划交接 | 系统是否已经拥有可审核的计划？ | 规划阶段、票据、待审核入口 |
| 5. 计划决定 | 我批准的是哪一版、会产生什么影响？ | Plan revision、风险、权限、决定 |
| 6. 执行看护 | Agent 正在推进哪一步，是否需要我？ | Run/Attempt、Step、阻塞与证据 |
| 7. 候选验收 | 结果候选是否满足标准、能否正式提交？ | Candidate、Validation、Evidence、Diff |
| 8. 交付回执 | 什么已经成为项目正式事实？ | Artifact、Commit 回执、revision、下一步 |

8 个状态共用同一个 Project Shell；它们是同一工作的连续投影，不是 8 套互不相关的页面。

## 1. 目标人格

### 1.1 五个感受词

| 感受 | 用户应当感到 | 不应滑向 |
|---|---|---|
| 沉静 | 页面把注意力还给事情本身 | 冷漠、空洞、像后台系统 |
| 清楚 | 一眼知道现在发生了什么、下一步是什么 | 信息过少、只能靠猜 |
| 可信 | 候选、决定、执行和正式结果彼此可辨 | 用动画或语气假装完成 |
| 可触摸 | Work、产物、交接像有形对象，可以拿起、展开、放下 | 拟物装饰或大面积纹理 |
| 略带机灵 | 局部动作和文案让人记住 | 卖萌、段子化、游戏化奖励 |

### 1.2 性格比例

- 系统骨架：`沉静 70 / 活泼 30`
- Agent 表达：`克制 55 / 鲜活 45`
- 事实状态：`严肃 90 / 轻巧 10`
- 探索空间：`结构 60 / 自由 40`

这些比例只是方向探索的旋钮，不进入量化评分。个性主要来自**对象行为、节奏和语言**，不是来自更多颜色、更多圆角或更多插画。

## 2. 三个专属交互语法

这些语法是 Chat 的候选“记忆点”。它们首先承载语义，视觉形式在方向探索时再确定。

### 2.1 票据 Ticket

对话中的意图被整理成一张可以交给 Project/Work 的“票据”。票据至少携带来源会话、目标、当前项目、采用的 Context Package 与提交状态。

- **出现条件**：Context Package 已正式提交为不可变产品事实，并可按 `id / revision / hash` 定位；被后续编译的是 Planning Input。
- **主要动作**：展开来源、修订目标、送入工作台。
- **禁止**：用户刚输入一句话就播放“生成任务卡”动画；本地草稿不得伪装成已记录 Work。

### 2.2 接力结 Relay Knot

人和 Agent 交接控制权时，界面用同一个连接点表达“谁持有下一步”。它不是加载动画，而是决定、恢复和执行之间的责任标记。

- **出现条件**：Decision 已正式记录；只有 Chat 的权威 Query 显示对应 Run/Attempt 已恢复执行后，才把控制权移交给 Agent。Workflow Hook 是后端私有机制，不成为用户状态。
- **主要动作**：查看决定版本、进入运行证据；只有产品合同与服务端 `allowedActions` 明确支持时，才显示停止后续执行或新的处置命令。
- **禁止**：按钮一按就直接显示执行中；持续呼吸、无限旋转或虚构队列位置。

### 2.3 落印 Stamp

只有正式产物或正式消息提交到 Product Store，并且证据可定位后，才出现一次短促的“落印”反馈。

- **出现条件**：`product_commit` 成功，正式对象 ID、revision/hash 与证据齐全。
- **主要动作**：打开产物、查看证据、回到项目。
- **禁止**：Provider 返回、Agent 自述完成、执行候选生成或本地缓存成功时提前落印。

## 3. 空间与对象连续性

### 3.1 六个空间的职责

| 空间 | 回答的问题 | 主要对象 |
|---|---|---|
| Today | 今天真正要关心什么？ | 日程、待办、需要决定、正在运行、阻塞 |
| Project | 这件长期事务现在走到哪？ | 目标、阶段、Work、决定、文档、Agent |
| Conversation | 我们正在讨论和决定什么？ | Message、引用、草稿、候选、决定入口 |
| Workbench | 系统正在怎样推进？ | Plan、Run、Step、Evidence、Artifact Candidate |
| Pulse | 哪些变化值得我看？ | 有来源的 Agent 动态、项目变化、需要接手的事项 |
| Agents | 谁负责什么，边界是什么？ | 身份、职责、权限、项目关系、近期活动 |

### 3.2 连续性硬规则

1. 同一个 Project、Work、Run、Decision 或 Artifact 在不同空间保持同名、同身份标记和同状态语义。
2. 从会话进入工作台时保留原位置；关闭预览应回到原滚动位置和焦点。
3. 桌面与移动端允许重排空间，但不得把同一对象重新包装成互不相干的卡片。
4. Project、Work、Conversation、Workbench 是稳定导航；运行状态不能让整个壳层频繁重排。
5. 深链接和浏览器返回必须可预测；“回去”不等于回到产品首页。

## 4. 构图与信息密度

1. 每个状态只回答 **1 个主问题**，只突出 **1 个主动作**。
2. 同一视口最多同时出现 3 个信息层级；同一对象最多使用 2 层容器表面。
3. 超过 5 个同级对象时，默认使用列表、时间线、表格或空间分组；不得继续堆卡片。
4. 卡片只用于确实具有独立边界、可单独操作或可跨空间移动的对象。标题、提示、统计和筛选项不自动卡片化。
5. 正文的理想行长为 24–40 个中文字符；需要长读的 Artifact 使用专用阅读宽度。
6. 空白代表节奏和归属，不代表“高级感”；任何大块空白都应能解释它在保护什么注意力。
7. 工作流图只在拓扑、并行或证据关系确实重要时出现；线性工作默认用步骤叙事。
8. Today 默认按时间、责任和需要介入程度组织，不做“所有模块的仪表盘拼盘”。

## 5. 排版、形状与材料

### 5.1 排版

1. 沿用系统字体栈，不通过新 Web 字体制造性格。
2. 工作状态默认使用 13 / 15 / 17 / 20 四级字号与 400 / 600 两档字重。
3. 当前 HTML 原型仍只使用正式规范批准的 13 / 15 / 17 / 20。代码中已有的 28 / 30 / 40 不等于已获规范授权；如选定方向确需用于 Today、Artifact 或身份时刻，必须先更新正式规范与 Token 用途后再使用。
4. 数字、版本、时间和耗时使用 tabular numerals；禁止斜体和全大写作为常规强调。
5. 文案层级首先靠词序、留白和字号，最后才考虑颜色。

### 5.2 形状

1. 沿用 10 / 14 / 18 三档圆角。
2. 当前 HTML 原型继续使用正式规范批准的 10 / 14 / 18。代码中已有的 `999px` 不自动授权新用法；头像、状态点或真正的胶囊控件如需使用，必须先在正式规范中补充用途。
3. 结构主要依靠背景层级和 1px hairline；默认 0 重阴影、0 发光描边。
4. 一个视口最多出现 3 种明显面板尺寸；尺寸差异必须对应职责差异。
5. 禁止把 Sparkle、Robot、Magic Wand、Brain 作为默认 AI 图标。Agent 身份优先用姓名、头像/符号与职责表达。

### 5.3 材料感

Chat 的材料不是玻璃，而是“纸、票据、线、印记”的轻量数字化：清楚的边缘、有限的折叠、明确的来源和去向。只允许在能说明对象状态时出现局部材料暗示，不做全局拟物皮肤。

## 6. 颜色规则

1. 产品骨架继续使用黑白、中性灰与既有状态色；产品界面内 0 渐变。
2. Agent 身份色优先来自珊瑚、橘、黄、暖粉等暖色族，与成功/警告/失败色分离。
3. 单个常规工作视口中，Agent 身份色目标覆盖面积不超过约 5%；超过 8% 视为失控，需要给出理由。
4. Agent 色用于头像、签名线、接力结和极小的来源标记；不铺满动态卡片背景。
5. 颜色永远不是状态的唯一信道；每个状态同时具有文字与形状/图标。
6. 同一 Agent 在所有空间保持稳定身份色；换项目不换人格色。

## 7. 动效与声音

1. 动效服务于“对象去了哪里、状态为何改变、控制权交给谁”。
2. 单次及完整状态动效都保持 150–250ms、`ease-out`；需要分段时，各阶段必须在同一总时长内完成。
3. 同一视口最多有 1 个自动状态动效；装饰性持续动画数量必须为 0。
4. 禁止默认的三点打字泡、呼吸光球、旋转脑袋、彩纸庆祝、随机浮粒子和骨架屏循环闪烁。
5. 长任务使用可解释的阶段、最近证据与更新时间，不用“AI 正在思考”循环动画填补未知。
6. `prefers-reduced-motion` 下取消位移、缩放和非必要脉冲；状态变化仍以文字和结构清楚表达。
7. 声音默认关闭。未来如引入，只允许用于需要人介入、运行恢复和正式落印 3 类事件，并提供独立开关。

## 8. AI 事实与控制权

### 8.1 必须分开的对象

- 浏览器草稿
- 用户正式 Message
- Agent/模型输出片段
- Plan Candidate
- Decision
- Product Run 与 Run Attempt
- Execution Candidate
- Validation Result
- 正式 Message / Artifact

它们不得因为“看起来都像一段文字”而复用同一种完成样式。

### 8.2 状态词典

| 用户可见状态 | 已经成立的事实 | 还不能暗示 |
|---|---|---|
| 草稿 | 只在本地输入区存在 | 已发送、已保存到项目 |
| 正在规划 | 后台规划步骤确实开始 | 计划一定会成功、已知道耗时 |
| 计划候选 | 候选通过结构校验并已发布 | 已批准、将自动执行 |
| 等待决定 | 存在版本绑定的 Approval Request | Agent 已获得执行权 |
| 决定已记录 | Decision 已提交为产品事实 | Workflow 已恢复 |
| 后台恢复中 | 恢复请求已发出，尚未确认执行 | 已执行、已完成 |
| 执行中 | 对应 Attempt 确实运行 | 完成百分比、可靠 ETA |
| 执行候选已生成 | Executor 已返回候选 | 候选已验证或已成为正式结果 |
| 验证中 | 确定性验证已经开始 | 一定会通过 |
| 验证通过 | Validation Result 已通过 | 正式对象已经存在 |
| 已正式提交 | Product Commit 成功且正式对象可定位 | 外部副作用一定已发生，除非已有对账证据 |
| 结果未知 | 外部系统可能已接收，但无法确定结果 | 安全重试、失败或成功 |

“决定已记录 → 后台恢复中 → 执行中 → 执行候选已生成 → 验证中/验证通过 → 已正式提交”是不同事实，不能压缩成一个带动画的“完成”。按钮请求期间可以显示本地瞬时的“正在提交请求”，但它不能暗示服务端 Product Commit 已开始，也不能在刷新后冒充产品状态。

### 8.3 AI 透明度

1. 用户应能知道哪部分由 Agent 生成、依据什么来源、当前是否仍是候选。
2. 高影响动作在执行前必须可读、可修订、版本绑定；主按钮旁明确说明将发生什么。
3. 不展示或伪造模型隐藏推理。解释只呈现可观察证据、采用的来源、规则和产品状态。
4. 不展示未经校准的置信度、完成百分比、队列位置、ETA 或“深度思考程度”。
5. AI 标签是责任说明，不是霓虹装饰；它可展开来源、模型/Agent 角色、限制和反馈入口。

## 9. Agent 动态与社交感

Pulse 的目标是让协作有生命感，不是复制社交媒体的成瘾机制。

1. 每条动态必须回答：谁、在哪个 Project/Work、发生了什么、这是事实还是建议、用户能做什么。
2. 排序优先级为：需要用户介入 > 订阅项目的重要变化 > 正在运行 > 普通近期动态；不使用“热门”或互动量排序。
3. 默认动作使用“查看证据、追问、接手、设为今天、归档”，不使用点赞数、转发数或虚构的在线热度。
4. Agent 可以有稳定语气、头像/符号和身份色，但失败、审批、权限与结果未知场景统一使用事实语言。
5. 相同 Work 的连续动态优先折叠为一条可展开叙事，避免事件风暴。
6. 动态必须显示来源时间和项目归属；聚合摘要要能下钻到原事件。
7. 用户可以按 Agent、Project、需要介入和时间筛选，并明确知道当前排序规则。
8. Pulse 只是 Project、Work、Run、Decision、Artifact 等产品事实的聚合投影；排序、折叠和摘要不能创建新的项目事实。

## 10. 文案合同

1. 状态文案采用“已经发生的事实 + 当前影响”，避免人格化填空。
2. 主动作使用结果动词，如“批准并执行”“请求修改”“打开正式产物”，不用“继续”“确定”“试试看”承担高影响动作。
3. 错误文案必须包含 3 件事：发生了什么、什么仍然安全、用户下一步能做什么。
4. 每屏最多 1 处轻松文案；审批、失败、权限、计费和结果未知场景为 0 处。
5. 系统导航与状态中使用 0 个 emoji；emoji 只可作为用户/Agent 自己的内容或明确选定的身份符号。
6. 禁用默认宣传词：`魔法`、`赋能`、`无缝`、`智能升级`、`解锁潜能`、`一键搞定`、`像魔法一样`。
7. 不说“我已经为你完成”来替代证据；应说“正式产物已提交，可查看 3 条验证证据”。

## 11. 响应式与可访问性

1. 375px 宽度无横向滚动；移动端把空间关系改成顺序关系，不缩成迷你桌面。
2. 所有可点/可触热区至少 44×44px；视觉图标可以更小，热区不能更小。
3. 正文对比度至少 4.5:1，大字号和交互元素至少 3:1；身份色也必须按真实背景测量。
4. 200% 缩放仍能完成核心流程；信息不能被固定高度裁切。
5. 全流程可键盘操作，焦点顺序与视觉顺序一致；抽屉、对话框和 Peek 关闭后把焦点还给触发元素。
6. 状态使用文字 + 形状/图标 + 颜色三通道。
7. `aria-live` 只播报关键状态变化；流式 token、耗时和频繁事件不得逐条播报。
8. “减少动态”“高对比度”和系统主题偏好必须被尊重，不能被品牌动效覆盖。

参考底线： [WCAG 2.2](https://www.w3.org/TR/WCAG22/)、[WAI-ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/)、[Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines/)、[Microsoft HAX Toolkit](https://www.microsoft.com/en-us/haxtoolkit/)、[Google PAIR Guidebook](https://pair.withgoogle.com/guidebook/)、[Carbon AI label](https://carbondesignsystem.com/components/ai-label/usage/)。

## 12. 一票否决清单

出现任一项，方向或原型直接退回，不以总分抵消：

1. 紫蓝渐变、发光球、宇宙背景、机器人头像或 Sparkle 作为默认 AI 视觉。
2. 首页由等尺寸圆角卡片铺满，缺少主次、连续性和真实对象边界。
3. 用三点跳动、伪进度、虚构 ETA 或庆祝动画掩盖系统不知道的事情。
4. Candidate、Decision、Run、正式 Artifact 的视觉与文案无法辨认。
5. 浏览器本地状态、Provider 成功或 Agent 自述被呈现成产品成功。
6. 低对比度灰字、隐藏焦点、仅靠颜色表达状态、触控目标小于 44px。
7. 高频自动动画、进入页面就抢焦点、抽屉关闭后焦点丢失。
8. 组件中新增硬编码色值、间距、字号、圆角或一次性状态语义。
9. 任何参考被像素级复刻，导致 Chat 看起来像换 Logo 的 Linear、Notion 或 ChatGPT。
10. 动态流引入互动量排序、虚构人气或无来源的“Agent 正忙”。

## 13. 100 分验收量表

评分前先过 2 个零分硬门：

1. 产品不变量、事实所有权与权限边界全部通过。
2. [`design-guidelines.md`](../../product/design-guidelines.md) 第 8 节的正式检查清单全部通过。
3. 本 Contract 第 11 节的响应式与可访问性条款全部通过。
