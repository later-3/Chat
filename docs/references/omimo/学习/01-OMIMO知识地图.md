# OMIMO 知识地图

## 1. 一句话理解

OMIMO是一组开放、极简、可独立组合的方法与模型。当前简体中文资料的核心是两层：

- **NUPP**回答“判断项目行为时遵循什么原则”。
- **P3.express**回答“一个普通项目按什么步骤持续管理”。

[OMIMO首页](../omimo.org/zh-hans/index/index.md)强调开放、极简和模块化；[P3.express简介](../omimo.org/zh-hans/modules/p3.express/manual/v2/index.md)说明其由7个活动组和33项管理活动构成。

## 2. 先判断你需要哪类方法

OMIMO的项目方法全景提供4个选择维度：

| 维度 | 左侧 | 右侧 | 实际判断 |
|---|---|---|---|
| 适用范围 | [通用](../omimo.org/zh-hans/modules/landscape/general-vs-domain-specific/index.md) | 领域专用 | 需要跨行业能力，还是只解决软件等特定领域问题？ |
| 使用权 | [自由](../omimo.org/zh-hans/modules/landscape/libre-vs-proprietary/index.md) | 专有 | 能否长期自由使用、修改和教学，还是依赖所有者政策？ |
| 内容规模 | [极简](../omimo.org/zh-hans/modules/landscape/minimalist-vs-maximalist/index.md) | 极繁 | 需要容易执行的核心系统，还是覆盖大量场景的参考库？ |
| 资源形态 | [路线图](../omimo.org/zh-hans/modules/landscape/roadmap-vs-advice/index.md) | 建议/指南 | 当前缺的是可直接执行的路径，还是补充知识？ |

OMIMO主张：先有一条可以运行的路线图，再用指南补充；P3.express就是一条通用、自由、极简的项目管理路线图。

## 3. NUPP六项通用原则

| 编号 | 原则 | 核心问题 | 典型误区 |
|---|---|---|---|
| NUP1 | [结果与事实比隶属关系更重要](../omimo.org/zh-hans/modules/nupp/manual/v1/nup1/index.md) | 我是在保护结果，还是保护自己所属的方法、团队或身份？ | 把敏捷、瀑布、PRINCE2或PMBOK当阵营 |
| NUP2 | [将精力和资源用在最重要的事情上](../omimo.org/zh-hans/modules/nupp/manual/v1/nup2/index.md) | 有限资源现在最值得投向哪里？ | 微观管理、无价值决策、长期加班、忽略团队精力 |
| NUP3 | [始终积极主动](../omimo.org/zh-hans/modules/nupp/manual/v1/nup3/index.md) | 能否在问题发生前规划、暴露和处理？ | 不规划、等风险变成问题、隐藏坏消息、推卸责任 |
| NUP4 | [细节决定成败](../omimo.org/zh-hans/modules/nupp/manual/v1/nup4/index.md) | 是否从整体系统检查最弱环节和相互影响？ | 只看进度、只看流程或随意拼接不兼容的方法 |
| NUP5 | [先定目标，后行动](../omimo.org/zh-hans/modules/nupp/manual/v1/nup5/index.md) | 这项工作、文档或会议具体要产生什么差异？ | 因为模板或惯例而行动，把产出当成收益 |
| NUP6 | [使用可重复的元素](../omimo.org/zh-hans/modules/nupp/manual/v1/nup6/index.md) | 哪些检查、流程和周期值得标准化并复用？ | 每次临时发明，或把可重复流程做得过度复杂 |

六项原则不是六个独立技巧。一个好的项目动作通常同时满足多项：例如每周风险检查既是主动管理（NUP3），也依赖可重复周期（NUP6），但必须只关注最重要风险（NUP2），并服务明确目的（NUP5）。

## 4. P3.express的核心结构

### 4.1 主要角色

| 角色 | 责任 |
|---|---|
| 发起人 | 对项目最终结果、高层决策、资金和资源负责；项目经理向其负责 |
| 项目经理 | 领导管理团队，协调项目管理活动，支持团队而非代替技术工作 |
| 管理团队 | 协助项目经理完成管理活动 |
| 团队负责人 | 领导内部生产团队，负责技术/生产工作 |
| 供应商项目经理 | 领导外部生产团队 |
| 生产团队成员 | 创建可交付成果 |

P3.express明确区分管理与技术生产：资深技术专家并不会因为资历高就自然适合担任项目经理。

### 4.2 四类管理文档

| 文档 | 用途 | 本地模板 |
|---|---|---|
| 项目说明书 | 目标、收益、成本、周期、要求、范围和干系人 | [project-description.odt](../omimo.org/zh-hans/modules/p3.express/manual/v2/project-description.odt) |
| 可交付成果导图 | 用名词分解产品、范围、依赖和优先顺序 | 自行使用思维导图或层级列表 |
| 跟进登记表 | 记录风险、问题、变更请求、应对措施和管理员 | [follow-up-register.ods](../omimo.org/zh-hans/modules/p3.express/manual/v2/follow-up-register.ods) |
| 运行登记表 | 记录同行评审和干系人满意度等项目健康信息 | [health-register.ods](../omimo.org/zh-hans/modules/p3.express/manual/v2/health-register.ods) |

### 4.3 七个活动组和33项活动

| 活动组 | 节奏 | 管理活动 |
|---|---|---|
| A 项目启动 | 每个项目一次 | A01任命发起人；A02任命项目经理；A03任命关键团队成员；A04描述项目；A05确定和规划可交付成果；A06确定风险并规划应对；A07同行评审启动；A08批准/否决；A09启动项目；A10重点沟通 |
| B 每月启动 | 每月一次 | B01修改和优化规划；B02同行评审月周期；B03重新批准/否决；B04启动月周期；B05重点沟通 |
| C 每周启动 | 每周一次 | C01衡量并报告绩效；C02规划偏差应对；C03启动周周期；C04重点沟通 |
| D 每日管理 | 持续/每日 | D01管理风险、问题和变更请求；D02接受完成的可交付成果 |
| E 每月结束 | 每月一次 | E01评估干系人满意度；E02吸取教训并规划改进；E03重点沟通 |
| F 项目结尾 | 每个项目一次 | F01移交产品；F02最终满意度评估；F03同行评审结尾；F04归档文件；F05庆祝；F06重点沟通 |
| G 项目后管理 | 项目结束后周期运行 | G01评估收益；G02形成提高收益的新想法；G03重点沟通 |

计数核对：`10 + 5 + 4 + 2 + 3 + 6 + 3 = 33`。

## 5. P3.express的运行逻辑

```text
A 先判断项目值不值得做，并建立角色、目标、产品、风险与承诺
→ B 每月更新整体计划，重新检查项目是否仍值得继续
→ C 每周预测偏差、协调下周工作
→ D 每天处理风险/问题/变更，并真正关闭可交付成果
→ E 每月从满意度和经验中改进工作方式
→ F 正式移交、复核、归档、庆祝并宣布结束
→ G 项目结束后继续评估收益，推动收益真正实现
```

这套方法的重点不是“更多会议”，而是用不同时间尺度回答不同问题：

- 每日关心即时事项和完成成果。
- 每周关心预测、偏差和协同。
- 每月关心整体计划、项目合理性、满意度和持续改进。
- 项目开始和结束关心正式承诺、移交与组织记忆。
- 项目后关心收益，而不是把交付物完成误认为目标已经实现。

## 6. 五个容易忽略的关键思想

1. **否决或取消不是失败**：如果项目已不再合理，停止投入是良好治理。
2. **按可交付成果而非活动组织范围**：成果用名词命名，工作只是产生成果的手段。
3. **预测比历史汇报更重要**：衡量是为了预测最终时间、成本和目标，而不是展示做了多少工作。
4. **完成必须是真的完成**：接近完成不能标记完成，减少在制品比维持表面进度更重要。
5. **项目结束不等于收益实现**：G组在项目后持续评估和促进收益。
