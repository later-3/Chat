## 1. 先回答：这次到底交付什么

P1.2只交付一个主要结果：**把P1.1的响应式网页变成可安装、能离线打开外壳并保存未发送草稿的PWA，同时把手机端和弱服务器发布边界做实。**

完成后，用户能够：

1. 通过HTTPS在桌面或手机把Chat安装为独立应用。
2. 至少成功在线打开一次后，在断网状态重新打开Chat外壳。
3. 在手机或电脑编辑草稿；刷新、切换会话或重开页面后，草稿仍保存在当前设备并按会话隔离。
4. 离线或服务不可达时明确看到“草稿已本地保存、当前不能发送”，不会出现新消息、成功提示或自动补发。
5. 在刘海屏、圆角屏、底部Home Indicator和软键盘出现时，仍能看见并操作输入框、对话/工作切换和底部导航。
6. 使用现有低性能服务器提供静态站点；编译、测试和打包全部在开发机或CI完成，服务器只接收已验证产物。

P1.2仍是前端任务。它不实现正式消息发送、服务端消息保存、真实Workflow、pi、Memory、BMAD、经验规则系统或服务端离线同步。

## 2. 背景与当前真实缺口

P1.1已经通过PR #2合并，现有Web具备今日入口、会话列表、持续对话、工作窗口、桌面平铺和手机“对话 / 工作”切换，但还不是PWA：

1. `apps/web/index.html`没有Manifest、PWA图标或安装元数据。
2. `apps/web/vite.config.ts`没有Service Worker构建与注册。
3. `ChatPane`中的草稿是组件内存状态，刷新后丢失；不同会话之间也没有明确的持久化隔离合同。
4. `/api/healthz`失败只影响连接提示，但当前本地发送仍可能继续上屏；离线写入边界没有被测试钉死。
5. 手机布局使用固定百分比高度和固定底栏高度，未处理`100dvh`、安全区、安装后的standalone视口和软键盘。
6. 仓库没有PWA真实浏览器离线测试，也没有静态产物部署与回滚说明。

本任务必须修复这些缺口，但不得借机提前实现P1.3的服务端Message合同。

## 3. 用户场景

### 场景A：安装到手机或桌面

用户通过HTTPS打开Chat，浏览器识别出有效Manifest、图标和Service Worker。用户可以从浏览器的安装入口把Chat添加到桌面、启动器或手机主屏幕，并以`standalone`窗口打开。

### 场景B：断网后重新打开

用户至少在线成功打开过一次Chat，随后断网并关闭页面。再次从浏览器或已安装入口打开时，P1.1外壳仍能渲染，连接状态明确显示离线；外壳不能用缓存伪装服务端在线。

### 场景C：未发送草稿跨刷新保留

用户在某个本地示例会话中输入内容但没有发送，刷新或重开页面后再次进入同一会话，草稿仍在。另一个会话只能看到自己的草稿，不能串写。

### 场景D：离线发送安全失败

用户断网或Chat服务不可达时，发送按钮不可执行，Enter也不能生成本地消息。界面用文字说明“当前离线，草稿已保存在此设备，联网后请手动发送”。恢复联网后只恢复发送能力，不自动重放草稿。

### 场景E：手机软键盘与安全区

用户在iPhone和Android手机上以浏览器或已安装模式打开Chat。键盘弹出后输入框仍在可视区域；底部导航不压住输入框；刘海、圆角和Home Indicator不遮挡主要操作；页面本身没有横向滚动。

### 场景F：发布到现有弱服务器

开发机或CI从审核通过的提交执行冻结锁安装、测试、构建和打包，再把静态压缩包及SHA-256校验文件传到服务器。服务器不得运行`pnpm install`、`pnpm build`、`vite`、`tsc`或任何前端编译，只执行校验、解压、原子切换、静态服务重载和必要时回滚。

## 4. 目标与完成后的保证

### 4.1 本任务保证

1. Chat具备有效Web App Manifest、192px/512px图标、maskable图标和Apple Touch Icon。
2. 在支持PWA的浏览器中满足安装条件；生产验收使用HTTPS真实地址，不以`vite dev`代替。
3. Service Worker只预缓存版本化静态外壳，不缓存或排队产品写命令。
4. 已访问过的P1.1外壳在离线时可重新打开。
5. 草稿使用版本化本地Schema，按会话隔离并可在刷新后恢复。
6. 离线发送被阻止且草稿保留；恢复联网后不自动发送。
7. 320px、375px、390px和430px手机宽度下页面无横向滚动，触控目标不小于44×44px。
8. Web静态产物在开发机或CI构建，服务器不承担编译与依赖安装。
9. 新版本可以原子发布并回滚到上一份已验证静态产物。

### 4.2 本任务仍不保证

1. 离线阅读正式历史消息、审批、Product Run或Artifact。
2. 在线发送后的服务端保存、幂等、刷新恢复或跨设备恢复；这些属于P1.3及后续任务。
3. 后台同步、Background Sync、Push通知或自动重发。
4. API、SSE、Workflow或pi在服务器上的部署拓扑。
5. 草稿跨设备同步、加密存储或长期备份。
6. Memory、BMAD、经验规则召回或Workflow计划/执行闭环。

## 5. 技术方案

### 5.1 PWA生成方式

在`apps/web`加入`vite-plugin-pwa@1.3.0`作为构建期开发依赖，使用Workbox `generateSW`策略，不手写一套长期维护的Service Worker缓存框架。

选择依据：

1. 当前Web已经由Vite构建，插件能从实际`dist`生成带Hash的预缓存清单。
2. `1.3.0`的Vite peer range包含Vite 8，Node要求低于本仓库基线。
3. 依赖是MIT许可证，只存在于构建边界；生成后的静态文件由Web服务器直接提供。
4. 如果依赖审计、实际许可证或Vite 8构建验证不通过，Kimi必须先报告，不得使用`--legacy-peer-deps`或忽略安全告警强行安装。

配置要求：

1. 使用`registerType: "prompt"`，不得用会在用户编辑时强制重载的更新策略。
2. 生产构建生成Manifest、Service Worker和注册代码；开发模式默认不启用Service Worker，避免缓存污染日常开发和组件测试。
3. 新版本等待激活时显示克制的“新版本可用，刷新”入口；用户确认后再更新。刷新前草稿必须已经写入本地存储。
4. Service Worker注册失败不能让React外壳白屏；错误只进入不含敏感信息的诊断日志。
5. 在`docs/architecture/version-evidence.md`补充PWA和真实浏览器测试依赖的版本、许可证、用途、边界和退出方式。

### 5.2 Manifest与图标

Manifest至少包含：

1. `name: "Chat"`和`short_name: "Chat"`。
2. 中文说明、`lang: "zh-CN"`。
3. `start_url: "/"`、`scope: "/"`。
4. `display: "standalone"`。
5. 与浅色/深色首屏不冲突的`theme_color`和`background_color`。
6. 192×192、512×512普通PNG图标和512×512 `purpose: "maskable"`图标。
7. `apple-touch-icon`和普通favicon。

图标使用Chat现有黑白、中性、无渐变的产品语言。源SVG与必要PNG是产品源资产，可以提交；构建生成的`dist`不是源资产，不得提交。

生产站点优先使用独立HTTPS Origin。Service Worker作用域不得覆盖同一服务器上已有的`pi-web`或其他应用。如果只能部署到子路径，必须同步配置Vite `base`、Manifest `start_url/scope`、Service Worker scope和服务器fallback，并新增子路径验收；不得用根作用域Service Worker控制无关应用。

### 5.3 缓存白名单与离线外壳

Service Worker只能处理明确白名单：

1. 预缓存构建产生的`index.html`、带Hash的JS/CSS、PWA图标和必要静态资源。
2. 同源页面导航在离线时回退到已预缓存的`index.html`，让React外壳启动。
3. 不增加任何API runtime cache规则。

以下内容必须排除：

1. `/api/**`的所有Query、Command和健康检查响应。
2. SSE事件流、未来的AG-UI事件、审批和Workflow状态。
3. `POST`、`PUT`、`PATCH`、`DELETE`等写请求。
4. Cookie、Authorization响应、Provider内容和任何服务端正式事实。
5. Background Sync队列和自动重放逻辑。

`navigateFallbackDenylist`必须排除`/api`。离线时`/api/healthz`应真实失败并投影为“未连接”，不能由旧缓存返回“ok”。

### 5.4 草稿所有权与存储

草稿属于浏览器本地、可丢弃的页面状态，不是Message。实现一个小而明确的草稿存储模块，不把PWA缓存、正式消息和草稿混进同一个全局Store。

存储合同：

1. 使用`localStorage`即可，不为当前短文本草稿提前引入IndexedDB依赖。
2. 键名包含产品前缀、Schema版本和会话ID，例如`chat:draft:v1:<sessionId>`；具体常量只定义一次。
3. 值通过运行时守卫读取；损坏、未知版本或Storage异常时安全回退为空草稿，不让应用崩溃。
4. 切换会话时保存当前草稿并加载目标会话草稿；不得短暂把A会话草稿显示在B会话。
5. 输入变化后及时保存，页面刷新、Tab切换和离线不依赖`beforeunload`才写入。
6. 离线发送失败不清空草稿。
7. P1.2在线点击发送仍只产生P1.1的“本地预览 · 未发送”，不产生服务端事实；只有这次本地预览成功上屏后才可清空对应草稿。
8. 不把本地预览消息写进草稿存储；正式消息持久化仍属于P1.3。
9. 界面在离线状态明确说明草稿仅保存在当前设备，可被浏览器清理，不能宣称已经保存到Chat服务端。

### 5.5 连接状态与离线发送

1. 监听浏览器`online/offline`变化，并继续保留现有`/api/healthz`投影。
2. `navigator.onLine === false`或Chat服务不可达时，发送能力关闭；连接中也不得先生成成功结果。
3. 发送按钮、Enter键和任何未来快捷入口共用同一个发送守卫，不能只禁用按钮而让键盘绕过。
4. 离线尝试发送时保留输入，并提供可访问的状态说明；不创建新的`ChatMessage`，不显示“已发送”。
5. 网络恢复只更新状态和按钮，不自动执行草稿、不创建Product Run。
6. Service Worker不能拦截健康检查并返回旧在线状态。

### 5.6 手机端布局优化

本任务不是重做P1.1视觉，而是修正安装和真实手机使用会暴露的布局问题：

1. `viewport`加入`viewport-fit=cover`；在兼容浏览器中允许布局随软键盘缩放。
2. 页面高度使用带回退的动态视口单位：先保留`100%`兼容，再使用`100dvh`；不得只依赖固定`100vh`。
3. 顶部、左右和底部主要操作使用`env(safe-area-inset-*)`，底部导航高度包含Home Indicator安全区。
4. 软键盘弹出后，消息区独立滚动，输入框、发送按钮和“对话 / 工作”切换仍可见；关闭键盘后布局恢复。
5. 手机输入框字号不得触发iOS自动放大；新增值必须进入Token，不在组件中写死。
6. 当前手机Tab高度从40px修正到至少44px，所有按钮继续满足44×44px触控热区。
7. 320、375、390、430px竖屏和至少一个手机横屏尺寸下，页面根节点无横向滚动。工作流画布、PPT和白板可以在自己的容器内滚动，但不能撑宽整个页面。
8. 安装后的standalone模式与普通浏览器模式都必须验证；不能只看桌面响应式模拟器。
9. 保持浅色/深色、焦点、减少动效和状态三通道规则不退化。

### 5.7 弱服务器静态发布合同

现有服务器性能较弱，**服务器不是构建机**。发布必须遵循下列顺序：

```text
审核通过的Git提交
-> 开发机或CI冻结锁安装
-> Typecheck/Lint/Test/Build/PWA E2E
-> 生成静态压缩包 + Git SHA + SHA-256
-> 上传到服务器新的release目录
-> 服务器校验并解压
-> 原子切换current指针
-> HTTPS/缓存头/离线Smoke
-> 保留上一版本供回滚
```

硬要求：

1. 服务器上禁止运行`pnpm install`、`npm install`、`pnpm build`、`vite build`、`tsc`和Playwright。
2. 不上传源码、`.git`、`node_modules`、测试缓存或本地配置；只上传Web静态产物、版本元数据和校验文件。
3. 构建使用`pnpm install --frozen-lockfile`及仓库固定Node/pnpm基线；产物必须能追溯到Git提交。
4. 发布包与校验文件放在仓库外的临时/产物目录，`dist`、压缩包和服务器配置秘密不得进入Git。
5. 远端使用每次一个新release目录，校验成功后再原子切换；不得在正在服务的目录内逐个覆盖文件。
6. 至少保留上一份已验证release；Smoke失败立即切回，不在服务器现场修代码或重新编译。
7. 服务器地址、账号、路径和密钥只从用户已有的私有配置或显式环境参数取得，不写进任务书、日志、PR或仓库。
8. 与现有`pi-web`共用物理服务器可以，但必须使用独立Origin或不重叠的静态根与Service Worker scope，不能覆盖`pi-web`文件。
9. 生产切换属于外部副作用：Kimi完成PR后先交用户检视，只有用户明确批准发布时才能执行远端切换。

服务器静态配置至少满足：

1. HTTPS有效，HTTP重定向HTTPS。
2. `index.html`、`sw.js`和`manifest.webmanifest`使用`Cache-Control: no-cache`或等价的每次重验证策略。
3. 带内容Hash的`/assets/**`使用长期`immutable`缓存。
4. SPA页面导航回退到`index.html`，`/api/**`不进入静态fallback。
5. Manifest、JavaScript、SVG和PNG返回正确Content-Type。
6. 发布后可用`curl -I`或等价方式复核HTTPS、缓存头、MIME和Git版本元数据。

## 7. 测试方案

### 7.1 单元与组件测试

至少覆盖：

1. 空草稿、已有草稿、损坏值和Storage抛错时的读取行为。
2. 不同会话分别保存和恢复自己的草稿。
3. 刷新等价重挂载后草稿恢复。
4. 在线本地预览成功后只清理当前会话草稿。
5. 离线或API不可达时，点击与Enter都不调用`onSend`、不清草稿、不新增消息。
6. 网络恢复后草稿仍在，且没有自动发送。
7. 新版本提示不会未经用户确认强制刷新。
8. P1.1的今日、桌面四区、手机切换、主题和fixture标记测试继续通过。

### 7.2 构建产物检查

从干净检出执行生产构建后验证：

1. `dist`包含`manifest.webmanifest`、Service Worker、图标和带Hash的JS/CSS。
2. Manifest字段、图标尺寸、scope和start URL有效。
3. Service Worker预缓存清单含静态外壳，不含`/api`或写请求队列。
4. `index.html`正确引用Manifest和图标。
5. 构建日志没有Workbox文件大小遗漏、Vite peer冲突或被忽略的依赖安全错误。

### 7.3 真实浏览器自动化

使用生产构建加`vite preview`，由Playwright Chromium完成至少一条真实Service Worker场景：

1. 在线首次访问并等待Service Worker激活、控制页面。
2. 打开会话输入草稿，重载后恢复。
3. 切换离线后重新导航，Chat外壳仍出现，状态显示未连接。
4. 离线发送被阻止，草稿与消息数量不变。
5. 恢复联网后没有自动发送。
6. 请求`/api/healthz`在离线时失败，而不是命中旧缓存。

不得只Mock `navigator.serviceWorker`宣称离线外壳已经通过。

### 7.4 手机浏览器人工验收

至少记录以下证据：

1. Android Chrome或等价Chromium手机：安装、standalone启动、离线重开、软键盘。
2. iPhone Safari：添加到主屏幕、standalone启动、安全区、软键盘。
3. 375px审核截图2张：对话输入态、工作流态；另提供至少1张已安装或安装入口证据。
4. 320/375/390/430px与一个手机横屏尺寸无页面级横向滚动。
5. 底部导航、输入框、发送和“对话 / 工作”触控目标均不小于44px。

Playwright设备模拟不能代替iOS主屏安装和真实软键盘验收；如果当前没有对应设备，PR必须把该项标为待用户实机检视，不能伪造通过。

### 7.5 服务器发布验收

用户批准发布后再执行：

1. 在开发机或CI完成全部门禁并生成带Git SHA与SHA-256的压缩包。
2. 上传到新的远端release目录；服务器日志中无依赖安装或编译过程。
3. 原子切换后检查首页、Manifest、Service Worker、图标和`/assets`。
4. 检查HTTPS与缓存头：入口/Service Worker/Manifest重验证，Hash资源长期缓存。
5. 在线访问一次后断网重开，外壳与草稿恢复。
6. 发布第二个可辨认测试版本，确认更新提示和用户确认更新流程；不得强制刷新丢草稿。
7. 演练切回上一release，确认回滚不需要重新编译。
8. 确认同服务器的`pi-web`仍可访问，文件和Service Worker作用域未被Chat覆盖。

## 10. 审核清单

### 产品边界

1. 离线只能保存草稿和打开外壳，没有把本地内容伪装成正式消息。
2. 恢复联网后没有自动发送或后台队列。
3. API与Service Worker缓存边界在代码和测试中都可见。

### PWA与更新

1. Manifest和图标通过真实浏览器检查。
2. Service Worker作用域不会影响`pi-web`或其他站点。
3. 新版本由用户确认更新，不在编辑中强制刷新。

### 手机体验

1. 软键盘、安全区和底部导航不遮挡输入。
2. 页面根节点无横向滚动，内部工作画布允许独立滚动。
3. 触控目标、焦点、主题和减少动效不退化。

### 发布

1. 构建发生在开发机或CI，服务器无编译命令。
2. 产物可追溯到Git SHA并经过SHA-256校验。
3. 发布是新目录加原子切换，可以回滚。
4. `index.html`/`sw.js`/Manifest与Hash资源使用不同缓存策略。

## 11. 明确不做

1. 不实现正式发送消息或服务端Message存储。
2. 不缓存正式消息、审批、运行、SSE或AG-UI事件。
3. 不做Background Sync、Push或离线自动重试。
4. 不实现Vercel Workflow、pi Agent、Memory Adapter、BMAD或经验规则系统。
5. 不创建Workflow编辑器或真实任务规划节点。
6. 不在服务器安装Node依赖或编译前端。
7. 不覆盖、迁移或删除现有`pi-web`部署。
8. 不在用户批准PR前合并或切换生产站点。

## 12. 失败与回滚

1. **Service Worker导致旧页面长期不更新**：入口、Service Worker和Manifest使用重验证缓存头；Hash资源长期缓存；保留用户确认更新入口。
2. **误缓存API产生假在线或旧事实**：不配置API runtime cache，`/api`加入navigation fallback排除并用离线真实浏览器测试证明。
3. **草稿损坏或Storage不可用**：运行时守卫与异常回退保证应用仍可打开；不把草稿提升为正式事实。
4. **新版本发布失败**：原子切回上一release；不在服务器重新编译补救。
5. **Service Worker范围与pi-web冲突**：生产切换前检查Origin与scope；发现重叠则停止发布，先改为独立Origin或严格子路径。
6. **实机键盘遮挡仍存在**：PR不得宣称移动验收完成，保留截图/设备信息并修复后再请求审核。

## 14. 用户最终检视只需确认5点

1. 手机和桌面是否都能安装，安装后是否像独立应用打开。
2. 离线重开时是否仍能进入外壳并继续编辑原草稿。
3. 离线发送是否明确被阻止，没有假消息、假成功或自动补发。
4. 手机软键盘、安全区和底栏是否使用舒服，没有遮挡和页面级横向滚动。
5. 发布是否真正做到“开发机/CI编译，服务器只接收并原子切换静态产物”，且没有影响现有`pi-web`。

这5点确认、PR自动门通过并完成用户审核后，才能合并P1.2并进入P1.3。
