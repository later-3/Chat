| 项目 | 内容 |
|---|---|
| 状态 | 候选，待用户审核后进入实现 |
| 任务类型 | 纯前端UI实现 |
| 目标PR | 1个独立PR |
| 拆分尺度 | 预计0.5～2个单人开发日，超过则继续拆分 |
| 前置条件 | P0工程骨架已完成 |

## 1. 先回答：这次到底做什么

> **范围调整（2026-08 用户批准）**：首版先交付**会话区 + 模型选择 + 本地发送上屏 + 双主题**，工作流运行区暂缓，由后续任务补回（真实数据仍在P1.5/P1.6接入）。发送只做本地即时上屏，不代表服务端已保存；消息持久化属于P1.3。本文件其余章节中工作流区域的描述作为该区域补回时的执行依据。

是的，P1.1是一个**纯前端UI任务**。

它要把Chat最基本的产品界面做出来，而且从第一版开始就包含两个同等重要的区域：

1. **对话区**：用户阅读消息、输入内容的地方。
2. **工作流运行区**：用户看见当前工作怎样推进、走到哪一步、是否失败的地方。

本任务不新增或修改后端，不启动真实Workflow，不接SSE，也不调用pi。工作流区域先使用本地fixture验证布局和状态；真实数据分别在P1.5和P1.6接入。

## 2. 用户场景

### 场景A：桌面同时看对话和工作进度

用户在电脑上打开Chat，左侧或中间阅读对话、输入消息，同时在右侧看到当前工作流的名称、状态、步骤和当前执行位置，不需要离开聊天页面。

### 场景B：手机在对话和工作流之间切换

手机屏幕不足以并排显示两个区域。用户通过清楚可见的“对话 / 工作流”切换入口查看两个完整视图；切换不会丢失输入内容或当前界面状态。

### 场景C：还没有工作流运行

首次打开时，工作流区域显示真实空态，例如“发送消息后，这里会显示工作进度”，不能显示一条看起来已经运行成功的假数据。

### 场景D：理解不同运行状态

开发和测试通过本地fixture分别渲染“等待、进行中、已完成、失败”4种状态，验证用户能从文字、图标和结构理解差异，不能只靠颜色。

## 3. 交付结果

P1.1完成后，Web应具有以下可运行界面：

1. 应用顶栏：产品名称、当前页面名称、非阻塞连接状态位置和浅色/深色手动切换按钮。
2. 对话区：消息列表/空态、输入框、发送动作位置。
3. 工作流运行区：当前运行摘要、步骤列表、当前步骤和错误/空态位置。
4. 桌面双栏布局与手机单栏切换布局。
5. 一套可复用的基础颜色、间距、字体、边框和状态Token；取值、双主题与切换机制以[设计规范](../product/design-guidelines.md)为准。
6. 支持界面测试的本地View Model与fixture；正式默认界面使用空态。

## 4. 页面结构

### 4.1 桌面

```text
┌──────────────────────────────────────────────────────────────┐
│ Chat                                      连接状态 / 设置入口 │
├─────────────────────────────────┬────────────────────────────┤
│                                 │ 当前工作流                 │
│ 对话区                          │ 状态：等待 / 运行 / 完成   │
│                                 │                            │
│ 用户消息                        │ ● 接收消息                 │
│ Assistant消息                   │ ● 后台处理                 │
│                                 │ ○ 生成回复                 │
│                                 │ ○ 保存结果                 │
│                                 │                            │
├─────────────────────────────────┤ 当前步骤说明 / 错误恢复提示 │
│ 输入框                    发送  │                            │
└─────────────────────────────────┴────────────────────────────┘
```

桌面端的默认结构是“对话为主、工作流为辅”的双栏界面。工作流区域始终有明确入口，但宽度不能挤压对话区到不可阅读。

### 4.2 手机

```text
┌──────────────────────────┐
│ Chat           连接状态  │
├──────────────────────────┤
│ [ 对话 ]   [ 工作流 1 ]  │
├──────────────────────────┤
│                          │
│ 当前选中的完整内容区     │
│                          │
├──────────────────────────┤
│ 输入框              发送 │  仅在“对话”页出现
└──────────────────────────┘
```

手机端不把工作流压缩成无法阅读的窄栏，使用两个同级入口切换。工作流入口可以显示当前状态或未读变化提示，但不能用动画持续打扰用户。

## 5. 工作流运行区显示什么

P1阶段显示的是**当前一次工作的运行投影**，不是完整Workflow编辑器。

### P1.1先建立的UI位置

1. 工作流名称或用户可读标题。
2. 整体状态：等待、进行中、已完成、失败。
3. 步骤列表及当前步骤。
4. 每个步骤的用户可见结果摘要或失败提示位置。
5. 后续人工决定、重试和恢复动作的扩展位置，但本任务不实现这些动作。

### 明确不显示

1. Workflow Run ID、Checkpoint ID和Hook Token。
2. pi Runtime Session ID或Provider内部请求身份。
3. 模型隐藏推理、原始Provider Payload和内部日志全文。
4. 尚未由产品确认的“正式成功”。

### 与P6的边界

P1的工作流区域回答“这次工作正在怎样运行”。P6才交付Workflow定义图、节点配置、组合、版本发布和编辑能力。P1.1不能提前做图编辑器。

## 6. 本地UI状态与fixture

为了在没有后端时把UI做完整，组件接受本地View Model。至少覆盖：

1. `empty`：没有运行，显示引导空态。
2. `queued`：工作已接收，尚未开始。
3. `running`：一个步骤高亮，其他步骤区分已完成和未开始。
4. `succeeded`：全部步骤完成，显示用户可读结果摘要位置。
5. `failed`：明确失败步骤、简短原因和未来恢复动作位置。

fixture只用于组件开发和测试。应用正常启动时默认展示`empty`，不得把fixture成功状态伪装成真实运行。

## 7. 前端实现边界

### 需要修改

1. `apps/web/src/App.tsx`：从P0状态页升级为产品界面组合根。
2. `apps/web/src/`下新增按责任拆分的对话区、工作流区和响应式布局组件。
3. 新增样式入口、设计Token和响应式规则。
4. 更新Web组件测试；必要时增加只服务当前界面的测试fixture。

### 可以保留

现有`/api/healthz`只可作为非阻塞连接提示。API不可达时，界面外壳仍必须完整渲染，不能让P1.1依赖后端才能查看。

### 不允许修改或新增

1. 不修改`apps/api`。
2. 不修改Domain、Application、Realtime、Workflow或pi包。
3. 不新增消息、运行或事件网络合同。
4. 不安装Workflow、pi、PWA或新的状态管理依赖。
5. 不使用浏览器缓存伪造正式消息或正式运行状态。

## 8. 交互和可访问性要求

1. 键盘可以到达对话/工作流切换、输入框和所有按钮。
2. 手机切换使用真实按钮或Tab语义，并暴露当前选中状态。
3. 状态变化不能只靠红、黄、绿颜色表达，同时使用文字和图标/形状。
4. 工作流状态区域具有合适的可访问名称；fixture切换测试不制造频繁的屏幕阅读器播报。
5. 375px宽度下无横向滚动，输入区不会被软键盘或固定区域永久遮挡。
6. 桌面缩窄到单栏阈值时，切换逻辑稳定，不丢失输入框内容。

## 9. 完成门

### 自动验证

1. Web的Build、Typecheck、Lint、Format和Vitest通过。
2. 组件测试覆盖：默认空态、桌面双区、手机切换和4种工作流状态。
3. 测试证明API不可达时界面仍渲染，不显示假成功。
4. 架构测试证明Web没有导入服务端实现。

### 浏览器验证

1. 桌面视口能同时看见对话区和工作流运行区。
2. 375px手机视口能通过“对话 / 工作流”切换查看完整内容。
3. 键盘可完成主要导航；焦点可见。
4. 空态、进行中和失败状态在视觉与文字上可区分。
5. 提供桌面和手机2张审核截图，用户可以直接判断整体结构。

## 10. 本任务明确不做

1. 不真正发送消息。
2. 不读取Session、Message或Product Run。
3. 不启动或查询Vercel Workflow。
4. 不接SSE和AG-UI事件。
5. 不接pi或模型。
6. 不做Manifest、Service Worker、安装和离线缓存；这些属于P1.2。
7. 不做Workflow图编辑器、节点拖拽和版本发布；这些属于P6。
8. 不做历史会话列表、搜索、文件、语音、审批和设置业务页。

## 11. 后续任务怎样接入这个区域

| 后续任务 | 接入工作流运行区的内容 |

## 12. 审核结论需要确认什么

用户审核P1.1任务书时只需确认3点：

1. 桌面采用“对话区 + 右侧工作流运行区”是否符合产品方向。
2. 手机采用“对话 / 工作流”同级切换是否符合使用习惯。
3. P1只显示当前运行步骤，完整Workflow图与编辑器留到P6，范围是否合适。

这3点确认后才进入P1.1代码实现。
