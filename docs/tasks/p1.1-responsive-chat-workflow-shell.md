## 1. 先回答：这次到底做什么

> **最终范围（2026-08 用户批准）**：先用原型确定整体工作空间，再实现**今日入口 + 会话列表 + 持续对话 + 工作窗口**。桌面可同时显示4个区域并调整对话/工作的比例；手机切换“对话 / 工作”。工作窗口用本地fixture展示工作流、PPT、代码和白板。发送只做本地即时上屏，不代表服务端已保存；消息持久化属于P1.3，真实运行状态属于P1.5/P1.6。

是的，P1.1是一个**纯前端UI任务**。

它要把Chat最基本的产品界面做出来，而且从第一版开始就包含两个同等重要的区域：

1. **对话区**：用户阅读消息、输入内容的地方。
2. **工作流运行区**：用户看见当前工作怎样推进、走到哪一步、是否失败的地方。

本任务不新增或修改后端，不启动真实Workflow，不接SSE，也不调用pi。工作流区域先使用本地fixture验证布局和状态；真实数据分别在P1.5和P1.6接入。

## 2. 用户场景

### 场景A：桌面同时看对话和工作进度

用户在电脑上打开Chat，左侧或中间阅读对话、输入消息，同时在右侧看到当前工作流的名称、状态、步骤和当前执行位置，不需要离开聊天页面。

### 场景B：手机在对话和工作流之间切换

手机屏幕不足以并排显示两个区域。用户通过清楚可见的“对话 / 工作流”切换入口查看两个完整视图；切换不会丢失输入内容或当前界面状态。

### 场景C：还没有打开会话

首次打开时停留在“今日”，不自动打开某个会话或假装真实工作正在运行。用于验证布局的会话、运行和产物必须明确标记为本地示例。

### 场景D：理解不同运行状态

开发和测试通过本地fixture分别渲染“等待、进行中、已完成、失败”4种状态，验证用户能从文字、图标和结构理解差异，不能只靠颜色。

## 3. 交付结果

P1.1完成后，Web应具有以下可运行界面：

1. 今日入口：汇总需要处理、已打开工作空间、日程和可追溯动态。
2. 会话列表：打开不同本地示例会话，每个会话恢复自己的工作窗口和布局状态。
3. 持续对话：消息、输入框、模型选择和本地发送；本地内容明确标记未发送。
4. 工作窗口：工作流运行图、节点详情、PPT、代码和白板示例；支持标签、最大化、收起和独立打开。
5. 桌面平铺布局：全局导航、会话列表、对话、工作窗口4个区域；两个侧栏可折叠，对话与工作之间可调整比例。
6. 手机布局：底部主导航和“对话 / 工作”同级切换，不丢失当前输入。
7. 一套可复用的基础颜色、间距、字体、边框和状态Token；取值、双主题与切换机制以[设计规范](../product/design-guidelines.md)为准。
8. 支持界面测试的本地View Model与fixture；所有示例都标明为本地数据，不伪装成服务端事实。

## 4. 页面结构

### 4.1 桌面

桌面端采用平铺工作空间：

```text
┌────────┬────────────┬──────────────────┬──────────────────┐
│全局导航│ 会话列表   │ 持续对话         │ 工作窗口         │
│今日    │ OKR整理    │ 消息与输入       │ 工作流运行图     │
│会话    │ 周会PPT    │ 当前工作卡片     │ PPT / 代码 / 白板│
│工作    │ 代码审查   │                  │                  │
└────────┴────────────┴──────────────────┴──────────────────┘
```

会话与工作窗口共同属于当前工作空间。点击会话中的“当前工作”只聚焦右侧窗口，不离开会话；侧栏可折叠，工作窗口可最大化或独立打开。

### 4.2 手机

```text
┌──────────────────────────┐
│ Chat           连接状态  │
├──────────────────────────┤
│ [ 对话 ]     [ 工作 ]     │
├──────────────────────────┤
│                          │
│ 当前选中的完整内容区     │
│                          │
├──────────────────────────┤
│ 输入框              发送 │  仅在“对话”页出现
└──────────────────────────┘
```

手机端不把工作窗口压缩成无法阅读的窄栏，使用“对话 / 工作”两个同级入口切换。工作入口可以显示当前状态或未读变化提示，但不能用动画持续打扰用户。

## 5. 工作流运行区显示什么

P1阶段显示的是**当前一次工作的运行投影**，不是完整Workflow编辑器。

### P1.1先建立的UI位置

1. 工作流名称或用户可读标题。
2. 整体状态：等待、进行中、已完成、失败。
3. 步骤列表及当前步骤。
4. 每个步骤的用户可见结果摘要或失败提示位置。
5. 后续人工决定、重试和恢复动作的扩展位置，但本任务不实现这些动作。

### 明确不显示

1. Workflow Run ID、Checkpoint ID和Hook Token。
2. pi Runtime Session ID或Provider内部请求身份。
3. 模型隐藏推理、原始Provider Payload和内部日志全文。
4. 尚未由产品确认的“正式成功”。

### 与P6的边界

P1的工作流区域回答“这次工作正在怎样运行”。P6才交付Workflow定义图、节点配置、组合、版本发布和编辑能力。P1.1不能提前做图编辑器。

## 6. 本地UI状态与fixture

为了在没有后端时把UI做完整，组件接受本地View Model。当前fixture覆盖未开始、进行中、已完成步骤、失败步骤和不同工作窗口。fixture只用于组件开发和测试；应用正常启动时默认停留在“今日”，没有活动会话，所有示例必须明确标记为本地数据。

## 7. 前端实现边界

### 需要修改

1. `apps/web/src/App.tsx`：从P0状态页升级为产品界面组合根。
2. `apps/web/src/`下新增按责任拆分的对话区、工作流区和响应式布局组件。
3. 新增样式入口、设计Token和响应式规则。
4. 更新Web组件测试；必要时增加只服务当前界面的测试fixture。

### 可以保留

现有`/api/healthz`只可作为非阻塞连接提示。API不可达时，界面外壳仍必须完整渲染，不能让P1.1依赖后端才能查看。

### 不允许修改或新增

1. 不修改`apps/api`。
2. 不修改Domain、Application、Realtime、Workflow或pi包。
3. 不新增消息、运行或事件网络合同。
4. 不安装Workflow、pi、PWA或新的状态管理依赖。
5. 不使用浏览器缓存伪造正式消息或正式运行状态。

## 8. 交互和可访问性要求

1. 键盘可以到达对话/工作流切换、输入框和所有按钮。
2. 手机切换使用真实按钮或Tab语义，并暴露当前选中状态。
3. 状态变化不能只靠红、黄、绿颜色表达，同时使用文字和图标/形状。
4. 工作流状态区域具有合适的可访问名称；fixture切换测试不制造频繁的屏幕阅读器播报。
5. 375px宽度下无横向滚动，输入区不会被软键盘或固定区域永久遮挡。
6. 桌面缩窄到单栏阈值时，切换逻辑稳定，不丢失输入框内容。

## 9. 完成门

### 自动验证

1. Web的Build、Typecheck、Lint、Format和Vitest通过。
2. 组件测试覆盖：默认今日、桌面四区、手机切换、工作流节点、分栏、侧栏、主题、模型与本地发送。
3. 测试证明API不可达时界面仍渲染，不显示假成功。
4. 架构测试证明Web没有导入服务端实现。

### 浏览器验证

1. 桌面视口能同时看见全局导航、会话列表、对话区和工作窗口。
2. 375px手机视口能通过“对话 / 工作”切换查看完整内容。
3. 键盘可完成主要导航；焦点可见。
4. 空态、进行中和失败状态在视觉与文字上可区分。
5. 提供桌面和手机2张审核截图，用户可以直接判断整体结构。

## 10. 本任务明确不做

1. 不真正发送消息。
2. 不读取Session、Message或Product Run。
3. 不启动或查询Vercel Workflow。
4. 不接SSE和AG-UI事件。
5. 不接pi或模型。
6. 不做Manifest、Service Worker、安装和离线缓存；这些属于P1.2。
7. 不做Workflow图编辑器、节点拖拽和版本发布；这些属于P6。
8. 不读取或新建服务端历史会话；当前会话列表只是验证工作空间布局的本地fixture。
9. 不做搜索、文件、语音、审批和设置业务页。

## 12. 审核结论需要确认什么

用户审核PR #2时只需确认3点：

1. 桌面“四区平铺”是否符合持续对话与并行工作的方向。
2. 手机“对话 / 工作”切换是否符合使用习惯。
3. 工作流运行图是否足以看懂当前进度和失败节点，同时没有变成完整图编辑器。
