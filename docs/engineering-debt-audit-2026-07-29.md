## 2. 总体判断（审计推断）

当前系统不是骨架，也不是演示：39节点主Workflow、472个收集到的后端测试、23次Alembic迁移、
组合根唯一、质量门真实可运行、Evidence/Result Commit具备fail-closed攻击测试。
主要风险不在方向，而在3件事：

1. **单文件复杂度进入临界区**：每加一个新能力，回归成本和误改半径非线性上升。
2. **身份与部署欠债正在从工程债变成产品债**：公网已真实使用，但仍是HTTP + Basic Auth。
3. **双轨并存的过渡债**：旧模型审批链与新主Workflow、同进程pi重挂接与跨进程恢复并存周期越长，
   每次依赖升级的验证面越大。

### D-02 真实身份与公网部署欠债（既有F07/Q03 + 审计推断）

项目既有事实：公网中转已真实使用（手机390×844真实模型回合、LaunchAgent常驻、
反向SSH + Nginx Basic Auth），但`PROJECT_STATE.md`风险8明确：无传输加密、无正式
Principal/Authentication Session、Basic Auth不是正式Product Identity。
F07（Principal/Role/Grant/Authentication Session）当前优先级P1、前置F02-F06。

审计推断：这条债的性质正在变化——它不再只是"未来能力"，而是**当前真实使用方式的安全基线缺口**。
日常使用每多持续一周，真实Product Store里就积累更多需要迁移语义的历史；F09超级管理员、
W10全部堵在F07之后。F07前置写成F02-F06意味着按当前排序它要等很久。

待审核决定：见§4决定卡B（F07是否拆出最小身份底座并提前）。

### D-03 MAF私有API与AG-UI RC耦合（代码事实 + 既有Q07/风险5）

代码事实：`continuous_chat.py`直接导入`agent_framework._workflows._request_info_mixin`
（下划线私有模块）；`pyproject.toml`锁定`agent-framework-ag-ui==1.0.0rc8`（RC版本）。
项目既有事实：风险5（RC8不转发`checkpoint_id`，隔离恢复桥依赖MAF私有Runner/编码API）、
风险2（AG-UI RC升级可能改变事件/Snapshot/Interrupt行为）、风险12（Workflow桥终态顺序兼容层）。
Q07方案级做法已包含"私有API使用点映射到版本锁定测试和替代计划"。

审计推断：Q07当前是P1且"随工程持续维护"，但这里的债有**明确爆点**——任何一次MAF/AG-UI
升级都可能同时打断Checkpoint恢复桥和Interrupt机制，而这两条正是主Workflow跨进程HITL
恢复（阶段6已兑现保证）的根基。恢复能力的根基建立在私有API上，值得单独升格处理。

待审核决定：见§4决定卡C（私有接合的版本锁定与移除路径是否单独立项）。

### D-04 双轨过渡债：旧模型审批链与同进程pi恢复（代码事实 + 既有事实）

代码事实：`composition.py`仍注入`InMemoryModelCallReviewStore`与旧`create_model_call_workflow`；
新主Workflow已全持久化（ModelCallDraft/Checkpoint/Interrupt Link）。
项目既有事实：风险43（旧模型审批Workflow仍依赖进程内草稿Store）；活动pi同进程Checkpoint
重挂接已实现，跨进程仍是中断收敛（F05未做，状态文件明确未外推）。

审计推断：两条链并存期间，每次MAF升级、每次审批合同调整都要验证两套行为。
旧链当前仍承担演示Workflow和工具Workflow入口（项目既有事实），不能简单删除，
但可以明确"冻结旧链、只修安全缺陷"的退役策略，降低验证面。

待审核决定：见§4决定卡D（旧链冻结与退役口径）。

### D-05 提交纪律裂缝：bulk commit（代码事实，**未在既有backlog中**）

代码事实：最新提交`86539b7 chore: 批量提交所有已修改文件——项目文档、后端模块、前端组件、
测试、脚本、部署、项目掌握`，一个提交横扫全部层。53次提交中另有若干跨层大提交
（如`5a62786 backend：更新协作上下文、意图、协议、执行调度、治理、harness、产品会话、运行时执行`）。
这与`PROJECT_STATE.md` Git状态自述"按Feature节点提交并推送"冲突。

审计推断：bulk commit的直接代价是行为回溯困难——当某个测试指纹或状态机需要定位引入点时，

后端、前端、脚本时，变更的真实边界被掩盖。

待审核决定：见§4决定卡E（是否把提交粒度写成可执行检查）。

## 4. 待审核决定卡

### 决定卡A：Q02收敛与SD4-D的先后顺序

- **决策原因**：D-01。在2,000-3,000行的聚合文件上继续叠加SD4-D失效传播和SD4-E界面，
  会持续扩大误改半径和回归面。
- **现有参考源是否涉及**：未涉及。这是项目自身工程判断，pi/nanobot/LibreChat等参考项目
  不为此背书。
- **全部可行选择**：
  1. **A1 先收敛后叠加**：在SD4-D开始前，把`continuous_chat.py`、`governance/service.py`、
     `harness/service.py`按事务边界/状态所有权拆到审查线附近，并把`App.tsx`拆分
     （含协调用户并行改动）。
  2. **A2 边做边拆**：维持当前节奏，SD4-D/E照常推进，每个新能力只拆自己触碰的部分。
  3. **A3 只拆最痛的一个**：只拆`continuous_chat.py`（3,096行、变更高频），其余维持。
- **优缺点**：
  - A1：优点是后续每个能力都落在清晰边界上，反例023不再恶化；缺点是SD4-D延迟，
    且无行为重构本身需要完整的指纹/回归证据（工程规范第9条），工作量不小。
  - A2：优点是不阻塞产品能力；缺点是"边做边拆"在过去几个里程碑实际拆得慢于堆得快
    （行数从审计时的2,849涨到3,096），趋势不利。
  - A3：折中；但`governance/service.py`和`harness/service.py`同样是SD4-D/E的直接写入目标。
- **当前建议**：A1的缩小版——先拆`continuous_chat.py`与`harness/service.py`这两个SD4-D/E
  直接写入目标，`governance/service.py`随F02收尾拆，`App.tsx`与用户确认后单独处理。
- **建议原因**：把收敛成本精确绑定到即将被改动的文件，不做泛化重构，符合"无行为重构
  先固定不变量"的既有规范。
- **信心**：中高。**未验证项**：三个Service内部的事务边界是否都已清晰到可拆，需要先做
  一次只读的不变量盘点（不改动代码）才能确认工作量。

### 决定卡B：F07最小身份底座是否提前

- **决策原因**：D-02。公网真实使用 + Basic Auth + 无Authentication Session的组合，
  每持续一天都在积累语义迁移成本，且阻塞F09/W10。
- **现有参考源是否涉及**：部分涉及——LibreChat研究（固定提交）覆盖其身份/Session拓扑，
  可作参考；但Chat的Principal/Scope/Role模型是项目推导。
- **全部可行选择**：
  1. **B1 提前F07最小切片**：把F07拆出"Principal + Authentication Session + HTTPS +
     固定本地Scope升级为真实单用户Scope"最小底座，排在SD4-D前后；Channel Binding、
     Delivery、多用户授权仍留在原位置。
  2. **B2 维持排序**：F07等F02-F06，期间公网继续Basic Auth + HTTP。
  3. **B3 只做传输层**：先上HTTPS，身份仍延后。
- **优缺点**：
  - B1：优点是堵住安全基线缺口、解锁F09设计、迁移成本低；优点是真实身份也让
    "谁登录"类指标第一次有可信来源。缺点是打断当前SD4节奏，需要一次详细设计审核。
  - B2：优点是不打乱计划；缺点是安全缺口持续，且越晚迁移越痛。
  - B3：优点是小而快；缺点是只解决窃听，不解决"没有真实Principal"这个根本问题。
- **当前建议**：B1，且最小切片必须先完成详细设计审核（符合先审核后实现规则）。
- **建议原因**：这是唯一一条"每晚一个月代价明显变大"的债；其他债（D-01/D-03/D-04）
  的代价曲线相对平缓。
- **信心**：中。**未验证项**：HTTPS在现有反向SSH/Nginx拓扑中的落点（云端终止还是本地终止）
  未核实；F07最小切片与现有固定`local-user` Scope数据的迁移方案未设计。

### 决定卡C：MAF私有接合的版本锁定与移除路径

- **决策原因**：D-03。跨进程HITL恢复是阶段6已兑现的核心保证，其根基是私有API。
- **现有参考源是否涉及**：涉及——必须以本地MAF源码（匹配安装版1.11.0/rc8）核实公开
  替代API是否存在；这是强制参考源规则内的查询。
- **全部可行选择**：
  1. **C1 单独立项**：建立"私有API使用点清单 + 逐点版本锁定测试 + 公开替代评估"专项，
     在下次MAF升级前完成。
  2. **C2 并入Q07**：按现有backlog随工程维护，不单独立项。
  3. **C3 冻结升级**：在替代路径明确前锁定MAF/AG-UI版本，不升级。
- **优缺点**：
  - C1：优点是爆点变计划，恢复保证有版本证据；缺点是额外一个专项。
  - C2：优点是不新增工作流；缺点是Q07是P1维护项，实际节奏可能赶不上一次突发升级需求
    （例如安全修复）。
  - C3：优点是最稳；缺点是错过上游修复，且RC版长期冻结本身有风险。
- **当前建议**：C1 + C3组合：版本先冻结，专项产出"每点能否移除、何时移除"的结论后再定升级。
- **建议原因**：把不可控的外部升级风险转成可计划的项目内工作。
- **信心**：高（方向）；**未验证项**：MAF安装版是否已公开`checkpoint_id`转发或等价API，
  需查本地MAF源码与rc8之间是否有新RC。

### 决定卡D：旧模型审批链冻结与退役口径

- **决策原因**：D-04。双链并存扩大每次升级的验证面。
- **现有参考源是否涉及**：未涉及。
- **全部可行选择**：
  1. **D1 冻结旧链**：声明旧`model_call_workflow.py`链只修安全缺陷、不再加能力，
     演示/工具Workflow入口设定退役条件（如主Workflow覆盖其场景后删除）。
  2. **D2 立即删除**：把演示/工具Workflow迁到主链后删除旧链。
  3. **D3 维持现状**。
- **优缺点**：
  - D1：优点是立刻缩小验证面，且不丢现有可运行场景；缺点是需要明确退役条件避免无限拖。
  - D2：优点是最干净；缺点是迁移工作量现在发生，且演示Workflow有其独立教学价值。
  - D3：无优点，只有惯性。

- **建议原因**：成本最小、立即见效、可逆。
- **信心**：高。**未验证项**：旧链当前在前端配置中心还有哪些用户可见入口依赖它。
