# Chat 系统生命周期与协同

## 1. 决策与范围

2026-09-08，用户确认：启动/停止应面向完整 Chat 系统，而不只是前后端脚本；采用成熟服务管理的做法，保持简单。本文件是已确认方向下的架构合同和后续实现输入，**不是当前已实现行为**。本轮只维护文档与导航，不改启动程序、不停止生产服务。

触发场景：用户停止 `scripts/dev-start.sh` 后，独立常驻的 NanoClaw 和生产 Backend 仍工作。脚本清理了自己创建的进程，但“一键启动 Chat”的产品含义与实际边界不一致。

一个运行实例是同一套 Chat Backend、其关联 NanoClaw Host及必要的开发前端/执行环境。它不是 Long Agent：一个实例内仍由一个 NanoClaw Host承载多个独立 Agent Group，所有模型执行仍走公共 Pi 装配。生产 Web 静态资源由 Backend 提供，没有独立 Vite 进程。

## 2. 复用成熟做法，不新增运行平台

- [Docker Compose 启停依赖](https://docs.docker.com/compose/how-tos/startup-order/)明确区分进程启动与服务就绪，并按依赖组织启停。借鉴依赖和就绪检查；不因此要求把 Chat 全部容器化。
- [systemd Unit 合同](https://github.com/systemd/systemd/blob/main/man/systemd.unit.xml)把启动依赖、顺序、停止传播分开表达。借鉴这些语义；不是配置一个 `After` 就自动获得整套生命周期。
- [Apple launchd 指南](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)提供进程管理、KeepAlive与终止信号。复用已有服务管理，应用自己负责业务就绪和收尾；不将systemd依赖选项机械翻译成plist。

实现沿用现有 `chatctl`、服务模板和Nano Setup，补一个共同的实例解析与生命周期操作入口；开发脚本、VSCode及后续Web管理消费同一合同。生产由systemd/launchd守护进程，开发前台入口管理自己的进程组，不再增加常驻Supervisor、任务引擎或通用DAG编排平台。跨系统只补必要的受控状态/停止接收新工作/收尾合同。

## 3. 实例身份、配置与所有权

每次操作先解析目标实例，再操作组件。沿用已登记的安装位置、Chat Home、服务标识及Nano实例关联，不从端口或进程名猜身份，也不另建一套Agent配置库。

统一解析结果至少能说明：环境与实例标识、Chat Home、Nano运行数据根、Backend/Gateway端点、启用组件、服务或进程归属、启动方式、停止期限和自启动策略。字段归属、Schema和存放位置由详细方案在[Chat配置系统](../configuration.md)内确定；定义只有一个可写来源，PID/就绪/执行数是运行事实，不混进产品配置。

约束：

1. 完整开发实例包含启用的Long Agent能力，Nano连接同一开发Backend；缺配置须显示不完整及原因，不能静默借用生产Host。明确未启用Long Agent时可运行Web功能，但状态标明未启用。
2. 开发/生产分别使用自己的Chat Home、Nano数据库、服务标识和端点。当前Nano数据随Checkout，未完成安全的数据根寻址前，不能用同一Checkout的默认数据同时启动第二个Host；复用原生隔离安装机制或先补窄数据根合同。
3. 同一实例同一组件只有一个生命周期管理者。重复启动返回现有状态或明确冲突；不同时启动服务版和前台版。已有组件只有核对实例身份后才能作为整套服务接管，不能仅因端口相同就当成自己的。
4. 同一微信/Telegram账号不能默认由开发和生产同时消费。开发使用测试通道或假Gateway；切换真实账号所属实例需显式操作，不自动复制生产Credential。
5. 系统停止覆盖目标实例拥有的服务和执行资源，不杀其他实例、共享Docker daemon、外部模型服务、数据库服务或共享隧道。专属辅助服务可按明确归属纳入，不能扩大为整机进程清理。

## 4. 用户操作与状态

| 操作 | 产品合同 |
|---|---|
| 启动完整系统 | 校验实例与配置，启动所需组件，完成就绪与连接检查后报告可用；没有配置好Long Agent不能显示全绿 |
| 正常停止 | 停止接受新工作，有界等待在途工作收尾，持久化结果/中断事实，再关闭组件；返回未完成事项 |
| 强制停止 | 明确中断当前工作，尽可能记录状态并结束该实例的进程/执行资源；不承诺每个外部动作都能撤销 |
| 重启 | 同一实例的正常停止→启动；保持身份、配置与数据，不用重新建Agent或Session |
| 状态/诊断 | 返回实例、组件健康、关联是否正确、在途/待投递数量、错误与可执行下一步；无模型调用 |
| 单独调试模块 | 显式选择并标注范围、依赖和哪些服务继续运行；不能使用“完整启动/停止”的成功文案 |

Web或Tool发起控制操作时，服务端必须校验实例管理权限与真实目标，不能让普通对话参数伪造停机身份。部署升级复用同一停止/恢复语义，同时保留现有版本校验、备份和Nano Tripwire门禁。

保持少量可理解状态：已停止、启动中、可用、部分可用、停止中、失败。组合状态由真实组件和合同状态计算，不在Web维护第二份状态机；进程存活与业务可用分开。关闭浏览器不是停止系统。

显式停止必须通过实际管理者执行，不能只kill PID后被KeepAlive立即拉起。当前运行的自动重启与“下次开机是否自启动”分开：stop结束本次运行，自启动遵循可见的独立配置；关闭自启动不是stop的隐藏副作用。状态与停止结果应说明这一点。

Web未来可以提供同义操作，但页面关闭/断线不能取消停止操作。Backend不能作为唯一拥有停止结果的进程：最终进程状态由外部生命周期入口/原生服务管理确认。远程停机后，重新启动须通过仍可用的主机管理入口；不为了网页自启动而新增一个常驻控制服务。

## 5. 启动顺序与部分失败

1. 校验配置、身份、数据独占和端口/服务冲突，不先杀端口占用者。重复并发启动按实例串行或返回进行中。
2. Backend先达到基础服务就绪，能响应健康与控制请求；Nano随后启动，建立认证连接并校验实例关联；开发Vite可在Backend基础就绪后启动。
3. 完成组合就绪后开放新工作。基础健康不能依赖Nano已完全就绪，否则双方互等；简单的 `/api/health` 200不能替代认证Gateway、正确实例及已启用Channel状态检查。
4. 启动中失败，回收本次新启动的资源，保留原因和日志；原本已在运行且只是被附着的组件不静默关掉。明确报告剩余组件与部分可用状态，不虚报完整启动成功。

正常产品操作由统一入口处理。故障恢复仍由服务管理者重启失败进程、通信层退避重连；Backend短暂失败不必把全部组件一起杀掉，Nano可按已有耐久合同保留待处理事件。没有被耐久接受的消息不能虚报已接收。

## 6. 停止顺序与在途执行

停止是有界收尾，不是等待所有长期职责完成，也不强迫每个Pi任务具备检查点续跑。

1. 将目标实例置为停止中，阻止自动拉起与新的入口工作。Web拒绝新执行；Nano暂停新任务触发和新入站的执行派发。对仍收到的消息，按通道能力停止接收或耐久留待下次处理，不接受后丢失。
2. 保持Backend、Nano投递/Gateway和必要执行资源存活，让已接受的Run和结果投递完成。正在执行的内部步骤可以在剩余期限内继续，不能通过派生任务无限延长停止。不能一开始就teardown Channel，否则已有结果无法送达。
3. 到达统一的收尾期限时，请求取消尚未结束的执行，记录已保存输出、未完成状态及未确认投递，再按组件依赖关闭。未结束的审批/长期等待不阻塞关机，保存等待状态即可。
4. 清理实例拥有的工具子进程和任务容器，关闭Nano及其通信、数据库，再结束Backend和开发Vite；具体资源必须在其最后一个消费者结束后关闭。超时可升级强制终止，但明确返回不完整项。操作总期限必须与原生服务管理的停止超时协调，避免应用尚在收尾便被提前强杀。
5. 由生命周期入口复核组件退出及端口/服务归属；停止失败显示仍存活的组件，不返回假成功。

跨组件收尾只需受控的“开始收尾请求”和“状态查询”两个基本动作，复用现有认证HTTP管理边界。请求携带同一操作关联与期限；双方明确确认新工作已关闭，并报告仍在执行、待投递及已持久化等待的状态。协调入口收到双方确认后才判断是否排空；长期等待持久化后不计作活跃执行。重复请求幂等，查询超时表示状态未知，不表示已停止；协调入口退出后再次执行stop应能重查并继续收尾。具体URL/Schema由执行方案确定，但不能遗漏这一确认接缝。

用户直接发终止信号、操作系统关机时，也应复用组件内同一收尾逻辑；整套信号由协调入口处理。强制kill、断电及主机崩溃无法保证末次状态落盘，下一次启动必须依赖既有耐久事实判断，不依赖退出钩子必定执行。

## 7. 恢复与记录

重启后按Project/Agent/Session/Run、入站事件与Delivery/Ack的稳定标识恢复：已完成不重做、待处理继续派发、有原生可恢复状态则恢复；被中断的普通Pi轮次不声称无缝续跑。外部动作已执行但回执未知时先核对，无法判断则标为待确认，不能自动重做发布、付款等动作。

沿用[诊断与记录](../development/diagnostics.md)：每次生命周期操作记录实例、操作关联、请求来源、开始/结束、组件结果、在途处置及错误；不记录密钥或复制全部对话。停止不删除Session、Memory、Agent配置或任务定义。停止期限到达时未投递结果保留到恢复；日记/摘要不是停机前强制调用模型的步骤。

## 9. 实施与验收顺序

先设计实例归属和启停合同，再贯通一套开发环境，随后复用到服务模式；同步配置/API与状态展示，最后验证异常恢复。此项是[Long Agent工程基线](./chat-long-agent-engineering-baseline.md)B0/B1的横向前置能力，不另起一套庞大的路线图。每阶段都要有可观察的完整小场景。

| 验收场景 | 必须证明 |
|---|---|
| 完整启动与正常停止 | Backend/Nano/开发前端关联正确；Ctrl+C或stop后本实例全部停止；无自动复活 |
| 未配置/未启用/Channel失联 | 区分未启用与失败；不能以端口存活冒充全系统可用 |
| 重复启动、启动失败、控制命令并发 | 无重复Host/数据写入者；失败回收只处理本次拥有资源；剩余状态可解释 |
| 停止时有模型/Tool/投递/审批 | 有界收尾、超时中断、等待状态持久化；投递阶段不被过早关闭 |
| 开发与生产并存 | 停开发不影响生产，不共享运行数据或默认抢同一账号消息；完整与模块操作文案一致 |
| Backend崩溃、断电、强停后恢复 | 不重复执行/投递已完成事项，不虚报中断轮次成功，未知外部结果可追踪 |
| 常驻与VSCode路径 | 服务管理者停止后不立即重启；F5停止调用同一语义；自启动策略可见 |

测试使用隔离Chat Home/Nano数据、假模型与假Channel，控制收尾期限及故障注入。进程/服务模式分别验收；只验证Shell退出或单一健康端口不能算完成。真实账号消息验收与生产切换仍走部署授权，不在自动测试中操作用户生产服务。
