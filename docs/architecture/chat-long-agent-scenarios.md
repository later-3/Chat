# Chat Long Agent 场景与验收要求

## 1. 状态

2026-09-07 用户确认以完整功能设想演练：道德经每日学习、旅游变化监控、每个 Agent 的每日日记、Ziji 项目开发。本文是产品目标与未来验收要求，不是测试通过记录，也不授权实际创建任务、发送通知、修改项目或部署。

配置定义见[能力模型](./chat-long-agent-capability-model.md)，运行合同见[架构](./chat-long-agent-architecture.md)，实现差距见[实施状态](./chat-long-agent-roadmap.md)。

多 Agent、用户共同参与与自由活动的新增交互见[场景收敛与模拟（评审稿）](./chat-long-agent-interaction-simulations.md)。该稿新增行为待用户确认，不自动扩大本文已确认验收范围。

## 2. 演练环境与共同约束

演练角色为 Nexus、规划 Agent、架构 Agent、开发 Agent 和审核 Agent；每个身份有独立配置、资源、Memory、Daily Project 与 Docker 环境配置。它们是示例角色，不表示此次创建了新 Agent。

有 5 个独立 Daily Project，以及道德经、旅游、Ziji 开发 3 个业务 Project。Ziji 以 ziji-plantos 具体子项目作为示例工作根，不能默认把整个上层工作区挂载给 Agent。

共同要求：

- 用户或 Agent 的每次工作先归属 Project，Session 的 projectId 不变。
- 业务 Project 可以有多个工作 Session，入口、任务与日记都通过 ID 关联它们。
- 新 Session 带有必要历史入口，进一步查询有授权和来源。
- 所有配置可从 Web 和 Agent 管理入口读取；实际执行与检查使用同一版本。
- 公共管理 Skill 可发现，真实 Tool/资源可查询；文档不会凭空赋予工具能力。
- Docker 只暴露授权工作范围，持久数据不依赖临时容器。
- 多 Agent 的角色划分与结果关联用于演练；中央协调、新 Session 拓扑及用户共同参与方式仍待讨论。

## 3. 道德经每日学习

### 3.1 用户意图

“创建道德经学习项目，每天晚上八点陪我学习一章，用生活例子解释，记住进度。”

### 3.2 正常路径

1. 从 Nexus 当天 Daily 发起，使用 Project 管理能力创建学习项目并关联来源。
2. 用户进入学习项目，选择或新建课程 Session；不能改写原 Daily Session 的项目归属。
3. 配置目标、材料、学习 Skill 和 Prompt 自定义区域；选择的模型来自 Chat。
4. 创建负责人为 Nexus、Project 为学习项目、时区明确的周期 Task。记录时间、Session 策略、通知目的地与运行政策。
5. 到点后建立 Run，读取项目学习进度及相关历史。未完成上一章则续接；已完成才进入新章节，解析结果固定到具体 Session。
6. 用户通过微信接收课程，可以在微信回复或从 Web 打开同一工作。后台通知不改变用户原本的其他项目焦点。
7. 学习反馈进入课程历史，项目进度和已授权 Memory 按来源更新；日记索引记录参与了该学习工作。

### 3.3 配置与资源变更

用户增加“联系生活”的 Prompt 区域，或让 Agent 在授权范围维护学习 Skill。修改生成新版本，下轮可发现；当前执行保持旧版本。

用户要求换到已配置的 Kimi 时，Agent 先通过自身配置及 Chat 模型目录查询有效选项，明确修改范围，再保存并报告生效状态。不能查找 ~/.pi 作为配置依据。

停用 Skill 或 Tool 时校验关联任务的依赖，说明受影响项；不能显示“已卸载”却继续在下一轮暴露该工具。

### 3.4 验收

| 编号 | 观察结果 |
|---|---|
| LA-S1-01 | Daily 和学习 Session 分属正确 Project，双方可通过来源关联找到工作 |
| LA-S1-02 | 课程已发送、已阅读、已完成不是同一个状态；未完成不会被自动跳过 |
| LA-S1-03 | Web/微信续接一致，重复触发不重复创建本次课程工作 |
| LA-S1-04 | 新 Daily Session 能定位昨天的学习与开放问题，无需用户重述 |
| LA-S1-05 | 自定义 Prompt、模型和 Skill 的配置来源、变更及有效版本在 UI/Agent 查询中一致 |
| LA-S1-06 | 模型故障保留失败状态，替代模型仅按已配置授权策略执行 |

## 4. 旅游变化监控

### 4.1 用户意图

“维护这次旅游计划，每两小时检查变化，重要变化再告诉我。”

### 4.2 正常路径

1. 在旅游 Project 建立用户沟通 Session，保存计划与关心的事项。
2. 如采用规划 Agent 分工，交给它明确目标、允许访问的资料、完成标准与反馈位置。交互协议本轮不定案。
3. 建立固定属于旅游 Project 的 Task，结构化配置检查来源、比较基准、频率、重要变化条件和 Destination。
4. 到点建立 Run，在 Docker 中执行检查。无变化则记录检查成功及时间，不强制调用模型或创建空 Session。
5. 有变化时建立/选择工作 Session，分析来源、前后差异、影响与建议；保存检查基准和产物。
6. 根据策略投递结果。演练可由 Nexus 作为微信入口转达规划 Agent 结果，须保留来源；最终跨 Agent 消息与会话安排待评审。
7. 用户回复某条通知，能够定位该 Run、Project 和工作 Session，而不是落到当时正在聊天的其他项目。

### 4.3 维护与失败

检查基准和进度存于持久数据，容器重建后恢复。获取来源失败不等于无变化；检查失败、分析失败和通知失败分别显示。

用户可以暂停、改频率、手动检查、更新来源。立即运行一次不恢复被暂停的周期计划。错过时间按配置补跑、合并或跳过；恢复后不无限补跑。

用户撤销某项目或来源权限后，后续检查停止访问，索引和通知摘要遵守更新后的权限。

### 4.4 验收

| 编号 | 观察结果 |
|---|---|
| LA-S2-01 | Task/Run 固定负责人和 Project，不跟随用户交互焦点漂移 |
| LA-S2-02 | 无变化检查与检查失败清晰区分，跳过模型仍有记录 |
| LA-S2-03 | 重要变化含来源、检查时间和对照结果，具有可恢复的比较基准 |
| LA-S2-04 | 通知失败只重试 Delivery，不重新分析或重复执行外部动作 |
| LA-S2-05 | 暂停、恢复、手动运行、错过执行和重复事件都有确定且可查看的行为 |
| LA-S2-06 | 不支持回复 ID/卡片的平台有可识别入口或澄清，不猜测用户指向 |

## 5. 每个 Agent 的每日日记

### 5.1 用户意图

“每天整理自己的工作，形成日记，并维护必要记忆和未完成事项。”

### 5.2 正常路径

1. 每个 Agent 在自己的 Daily Project 中拥有整理 Task；配置时区、执行时间、覆盖日期、来源范围和通知策略。
2. 系统提供该 Agent 当天参与的 Session、任务、Workflow、产物和 Memory 修订索引，包括业务 Project 中的工作。
3. 在独立整理 Session 中生成完成事项、进行中事项、待决策、回顾与明日计划。系统状态与 Agent 自述分开。
4. 按权限维护自身 Memory 和交接信息；项目事实保留在 Project，共享资源修改继续遵守原 Policy。
5. Social 生成该 Agent 当天卡片，支持日历与时间流，展开可见原 Session、Run、产物和 Memory 变更。
6. 第二天新的 Daily 主 Session 自动获得必要交接和历史入口。继续业务工作时打开原业务 Session；继续日常事项时带来源进入今天 Daily。

### 5.3 跨日、纠错和缺失

正在运行的工作跨午夜不移动、不取消。日记用截止点表达当时状态，迟到结果可形成修订，并保留其实际发生时间。

没有 Daily 聊天但有项目活动时仍可形成卡片；没有活动时不编造工作。整理失败时显示缺失状态，仍能查询活动和开放事项。

同一覆盖范围重新整理保持幂等，不能重复写入相同长期事实。用户纠正或删除来源后，派生内容随之修正、失效或遮蔽。

### 5.4 验收

| 编号 | 观察结果 |
|---|---|
| LA-S3-01 | 每个 Agent 的 Daily、Memory、整理 Task 和日记彼此独立 |
| LA-S3-02 | 日记覆盖业务项目活动，不只总结一条 Daily 对话 |
| LA-S3-03 | 新日常主 Session 按时区和日期唯一选择，业务 Session 可以跨日 |
| LA-S3-04 | 日记失败不影响翌日连续性，索引可定位未完成事项和原始来源 |
| LA-S3-05 | 计划、进行中、已完成以及总结缺失分别呈现 |
| LA-S3-06 | 来源纠错/删除/权限撤回作用于卡片、摘要、索引和缓存 |

## 6. Ziji 项目开发

### 6.1 用户意图

示例：“进入 Ziji PlantOS，为养护计划增加可配置提醒，安排设计、开发和审核，随时能查看进度。”

这是演练需求，不断言 Ziji 当前缺少该功能，也不授权开发或部署。

### 6.2 正常路径

1. 解析具体 Project 根、已有配置、开发规则、历史决定与授权；建立需求 Session，并关联来源 Daily。
2. 形成目标和验收条件。如分配给架构 Agent，其输入、工作 Session 和方案需可追溯；用户在方案中作出的决定绑定具体版本。
3. 开发 Agent 获得 Docker 环境与独立工作副本，加载获授权的项目资源。依赖、镜像和配置具有版本。
4. 修改代码、运行测试、生成产物及预览证据。缺少依赖时通过环境管理合同处理，报告构建与应用状态；不能默认改宿主全局环境。
5. 可调用既有 Workflow 完成确定的多阶段流程，继续使用公共 Pi 装配和原有 Workflow Run 状态。
6. 如由审核 Agent 检查，应取得明确版本的变更与验收依据，修复和复审对应同一可定位版本。
7. 用户可从 Web 或微信查询实际进度、阻塞、预览和待决策；需求修改记录影响范围，不静默改变已批准的任务目标。
8. 结果包含变更、验证、审核和来源。合并/部署继续遵守项目授权，不因进入开发场景自动执行。
9. CI/Webhook 等后续事件可触发项目工作，并关联此前任务和会话。参与 Agent 的日记分别引用自身工作。

### 6.3 多 Agent 尚未确定的部分

上面的架构、开发、审核角色说明产品要能支持的协作结果，不锁定以下机制：

- 是否由 Nexus 调用另一个 Agent，还是用户直接加入新的工作 Session。
- 新 Session 的参与者、往返消息与结果回传如何表达。
- 是否形成共同会话，以及多个 Agent 与用户如何轮流或并行参与。
- 是否使用已有 Workflow 包装流程，或开放直接 Agent 调用。
- 是否需要外部 A2A 协议适配。

这些项目需要后续讨论后再追加验收，不能按一个固定协调树直接开发。

### 6.4 已确认的验收

| 编号 | 观察结果 |
|---|---|
| LA-S4-01 | 项目根和资源授权明确，不把整个 Ziji 上层工作区默认挂载 |
| LA-S4-02 | 并行工作有隔离副本和明确产物版本，不共同无锁写同一代码目录 |
| LA-S4-03 | 每轮能够重现所用模型、Prompt、资源和环境版本 |
| LA-S4-04 | Workflow 调用复用已有执行机制，完整历史与 Run 状态可查看 |
| LA-S4-05 | 审核结论关联实际审核版本，修复后的再次审核证据可定位 |
| LA-S4-06 | 容器重建保留工作、历史和已提交产物，失败可恢复或明确报告 |
| LA-S4-07 | 用户改变需求与批准交付有具体来源、版本和影响范围 |

## 7. 跨场景验收

| 编号 | 必验边界 |
|---|---|
| LA-X-01 | 连续多日、新 Daily、跨业务 Project、换 Channel 后能查询并继续正确工作 |
| LA-X-02 | Chat/NanoClaw/容器重启与重复事件不丢已接收工作，不因 Delivery 重试重复模型执行 |
| LA-X-03 | 私有 Agent 数据和 Project 数据隔离；检索摘要也不泄露未授权内容 |

| LA-X-06 | 模型选择使用 Chat 配置，历史 Session 或 ~/.pi 不覆盖有效定义 |
| LA-X-07 | 自定义 Prompt 区域可增删改、排序、启停，并能预览实际装配 |
| LA-X-08 | Docker 隔离覆盖实际文件/命令/MCP路径，不保留无边界宿主工具旁路 |
| LA-X-09 | 取消、暂停、权限撤回、配额不足、超时及外部动作结果不确定均有可见处理结果 |
| LA-X-10 | 旧共享 Daily 和唯一主 Session 可迁移，既有 ID、来源和项目归属不被伪造改写 |
| LA-X-11 | 公共管理 Skill 随产品安装并能在实际 Agent 环境读取文档，显式资源选择下也不丢管理入口 |
| LA-X-12 | Project、Agent、Task 与 Social 导航指向同一工作事实，无复制聊天、无限摘要链或上下文无界增长 |
| LA-X-13 | 同一个Agent可同时与用户及其他Agent交互；独立工作可并行，共享写入和独占工具受冲突保护，等待某一方不阻塞整个Agent或造成互等死锁 |

## 8. 验收证据要求

执行 Agent 应提交覆盖编号、实际使用路径、配置与资源版本、Session/Run/Delivery 关联、观察结果及剩余限制。需要真实入口、失败恢复和跨日行为的场景，不能只用相邻模块的单元测试代替。

本轮只完成定义和文档检查，不运行或宣称以上产品场景已经通过。
