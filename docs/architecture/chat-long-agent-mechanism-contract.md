# Chat Long Agent 机制与扩展合同

## 1. 收口范围与状态

2026-09-07：用户认可独立 Long Agent、共享项目认知、长期职责（灵魂模式）、自由活动与时间/事件触发的方向，要求从场景讨论收口为可组合、可扩展、可落地的机制，目标覆盖约70%～80%的常见需求。本轮为架构收口，不实施代码或部署。

本文是新增场景归类、机制职责、扩展边界和交付评审的入口。身份/配置细节仍以[定义与配置模型](./chat-long-agent-capability-model.md)为准，运行与迁移分别见[架构](./chat-long-agent-architecture.md)和[实施状态](./chat-long-agent-roadmap.md)。既有场景文档作为合同的例子和验收材料，不能按每个业务例子另建核心子系统。

进入工程管理与详细设计前，先核对[实施前约束、验证与场景依赖](./chat-long-agent-engineering-baseline.md)，确认Nano原生接入、Skill/Session接缝、测试与依赖，并收口其中决策。

本文收口产品机制和扩展规则。具体 Schema、Tool/API 名称、持久化实现、多参与者与 Pi 消息的映射、队列算法和默认预算数值，由实施 Agent 在开发前提交详细合同和验证方案。它们不得改变本文已明确的归属、并发和事实边界；若需改变，先提交架构变更理由。

70%～80%是设计目标，不是当前已测覆盖率。未覆盖需求应暴露明确缺口，不能通过无类型参数、隐式全局状态或绕过统一执行入口宣称全部支持。

## 2. 场景分类：工作意图与触发来源分开

### 2.1 三类工作意图

| 类别 | 内容与结束条件 | 配置与状态 |
|---|---|---|
| 明确请求 | 用户或获授权 Agent 提出的具体交互/工作；回答完成、任务完成或明确取消 | 请求与必要 Task；可由自然语言表达，不要求普通聊天先填写目标表单 |
| 长期职责 | 持续负责某项工作，自主选择、安排和推进；单项完成不终止职责 | Agent 职责配置、明确 Project 范围、项目工作与未完成事项；用户称灵魂模式 |
| 自由活动 | 根据兴趣探索或社交，没有规定的交付职责；可自然结束或不活动 | 兴趣、范围、接触偏好、预算及实际活动，不制造业务任务证明有产出 |

类别用于表达活动的来源与自主范围，不是 Agent 互斥模式。一个 Agent 可以同时有多项职责、处理明确请求和开展自由活动。活动转为另一类时保留新委托或职责关联；例如闲聊形成开发请求，应明确建立对应业务工作。

### 2.2 三类触发来源

| 类别 | 例子 | 稳定要求 |
|---|---|---|
| 消息 | 用户发问、Agent 请教、工作结果回传 | 可信发送者、目标、回复/工作关联 |
| 时间 | 一次性时间、周期、Agent 自主安排的下次推进时间 | 时区、到期状态、错过时间策略、重复控制 |
| 事件 | 新素材、项目进度变化、Social更新、审核完成、资源条件变化 | 可信来源、对象/版本、订阅过滤、去重和因果关联 |

工作节奏、空闲条件和优先级通过策略影响处理机会，不另建一套“灵魂运行时”。同一职责可由时间和事件共同推进；具体定时任务是明确工作与时间触发的组合；事件可引起工作、自由活动或只更新可查询状态。

收到触发不等于必须启动模型、创建 Session 或发通知。系统可确定性检查、过滤、合并、记录后等待；进入模型交互时再按策略选择 Project 下的 Session。

## 3. 六项稳定机制

这些是职责边界，不要求拆成六个服务、六个进程或六套存储。

| 机制 | 负责什么 | 新业务可配置/扩展什么 |
|---|---|---|
| K1 定义与能力装配 | 独立 Agent 配置、Chat 模型、Prompt区域、资源目录、版本及实际装配 | 身份、职责、任意自定义Prompt区域、Skill/Tool/Workflow及运行策略 |
| K2 发现与共享 | Project/Agent/资源发现、可见进度和活动、按需查询、来源与刷新 | 概览字段、受众、相关信息选择、领域进展来源 |
| K3 归属与连续性 | Project-first、Session选择、独立Daily、历史/Memory、活动索引及交接 | 项目模板、工作主题、历史查询与整理策略 |
| K4 触发与推进 | 消息/时间/事件、持久职责和具体任务、运行状态、预算及恢复 | 任务、职责节奏、订阅、检查条件、重试与下一次安排 |
| K5 交互与并发 | 真实参与者、共同或分项交流、等待/继续、因果关联、资源冲突 | 参与者、协作范围、发言策略、优先级与可用并发预算 |
| K6 执行与反馈 | 公共Pi执行、Tool/Workflow、Docker工具环境、结果、Delivery与前端投影 | 领域工具、工作流程、执行环境、Channel/事件适配和展示 |

权限、配置版本、来源、失败恢复和前后端同源贯穿六项机制。它们由系统执行；Skill负责说明怎样使用，Prompt负责指导判断，不能用自然语言承诺代替持久状态或权限检查。

### 3.1 共享认知的收口

Project概览、进度和活动通过统一服务供Web与Agent查询，公共装配提供有预算的相关概览和完整查询入口。Agent不必先参与项目或听用户介绍，才知道可见项目存在。领域状态自动关联，语义进展可由Agent补充，但要有来源和更新时间。

共享范围通过持久配置表达；配置范围内的读取不逐次询问用户。建议新建普通业务Project默认继承用户级“概览共享”设置，项目可以覆盖；Agent Daily原始历史和私有Memory仍保持自身作用域。升级已有数据不自动扩大原可见范围。默认设置属于可编辑产品配置，不硬编码具体项目名。

概览可见、详情可读、工作可执行分别判断。查询不会自动切换用户工作位置；实际进入项目工作才选择该Project的Session。所有Agent引用同一事实，不在每个私有Memory中维护项目进度副本。

### 3.2 交互与并发的收口

支持临时互助、多方共同讨论、分工和往返审核。参与者、具体工作及其对话关系分别记录；不强制中央协调者，也不按Agent身份全局串行。用户能直接与参与者交流或进入某项工作，背景范围由现有可见配置决定。

消息和决定保留真实来源、目标、回复关系及适用工作版本。点名回应、相关者补充、可选主持是可配置发言策略；没有贡献时允许沉默。具体多参与者讨论如何映射到Pi原生Session和消息，需要详细合同证明，不另存一套与Pi历史分歧的聊天事实。

同一Session的上下文推进和历史写入有序；独立Session允许并发。同一稿件、配置、Memory或其他共享写入采用版本冲突保护或短时互斥；独占工具按实际资源排队。等待用户或Agent回复不能锁住整个身份，也不能持有对方回应所需的资源。调度要兼顾及时交互与持续工作，避免长期职责饥饿。

暂停/取消针对明确职责、任务、运行或交互；不能把移除参与者、取消其所有工作和撤销全部权限当作同一动作。旧结果返回时核验适用版本，已发生的外部动作不能靠改状态撤回。

## 4. 通用处理过程及事实责任

~~~text
消息 / 时间 / 事件
→ 耐久接收并固定可信来源、目标和关联
→ 校验可见范围、Agent/Project/定义状态，去重与调度
→ 读取职责/任务、当前工作与必要共享事实
→ 确定性处理，或选择Project Session并冻结配置后进入公共Pi装配
→ 调用Tool / Workflow，在授权环境完成动作
→ 保存结果与工作状态，更新活动关联
→ 按策略投递、发出变化事件或安排下次机会
~~~

没有调用模型的处理仍有归属与可查询记录；无需创建空Pi Session。消息原有交互、Task定义、一次Run、Workflow Run和Delivery继续保留各自生命周期，不能因流程图相似而合并成一个状态字段。

| 事实 | 管理责任 |
|---|---|
| Agent定义、职责、共享策略、任务与订阅 | Chat文件配置服务；Web与Agent使用相同校验、版本和应用合同 |
| 具体计划、选题、稿件、阶段与产物 | 所属Project及领域工作服务，保留来源和版本 |
| 原始对话、上下文压缩与恢复 | Pi原生Session；Chat只增加产品关系和执行元数据 |
| Chat Personal/Project Memory与Agent Memory | 保留各自已确定的领域服务及作用域 |
| Channel、触发投影、Inbox、Delivery/Ack | NanoClaw按窄合同与Chat协作，不恢复第二套Agent Runtime |
| 概览、活动、日记和页面 | 基于上述事实的视图；不能反向成为另一份配置或执行真相 |

## 5. 新需求的扩展顺序

| 优先级 | 扩展方式 | 例子与边界 |
|---|---|---|
| E1 配置组合 | 配置Project、职责、触发、Prompt、资源选择、可见范围和策略 | 把提醒时间从22点改为23点；增加一个学习项目；调整职责重点 |
| E2 能力资源与流程 | 添加/调整Skill、Rule、Experience、Tool及Workflow，走现有注册装配 | 增加读书方法、图文校对、素材处理与审核流程；业务步骤不写进调度核心 |
| E3 领域或接入适配 | 接入新数据源、领域服务、Tool/MCP、Channel、事件或环境适配器 | 新视频源、日历、文档库；使用有类型合同、可信来源与既有权限/版本/恢复规则 |
| E4 核心机制变更 | 现有合同确实无法表达时进行架构评审 | 改变Session归属/事实源、身份信任边界、执行生命周期或并发语义 |

上述顺序是最小改动选择，不是要求业务必须零代码。新的领域服务可以保存自己的工作事实，但不能复制Agent Loop、模型配置、对话或权限系统。Plugin可以包装资源与适配器，仍接受同样的注册、授权和生命周期管理。

只有出现以下证据才升级E4：现有组合不能表达必要行为；需要改变核心对象关系/生命周期/事实责任；多个独立真实需求暴露同一缺口。单个需求若已涉及核心边界也必须评审，不必等待第二个。新行业名词或不同项目名称本身不是核心变化。

不把每个业务写成核心枚举。例如道德经、旅游、Content Lab是Project与能力组合；“转译”“小红书排版”是领域能力；“新素材到达”是事件适配，不在通用调度器中判断项目名称。

| Ziji开发与审核 | 明确请求，或长期维护职责；消息/开发事件 | 项目规则、开发/审核能力、Workflow、Docker和参与关系 |
| Content Lab日常运营 | 长期职责＋自主安排时间/素材或结果事件 | 职责配置、项目制作状态、内容Skill/Tool/Workflow |
| 自由读书和闲聊 | 自由活动＋时间机会/兴趣事件 | 兴趣与接触策略、可见资料与交流能力 |

一项业务可以组合多类活动，不强迫整个Project只有一种模式。跨日、跨Channel、并发、失败、权限变化和版本冲突是共用验收条件，不为每个行业重新实现。

## 7. 落地与执行Agent的交付要求

实施按[路线与迁移要求](./chat-long-agent-roadmap.md)推进。先提交具体合同，再完成配置、服务、运行和界面；每个能力的完整交付至少包含：

1. **配置**：Schema、作用域、默认/继承、校验、版本、应用状态和旧数据迁移。
2. **管理与能力**：同源API/Tool、真实注册、公共管理Skill、资源发现/更新与运行环境内可读性。
3. **执行**：用户真实入口、公共Pi装配、固定Project、Session/工作关联、并发、恢复与投递。
4. **前端**：配置查看/编辑、有效Prompt与资源、工作/参与者/等待状态、来源与继续入口，刷新可恢复。
5. **证据**：正常路径和关键异常验证，标明当前能力与剩余限制；新增业务需说明用了E1～E4中的哪一级。

只增加Tool声明、文档、配置表单或一个后台定时器，均不构成机制交付。资源缺失、来源失效、权限不足或外部结果不确定时，必须能定位具体工作与恢复方式，不以成功摘要替代证据。

任务书按机制的完整可用能力组织，业务场景作为贯通验收；不拆成互不兼容的“道德经系统”“旅游系统”“灵魂系统”。架构师负责合同审核与验收，执行Agent实现，遵守当前仓库验证和发布规则。

## 8. 如何评价70%～80%的目标

维护实际需求样本，记录意图、触发、Project、参与者、可见数据、所需能力、持续状态和扩展级别。以事先确定的代表性样本为分母，统计通过E1～E3接入、没有改变核心合同且通过真实入口验收的需求占比；同时单列只需配置/资源组合的比例与适配开发成本。

已有场景是初始验收集合，后续应加入未为其专门设计的新业务验证扩展性。不能只反复通过同一组示例就宣称覆盖全部需求，也不能临时排除失败案例美化比例。高频场景优先，低频缺口记录为适配待办或E4评审。

这个比例衡量接入方式的通用性，不表示允许20%～30%的运行失败；既定支持范围内的数据、归属、并发与恢复合同必须成立。

至此停止按业务无限发散。下一步先确认实施前约束、测试与基础场景依赖，再准备工程管理记录、详细合同及任务书。新需求使用本文件归类，发现真实机制缺口时再修订架构。
