## P1：补偿恢复再次覆盖更新版本

位置：`src/long-agents/artifacts/service.ts:398`–`:404`。

复现顺序：

1. v1 已落盘，回执丢失；恢复 v1 在 rename 前暂停。
2. 第二次 occurrence 生成并提交 v2，确认 committed。
3. 放行 v1，它落盘后发现 v2，准备执行写后补偿恢复；在补偿的 atomicWriteText rename 前暂停。
4. 第三次 occurrence 生成并提交 v3，确认 committed。
5. 放行补偿恢复。

结果：磁盘为 **v2**，最新 v3 记录仍 committed。补偿使用锁外旧快照直接 atomicWriteText，没有归属/版本条件保护，导致恢复动作本身回滚新版本。不是外部编辑器，不是未定义的微秒窗口，而是所有写入均经过受管服务仍失败。

应停止增加“写后再恢复”的补丁链；目标文件所有权和提交必须形成闭合协议。可选方案为受管路径串行化并在正确释放暂停点的测试中验证排队，或不可变版本文件与受保护的当前指针。不能要求后到的同锁写入先完成才释放前者，再据此否定锁。跨产物同路径与补偿动作应服从同一规则。

## 旧问题未关闭：已有文件人工修改仍可丢失

位置：`src/long-agents/artifacts/service.ts` 中 writeNoteFile 的 readFile→rename。

适配探针先创建实际文件，再模拟回执丢失，暂停恢复 rename；用户写入 `user edit`，放行恢复后磁盘变回 v1。第一轮原子 link 仅保护不存在的文件，不保护已存在文件的修改。

[当前产物合同](../../modules/long-agents/deliverables.md) §3 已将该行为写成残留窗口。这属于保障范围缩小，不是原需求已修复的证据；本轮没有用户批准该缩小。窗口也没有“微秒级”的可靠上界，调度和 I/O 可延长它。

不要求实现不可移植的万能文件 CAS；可采用保留版本、显式冲突处理等方案，避免不可恢复的数据损失。如果要接受外部并发修改可能丢失，必须作为明确取舍交用户审核，不能在验收报告中算已修。
