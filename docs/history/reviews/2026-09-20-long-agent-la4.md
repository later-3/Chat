### 复核探针的复跑与一项**已披露的偏差**

复核者第二轮探针（`.data/verification/la4-review-round2/la4-round2-probe.test.mjs`，6 项）在本实现上复跑：**3 项通过，3 项因与所采纳的替代协议不相容而挂起**（逐项有 `--test-timeout` 记录，非静默跳过）：

- 通过：`recovery checks body`、`maintenance and resubmit share one publication`、`revocation completed before append blocks publication`。
- 挂起第 1 类（探针第 2、3 项）：探针把暂停点挂在 `fsp.rename` 上，等待 `gate.ready`。采纳替代方案后**首写走原子 `link`**（目标不存在时不再调用 `rename`），探针的 gate 永不触发，是其自身构造死锁。同一不变式已改写为确定性门禁 R11（旧写入迟到）与 R12（外部创建）。
- 挂起第 2 类（探针第 5 项）：探针要求"同产物第二个写入者在第一个被暂停期间完成"，与本实现**同产物串行化**（R2-2 的修复手段）冲突。不变式改写为 R13（陈旧回执不能完成新版本）+ R15（后到写入者等待后完成）。串行化是刻意选择：串行保证"查重→副作用→落账"原子，代价是同一产物的第二写入者要等在途写入。

### 返工过程中的异常发现（如实记录）

1. **10 分钟挂起（609s）**：第一轮返工曾用"按路径阻塞锁"（`withFileLock(<artifactFile>.path:<canonical>)`）协调写入。该锁是**无超时的进程内 promise 队列**，被暂停的在途写入持有时会**无限阻塞**其他写入者；与复核探针的暂停点组合后形成死锁，表现为用例挂起约 10 分钟直到命令超时。这确认复核者"检查与写入分离"的判断，并进一步说明**跨 I/O 的阻塞路径锁本身不可用**；本轮已改为无路径锁的"原子创建 + 条件替换 + 写后归属恢复"。永久门禁加 `--test-timeout`，本地全套 16 项 4.4s 完成。
2. 首轮返工曾在不可覆盖时把内容另存为 `*.conflict-*` 副本文件；现改为**内容保留在产物记录中**（不再产生无规则归属的旁路文件），门禁同步调整。

返工后门禁：`pnpm verify` 通过（44 tooling + **431** Backend + 178 Frontend + 30 生产构建 + 1 Nitro 开发 Runtime），`check:architecture` 与父仓库/Frontend/Nano 三处 `git diff --check` 全过；边界门禁扩至 **16 项**（R1–R15，含本轮新增 R11–R15）。

[第三轮复核](./2026-09-20-long-agent-la4-independent-review-round3.md) 判定"暂不通过"，给出 1 个新 P1（补偿恢复再次覆盖更新版本）与 1 个未关闭的旧问题（已有文件的原地人工修改仍可丢失）。复核者的核心要求：**停止"写后再恢复"的补丁链，让目标文件所有权与提交形成闭合协议**（首选受管路径串行化；或不可变版本文件 + 受保护当前指针），并且如果接受任何残留覆盖窗口，必须作为明确取舍交用户审核，不能在验收报告里算已修。

### 修复（协议级，非增量补丁）

1. **删除写后补偿**：`commitFrozen` 中"发现更新版本就恢复其内容"的补偿被整体移除——它使用锁外旧快照直接写入，正是 P1 的成因（三次写入交错时把 v3 回滚成 v2）。
2. **受管路径串行化（复核者首选方案）**：同一规范化笔记路径由**一把路径锁**串行化，**归属检查 + 已知内容检查 + 写入 + 写后回读校验全部在同一把锁内重新读取**（不复用锁外快照）；任何更新记录（`pending` 或 `committed`）都阻止更旧记录写入。旧记录迟到写入类别在结构上被排除，补偿因此不再需要。
3. **关闭"已有文件原地修改丢失"**：replace 之前先用硬链接保留**被替换 inode 的快照**，rename 之后回读快照——若与校验时的已知内容不一致（外部原地修改，无论发生在检查前还是 rename 前），立即把外部内容**恢复回目标路径**并记为不可重试阻塞，同时本次生成内容保留在产物记录中；一致则删除快照，不留临时文件。

### 待用户明确确认的取舍（复核者要求，不视为已修）

修复后剩余窗口**只有一种**：外部编辑器**自己**用"写临时文件 + rename"的方式写入，且恰好落在我们"快照 link"与"rename"之间的单次系统调用间隙。该间隙内没有其他 I/O 语句，但进程可能在 await 边界被挂起，因此**不承诺墙上时间上界**；此窗口内不可检测，也不可恢复。其余情形（检查时已存在的外部内容、检查与 rename 之间的**原地**修改、并发新建）均已被"拒绝写入 / 恢复外部内容 / 原子 create-if-absent"覆盖，已记录版本的内容不会丢失。

按复核者要求，此项需用户确认：
- **方案 A（当前实现）**：接受上述单次系统调用间隙内的"写临时文件 + rename"式外部写入可能丢失，其余外部修改均被保护。
- **方案 B**：改为不可变版本文件 + 受保护当前指针——受管路径只在首次创建时写入，后续版本写入不可变文件并把"当前"指针与最新内容解耦，可消除该窗口，但用户可见的笔记路径会变为版本化布局。
- 用户确认 A 之前，本记录**不把该窗口算作已修**。

## 第四轮：用户选择方案 B 与实现（2026-09-20）

用户明确选择 **方案 B**（笔记是用户资产，不接受人工修改可能静默丢失），并给出约束：底层不可变版本 + 受保护指针；前端仍是一篇笔记、历史按需展开；用户编辑的文件与生成版本分开管理、冲突时保留双方并明确提示；**B 只有在版本文件本身不会被外部编辑器覆盖时才成立**。

### 实现（写入协议重建，而不是再加补丁）

新增 `src/long-agents/artifacts/note-store.ts` 与契约字段 `note`（版本文件、指针、工作区状态、冲突、冲突处理结果），把笔记提交改为：

1. **不可变版本**：内容写入 `<笔记目录>/.chat-notes/<名字>-<路径哈希>/versions/r<版本>-<哈希前8位>.md`，用 `link` **原子 create-if-absent**；同名路径已有不同内容时改用新的不冲突路径，**从不 rename 覆盖**，写后回读校验哈希。即使版本文件被人为改写，被改写的内容也会被另存为 `user/` 版本、我们的内容写到**新的**不可变路径（`r<版本>-<哈希>-1.md`），原文件保留 —— 版本文件因此不可被静默覆盖或丢失。
2. **受保护指针**：`current.json` 由服务端原子写入，但**权威副本是 Chat Home 里的产物记录**（工作区外）；指针被删除、篡改或版本文件被替换时由记录重建（永久门禁 R18）。
3. **用户文件永不覆盖**：用户可见笔记文件只在**不存在**时以 `link` 创建一次；此后只做只读分类 `clean` / `older` / `edited` / `missing`。人工修改被保留为独立不可变版本（`user/…-user.md`）并记为冲突，**不修改用户文件**。
4. **冲突显式处理**：`resolve` 提供"以我的修改为准"（外部内容登记为新的 `user` 版本，工作区文件本来就是它，无需任何写入）与"以生成版本为准"（记录决定，双方内容继续保留）；`export` 把当前版本写到**新文件**，已存在文件永不替换。
5. **归属与串行化**：同路径一把路径锁内完成归属检查、版本写入、指针更新与回读校验；最新记录拥有当前版本，旧记录只保留历史。写后补偿被删除（不再需要）。

**结果：服务端对工作区不再有任何"覆盖已存在文件"的动作**，第三轮指出的残留窗口（以及"不能只换目录就宣称消除风险"的质疑）由**结构性不变式**消除，而不是由更小的窗口缓解。
