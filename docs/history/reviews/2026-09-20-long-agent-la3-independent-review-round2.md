## 尚存的验收阻塞项

### R2-1 / P1：到期的自调度计划被维护循环撤销

位置：`src/long-agents/duties/service.ts:43`，`selfScheduledAt`、`dutyTaskDefinition`、`desiredTaskStatus`。

独立复现：cadence=none；report 给出未来一分钟 nextCheckAt，得到 active 的 once 投影。将 Date 推进到到期后 1 秒，先运行真实 `reconcileFriendDuties`，再交付原已计划触发。维护把 once 改成占位 cron 并暂停，触发被判为“旧任务版本已失效”，执行数为零。

原因：只要时间已到便把计划当作不存在，未区分“到期尚待交付”与“已经消费”。正常维护、Nano 扫描和网络交付存在此合法顺序，因此不能靠先交付再维护的幸运顺序工作。

修复门槛：用持久计划身份/消费状态维持到期任务，接受或终结后再转换；验证维护先到、触发先到、重启后到期、重复交付均至多执行一次，不丢一次。

### R2-2 / P1：进度纠错的并发 CAS 仍无效

位置：`src/long-agents/duties/service.ts:502` 的 report 分支。

独立复现：两条不同 requestId、expectedRevision 均为 1 的 report 同时修改累计进度和下一步，结果两条都成功。锁内检查已存在，但 report 写入后不增加任何用于后续冲突判断的版本；最终当前值仍由提交顺序决定。

配置 CAS 已修复不代表进度 CAS 已修复。保留两条历史不能替代当前状态的冲突保护。修复门槛：明确进度并发版本或推进整体 revision；用户纠错与后台报告竞争时旧写入应拒绝或显式合并，并保持同请求幂等和不同载荷冲突规则。

### R2-3 / P1：排队后预算复核读取旧计量，仍能超额启动

位置：`src/long-agents/tasks/service.ts:504`、`:543` 与职责 `tokensToday` / 回执计量。

独立复现：3 个其他工作加一次职责推进占满 4 项容量，职责日预算为 50 tokens；第二次自动触发处于 accepted 等待。第一次职责执行结束已产生 60 tokens 的原生 usage；释放容量后调用真实派发器，第二次仍变 started，最终职责计量达到 120 tokens。

维护主循环虽改为先记账再派发，但触发入口直接调用同一个派发器，不经过该记账顺序。故新增的 recheck 仍可能读到 0。此处不是允许单次运行超过软上限的问题，而是已耗尽后又启动一次。

修复门槛：所有派发入口在检查预算前统一处理已结束但未入账的执行，或从权威用量获取保守事实；计量失败不能当作零永久落账。回归需覆盖触发直达派发、维护派发和重启后派发三条路径。
