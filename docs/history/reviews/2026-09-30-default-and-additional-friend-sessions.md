# 每日默认会话与额外会话：现场复核及待审核方案

日期：2026-09-30。

状态：用户已明确“每天默认一个 Session，不代表只有一个 Session”，并在后续反馈中确认了创建新 Session 的理解。每日默认入口与额外独立会话并存的产品方向已确认；本文其余实施细节仍为方案，未实施、迁移或部署。旧文档及代码中的“每日唯一直接交流”不能再作为拒绝此需求的产品依据。

本轮按用户要求先还原过程供审核。真实会话正文、Session/Work 标识、Prompt 快照和精确时间线只保存到本机被忽略的 `.data/verification/session-review-20260930/`，不进入 Git。本文保留可复用机制和脱敏发现。

## 1. 已核实的运行链

证据来源：生产 Session API、API 返回路径对应的原生 Pi JSONL、日历 API、浏览器实际消息及过程详情；代码用于解释这些证据。没有重新调用模型或发送消息。

1. 日常 Session 在本轮用户输入之前已创建。单凭 Session 头无法确定最初由哪个页面操作创建。
2. 当天定时工作使用独立 Work Session；完成后向日常 Session 追加 `display=false` 的工作回执，只保留状态和结果引用。
3. 后续 Web 用户仅打招呼。工作 Agent 获得本轮项目、长期身份、昨日总结及上述回执，再主动读取工作结果与长期记忆。
4. 工作 Agent 完成会话记忆和 Agent Memory 写入，然后回复用户。
5. 同一 Workflow 的 `remember` 节点继续执行。记忆写入 Agent 本轮未调用工具，生成了包含既有写入回执的近似重复回复。
6. 浏览器正常消息区显示主回复；记忆节点回复位于展开后的过程详情。不能将内部重复产物误述为默认界面连续显示两条主回复。

本例共 1 条用户输入、6 次模型响应、7 次工具调用；累计输入/输出/缓存读取计量为 168,768 tokens，不是单次上下文长度。页面总耗时约 210 秒。主回复持久化到下一阶段标记之间存在约 130 秒空档，记忆节点模型响应本身约 15 秒。

## 2. 发现与结论边界

| 发现 | 证据与影响 | 后续处理方向 |
| --- | --- | --- |
| 默认会话被误建模为唯一会话 | `project-agent.ts` 按 Friend/date 返回既有日常 Session；同日多个日常标记视为恢复冲突；`start` API 没有额外会话创建语义 | 唯一性约束只保留在默认入口映射，额外直接会话按原生 Session ID 绑定 |
| 创建不是唯一拦截点 | `openAcceptedDay`、`startFriendWork`、工作回传均依赖日常绑定；任意新建一个 Pi 文件不足以获得 Friend 归属及完整功能 | 统一明确归属验证与默认指针职责；不得放开任意 Session 接管 |
| 轻量聊天触发过度记忆维护 | 本例写入 2 条会话记忆，并全量重写约 16 KB 的 Agent Memory 文件 | 保持可查询事件与值得沉淀的记忆分工；打招呼不应仅为证明连续性重复记账 |
| 记忆内容缺乏事实约束 | 工作 Agent 把 turn/request 标识写成会话标识；实际回复前写“已回复”；`author=user` 的条目混有 Agent 的历史推断 | 事实、推断和计划区分；来源引用由可信上下文绑定，操作完成以实际回执为准 |
| 记忆节点的职责与继承内容冲突 | 实际 Prompt 约 22,200 字符；仅注册 `session_memory`，却继承完整长期身份、昨日总结及多工具使用指引；本轮无工具动作而重复主回复 | 继续复用公共装配，按节点职责限定适用指令与上下文；维护结果表达新增/修订/无需写入，避免重复业务答复 |
| 旧身份文本与运行能力冲突 | 历史 Standing Instructions 仍声称 Web/桥接尚未上线，实际本轮已有这些入口和工具，另有运行能力合同纠正 | 清理已失效的能力断言，身份职责与实时能力事实分开，不能无限叠加相互矛盾的补丁 |
| 用户输入被既有事项主导 | 打招呼后主动回顾过往待决事项；工作回执与昨日总结为该行为提供了背景 | 历史是连续性材料，不应等同本轮待执行指令；先判断当前意图与时效 |
| 阶段间等待难以解释 | 原生时间线有约 130 秒空档；`runtime.ts` 会等待 observer，`chat-run-events.ts` 的 `finish()` 等待事件队列写完 | 事件积压/持久化为候选调查方向，尚未证实为本例根因；补充分阶段耗时证据后再修复 |

工作结果及 Memory 中关于其他 Agent、历史投递或平台错误的描述，本轮仅核实它们被读取和使用；没有据此宣布那些外部状态仍然真实。昨日总结的注入已由本轮 Prompt 快照证实，不等于其全部内容质量合格。

## 3. 供审核的产品合同

### 3.1 默认入口与独立会话

- 同一 Long Agent 可以拥有多个用户主动创建的直接会话；它们共用身份、授权范围和该 Agent 的长期记忆能力，各自拥有独立原生 Session、消息历史和会话记忆。
- 每个 Agent/日期只保留一个默认 Session 引用。“打开今日默认会话”幂等；“新建会话”是显式的新建意图，重试同一次创建请求仍幂等。
- 创建额外会话不替换当天默认引用，不复制当天完整聊天历史，不创建另一个 Agent，也不要求用户先创建后台任务或主题节点。
- 点击 Friend 的默认聊天入口仍打开今日默认会话；用户显式选中的 Session 在刷新、续聊和跨日后保持原目标。次日从默认入口打开时才选择新日默认会话。
- 所有直接会话仍固定存储在 Agent Home。执行项目继续由 Web 顶栏选择并在每轮接受时冻结，切项目不移动或隐式拆分 Session。

### 3.2 前端行为

在 Friend 的会话列表提供“新建会话”，与“打开今日默认会话”有明确区别。列表能识别默认会话、用户额外会话及后台工作；额外会话可命名、打开和继续。使用现有公共 ChatWindow、服务端归属与日历投影，不在浏览器维护另一套 Session 清单。

新建无需填写任务定义。若用户需要复制已有上下文，应是另一项明确的 Fork 操作，不混入普通新建语义。刷新后从服务端恢复新会话与其身份，而非靠当前 UI 选中状态推断 Friend。

### 3.3 每日工作与记忆

- 每日档案聚合该 Agent 当天所有有活动的会话与各类任务，不只读取默认 Session。跨日继续同一 Session 时按实际活动日期归档，并保留同一 Session 引用。
- 每日总结继续是独立定时工作，保存独立 Markdown；日常消息不是归档容器，总结不作为用户发言或普通聊天回复出现。
- 新会话按既有连续性合同获得昨日总结和必要核心记忆，更早总结/会话按权限按需读取；不会自动得到其他会话的全部历史。
- 用户从额外会话委派的工作应返回真实来源会话。定时任务按其任务来源归档，不因“必须有 originSessionId”就伪装成用户在默认会话里发起的工作。是否向默认会话提供轻量回执应作为独立可审核的通知策略。

### 3.4 顺序、恢复与兼容

沿用每个 Session 的有序队列，不用每日默认指针锁住整个 Agent。独立 Session 的并发仍受现有容量/预算控制，共享 Memory、文件和配置使用 revision/资源级冲突保护。

既有每日 Session 保留原 ID 和历史，继续作为对应日期的默认 Session。额外会话不能写入旧的唯一日常标记而触发恢复冲突；恢复、删除/归档默认项、过期创建请求、跨日接受和失效归属必须有明确行为。具体元数据版本、API 字段和默认项删除后的策略仍需在实施合同中落定，本文不虚构已支持的参数。

## 4. 改造范围与验收门槛（待实施）

本需求属于 K3 归属/连续性、K5 交互/并发、K6 反馈；改变每日 Session 的对象关系，按机制合同 E4 审核。复用 Pi SessionManager、Chat 归属元数据、公共装配和现有日历/任务领域，避免新增另一套聊天运行时。

| 范围 | 核对入口 |
| --- | --- |
| 默认定位、额外会话归属、恢复 | `src/long-agents/project-agent.ts`、`daily-state.ts`、`daily-service.ts`、Session owner resolver |
| 创建/打开与每轮接受 | `src/routes/api/long-agents/[longAgentId]/start.post.ts`、Long Agent turns/accept 路径 |
| 来源与工作回传 | `src/long-agents/work.ts`、`tasks/service.ts` |
| 每日聚合、总结与连续性 | `src/long-agents/day-archive.ts`、`daily-summary-task.ts`、公共装配 |
| Web 导航、刷新、默认入口 | Friend 会话列表、`AppShell`、现有日历和 Session HTTP parser |
| 内部记忆节点 | `src/workflows/session-memory/writer-run.ts`、writer runtime/配置、公共装配与读模型 |

最低业务验收：

1. 同日创建 2 条额外会话，再打开默认入口，3 条各自稳定且不互相替换。
2. 同一次创建重试只有 1 条结果；不同创建意图得到不同 Session；刷新与服务重启保持归属。
3. 新会话保留 Friend 能力和必要连续性，但不混入其他 Session 正文；普通项目/其他 Friend 的会话不能被接管。
4. 多会话中分别切项目、委派任务，执行上下文及回传来源正确。
5. 同 Session 排队、不同 Session 独立推进；并发写同一 Memory 能检测冲突。
6. 次日默认入口轮换，显式旧会话可继续；日归档/总结覆盖全部实际活动，不重写历史时间。
7. 闲聊无可沉淀信息时允许不写记忆；维护节点不重复回答用户；来源、写入回执和完成状态可核验。
8. 阶段耗时分开记录；不能把事件发布/收尾等待显示为模型一直 Thinking。

涉及实现后依仓库规则执行 `pnpm verify`，Workflow/装配变化另覆盖真实 Nitro 开发链和 Runtime。当前仅完成只读核验及文档记录，未运行新代码测试。
