# LA3 独立复核：需返工

2026-09-20。对照阶段任务书、LA3 验收记录与职责合同，检查实际职责服务、Task 派发和 Tool，并运行隔离复现。结论：已有同源管理和独立执行的基础，但不能接受“LA3 已完成”；先修复下列问题再联合复验。本轮没有修改业务代码、提交或部署。

## 验收阻塞项

1. **P1：暂停/恢复使学习进度与当日预算失效。** `duties/service.ts` 的生命周期操作都增加 `revision`，而 `currentUnitsDone`、推进上下文、`tokensToday` 只读取当前 revision。实测先报告 1/3，再暂停恢复，得到 `unitsDone:null`，原记录 `superseded:true`。仅暂停不应当作更换学习目标，预算也不能因修订重置。需分离配置并发版本、目标版本和消耗统计口径，补暂停/恢复、仅调节节奏和预算后的连续性测试。
2. **P1：进度报告没有核对职责与接受时目标版本。** `resolveAdvancementKey` 只确认 turn 属于本 Friend 的后台 work，然后返回 requestId；没有核对 occurrence→task→dutyId/dutyRevision。实测 B 的 work 可以给 A 提交 agent 进度。还可能将旧目标执行用最新 expectedRevision 写入新目标。必须从可信接受记录验证完整绑定，迟到结果只能归原目标历史；补错职责、普通后台 work、过期目标和无效终态测试。
3. **P1：修订检查在锁外，并发修改静默覆盖。** `manageFriendDuty` 在读取 current 后检查 expectedRevision，进入 `changeDutyState` 锁内未复核。实测两个 expectedRevision=3 的不同目标修改均成功，第二个覆盖第一个。report 又不推进并发版本，相同推进键重提会覆盖原报告而非保留纠错历史。需锁内 compare-and-swap，明确报告独立版本/追加修订及相同请求异载荷冲突，补真正并发测试。
4. **P1：心跳下一步时间只保存和展示，不控制推进。** `nextCheckAt` 未参与前置检查或 Nano 投影，实际只由固定 cron 驱动。实测设置 2099 年检查时间，自动前置检查仍返回可执行；cadence none 时未来 nextCheckAt 也不会唤醒。应按已确认合同实现持久下一步时间与 LA2 调度联动、无有效计划等待及去重，不把元数据展示当自主推进完成。
5. **P1：排队到真正执行之间不复核职责前置条件。** `evaluateDutyOccurrence` 在触发接受时运行；`dispatchTaskOccurrences` 容量等待结束后直接启动冻结 workText，不重新核对预算/允许时段/目标变化。维护循环也先派发再回收职责消耗。前次运行耗尽预算后，已等待推进仍可启动；旧目标排队项也缺少明确处理。保留耐久接受和输入冻结，但在启动前按合同复核并记录跳过/阻塞，不悄悄改写旧输入。此项为代码路径确认，尚未运行专门队列复现。
6. **P2：证据可用性和路径边界没有完整落实。** Friend 空间只检查相对路径，不检查文件存在；实测 `does-not-exist-review.md` 被接受。Project 路径用词法 resolve + stat，未 realpath 校验，符号链接可能指向授权根外。应经既有受控资源接口核验 Friend 文件，Project 使用规范化真实路径；无法验证时明确未验证，不能记为已核验成果。补不存在文件与符号链接边界测试。
7. **P2：聊天中的进度纠错尚未打通。** Tool 所有 report 都标为 agent 并要求后台 workId；日常主聊没有该绑定。因此用户在聊天中要求纠正进度或解除缺资料状态时，Agent 无法使用报告入口完成，而 Web 可以。需区分受权管理纠错与后台执行报告，维持可信来源和审计，补真实主聊纠错→页面恢复推进的场景。
