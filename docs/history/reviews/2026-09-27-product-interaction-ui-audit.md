# Chat 功能、交互与 UI 审计

日期：2026-09-27。状态：盘点完成、整改建议；除规范补充外，本轮不实施界面或业务行为变更。

## 1. 结论与统计口径

主要布局参考是 **LobeHub、Cherry Studio**。仓库已有 UI/UX 规范，问题是新增功能未持续遵守规范，以及对象/执行/导航合同没有同步收口。不能把此次问题归结为换一套颜色。

按 **30 个用户任务界面/区域** 盘点，**17 个有明确 P1/P2 整改项**：功能或状态逻辑涉及 **5** 个，交互涉及 **14** 个，视觉涉及 **7** 个。类别有重叠，不能相加。剩余 **13** 个在本轮没有确认 P1/P2；其中含仅做源码初审、仅观察空态/错误态的界面，不能称为全部合格。

这里的“界面”不是路由数：6 个全局任务面、9 个 Friend 管理标签、7 个配置/资源面、8 个共享任务区域。普通聊天的正文、过程、输入不拆成多页；同一组件在独立的主题工作区与 Friend 管理中分别计入两个实际任务入口。优先级：P1 可能造成错对象/重复操作/错误事实判断或严重妨碍主任务；P2 是明确的理解、操作、可读性偏差；轻微 P3 不计入 17。

证据范围：26 个界面打开了浏览器页面或相应任务状态，4 个仅源码初审。并未对 30 个界面的所有运行、断网、保存与移动状态做全量验收。

## 2. 审计环境与限制

- 审计基线是 `codex/unified-session-performance` 工作区的当前未提交实现，目录为 `/Users/xulater/.codex/worktrees/unified-session-performance/Chat`。主仓库旧构建不能代表本次修复后的预览。
- 浏览器为 Codex In-app Browser，地址 `http://127.0.0.1:63291/`，隔离的真实数据副本。没有发送消息、运行模型、创建任务、保存配置或操作生产服务。
- 主观察主题是跟随系统的暗色；用户附件提供浅色群聊问题的补充证据。浅色配色问题以当前源码颜色值与主题背景计算，明确区别于真实截图测量。
- 默认浏览器截图约 923×1125；另设置 1440×900 和 390×844 进行空间检查。浏览器缩放导致 CSS 实际窄视口约为 400×865。改视口后的截图有缩放/留白采集现象，不把采集空白算产品缺陷；尺寸结论来自 DOM 的 `getBoundingClientRect`。结束已恢复视口。
- 隔离预览故意没有 NanoClaw 连接、模型认证。连接失败、模型目录为空不计为生产故障；但失败时误导性的页面状态仍可验证。
- 不覆盖真实 iOS 键盘、standalone PWA、屏幕阅读器、多窗口、完整 200% 缩放、全部明暗主题组合。竞态和重复执行没有通过真实发送复现，仅记录代码中缺少的保护。
- 原始截图保存在忽略目录 `.data/verification/ui-audit-2026-09-27/`；其中可能包含用户已有历史，不应提交或发布。报告只记录必要的界面事实。

## 5. 按用户流程排列的证据与发现

### 步骤 1：选 Friend → 选日期 → 当日会话和工作

健康度：已改善，仍有命名问题。新证据 `21-calendar.png`、`22-day-work.png`、`23-session-memory.png`。

9/26 点击后进入当天原 Session，侧栏出现 1 条后台工作与开始时间 08:00:53。此前的重复标题问题不能用按 title 去重解决：不同日期执行可以有不同 work/Session；同一执行也可能跨日继续。之前的日期修复不在本轮重复宣称为新成果。

**I01：对象名称与类型不清楚（#2/#24）。** 工作列表仍以机器任务 ID 为主标题；项目列表中的群公共记录与成员参与记录缺少类型。建议优先名称/任务目的，再展示开始时间、执行状态和来源；详情保留稳定 ID。群记录应明确“群公共历史/某成员参与记录”并提供进入群工作区的路径。是否调整普通列表的收录范围需核对后端 owner 合同；本轮没有证据证明存在越权读取，不把它写成权限漏洞。

源码：`frontend/components/FriendWorkPanel.tsx`（该组件已在任务与归档区域重建时删除，Frontend `e8d6b08`）第 124 行直接显示 `work.title`；[SessionSidebar](../../../frontend/components/SessionSidebar.tsx) 第 896 行按 ordinary owner 过滤；[session-owner](../../../src/session-owner.ts) 当前索引不表达群公共/参与类型。改变后端 owner 不能靠前端按标题猜测。

### 步骤 2：进入群聊 → 看消息 → 理解如何让成员响应

健康度：优先整改。新证据 `25-groups-medium.png`、`26-groups-compact.png`；用户浅色截图与新暗色截图呈现同一结构。

**I02：页面没有围绕群聊主任务组织（#4/#12）。** 群标题下面 4 个成员历史加 1 个群历史，共 5 条全宽胶囊；群公共记录和成员参与记录视觉同级。“发送”与“开始一轮”分离，发言策略直接显示 mention/round-robin/parallel/moderator/free。管理页又包含消息输入、开始一轮、咨询和后台工作，成为第二个聊天控制面。

根因不是截图变形：[群聊 CSS](../../../frontend/components/LongAgentGroupChatView.module.css) 第 106 行 `groupHeader` 为纵向 flex，成员按钮直接作为子项，被默认 stretch 拉满。第 43 行媒体规则想隐藏侧栏，但第 52 行 `.sidebar { display:flex }` 后定义而覆盖它。实测窄屏约 400×865：群列表高 288px，消息区仅 104px；历史按钮高 27px，发送高 34px，返回/刷新 28px，均未达到触控基线。

建议群标题只保留名称、成员摘要、一个历史入口与更多菜单；公共历史为默认，成员参与记录在历史范围选择/成员详情中查看。窄屏采用列表 → 群聊单主任务面，给出明确群切换/返回。管理页保留成员、权限、策略等配置及“进入群聊”，执行入口归到群工作区。发送与发言轮如何组合须先明确当前业务语义，不能未经评审直接改成“一发就全员运行”。

**F01：两套群界面均缺少必要异步保护（#4/#12，源码确认，未制造重复执行）。**

- `reloadDetail` 的结果直接写状态，缺目标代次校验；管理页虽有 AbortController，未将 signal 传入详情请求，也未在成功回写前检查。慢旧请求有覆盖新选择的风险。
- 提交没有统一 busy/pending 防重复，消息每次临时生成新的 clientMessageId，不能在结果未知时沿用同一次提交身份。成功回调直接清空 draft，可能清掉等待期间新输入。
- 群消息 draft 是组件单一 state，不按群分区；选中群与策略也缺完整恢复合同。
- SSE 的 error 处理主动 close，没有该视图的重连或轮询恢复；管理组件注释所称“polling fallback”与实际实现不一致。

来源：[LongAgentGroupChatView](../../../frontend/components/LongAgentGroupChatView.tsx) 第 94/117/124/186 行；[LongAgentConversationsPanel](../../../frontend/components/LongAgentConversationsPanel.tsx) 第 81/105/111/184 行。应共享稳定提交身份、按群草稿、目标隔离和连接恢复；后端仍是执行事实源。

### 步骤 3：进入主题 → 节点聊天 → 会话记忆

健康度：聊天复用已成立，辅助交互未收口。新证据 `03-topics-desktop.png`、`27-topic-contrast.png`。

**I03：同一会话记忆出现两个入口（#5/#13）。** 节点顶栏一个文字按钮，公共 ChatWindow 底部又有笔记图标；节点辅助详情另保留 ON/OFF。虽然读取同一记录，入口布局和开关位置不同，用户难以判断是不是两类记忆。复用共享会话记忆入口；节点来源、锚点和补充整合仍在节点详情。

来源：[LongAgentTopicsPanel](../../../frontend/components/LongAgentTopicsPanel.tsx) 第 289–318 行与 [ChatWindow](../../../frontend/components/ChatWindow.tsx) 第 347/442 行。主工作区、管理标签均受影响。

### 步骤 4：Friend 管理 → 任务/职责/交付物/活动

健康度：配置可读，但身份、执行与管理混在一个横向标签串。证据 `07-friend-settings.png` 至 `14-agent-group.png`。

**I04：范围和管理层级不清楚（#6/#7）。** 运行策略、任务、职责、交付物、活动、群聊、主题、Agent Group、Agent Memory 共 9 标签并列。923px 窗口只能看到前一段，需要横向发现后面标签。运行策略表单的 Default Project 当前值是内部 Nexus Home，名称又与用户本轮协作 Project 接近。应先区分身份与能力、工作与产物、资源与诊断；内部 Home 不能用与协作项目相同的产品词暗示可替换关系。

全局设置中，Friend 无协作项目时 5 类项目资源禁用，标题却显示 workspace，当前页也无法直接选项目。设置类别部分硬编码中文；`settingsVisible` 是局部 state，URL 仍保留之前 view，刷新不是返回当前设置位置。建议明确资源范围并提供选择入口，设置类别采用一致导航/恢复模式。来源：[WorkspaceSettings](../../../frontend/components/WorkspaceSettings.tsx) 与 [AppShell](../../../frontend/components/AppShell.tsx) 第 1578/1590/2278 行。

**F02：不可确认与真实空列表同时出现（#8/#9）。** 任务、职责页面收到 projectionError 时，仍按长度为 0 显示“暂无任务/职责，创建一个”。错误本身来自隔离环境不接 NanoClaw；缺陷是页面让未知/尚未迁移看起来像确实没有数据。用户可能据此重建任务。应优先显示无法确认和恢复动作，只有后端确认完整空集才展示创建引导。来源：TasksSettings 第 213–221 行、DutiesSettings 第 242–245 行。Agent Memory 的“未知，不表示已删除”可作为现成恢复模式。

**I05：交付物围绕实现而非用户成果组织（#10）。** 首屏突出 3+1 slots、冻结/提交/通知之间的实现区别。空态让用户去 Tasks 配置，却没有跳转。改以“要产出什么、进行到哪、在哪里看、失败如何恢复”为主，技术状态保留在详情。尚未核实的产物不得标完成。

**F03：活动数量未呈现，范围说明不足（#11）。** `activityTurns` 调用传入 turns/sessions，但中英文翻译都只有“轮次/Turns”，实机看不到数量。这是数据呈现遗漏。选中 Nexus 的活动下同时列出其他 Friend 动态；API 的全部可见语义有既有合同，因此不认定数据返回错误，但需要标“所有 Friend 动态”或移到全局动态。来源：[LongAgentActivitySettings](../../../frontend/components/LongAgentActivitySettings.tsx) 第 70/78–100 行、`lib/i18n/messages/{zh-CN,en}.ts` 第 1307 行。

## 6. 推荐整改顺序与验收

| 顺序 | 交付范围 | 必须证明的结果 |
|---|---|---|
| 1. 功能与状态 | 群目标隔离、草稿、接受/重试/断线；任务和职责错误/空态；活动数据 | 快切不会错群；连点不会多启动；连接错误不假装空；统计显示真实数量 |
| 2. 交互与对象 | 群聊/管理分工，公共与成员历史，主题记忆单入口，任务名称，资源范围与生效时点 | 用户清楚“我在哪、点后发生什么、何时生效、从哪里返回”；不新增执行旁路 |
| 3. 视觉与适配 | 按既有 Token 统一按钮/状态/文字；桌面、Medium、Compact 主任务布局 | 群聊窄屏保留可用消息区；触控主要目标 44px；有效小字 4.5:1；工具栏完整可见 |
| 4. 剩余验证 | 4 个源码初审区域及在线/编辑/失败状态，真实 PWA/键盘/缩放 | 记录覆盖矩阵及证据，不能把“未发现”改称“通过” |

群聊建议交互：进入群 → 中央公开消息；标题显示成员摘要与一个历史入口；输入旁明确响应对象/策略。群管理打开同一群的成员与策略详情；成员参与历史归成员详情/历史范围选择。底层群公开 Session 与参与 Session 的隔离和授权保持原合同；具体发送行为是否合并需先写场景与验收例，再实施。

文档归属保持三层：Chat Web 负责对象和导航；模块合同负责归属、接受、执行与恢复；Frontend UI/UX 负责布局、组件、颜色和验收。每个功能变更应同步这三层相关部分，不再增加一份与它们竞争的“总设计文档”。
