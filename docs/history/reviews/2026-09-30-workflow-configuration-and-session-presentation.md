## 1. Memory 文件存在，但链接选错了资源域

用户点击的 `outreach/cadence.md` 是该 Long Agent 的 Markdown Agent Memory，标题为“主动触达的频次与去重规则”。cadence 表示频次/节奏，不是系统要求的特殊文件名，也不是项目源码。通过 Agent Memory HTTP API 读取成功，浏览器按普通文件链接打开则显示 `Not found`。

根因链：

1. `frontend/lib/tool-names.ts` 将 `_write` 后缀统一识别为文件写入，因此包含 `agent_memory_write`。
2. `frontend/lib/turn-written-files.ts` 取工具参数中的 `path`，按当前执行目录解析为本地绝对路径。
3. `ChatWindow` 将结果放入文件变更列表，进入项目文件查看器；它没有按 Long Agent 的 Memory 所有者和相对路径读取资源。

修改方向：工具回执投影为带资源类型、所有者、资源路径及可用 revision 的引用。项目文件进入文件查看器；Agent Memory 进入现有 Memory 服务和查看器。必须验证成功回执、授权及路径边界，不靠工具名后缀猜资源域，不复制 Memory 到项目目录来迁就错误链接。

同类排查覆盖 Agent Memory、Personal/Project Memory、会话记忆和日总结引用；这些领域不能仅因参数都叫 `path` 就共用项目文件路径解析。

## 2. 每日默认不是每日唯一

已确认方向见[会话方案](./2026-09-30-default-and-additional-friend-sessions.md)。一个 Agent/日期只有一个默认入口引用，但同一 Agent 可以有多个独立直接会话。

新建、刷新恢复、继续旧会话、任务回传、日归档和每日总结必须一起遵守该对象关系；不能只添加按钮。原有每日 Session 保留 ID 和历史，额外会话不替换默认引用，也不自动复制其他会话正文。

## 3. Direct execution 的实际设计

前端“Direct execution”对应内置 Workflow `minimal-pi-coding-agent`，不是绕过 Workflow 的模式。

| 职责 | 代码 |
| --- | --- |
| 声明 `execute`、`remember` 两个 Agent 节点 | `src/workflows/minimal-pi-coding-agent/workflow.json` |
| 先执行工作节点，再等待会话记忆节点 | `src/workflows/minimal-pi-coding-agent/workflow.ts` |
| 工作节点的普通 Session / Long Agent 分支 | `src/workflows/minimal-pi-coding-agent/step.ts` |
| Long Agent 接受记录与工作阶段执行 | `src/workflows/long-agent-context.ts` |
| 会话记忆尾节点准入、等待与主结果返回 | `src/workflows/session-memory/tail.ts`、`tail-policy.ts` |
| 会话记忆 Agent 定义和上下文 | `src/workflows/session-memory/agents/writer/`、`writer-run.ts` |

`runSessionMemoryTail` 等待记忆阶段后返回原工作节点结果。记忆节点不应替代主答复；它不是每日总结任务。未启用或不满足尾节点运行条件时，不能伪造一个已执行节点。

## 4. 共用 Workflow 外层，不代表配置已经统一

当前 `runPiCodingAgentPromptStep` 发现 `acceptedLongAgentTurn` 就调用 `executeLongAgentWorkflowStep` 并提前返回。它没有继续执行普通 Session 的 `prepareChatWorkflowTurnConfiguration` 路径，而是沿用接受时冻结的 Long Agent 定义执行。Friend 设置中因此仍有独立模型/Thinking 编辑。上一轮把“走同一 Workflow”当作配置统一，漏掉了这一分支。

用户要求的统一方向：

- Workflow 各 Agent 节点使用同一配置 Schema、Resolver、继承规则、冻结机制、检查接口及前端编辑器。不同入口不另设一套模型选择语义。
- Long Agent 仍保留长期身份、Standing Instructions、Memory 归属、任务/日程、Channel 绑定和能力授权。执行节点获得其所需身份与资源上下文；维护节点按职责获得必要上下文。
- 若需要 Agent Home 范围的默认执行配置，应采用同一 Workflow 配置机制明确作用域，不继续保留并行的 Long Agent 模型字段作为独立事实源。
- 模型目录中的图片能力、token 限额、provider/API 参数属于共享模型定义；Workflow 节点选择模型和运行参数。两者的修改影响范围必须在界面上清楚表达。
- Web、IM、定时任务和后台工作均核对相同生产装配路径；不能只让 Web 表单看起来统一。
- 迁移已有模型和 Thinking 设置时展示原值、目标作用域与生效来源，保持历史已冻结轮次可还原；发生冲突不得静默覆盖。

此变更涉及配置事实源，实施前必须同步核对 `docs/configuration/README.md`、公共装配与 Context 合同、Long Agent 架构/工程基线及前端配置合同。不能只删除 Friend 模型控件，也不能把长期身份与 Memory 一并删除。

## 6. Completed 展开缺少节点，不是用户不会看

后端和前端各有一处缺口：

- `src/session-read-model.ts` 的 `nativeMessageForFrontend` 给消息加上 `chatLongAgent` 后提前返回，未继续附加 `chatWorkflow`。长期身份元数据和 Workflow 阶段元数据本应共存。
- `frontend/components/ChatWindow.tsx` 将过程按消息平铺，对会话记忆 Agent 做局部标签处理，没有完整表达当前 Workflow 的节点结构和各节点结果。

原生 Session 中已有 Workflow 阶段标记，不能把投影遗漏说成“后台没有执行节点”。此前还核实记忆节点没有调用工具却生成近似主回复，说明其上下文与职责也要收紧，不能仅改显示名称。

目标交互：

```text
直接执行 · 完成
  执行 · 完成                  → 主回复位于聊天正文
    模型、实际运行耗时、工具与过程
  会话记忆 · 完成 / 无需更新 / 跳过 / 失败
    有实际写入时展示新增/修订及可核验回执
```

图示是目标行为，不是本轮实际运行结果。节点按 Workflow 定义、调用 ID、阶段事实组织，不能硬编码全产品只有两个节点。记忆阶段无工具回执时，不得声称该阶段完成了写入。模型响应、工具执行与事件收尾耗时分开，等待不能被全部命名为 Thinking。主回复出现后可显示“正在维护会话记忆”；整体完成/失败和提示音以 Workflow 生命周期为准。

## 7. Full history 仍承担整份 HTML 导出成本

本轮实际观测：

| 请求 | 实际 HTTP 耗时 | 响应体 | 缓存 |
| --- | ---: | ---: | --- |
| 前一日会话首次测量 | 2.771 秒 | 753,393 bytes | 未命中；CLI 导出约 2.671 秒 |
| 当前会话第一次测量 | 0.070 秒 | 861,505 bytes | 命中 |
| 当前会话第二次测量 | 0.037 秒 | 861,505 bytes | 命中 |

浏览器本轮能打开当前会话完整历史，没有复现持续停留在 Loading。上述是少量请求观测，不是 p95、浏览器首屏时间或大历史容量结论。

现有路径：`FullHistoryDialog` 请求 export API → `exportChatSessionHtml` 缓存未命中时启动 Pi CLI `--export` → 加工整份 HTML → 浏览器 iframe `srcDoc` 解析渲染。缓存上限为 8 项，文件变化会产生新 key；暖缓存快不能证明冷加载问题已解决。缓存命中时仍返回旧生成 timings，因此 Server-Timing 的旧 `total` 不能当作本次真实耗时。

建议分层处理：

- 浏览历史优先复用原生 Session 读模型，分批加载条目，按需展开工具、Thinking 和分支。必须保留 Pi 的分支/压缩事实，不能新建第二套历史存储。
- HTML 导出保留为导出动作。若保留原生 HTML 浏览方案，则先核实可用的 Pi 公共导出接口或隔离 worker，避免每次冷加载引入不必要的完整 CLI 启动；并处理同一 revision 的并发重复生成。
- 区分本次请求耗时、缓存生成耗时、传输和 iframe 可见时间；保持取消、超时、重试及 Session 切换隔离。
- 覆盖新旧 revision、大小会话、冷/暖缓存、并发打开、失败重试和关闭后取消。必须以浏览器首次可读内容验证，不能只测缓存 API。

## 8. 后续实施顺序与验证

1. 固定已确认的产品关系：默认与额外 Session、统一 Workflow 配置、主回复与记忆节点职责。落定配置迁移和各入口冻结时点。
2. 修复资源链接和消息阶段投影；实现通用节点展示及职责匹配的记忆上下文，同时验证普通项目、Long Agent、委派和活动消息。
3. 把历史浏览与导出成本分开，记录性能基线并验证冷加载。
4. 依据统一后的对象关系完成关键页面视觉稿与真实页面验收，再推广配置页面。

最低回归门槛：

- Memory 写入回执可打开正确所有者的资源；同名项目文件不会串用，越权路径拒绝，失败写入不生成成功产物。
- 同一条消息可以同时携带 Long Agent 身份和 Workflow 阶段，刷新/完整历史/实时事件的归属一致。
- 两节点正常执行、记忆无需更新、关闭记忆、失败/取消均有真实状态；聊天主回复不被维护产物替换，也不将维护产物重复当作业务答复。
- 不同入口相同配置范围解析结果一致，检查与生产执行一致；历史冻结值不被新配置改写。
- 每日默认与额外会话方案中的创建、恢复、归档和工作回传验收仍需完成。
- 历史验证覆盖冷/暖缓存和浏览器可读时间；视觉验证覆盖关键页面完整状态而非局部控件。

实现代码后运行 `pnpm verify`、父仓库和 Frontend 的 `git diff --check`；Workflow/装配改动另执行仓库要求的 Builder、Nitro Step、生产构建及 `pnpm test:dev` 真实 Runtime 门禁。本轮仅修改审核文档，不将已有测试成绩冒充这些改动已通过。
