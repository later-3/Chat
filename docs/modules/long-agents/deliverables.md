# Friend 产物闭环：笔记与动态（LA4）

LA4 把"模型生成了内容"变成"可查、可核、可恢复的产物"：站内动态（3 个时段）与自身 Workspace 笔记（每晚 1 篇）。调度与执行完全复用 LA2 任务/触发与 LA1 独立工作 Session；本文件只定义**产物身份、提交、验证与状态**的合同。机制边界见[机制合同 §9.3–9.5](./chat-long-agent-mechanism-contract.md)。日终交接、Memory、职责进度、笔记、动态各自保留原有职责，不能互相冒充。

## 1. 配置：产物任务

产物通过**已有任务**声明，不新增调度器：`FriendTask` 增加可选 `deliverable`：

| 字段 | 说明 |
|---|---|
| `kind` | `post`（站内动态）或 `note`（Workspace 笔记） |
| `slot` | 时段/槽位标识（小写字母、数字、连字符，1–40 字符），例如 `morning`、`noon`、`evening`、`night-note`。同一天不同槽位各自独立，日期只作展示/筛选 |
| `audience` | 仅 `post`：`friends`（全部长期同事，默认）或 `self`（只在自己的记录中可见）。**受众来自用户配置的任务修订**，执行中的模型与 Tool 不能改宽 |

用户显式配置 Friend、时区、具体时刻、职责或材料来源、受众与允许范围；程序不写死"小思/道德经"，也不默认启用任何正式任务。任务页与职责页的 3+1 只是这类任务的展示视图。

## 2. 产物身份与幂等

产物身份由服务端从执行上下文推导，模型不能伪造：

```
artifactKey = hash(taskId, occurrenceId, kind, slot, target)
artifactId  = art-<hash(longAgentId, artifactKey) 前 32 位>
```

- 同一次发生（occurrence）重试、崩溃重放、重复提交命中同一 `artifactId`：**不新建帖子、不写第二篇笔记**。
- 同一任务的 `morning` 与 `noon` 是不同 occurrence、不同 key；同一日期多条自主动态不会被按日期合并（`date` 只是索引维度）。
- 非产物任务、普通后台工作、职责推进（未配置 `deliverable`）都不能提交产物。

## 3. 内容冻结与提交

提交分两步且顺序固定：**先把生成内容耐久写入产物记录（`pending` + `contentHash` + 内容）**，再执行副作用（写文件或发布动态），然后按身份校验副作用并转 `committed`。

- 笔记：服务端在授权根（该 Friend 的 agent home 项目）内**只写不可变版本文件**（写后按内容哈希校验）；工作区里用户可见的文件只在**不存在**时创建一次，此后**永不覆盖**。普通文件内容**不等于**"夜间笔记已完成"，只有产物记录 `committed` 才是完成。
- **笔记存储模型（不可变版本 + 受保护指针，方案 B）**：
  1. **版本文件**：`<笔记目录>/.chat-notes/<名字>-<路径哈希>/versions/r<版本>-<内容哈希前 8 位>.md`，用 `link` 原子创建（create-if-absent），**从不 rename 覆盖**；同名路径若已有不同内容，改用新的不冲突路径。每次提交都回读校验版本文件内容哈希。
  2. **当前指针**：`<同一目录>/current.json`，机器管理且**可重建**；权威副本是 Chat Home 中的产物记录（工作区之外，Agent 不可写）。指针被删除或被篡改时由记录重建；指针自身从不承载唯一内容副本。
  3. **用户可见笔记文件**：仅在缺失时以 `link` 创建一次（并发创建不会被覆盖）。服务端此后**只读分类**，不再改写它：
     - 内容等于当前版本 → `clean`；
     - 内容等于我们为该路径产出的任一版本（本记录或同路径其它记录的历史版本）→ `older`（界面提示"工作区文件是较早版本，不会自动覆盖"）；
     - 内容不匹配任何我们产出的版本（人工修改）→ `edited`：外部内容被**另存为独立不可变版本**（`user/r<版本>-<哈希>-user.md`）并记录为冲突，**不改动用户文件**；
     - 文件缺失 → `missing`（界面提示，可由用户导出恢复）。
  4. **冲突处理**：界面同时展示"生成版本"与"我的修改"，提供两个显式选择：**以我的修改为准**（把已保留的外部内容登记为新的 `user` 版本；工作区文件本来就是它，因此不需要任何写入）或**以生成版本为准**（记录决定，双方内容继续保留）。两种选择都不覆盖文件。
  5. **导出**：`export` 把当前版本写到**新文件**（默认 `notes/<名字>.v<版本>.md`，必要时自动加后缀）；已存在的文件永不替换。
- **归属与串行化**（笔记）：同一规范化路径由一把路径锁串行化，归属检查、版本写入、指针更新与回读校验都在锁内；同一路径由**创建时间（同刻按 id）最新**的记录拥有，旧记录只保留历史，不得推进指针或写新版本。
- **派生存储路径同样受授权约束**：`.chat-notes`、`versions`、`user` 与指针文件都由笔记路径派生，任何写入（首次提交、维护重建、冲突保存、导出）之前都必须先用 `canonicalToolPath` + `assertFileWithin` 校验，并确认规范化结果与预期路径一致；预先存在的符号链接（例如把 `notes/.chat-notes` 指向工作区外）一律拒绝，且在任何目录/文件创建之前就拒绝。原子 create-if-absent 只保证"不替换目标"，不代替"目标在授权范围内"。
- **已完成记录的刷新也是写操作**：维护循环对已提交笔记的刷新（重建版本文件、修复指针、重判工作区状态）必须与提交/修订/冲突处理共用同一套协调——在同一记录锁内用 **`(revision, contentHash, versionFile)` 作为期望值**做 CAS，并再次确认本记录仍是该路径的最新所有者；快照过期的刷新**不得**改动当前指针或 `note` 元数据（一次 stale 刷新只能什么都不改）。
- **冲突决定绑定冲突身份**：`conflictResolution` 只对某一具体冲突（来源 + 内容哈希）有效；冲突来源或内容变化、冲突消失时自动清除，界面重新给出"保留我的修改 / 保留生成版本"两个选择。冲突处理同样按 `(revision, contentHash, conflictHash)` 校验期望值，冲突已变化时拒绝并提示重新读取。
- **写入不变式（笔记）**：服务端对工作区**没有任何"覆盖已存在文件"的动作**——所有创建都是原子 create-if-absent。因此不存在"检查与写入之间的窗口"：外部修改要么被检测并保留为独立版本，要么因目标被占用而改用新路径；任何一方的既有内容都不会被静默覆盖或丢失。
- **回执按版本 CAS**：`settle` 必须携带 `(revision, contentHash)`；若期间记录已被修订（版本已变），回执被跳过，**旧的校验结果不能把更新的版本标记为完成**。
- **并发写入者串行化**：同一产物身份的提交/补交/维护重试在同一把产物锁内串行执行；后到的写入者等待在途写入完成后继续，不会死锁也不会重复发布。
- 动态：发布时把 `artifactKey` 与受众写入帖子行，发布后回读 feed 校验该 key 存在；`postId` 仍是独立身份。
- 长度合同：动态正文上限 4000 字符、笔记 60000 字符，**冻结前拒绝超限**（发布服务不截断）；提交后按身份与**正文**双重校验（回读正文必须与冻结内容完全一致）。
- 同键异内容：拒绝（409），不静默覆盖。笔记的显式修订用 `revise`（同一路径、新版本、旧版本保留在产物修订记录中）；动态不做同 occurrence 覆盖——需要新内容时走"重新生成内容"（新的 occurrence → 新 key → 新帖子）。
- "重新生成内容"对笔记产生新的产物记录与新的不可变版本；旧记录及其版本文件都保留，**工作区文件不变**（界面按记录与版本区分）。

## 4. 目标归属、授权复核与阻塞状态

副作用执行前按顺序检查，任一不满足就记为 **不可重试的阻塞失败**（`retryable: false`，历史与冻结内容保留，界面只提供"重新生成/修改"，不提供"补交"）：

1. **路径授权**（笔记）：先用 `canonicalToolPath` 规范化真实路径（缺失路径经最近存在的祖先解析，不跟随失效符号链接），再用 `assertFileWithin` 校验仍在工作区内；**任何目录创建与临时文件都在校验之后**。符号链接父目录、链接到外部、越界都不会先写后查；导出路径同样校验。
2. **路径归属**（笔记）：同一路径由**创建时间（同刻按 id）最新**的产物记录拥有。旧记录不得推进指针或写新版本（记不可重试阻塞、保留历史）；由于服务端从不覆盖工作区文件，归属规则只决定"谁有权更新当前版本"，不再需要"已知内容才允许替换"的判断。
3. **当前授权**：读取任务当前修订——任务不存在或已取消、产物配置（kind/slot）变更、动态**受众被收窄**、关联职责已结束或目标代号已修订，都不得按旧授权发布；保留历史并提示重新生成。
4. **副作用串行化**：同一产物身份的提交/补交/维护重试在同一把产物锁内完成"查重 → 副作用 → 落状态"，Social 发布的按 `artifactKey` 查重与追加也是原子的；并发补交只产生一条帖子。仍无法确认的副作用显示 `pending`，不承诺 exactly-once。
5. **不做写后补偿**：早前版本曾在写入后用"恢复更新版本内容"补偿迟到写入，该补偿自身会在三次写入交错时回滚更新的版本（第三轮复核 P1）。方案 B 下这类补偿已无存在必要——按路径串行化 + 锁内归属检查 + 永不覆盖，使旧记录既无法倒灌也无法改坏工作区文件。跨产物同路径写入与恢复动作服从同一条规则。
6. **发布前的最后一道授权门**（动态）：受众收窄、任务取消、职责结束或目标修订的复核在**取得 Social 追加锁之后、真正追加之前**再执行一次；期间完成的撤权仍会阻止追加。检查与追加之间的毫秒级窗口同理如实说明，不以"已检查"代替原子性声明。

## 5. 恢复与未知结果

- 副作用已发生但回执未落盘：按稳定身份回读（feed 里是否已有该 `artifactKey` 的帖子；文件是否已是指定内容）→ 补记回执，**不重新调用模型**。回读动态时必须同时比对**正文**：key 存在但正文不一致（例如被截断）记为不可重试阻塞，绝不因为 key 命中就标记完成。
- 恢复笔记时在**路径锁内**先做归属检查（存在更新记录即阻塞，不写入），再走同一套不可变提交：版本文件按哈希校验（被人为改动或删除时，外部内容另存为独立版本，我们的内容写到新的不可变路径，并重建指针）；工作区分歧按只读分类保留双方。不存在"写后补偿更新版本"，也不存在任何覆盖动作。
- 内容已冻结但副作用未确认：维护循环按冻结内容重试提交（有界），失败原因写入产物；重试不改变内容。
- 无法确认真实副作用时显示 `pending`（待核查），不承诺无法保证的 exactly-once。
- 同一发生并发提交由产物存储的文件锁串行化，第二个请求命中同一 `artifactId`。

## 6. 真实完成状态

四个状态分开，界面从各自事实源投影：

| 事实 | 来源 | 不代表 |
|---|---|---|
| 模型完成 | LA1 work/turn 终态 | 内容已保存 |
| 内容已冻结 | 产物记录 `pending` | 已写文件/已发布 |
| 笔记已落盘 | 产物 `committed` + 文件存在且哈希一致 | 用户已读 |
| 动态已发布 | 产物 `committed` + feed 可读回该 `postId`/`artifactKey` | 通知已送达 |
| 通知已发出 | 返回收据（LA1）或补发记录 | 产物状态改变 |

通知失败不把产物改成生成失败，也不再次生成内容。

## 7. 来源与隐私

- 产物记录关联 `taskId`、`occurrenceId`、`workId`；由职责推进产生时额外关联 `dutyId`、`goalRevision` 与所用进度条目 `progressEntryId`。**LA3 未应用/未核验的历史不能自动作为已学事实**：只有 `applied` 且当前目标代号的进度条目可被引用为来源。
- 发布前校验受众：`audience` 取自冻结的任务定义；`self` 帖子不进入其他 Friend 的可见 feed，并且**读取、评论与返回正文之前**都做对象级校验——不可见的对象不返回正文也不允许评论。Friend 通过 `social_manage` 读取时，视图身份由服务端执行上下文传入，模型不能自填。
- 私有日终交接、Memory、群内私有 Session 不自动复制成公开内容；模型选择文本与格式，权限判断留在服务端。

## 8. 时间与取消

沿用 Task 的 IANA 时区与既有 `missed`/`overlap` 策略：过期社交内容默认**不自动补发**（`skip`），用户可显式补跑；暂停阻止后续运行但已接受执行照常完成；停止单次不删除已有产物；目标/授权改变后的迟到结果保留历史，不能用旧授权发布。有限重试与明确等待/失败原因，不无限堆积。

## 9. 升级兼容

- 旧帖子/评论/任务继续可读：缺少 `artifactKey`/`audience` 的旧帖子按"未关联产物、`friends` 可见"读取，**不推断**其曾经被发布或已授权。
- 产物存储 `artifacts.json` 使用 `schemaVersion 1` + 迁移标记；读不到即空，不读 Nano 数据库，不产生第二份可写任务定义。
- 缺失来源的产物显示为"来源未记录"，不编造关联。

## 10. 入口

| 层 | 入口 |
|---|---|
| 配置 | 任务（kind/slot/audience）沿用 `task_manage` 与任务页；职责推进的产物来源来自职责配置 |
| Agent | `artifact_manage`（`list`/`submit`/`resubmit`/`notify`）；`social_manage` 保留人工浏览与评论 |
| API | `GET/POST /api/long-agents/:id/artifacts`，`schemaVersion 1` |
| Web | Friend 设置"交付"页：3+1 配置视图、按日期状态、产物链接、补交/重新生成/补发通知；动态出现在现有 feed |
