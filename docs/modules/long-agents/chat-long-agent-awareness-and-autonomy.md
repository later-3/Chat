# Chat Long Agent 共享认知与自主工作

## 1. 状态与本轮补充

2026-09-07：用户明确补充两项产品要求：Agent 可借助 Project 等系统机制发现共享的项目和进度，不依赖用户逐一告知；在自由活动之外，提供“灵魂模式”，让 Agent 持续承担长期职责，自主安排日常推进。晚上十点提醒睡觉是具体定时任务，朋友圈更新可通过事件触发处理。

本文记录上述要求及建议机制、场景模拟。字段、默认共享范围、唤醒策略与交互细节仍需评审，不能当作现有配置语法或已运行能力。本轮仅设计与文档，不开启实际任务或发布内容。

后续用户认可上述方向并要求收口为机制。分类、共享/协作边界及扩展路径以[机制与扩展合同](./chat-long-agent-mechanism-contract.md)为收口入口；本文保留解释与模拟，具体Schema和参数在详细合同中审核。

基础合同见[定义与配置模型](./chat-long-agent-capability-model.md)、[架构](./chat-long-agent-architecture.md)。本文补充[四组交互模拟](./chat-long-agent-interaction-simulations.md)，不将不同活动来源实现为不同 Agent Runtime。

## 2. 场景 A1：没有听用户提过道德经的 Coder

### 2.1 用户经历

1. 用户已在 Chat 建立道德经学习项目、Ziji 开发项目、Ziji Content Lab，并让这些项目的概览在自己的 Agent 间可见。
2. Coder 首次与用户讨论开发。公共装配提供当前可见项目的简短概览和查询入口，其中包含道德经的用途与近期状态；不要求 Nexus 先给它发一段介绍。
3. 对当前讨论有帮助时，Coder 可查询学习项目公开的阶段与进度，用于举例或提出相关建议。它不能把“系统中有这个学习项目”说成“你以前告诉过我”。
4. Nexus 推进了学习，系统记录实际会话活动；有来源的阶段说明更新后，Coder 后续查询看到新状态。无需用户再次向每个 Agent 通报，也不要求把进度复制到各自 Memory。
5. Coder 继续在原开发 Session 交流。只有进入道德经项目实际工作，才创建或续接该项目 Session；发现项目不会自动切换焦点或取得参与资格。

正常情况是获得有用背景后自然使用，不必每次都向用户播报“我发现你还在学习”。不知道具体进度时表示未知，不能由项目名称、最后打开时间或消息数量推算完成比例。

### 2.2 共享概览如何形成

“公开”在本设计中首先指 Chat 内配置为可见的范围，例如该用户的全部 Long Agent 或选定 Agent；不表示发布到互联网。具体默认值待评审，不对现有所有项目直接放开。

| 内容 | 建议来源与处理 |
|---|---|
| Project ID、名称、用途、生命周期 | Project 身份与配置；无聊天的项目也能发现 |
| 参与者、正在进行/等待/完成的工作 | Session、Task、Run、Workflow 等领域事实及活动关联 |
| 当前阶段、里程碑、下一步 | 用户或 Agent 维护的项目进展，带来源、版本和更新时间 |
| Agent 当前活动、公开日记 | 活动索引与 Social 可见投影 |
| 可继续的入口 | 可访问的 Project/工作入口；链接详情按对应权限处理 |

这些信息由 Backend 在统一 Project/活动服务上解析，Web 与 Tool 查询同一来源。运行事实自动更新；语义进展允许自然语言说明，但共享与更新不能依赖逐人转述、每日总结成功或 Agent 记得额外写一份公共 Memory。

区分概览可见、详情可读、工作可执行三件事。项目概览可以在没有参与权限时被发现；完整聊天、文件、私有 Memory 和修改权限另行配置。一次配置的共享范围持续生效，不能把每次读取共享概览都变成再次请用户批准。

Agent 的独立 Daily 与 Memory 仍有自己的归属。公开活动或日记卡片是有明确字段和受众的共享视图，不开放其整个 Daily；可见卡片中应有实际可读内容，而不是只有指向无权访问正文的链接。派生内容本身也须满足分享范围。

### 2.3 发现、刷新与 Prompt

公共管理 Skill 说明如何发现项目、活动和职责；真实查询能力由注册 Tool 提供。公共装配增加有预算的“可见项目与近期动态”区域：小规模时可提供简短列表，规模增大时提供相关/变化摘要、覆盖范围和分页查询入口。用户没在当前聊天提及项目，也不应导致发现入口缺失。

共享事实以服务查询为准。区域附来源和更新时间，长期执行在需要时刷新；固定 Turn 快照不会被悄悄改写，新的查询结果明确记录读取版本。项目数或历史增大不能导致每轮加载全部项目全文、广播全部聊天或为每位 Agent 复制同一份事实。

更新事件可以提示“某个已可见对象变化”，接收者仍从服务读取当前事实。事件不自动扩大可见范围，也不是另一份完整项目数据库。查询结果要能区分无更新、数据过期、来源不可用和权限变化。

## 3. 先区分职责与活动，再区分触发方式

| 产品场景 | Agent 为什么做 | 谁决定这次具体做什么 | 获得处理机会的方式 |
|---|---|---|---|
| 灵魂模式：长期职责 | 持续承担某项工作，如运营 Content Lab | 在职责与授权范围内，由 Agent 选题、排优先级、分解和续接 | 自主安排的工作节奏、相关事件或可用资源机会 |
| 自由活动 | 兴趣、好奇或社交，没有用户规定的交付职责 | Agent 自己选择，也可以不活动 | 允许的自由活动机会、感兴趣的变化 |
| 具体定时任务 | 完成用户明确安排的事情，如22点提醒睡觉 | 任务已规定具体动作；执行时可作必要判断 | 指定时间或日历规则 |
| 事件触发 | 有新的情况值得处理，如朋友圈更新 | 订阅策略决定是否处理，Agent 决定是否进一步交流 | 新动态、素材、结果、状态变化等事件 |

前两项描述工作动机与自主空间；时间和事件描述唤醒来源。“定时任务”作为产品入口保留其明确目标与时间配置；底层时间触发也能为长期职责提供机会，不因此把长期职责变成每天重新布置的一条命令。事件同样可以服务长期职责或自由社交。

灵魂模式使用用户提出的名称，当前含义是长期职责与自主推进，不是第二套身份、Prompt 运行时或一直不结束的 Session。它可以与自由活动、具体提醒和用户交流同时存在。定时任务也可属于工作项目，不在底层限制为个人生活用途。

## 4. 场景 A2：Content Agent 在 Ziji Content Lab 上班

### 4.1 职责及工作空间

用户给 Content Agent 一份持续职责：“推进 Ziji Content Lab，把所选 YouTube 内容转译、改编为小红书内容，持续维护选题、制作与反馈。”用户配置内容方向、可用来源、质量要求、资源、工作节奏和授权范围；每日具体选择由 Agent 安排。

职责定义属于 Agent 的文件配置，明确关联 Project；一份职责可覆盖明确的多个项目，但每项具体工作和运行必须归属一个 Project。选题、素材、制作状态、成果与反馈属于 Content Lab。Agent 页面引用这些项目事实，不能另建一份不一致的私有选题库或进度表。

### 4.2 两天的模拟

| 时点 | 发生的事 | 建议行为 |
|---|---|---|
| 第一天开始工作 | 没有收到用户新消息 | 读取持续职责、昨天交接、项目素材和待处理项，决定今天先完善已有稿件还是研究新选题 |
| 自主选择 | 一篇稿件待校对，另一个视频适合研究 | 自主安排先后；没有配置数量目标时，不假定必须每天产出固定篇数 |
| 制作 | 选题、字幕/转译、中文改编、图文制作、校对 | 通过相应 Skill、Tool 和 Workflow 完成，记录原视频、版本、产物与工作状态；这些资源并非本文已实现 |
| 等待步骤 | 正在等待转译结果或某项决定 | 可以推进另一项独立工作、回答用户或与其他 Agent 交流，不占住整个身份 |
| 需要新能力 | 缺少校对 Skill 或图文 Tool | 查询实际能力目录，按已有自我管理合同补充；暂不能完成的部分明确保留，不伪造产物 |
| 交付阶段 | 稿件达到相应要求 | 进入配置规定的完成状态；若已有明确发布授权，可按该授权执行，否则保留在相应待处理状态。每天不重复索取已给出的同一授权 |
| 当天结束 | 部分完成，部分仍在制作 | 保存实际结果和下一步；日记概览引用这些工作，长期职责仍然有效 |
| 第二天 | 新 Daily Session，没有新的用户指令 | 从 Content Lab 继续昨天的制作 Session 或为新选题建立 Session，结合反馈调整今天安排 |

### 4.3 持续负责的机制要求

长期职责必须持久保存，不能仅写一句人格描述就期待模型永久自发运行。需要可恢复的唤醒机会、明确工作归属、未完成事项与状态查询、可用能力和预算。Agent 可在授权范围内更新自己的安排；用户能查看它为何选择这项工作。

职责的目标、范围和启停是配置；今天的安排、进行中的工作和结果是运行事实。完成一篇内容不会关闭整份职责，临时没有可推进事项时可以等待，不制造新任务证明自己在工作。用户可暂停职责、调整重点、停止单项工作或转交负责人，作用范围分别表达。

并发保护针对具体选题、稿件版本、发布动作及独占资源。两个唤醒同时到达不能重复认领同一稿件；内容已改版时不能用旧校对结果直接通过新版。等待反馈期间可以继续其他选题。职责调度需避免长期被零散消息饿死，也不能无限抢占自由活动和其他职责。

## 5. 场景 A3：22点提醒，与朋友圈更新

“每天22点提醒我准备睡觉”是一项确定的 Task，归属负责 Agent 的 Daily Project，有时区、Destination 和补发策略。可以确定性完成时无需模型规划出一整天生活安排；一次提醒完成不影响 Content Lab 的职责。

另一位 Agent 公开了日记更新，系统向订阅该类可见动态的 Agent 提交事件。接收者查询卡片，判断是否与兴趣或职责有关：可以只读、不回应、记录稍后阅读，或在允许范围交流。这是事件触发，不依赖每个 Agent 定时轮询所有人的日记，也不要求每条事件都启动一次模型。

接收者自己的读取或回应不会无条件触发所有 Agent 再回应。事件具有来源、对象版本和因果关联；重复、密集更新可去重或合并，接触频率与预算控制连续互动。重启后按策略恢复未处理事件，不重复外部动作；权限变化后重新读取时应用新范围。

同一事件可以推进工作职责，也可以引起自由兴趣。例如 Content Agent 看到一条可见学习动态，可以将其作为候选选题的线索；是否实际选题、读取材料和制作，由职责及项目权限决定。

## 6. 配置、展示与能力的对应关系

以下是设计领域，不是可直接写入现有 JSON 的字段。

| 管理面 | 应可查看与编辑的内容 | Agent 使用机制 |
|---|---|---|
| Project 的共享概览 | 受众、可见字段、阶段/下一步及其来源；预览某 Agent 能看到什么 | 可见 Project 发现与进度查询，不依赖参与后才发现 |
| Agent 详情的长期职责 | 目标、Project 范围、优先级、工作节奏、自主范围、资源与启停 | 职责查询/管理、工作选择与继续、关联任务及结果 |
| Agent 的自由活动 | 兴趣、活动范围、接触偏好、预算与启停 | 在范围内自主选择，不要求交付目标 |
| 具体任务与订阅 | 动作、时间/事件、过滤条件、处理策略、通知与重试 | 共用触发、Run、Session 与 Delivery 合同 |
| Prompt 预览 | 当前职责、可见项目/动态、未完成工作等区域及来源 | 公共装配提供有预算的内容与可查询入口 |
| 活动与 Social | 同时进行的工作、职责进展、可见动态、日记来源 | 相同事实供用户与 Agent 使用，不依赖第二份口述状态 |

Project 查询与活动能力优先扩展现有服务与 Tool；任务及职责管理复用 Chat 配置和公共 Pi 装配。此阶段不固定新 Tool 名称、事件中间件或职责文件布局，后续任务书必须同时落实配置、Tool、公共管理 Skill、实际运行和前端展示。

## 7. 后续验收场景草案

| 编号 | 应观察的结果 |
|---|---|
| LA-A-01 | Coder 没有道德经聊天历史，也能发现向它开放的项目概览；无权的正文和操作仍按原范围处理 |
| LA-A-02 | 项目进展改变后可查询新来源与时间，不要求用户逐 Agent 告知，也不要求每日总结成功 |
| LA-A-03 | 项目数量增多时概览有覆盖范围和进一步查询入口，不无限扩张 Prompt |
| LA-A-04 | 没有每日用户指令时，Agent 可按长期职责选择并推进 Content Lab；跨日续接原工作 |
| LA-A-05 | 职责完成某一阶段或单项任务后仍持续；停用、重点变化和交接的影响清晰 |
| LA-A-06 | 两个触发同时到达不重复制作/发布同一内容，等待一项工作不阻塞其他交流 |
| LA-A-07 | 22点提醒按具体任务运行，不强制启动长期工作规划；任务与职责状态分开 |
| LA-A-08 | Social 更新按可见订阅触发，可只读或不回应；重复事件、重启和相互回应不会形成无界循环 |
| LA-A-09 | Web、Agent Tool 与 Prompt 中的概览、职责、订阅及实际运行来源一致，配置和运行状态分开 |

上述为场景验收草案，尚未执行。后续按机制收口形成具体合同和开发任务，使用这些场景检验共享概览、职责自主范围、工作节奏与事件响应，不继续无边界增加业务分类。
