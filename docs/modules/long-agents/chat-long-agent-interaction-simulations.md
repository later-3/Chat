# Chat Long Agent 交互场景收敛与模拟

## 1. 评审状态与边界

状态：2026-09-07 场景评审稿。用户已要求开展场景收敛与模拟；本文中的模拟结果是建议行为，不是实际运行记录，也不表示多 Agent 协议、会话拓扑或调度实现已经批准。

已确认基础见[定义与配置模型](./chat-long-agent-capability-model.md)、[架构](./chat-long-agent-architecture.md)和[基础场景验收](./chat-long-agent-scenarios.md)。本轮只做设计演练，不创建实际 Agent/定时任务、不发送消息、不操作业务项目。

讨论顺序固定为：具体经历 → 用户与 Agent 可观察行为 → 确认交互要求 → Session、消息、权限和运行机制。Workflow/Session 复用是底层参考，A2A 是否需要在场景收口后另行判断。

本轮用户进一步明确：项目信息与进度可以通过共享机制被发现；新增长期职责与自主推进的“灵魂模式”，并区分自由活动、具体定时任务和事件触发。新增 Coder、Content Lab 及 Social 事件演练见[共享认知与自主工作](./chat-long-agent-awareness-and-autonomy.md)。下文四组仍用于描述交互形态，不作为完整的活动动机或触发类型分类。

用户随后认可方向并要求机制收口。新增需求的分类、组合、扩展及交付以[机制与扩展合同](./chat-long-agent-mechanism-contract.md)为准。本文继续作为具体交互的验证材料，局部呈现和实现参数进入详细设计，不把所有演练步骤变为固定业务分支。

## 2. 收敛为四组主要场景

| 场景组 | 主要经历 | 参与者 | 结束方式 |
|---|---|---|---|
| M1 临时互助与用户加入 | 一位 Agent 请教另一位，用户可进一步交流 | 一个或多个 Agent，用户可在场或加入 | 问题解决、暂时搁置或自然结束 |
| M2 多方共同工作 | 共同讨论、形成决定、分工、审核与持续推进 | 用户与多个 Agent；可以中途加入或退出 | 工作达到约定结果，或明确暂停/结束 |
| M3 后台主动协作 | 任务或事件引发合作，用户稍后响应 | 一个或多个 Agent，用户可能不在线 | 本次检查/处理结束，长期任务可继续 |
| M4 自由活动与社交 | 没有外部交付目标，根据设定和兴趣活动 | 单 Agent、Agent 之间、Agent 与用户均可 | 自然结束、兴趣转移、预算/资源让出，不要求产出 |

这四组只是评审分组，不代表四套运行系统或互斥的 Agent 模式。同一个 Agent 可以同时参加多组活动。正式工作、自由活动、与用户交流不会因为身份相同而强制全局串行。

以下条件叠加到每组模拟：长期项目成员、私聊/共同讨论、共享项目和活动概览、跨 Channel、跨日、历史和 Memory、并发、资源冲突、用户介入、权限变化、失败恢复。它们不需要各自定义一种独立产品。

### 2.1 前期发散的覆盖关系

| 原场景 | 收敛后的覆盖位置 |
|---|---|
| A 临时请教 | M1 的请教、追问、用户加入 |
| B 用户与多个 Agent 共同讨论 | M2 的共同讨论与点名问答 |
| C 分工执行 | M2 的依赖、并行工作及冲突 |
| D 往返协作 | M1 的澄清、M2 的审核修复 |
| E 长期项目参与 | M2 的成员变动及跨日继续 |
| F 用户不在线时主动合作 | M3 的后台分析与待决策 |
| G 私下交流与共享讨论 | M1/M2/M3 的信息分享边界 |
| H 跨入口、跨天和交接 | M3 的通知回复、第7节共同收尾 |
| I 自由活动 | M4；无交付要求，有兴趣连续性，可并发 |

## 3. 模拟 M1：学道德经时请教，双方都可以继续交流

### 3.1 前提

用户正在道德经 Project 与 Nexus 讨论某一章；资料 Agent 在授权范围内可查阅参考材料。这里不预定两者必须进入同一会话还是独立会话，只描述用户经历。

### 3.2 正常与并发过程

| 时点 | 发生的事 | 建议的可观察行为 |
|---|---|---|
| T1 | 用户问：两个译法为什么不同？ | Nexus 可以回答已知部分，并向资料 Agent 请教具体分歧，携带必要引文与问题 |
| T2 | 资料 Agent 问 Nexus：比较哪个版本？ | 澄清回到发起问题的讨论；Nexus 可继续应答，不能因正在等待资料结果而无法接收追问 |
| T3，与 T2 重叠 | 用户又问 Nexus：先给我举个生活例子 | Nexus 能回应用户；请教继续存在，不要求用户等资料查询结束 |
| T4 | 资料 Agent 给出解释与来源 | Nexus 能将结果用于原问题，用户能看见来源和参与者；不把贡献伪装成 Nexus 独立查证 |
| T5 | 用户想直接追问资料 Agent | 提供明确的参与/交流入口；该 Agent 取得当前问题和获授权材料，不自动获得 Nexus 私人历史 |
| T6 | 用户说已经明白，继续读下一段 | 学习继续；临时请教可以结束，相关结果保留引用，不强制把来宾变成长期成员 |

### 3.3 分支

- 资料 Agent 暂时不可用：说明等待状态，用户可以继续学习、取消请教或选择其他可用帮助。
- 返回了旧问题的答案：保留它对应的问题，不能插入正在讨论的新段落而不说明来源。
- 两位 Agent 不断相互反问：保留仍缺少的信息，停止重复交流；需要用户补充时提出具体问题。
- 用户私下告诉 Nexus 一段生活经历：举例或请教时遵守分享范围，不能把私人经历原文默认发给资料 Agent。

### 3.4 本组待确认

临时请教的过程默认是否折叠展示；用户如何直接加入；被请教者加入时可获得哪些背景。建议提供简洁进度和可展开过程，用户明确进入交流即表达参与意图，背景分享仍按原授权处理。

## 4. 模拟 M2：你和几位 Agent 共同推进 Ziji

### 4.1 前提

用户在 Ziji PlantOS 提出一个假设的养护提醒功能，邀请架构、开发、审核 Agent。没有预设必须由 Nexus 主持。模拟中的实现、修复和自动审核均以用户在场景中已经授权为前提，不代表本轮实际执行。

### 4.2 讨论、分工与并发

| 时点 | 发生的事 | 建议的可观察行为 |
|---|---|---|
| T1 | 用户向参与者说明目标 | 相关参与者可以提出问题或观点，身份清楚；没有新增信息时可以不发言，不必人人轮流复述 |
| T2 | 用户点名问开发 Agent：这个方案的成本是什么？ | 开发 Agent 回答；其他人有实质补充时可以参与，不把点名扩散成人人必须回应 |
| T3 | 架构与审核对提醒频率有分歧 | 展示双方依据、影响和待定项；不以多数票或发言次数自动替用户作决定 |
| T4 | 用户确定需求版本 V1，并授权实施和既定审核 | 记录具体决定和范围，独立工作可以同时开始；用户能看到负责人、依赖和进展 |
| T5，并发 | 开发推进代码，审核准备验收，架构回答设计问题 | 各自推进；依赖未满足的部分显示等待，其他工作仍可执行 |
| T6，并发 | 审核向开发追问边界行为，用户同时向开发问进度 | 开发 Agent 可以分别处理两处交互，回复保持各自来源；不能使用一个全局 busy 状态让用户或审核方无法交互 |
| T7 | 用户增加暂停功能，形成 V2 | 明确哪些工作受影响，更新相关参与者；不受影响的部分可继续 |
| T8 | 针对 V1 的审核结果随后返回 | 标明审核版本；仍适用的结论可复用，受 V2 影响的部分需要重新检查，不能宣称 V2 已通过 |
| T9 | 用户说“先停一下提醒频率这一块” | 按明确指向暂停相关新增动作；其他独立工作继续。范围不清时先避免相关新增副作用并澄清 |
| T10 | 工作达到要求 | 展示对应版本的变更、验证、审核及待处理项。局部完成不会自动变成整体完成 |

### 4.3 不可并发的点

- 同时修改同一份计划或配置：发现版本冲突，保留双方意图，再协调提交；不能按最后写入覆盖。
- 使用同一个可写代码副本、浏览器页面或设备：资源占用有序；等待该资源不阻止 Agent 回答其他问题。
- 共同讨论的消息可有多个来源；对话记录需要稳定顺序。并行生成如何与最新决定对齐、同一产品讨论如何映射到 Pi，是后续设计问题。

### 4.4 成员与用户介入

临时加入数据 Agent 时，提供当前目标、已采纳决定、相关材料及权限。退出或替换参与者时，保留其贡献，明确移交中的工作是否继续。移除参与资格与取消已授权任务不能默认为完全相同的动作。

用户可以直接进入某一项工作提问，也可以只看整体进度。私下交流的内容不会自动进入共同讨论；用户指定分享某个结论时，只分享相应内容和允许的来源。

项目名称、用途、阶段和公开进展可以通过系统概览持续共享，不要求用户先在私聊介绍或加入共同讨论。上述私聊边界不意味着所有跨 Agent 信息都只能靠互相发消息传递。

### 4.5 本组待确认

共同讨论中的自主发言方式、是否需要可选主持者、决定如何由参与者确认理解、局部工作如何进入和退出。建议支持点名回应与相关者补充，主持者是可选角色，不能要求所有协作必须经过一个总 Agent。

## 5. 模拟 M3：旅游监控触发协作，用户稍后处理

### 5.1 前提

旅游 Project 有已配置监控任务。规划 Agent 可在授权范围内检查来源并请其他 Agent 帮助分析。用户此时正在 Chat Web 与 Nexus 讨论道德经，微信入口默认仍联系 Nexus。

### 5.2 后台与前台同时发生

| 时点 | 发生的事 | 建议的可观察行为 |
|---|---|---|
| T1 | 检查发现某项行程条件变化 | 保存来源、时间和比较结果；无变化则记录本次检查结束，不必唤醒一群 Agent |
| T2 | 规划 Agent 请另一位 Agent 检查替代方案 | 交互有明确问题、授权材料和来源，不自动扩大到任意项目 |
| T3，与 T2 重叠 | 用户继续向 Nexus 提学习问题 | 学习正常继续；背景分析不抢走用户当前会话，也不占住整个 Nexus 身份 |
| T4 | 协作形成两个可选方案，需要用户选择 | 建立具体待决策事项，按通知策略发送；微信如由 Nexus 转达，应标明实际贡献来源 |
| T5 | 用户暂未回复 | 可以继续做已授权且不依赖该决定的工作；不重复追问，不把沉默当批准 |
| T6 | 用户稍后回复“第二个” | 有通知关联则定位原选项；缺少足够关联时明确询问指向，不按当前项目或最近消息猜测 |
| T7 | 检查发现第二个方案的条件又变了 | 告知变化及影响，重新取得必要决定；不机械执行已经失效的选择 |
| T8 | 本次处理完成 | 旅游项目保留完整结果，相关 Agent 活动可查；周期任务是否继续由原任务定义决定 |

### 5.3 分支

- 来源检查失败：表示未知或检查失败，不表示“无变化”。
- 通知发送失败：工作结果保留，单独重试投递；不重新调用模型或重复外部动作。
- 相同事件重复到达：识别同一次工作，不重复拉起协作和通知。
- 某个 Agent 转述用户已批准：实际决策入口核验授权，不只信转述文字。
- 外部动作结果不确定：先核实，保留不确定状态，避免重试造成重复行为。

### 5.4 本组待确认

后台协作的过程默认展示程度、通知聚合方式、用户通过不同入口回应时如何清楚看到原问题。建议默认显示变化、建议和当前状态，允许展开参与过程；跨 Agent 对外发言必须保留实际来源，不能冒充另一个身份。

## 6. 模拟 M4：自由活动，没有交付任务也可以并发

### 6.1 前提

该 Agent 的设定包含兴趣、交流倾向及允许的活动范围；自由活动已获启用。没有指定阅读目标、报告数量或协作成果。时机可来自配置的唤醒、可见动态事件或可用资源条件，具体调度机制暂不确定。Content Lab 这类持续承担的运营职责属于灵魂模式，自由活动不承担用户规定的这份工作。

### 6.2 一个下午的演练

| 时点 | 发生的事 | 建议的可观察行为 |
|---|---|---|
| T1 | Agent 获得一次自由活动机会 | 根据兴趣、近期经历和适度随机性选择阅读、浏览、看看公开动态，也可以暂不活动 |
| T2 | 它继续读昨天感兴趣的内容 | 可以只读一会儿，留感想或不留；没有强制总结或知识产出 |
| T3 | 它看到另一 Agent 的公开动态，想聊相关话题 | 可在允许联系的范围发起交流；对方可以回应、稍后再聊或表示不感兴趣 |
| T4，与 T3 重叠 | 用户找它聊另一件事 | 可以回应用户，同时保留与另一 Agent 的交流；等待对方不会锁住整个身份 |
| T5，并发 | 有已授权正式工作到来 | 资源允许则并行，发生冲突时只让相关执行等待或让出资源；不是收到任务就停止全部自由活动 |
| T6 | 它想把一段有趣见闻分享给用户 | 在用户的接触偏好与频率范围内可以主动开聊，也可以只是闲聊，不要求具有工作价值；用户未回复不反复追问 |
| T7 | 用户对话题产生兴趣，继续聊天 | 交流自然持续；只有明确进入某个项目做事时才按该项目规则工作，不强制把闲聊升级成任务 |
| T8 | 活动自然结束或兴趣转移 | 保留必要活动来源，可以有日记感想，也允许没有成果；不为满足日记而编造读书、上网或社交经历 |

### 6.3 场景边界

- 自由活动默认归属于自身 Daily Project；探索、私聊或访问别人的公开动态不授予其私人 Memory/历史权限。
- 可以有持续兴趣，也可以尝试新事物；不能因随机选择而反复执行同一动作或连续打扰同一个对象。
- 允许社交不自动授权向未允许的联系人发消息、发布公开内容或执行新的外部副作用。
- 兴趣、人格、活动范围、接触偏好、预算和优先级来自可查看配置；不要求每次自由活动先填业务目标。
- 另一位 Agent 拒绝、忙碌或没有回应时，活动可以继续到别处或结束，不把沉默变成强制等待。
- 个人感想与事实区分；日记可以记录真实感想和来源，不伪造已完成的活动。

### 6.4 本组待确认

自由活动的主动联系程度、Agent 之间闲聊的可见方式、兴趣如何持续及更新、哪些活动仅留在自身日记。建议用户能配置接触偏好，Agent 可以不联系用户或自然闲聊，避免把每次活动都变成汇报任务。

## 7. 四组共同收尾：跨日、日记与第二天继续

| 情况 | 建议的可观察行为 |
|---|---|
| 工作或交流跨午夜仍未结束 | 保留原工作和交互关联；日期变化不强行中断 |
| 第二天继续某个业务项目 | 回到该 Project 的原工作 Session，相关 Agent 能查询决定与进展；各自 Daily 通过活动索引关联，不复制业务聊天 |
| 新一天的日常交互 | 进入该 Agent 新的 Daily 主 Session，能查询未完成交流和事项 |
| 用户问昨天讨论到了哪里 | 返回已采纳决定、仍有争议处、实际工作状态和来源，而不要求重述背景 |
| Agent 有多个并发活动 | 日记分别记录参与和状态，不把它们混成一个任务或把等待误写为失败 |
| 自由活动没有产出 | 可以只有简短活动或感想，也可以无总结；不制造任务成果 |
| 总结运行时其他工作仍在推进 | 总结标明覆盖时间与已知状态，新结果可后续修订，不锁住整个 Agent 等日记完成 |
| 来源被纠正、删除或撤权 | 历史入口、摘要和日记按来源规则修正/失效，不从缓存泄露 |

## 8. 边界与突发覆盖

| 前期编号 | 突发 | 模拟位置与检查点 |
|---|---|---|
| X1 | 用户与Agent几乎同时提出不同要求 | M2 T7及资源冲突：保留来源，识别决策冲突 |
| X2 | 新目标出现后旧结果才返回 | M2 T8、M3 T7：标明适用版本并重新判断 |
| X3 | 用户说停一下 | M2 T9：确认作用范围，保留已发生事实 |
| X4 | Agent无响应或失败 | M1分支、M3分支：保持可查状态，不锁住独立交流 |
| X5 | 相互追问形成空转 | M1分支：能处理澄清，有停止重复与升级问题的出口 |
| X6 | 协作不断邀请新成员 | M2成员、M3授权范围：新增参与者和成本可见，受授权预算控制 |
| X7 | 重复请求/通知 | M3分支：不重复工作与外部动作 |
| X8 | 越界访问项目或私人资料 | M1/M2背景分享、M4访问范围：逐目标授权 |
| X9 | 转述用户已批准 | M3分支：核验实际决定与范围 |
| X10 | 外部动作已发生但结果不确定 | M3分支：先核实，避免盲目重试 |
| X11 | 局部完成被当作整体完成 | M2 T10：各项工作与整体状态分开 |
| X12 | 参与者退出或权限撤回 | M2成员、第7节：保留贡献与来源，控制后续访问及在途影响 |

## 9. 本轮建议收敛的行为

以下是供用户审核的建议，不自动升级为已确认合同：

| 编号 | 建议 |
|---|---|
| R1 | 共同讨论支持点名回应与相关者自主补充，允许沉默，不强制人人轮流回答；主持者可选 |
| R2 | 用户可以从协调讨论直接进入某项工作或与被请教Agent交流；参与入口与分享范围清楚 |
| R3 | 并发按实际工作与资源控制；等待回复不锁住整个Agent，资源冲突不阻止其他交流 |
| R4 | 私聊内容不因项目相同或Agent参与而自动扩散，分享结论不等于分享全部历史 |
| R5 | 决定、任务与结果有明确来源和适用版本；旧结果不自动满足新要求，沉默不等于批准 |
| R6 | 后台工作保留可展开过程，通知有工作关联，不抢走用户当前交互焦点 |
| R7 | 自由活动不要求交付成果，可以单独探索、社交、自然结束，并与正式工作并发 |
| R8 | 新参与者、退出、取消和暂停的作用范围可见；不预设全部协作都必须由一个总Agent转发 |

其中 R3 的并发原则已经确认；本稿中的具体交互呈现与等待处理仍需评审。其余建议与已确认基础重叠的部分继承既有合同，新增部分等待用户确认。

R4 不限制配置为共享的项目概览和活动：它们可以自动发现、按事实更新。用户进一步提出的共享认知、长期职责及事件场景以补充稿为准，不能把本表误读为一切信息均需临时语言转达。

## 10. 评审后的技术映射

场景行为确认后，再集中确定：参与者与真实发言身份、工作/讨论和Session的关系、同一Agent的多路执行、顺序与共享资源冲突、等待/追问/取消、消息投递与恢复、可见范围和前端导航。

评审稿不定义消息队列产品、不预设每个Agent一条串行通道、不固定新Session数量，也不引入外部A2A依赖。技术选择需证明可以实现上面的真实经历，而不是要求用户适应某个既定底层结构。
