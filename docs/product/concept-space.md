# Chat 概念空间

## 1. 为什么需要这份文档

复杂项目最常见的误解之一，是双方用了同一个词，却在说不同的东西。另一个问题是用内部技术词直接描述用户任务，让计划虽然“专业”，却很难理解和审核。

Chat采用“概念空间”方法：先为当前场景建立共同语言，再讨论需求、计划、架构和实现。

一句话理解：**概念空间就是一个具体协作场景里的共同语言边界。**

本方法由OPC-OS概念空间及其概念资产治理规则移植，并按Chat项目需要缩小。Chat不复制OPC-OS的全部概念，只保留会影响当前产品理解和开发决定的词。

## 2. 使用规则

1. 先说用户要完成什么，再引入技术名称。
2. 第一次使用重要术语时，用一句普通话解释它解决什么问题。
3. 一个词只指一个主要对象；不同对象不能因为名称相近就合并。
4. 定义同时说明“是什么”和“不是什么”。
5. 只在当前讨论临时使用的词就地解释，不建立无用词典。
6. 用户指出“看不懂、太抽象或粒度太大”时，先修订共同语言和任务拆分，再继续开发。
7. 技术字段和代码名称可以保留英文，但面向用户的计划先使用可观察结果表达。

## 3. 当前最重要的产品概念

### 3.1 Chat产品

**普通话**：用户用来持续推进事情的完整产品。

**包含**：对话入口、后台工作、人工决定、恢复、结果、证据和长期状态。

**不包含**：只有一个聊天页面的Demo、单独的Agent外壳或单独的Workflow演示。

### 3.2 产品会话（Product Session）

**普通话**：用户可以打开、继续和归档的一段协作空间。

**不是什么**：不是浏览器标签页，不是一次Workflow运行，也不是pi内部会话。

### 3.3 一次交互（Interaction）

**普通话**：围绕用户一次输入，从接收、处理到形成结果的一整轮过程。

**不是什么**：不是一条消息，也不保证只启动一次底层执行尝试。

### 3.4 正式消息（Message）

**普通话**：已经由Chat服务端确认并保存、用户以后还能重新读取的内容。

**不是什么**：输入框草稿、模型生成中的片段、前端缓存和Agent候选回答都不是正式消息。

### 3.5 一次后台工作（Product Run）

**普通话**：用户能看到状态、结果和失败原因的一次工作记录。

**不是什么**：它不是Vercel Workflow Run，也不是pi的一次内部运行。底层实现可以更换，用户看到的工作记录仍由Chat拥有。

### 3.6 后台流程（Workflow）

**普通话**：让一项工作能够分步骤执行、等待并在以后继续的后台机制。

**不是什么**：它不拥有用户会话、正式消息、审批和最终完成事实。

### 3.7 Agent节点（pi）

**普通话**：后台流程中的一个执行步骤，负责调用模型、生成回答候选，未来还可以受控调用工具。

**不是什么**：pi不是Chat产品本身，也不能决定工作是否正式完成。

### 3.8 正式结果（Product Commit）

**普通话**：系统检查候选结果后，把它提交为正式消息、状态或产物的动作。

**不是什么**：模型说“完成了”、Workflow结束或Agent运行成功，都不自动等于正式结果已经成立。

### 3.9 实时进度（Chat Event Feed）

**普通话**：网页用来显示“开始、处理中、输出、失败”等变化的一条有顺序、可续接的事件流。

**不是什么**：事件流不是正式历史，也不能取代查询服务端消息和运行状态。

### 3.10 工作流运行区（Workflow Run View）

**普通话**：Chat界面中显示当前一次工作怎样推进、现在走到哪一步、是否暂停或失败的区域。

**不是什么**：它不是Vercel Workflow控制台，不直接连接Workflow或pi，不显示内部身份和隐藏推理，也不是用于拖拽和发布流程定义的编辑器。P1先交付运行投影，完整定义图和编辑能力属于P6。

### 3.11 DSH Web Host

**普通话**：Chat唯一主界面的网页宿主，提供原生会话、消息、Composer、布局和插件表面。

**不是什么**：DSH Session不是Chat Product Session；页面可打开也不代表Workflow、pi或Product Store运行在浏览器里。

### 3.12 可恢复

“可恢复”必须说明是哪一层，不能笼统承诺：

1. 页面刷新恢复：重新查询服务端正式内容。
2. 网络断线恢复：重新连接事件流并从Cursor继续。
3. API进程退出恢复：依赖持久Product Store。
4. Workflow Worker退出恢复：依赖Workflow Checkpoint和接管机制。
5. 外部调用失联恢复：可能需要查询、对账或人工处理，不能盲目重试。

### 3.13 项目（Project）

**普通话**：围绕一个长期目标，把真实资源、参与者、工作、决定和证据组织起来，并可跨会话持续推进的工作边界。

**不是什么**：不是一个聊天Session、Git仓库、Iteration、待办列表或BMAD目录。

### 3.14 阶段与阶段目标（Stage / Stage Goal）

**普通话**：项目在较长时间里的发展位置，以及这个阶段要达成的可验证结果。

**不是什么**：Stage不是Sprint、Iteration或一条任务状态；一个Stage可以包含多次Iteration。

### 3.15 里程碑（Milestone）

**普通话**：项目或阶段中一个重要、可验证的结果检查点。

**不是什么**：不是自动计算的完成百分比，也不是每个Task都要变成Milestone。

### 3.16 迭代与承诺（Iteration / Commitment）

**普通话**：在有限投入或周期内，明确由谁交付什么结果的一次承诺。

**不是什么**：不是Project生命周期；到期不能自动延期或把未完成事项无记录地滚入下一轮。

### 3.17 Proposal与Shaping

**普通话**：把一个模糊想法整理成问题、投入边界、预期结果、方案轮廓、风险和明确不做内容，再决定是否值得投入。

**不是什么**：Proposal不是已经批准的Work；模型生成内容未经用户确认仍只是Candidate。

### 3.18 Work、Scope与Action

1. **Work**：有独立交付结果和验收标准的工作单元。
2. **Scope**：Work中可以相对独立完成、并常在真实执行中逐步发现的结构区域。
3. **Action**：现在可以执行、能够分派和完成的具体待办。

三者不能因为都“像任务”而合并。Action全部完成也不能自动证明Work、Iteration或Project完成。

### 3.19 参与、贡献与证据

1. **Participant**：项目中的用户、Agent、自动化或外部参与方。
2. **Contribution**：谁在何时为哪个Work做了什么、影响了哪些真实资源。
3. **Evidence**：Commit、PR、测试、文档版本、Artifact或部署等可验证依据。

Agent说“我完成了”最多是reported Contribution，不是verified Evidence。

### 3.20 决定、观察与项目更新

1. **Decision**：谁基于哪些选项和理由确认了什么，以及影响哪些对象版本。
2. **Observation**：Resource Adapter在某一时刻看到的真实代码、文档、脚本或服务状态。
3. **Project Update**：负责人署名的健康、变化、阻塞和下一步叙事。

Observation不能自动变成Decision，Activity或模型摘要不能冒充Project Update。

## 4. 不再直接用来描述用户任务的说法

| 不清楚的内部说法 | 面向任务的表达 |
|---|---|
| pi工件 | 确保本地开发、CI和未来部署实际使用同一份经过确认的pi代码 |
| Product Store证明级别 | 说清楚本阶段在什么情况下数据还在：只支持页面刷新，还是也支持服务进程重启 |
| 测试运行合同 | 说清楚哪些测试运行真实组件，哪些使用可控替身，以及默认CI是否需要私有凭据 |
| 打通纵向链 | 明确写出用户从哪里开始、看见什么、结果保存在哪里、失败后怎样恢复 |
| 完成门 | 列出能够实际操作和复核的通过条件 |

内部技术文档仍可使用精确术语，但计划、任务说明和用户审核材料必须先给出右侧含义。

## 5. 概念怎样维护

1. 产品语言以本文为共同入口；字段级Schema仍由合同和代码拥有。
2. 技术状态以`PROJECT_STATE.md`为准，任务顺序以`PROJECT_PLAN.md`为准；本文不复制进度。
3. 新概念只有在反复使用、曾造成误解或影响架构和权限时才加入。
4. 发现定义不清时在本文修正，并检查计划、状态、合同和代码是否受到影响。
5. 概念是否有效要靠后续真实沟通验证，文件存在不等于用户已经理解。
