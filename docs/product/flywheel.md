# Chat 项目飞轮

## 1. 一句话理解

**每次开发和审核不只完成当前任务，还要让下一次任务更容易理解、更少返工、更容易验证。**

本方法由`/Users/xulater/Code/opc-os/飞轮概念.md`和`飞轮系统/`移植。Chat只采用与产品推进直接相关的最小闭环，不复制一套庞大的管理系统。

## 2. Chat的项目飞轮

```text
选择一个小的用户场景
-> 写清楚可见结果和边界
-> 实现并测试
-> 代码审核与用户反馈
-> 记录真实问题和有效做法
-> 修订概念、计划、规则或测试门
-> 下一任务开始前重新使用
-> 再次验证、修正或淘汰
```

只有“写进文档”还不算飞轮。下一次任务能找到并真正使用，随后获得新的反馈，才形成闭环。

## 3. 飞轮持续增强什么

1. **用户**：更容易理解产品正在做什么，能够审核范围、结果和风险。
2. **AI与开发者**：更准确恢复项目事实，减少重复研究、错误假设和无关实现。
3. **协作系统**：任务更小、边界更清楚、审核更快，失败经验能改变下一轮行动。
4. **Chat产品**：每个阶段都增加一段真实可用、可验证的能力，而不是只增加架构和文档数量。

## 4. 每个开发任务的最小闭环

### 开始前

1. 从用户场景说明“为什么做”。
2. 读取已有概念、状态、计划和相关技术合同。
3. 确认任务只包含一个主要结果，并写清不做什么。

### 进行中

1. 保留决定方案的事实、失败和权衡。
2. 行为变化同时补测试，不用口头保证替代证据。
3. 发现范围扩张时立即拆任务，不把它藏进当前PR。

### 完成后

1. 记录实际通过的测试和仍不保证的边界。
2. 用户或审核者指出的问题进入`PROJECT_LESSONS.md`或相关唯一事实源。
3. 如果经验可能复用，说明下一次在哪个任务验证；没有复用价值就不制造文档。

### 下一次同类任务

1. 先使用已有经验。
2. 检查它是否真的减少误解、返工或失败。
3. 根据结果保留、修正、拆分或停用。

## 5. 本轮真实反馈怎样进入飞轮

2026-08-06，用户指出了3个具体问题：

1. `pi工件`等内部术语没有说明用户究竟要得到什么。
2. 原P1把消息、存储、Workflow、pi、实时事件和Web恢复放在一个工作包中，粒度过大。
3. PWA虽然是前端目标形态，却被排到很后面，没有从第一批界面任务开始验证。

本轮采用的修正是：

1. 新增[Chat概念空间](./concept-space.md)，先用普通话解释任务，再保留必要技术名词。
2. 把P1改为阶段目标，并在`PROJECT_PLAN.md`中拆成8个独立任务。
3. 把响应式外壳和可安装PWA放到P1.1、P1.2。
4. 原来3个全局“入口决定”改为就近决定：存储保证在P1.3说明，真实Workflow与确定性步骤的测试方式在P1.4说明，pi代码来源和模型测试在P1.7说明。
5. 每个任务固定包含用户场景、交付结果、不做什么和完成门。

## 6. 下一次怎样验证这次修正有效

1. 用户能否只看P1.1任务说明，就明白下一步要做什么和不会做什么。
2. P1.1是否能用一个独立PR完成并审核，不夹带Workflow或Agent实现。
3. P1.2是否从真实安装、离线打开和离线发送失败场景验证PWA边界。
4. 到P1.7时，开发者是否会自动检查本地与CI使用的是同一份pi代码，而不需要再次返工。
5. 如果某个P1.x仍超过一次可审核开发量，继续拆分；编号变化不影响P1整体用户目标。

## 7. 飞轮的反面

1. 只有文档，没有在下一任务使用：这是归档，不是飞轮。
2. 只有重复开发，没有反馈和测试：这是机械循环。
3. 每次都从零解释项目：说明恢复入口没有起作用。
4. 为了显得完整不断增加规则和文件：会让维护成本吞掉收益。
5. 把一次反馈直接提升为永远正确的规则：缺少后续真实验证。
