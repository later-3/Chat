## 1. 系统全景:三个独立进程

本系统是**多进程架构**,三个进程各自独立运行,通过 HTTP 通信。

```
┌─────────────────────────────────────────────────────────────┐
│ 进程 1: 前端 (apps/web, React PWA, Vite dev server)          │
│ 端口: 43110                                                  │
│ 职责: 用户交互、渲染 Plan / 执行结果、提交审批决定             │
│ 类比: 用户态应用程序                                         │
└───────────────────────┬─────────────────────────────────────┘
                        ↓ HTTP (43110 Vite 代理 → 43111 API)
┌───────────────────────┴─────────────────────────────────────┐
│ 进程 2: 后端 API (apps/api, Hono)                             │
│ 端口: 43111 (公开 + 内部路由同端口)                           │
│ 职责: 产品事实管理、Outbox 派发、Application 业务逻辑         │
│ 权威存储: Product Store (.data/product/chat-product-store.v1.json) │
│ 类比: 内核(权威状态 + 系统调用入口)                          │
└───────────────────────┬─────────────────────────────────────┘
                        ↓ Outbox 派发 (HTTP POST → 43112)
┌───────────────────────┴─────────────────────────────────────┐
│ 进程 3: Workflow Runtime (packages/workflows, Vercel Workflow) │
│ 端口: 43112 (运行时), 43121 (V8 Inspector 调试)              │
│ 职责: 工作流编排、耐久 checkpoint、Hook 等待/恢复、调 LLM     │
│ 数据: .data/workflow/ (checkpoint), .workflow-bundle/ (bundle) │
│ 类比: kthread(后台工作线程)                                  │
└─────────────────────────────────────────────────────────────┘
```

### 为什么是多进程而不是单进程?

| 考量 | 说明 | 内核类比 |
|------|------|---------|
| **故障隔离** | Workflow Runtime 崩溃不影响后端 API 服务 | 进程隔离(vs 内核线程 crash 拖垮整个系统) |
| **独立调试** | 可以单独附加调试器到 Workflow Runtime | `gdb -p <pid>` 附加到特定进程 |
| **资源隔离** | LLM 调用耗时长,不阻塞 API 请求处理 | CPU 密集任务放到 kworker,不阻塞系统调用 |
| **生命周期独立** | Workflow 可暂停(Hook 等待)而不占内存 | `wait_event` 时不占 CPU,可被 `wake_up` |
| **生产一致性** | 本地和云端都是多进程,行为一致 | 开发机和生产环境内核配置一致 |

## 3. 身份层级:七层不可合并

参考 [docs/product/concept-space.md](file:///Users/xulater/Code/Chat/docs/product/concept-space.md) 和 [AGENTS.md](file:///Users/xulater/Code/Chat/AGENTS.md) §6.7。

```
Product Session    一次会话        psn_xxx    用户和 AI 的协作空间
    ↓
Product Run        一次运行        run_xxx    用户可见的一次工作记录(绑定 session)
    ↓
Run Attempt        一次尝试        att_xxx    workflow / planning / execution 各有独立 attempt
    ↓
Workflow Run       工作流运行      wrun_xxx   Vercel Workflow 的 Run(后台执行机制)
    ↓
Workflow Checkpoint 检查点         -          每个 step 后的持久化状态(耐久恢复用)
    ↓
pi Runtime Session Agent 执行会话  -          模型调用的上下文(Planner / Executor)
    ↓
Realtime Connection 实时连接       -          前端订阅(当前用轮询,未来 SSE)
```

### 为什么七层不能合并?

| 层级 | 如果合并会怎样 | 内核类比 |
|------|---------------|---------|
| Session ≠ Run | 一个会话可以有多次运行(用户发多条消息) | 一个 socket 可以有多个连接 |
| Run ≠ Attempt | 一个 Run 可以有多次尝试(Plan 修订循环) | 一个 syscall 可以重试 |
| Attempt ≠ Workflow Run | Attempt 是产品概念,Workflow Run 是执行机制 | task_struct ≠ pid |
| Workflow Run ≠ Checkpoint | 一个 Workflow Run 有多个 Checkpoint | 一个进程有多个 crash dump |
| Checkpoint ≠ pi Session | Checkpoint 是状态快照,pi Session 是模型调用上下文 | core dump ≠ 线程上下文 |
| pi Session ≠ Connection | 模型调用和前端订阅是独立的 | 网络请求 ≠ 文件描述符 |

### 关键区分:Product Run ≠ Workflow Run

> 参考 [docs/product/concept-space.md](file:///Users/xulater/Code/Chat/docs/product/concept-space.md) L51-62:
>
> Product Run 是用户可见的一次工作记录,不是 Vercel Workflow Run;Workflow 只是后台分步骤执行、等待和继续的机制,不拥有会话、消息、审批和完成事实。

- **Product Run** (`run_xxx`):用户视角的"一次工作"。状态:pending → running → waiting_human → running → succeeded/failed。存在 Product Store。
- **Workflow Run** (`wrun_xxx`):Vercel Workflow 的执行实例。状态:running → paused(Hook) → running → completed。存在 `.data/workflow/`。

一个 Product Run 对应一个 Workflow Run。Product Run 是产品事实,Workflow Run 是执行机制。用户只关心 Product Run;Workflow Run 是实现细节。

## 4. 数据流:消息原文在哪里?

这是理解系统的关键:**数据原文只在 Product Store 里,Workflow 只持引用**。

```
用户输入"你好"
    │
    ↓ HTTP POST
后端 API 收到请求
    │
    ├──→ Product Store: 存消息原文 {text: "你好", sha256: "596b..."}
    │    (原文从此不再移动,所有后续都通过 ID + sha256 引用)
    │
    ├──→ Product Store: 创建 Run {productRunId, sourceMessageId, sourceMessageSha256}
    │                                      ↑ 引用,不是原文
    │
    └──→ Outbox: 写 workflow_start 任务 {productRunId, attemptId}
                                        ↑ 只传 ID
    
    ↓ Outbox 派发
Workflow Runtime 收到任务
    │
    │  Workflow 只持有:productRunId, attemptId
    │  Workflow 不持有:"你好" 原文
    │
    ├──→ step: beginPlanningContext(productRunId)
    │         ↓ HTTP POST 到后端
    │    后端: 用 productRunId 查 Product Store → 读"你好"原文 + 历史
    │         → 组装上下文 → 返回 contextPackageRef(引用)
    │    Workflow: 拿到 contextPackageRef(不是原文)
    │
    ├──→ step: compilePlanningInput(productRunId, contextPackageRef)
    │         ↓ HTTP POST 到后端
    │    后端: 用引用查 Product Store → 读原文 + 上下文 → 组装模型输入
    │         → 返回 planningInput(包含原文,但是后端组装的)
    │    Workflow: 拿到 planningInput → 传给 Planner 模型
    │
    ├──→ step: ctx.planner(planningInput)
    │         ↓ 调用百炼 LLM
    │    LLM: 生成 Plan(结构化 JSON)
    │    Workflow: 拿到 Plan candidate
    │
    └──→ step: publishPlanReview(productRunId, planCandidate)
              ↓ HTTP POST 到后端
         后端: 存 Plan 到 Product Store {planId, sha256, content}
         前端: 轮询拿到 Plan → 渲染给用户
```

### 为什么 Workflow 不持有原文?

| 原因 | 说明 | 内核类比 |
|------|------|---------|
| **Checkpoint 轻量** | 每个 step 后做 checkpoint。如果存原文,checkpoint 会很大 | crash dump 只存寄存器+栈,不存全部内存 |
| **权威单一来源** | 产品事实只在 Product Store 存一份,避免冗余/不一致 | 进程的权威状态在 task_struct,不在文件描述符表 |
| **重放安全** | 崩溃恢复时重放 step,如果持原文,原文可能已变 | BPF verifier 重放时不信任用户态内存 |
| **Trace 隐私** | Trace 只存引用 + Hash,不存正文 | ftrace 不记录数据内容,只记录事件 |
| **引用稳定** | sha256 保证引用的内容不变,即使原文被编辑也指向原版本 | COW(Copy-On-Write):写时复制,读时引用 |

## 5. 设计原则

参考 [AGENTS.md](file:///Users/xulater/Code/Chat/AGENTS.md) §4 冻结架构原则。

### 原则 1:职责分离,各司其职

```
浏览器    → 只做用户交互,不直接调用 Workflow/pi
后端 API  → 只管产品事实 + Outbox 派发,不直接调用 Workflow Runtime
Workflow  → 只编排步骤顺序 + 耐久保障,不持有产品事实原文
pi        → 只调 LLM,不拥有产品事实
```

> 类比:内核中 VFS 不直接操作 ext4 的磁盘块,ext4 不直接操作 block device 的 DMA。每层只通过定义好的接口和下一层通信。

### 原则 2:Product Store 是唯一权威

所有产品事实(消息、Run、Plan、Decision、执行结果)只在 Product Store 里存一份。

- Workflow Run 的返回值**只用于诊断**,不是产品成功标志
- Product Store 的终态(`succeeded`/`failed`/`cancelled`)才是产品成功标志
- 类比:进程的退出码在 task_struct 里,不在 core dump 里

### 原则 3:Outbox 解耦提交与执行

HTTP 请求提交事实后立即返回 201,耗时工作流异步执行。

```
HTTP 请求 → Product Store 提交(同步) → 返回 201
                ↓
           Outbox 写任务(同步)
                ↓
           Dispatcher 派发(异步) → Workflow Runtime 执行(异步)
```

> 类比:`queue_work()` 把耗时操作入队后立即返回,实际执行推迟到 kworker 线程。

### 原则 4:Hook 实现耐久等待

工作流等用户审批时,不阻塞进程,不消耗 CPU。Hook 记录持久化到磁盘,进程崩溃可恢复。

> 类比:`wait_event_interruptible()` 把进程加入等待队列后调用 `schedule()`,CPU 给其他进程。事件到来时 `wake_up()` 唤醒。

### 原则 5:不可变执行合同

Plan 批准后编译成 Execution Contract,不可修改。Executor 必须按合同执行。

> 类比:BPF 程序通过 verifier 验证后,运行时不能再修改字节码。保证执行的可预测性。

### 原则 6:模型 Step 不自动重试

`maxRetries=0`。模型调用失败后,工作流走失败收敛(`commitRunFailure`),不自动重试付费调用。

> 类比:`request_irq()` 失败后不自动重试,返回错误让调用方决定。防止中断风暴。

## 6. 关键概念速查

| 概念 | 定义 | 存储位置 | 内核类比 |
|------|------|---------|---------|
| **Product Store** | 权威产品事实存储(JSON 文件,原子提交) | `.data/product/chat-product-store.v1.json` | sysfs / procfs |
| **Product Run** | 用户可见的一次工作记录 | Product Store `entities.runs` | task_struct |
| **Outbox** | 派发任务队列(workflow_start / workflow_resume) | Product Store `outbox` | workqueue |
| **Workflow Run** | Vercel Workflow 的执行实例 | `.data/workflow/runs/` | kthread |
| **Checkpoint** | 每个 step 后的持久化状态快照 | `.data/workflow/events/` | crash dump |
| **Hook** | 耐久等待点(等用户决定) | `.data/workflow/.locks/hooks/` | wait_queue |
| **Trace** | 结构化事件日志(JSONL,追加写) | `.data/traces/chat-trace-*.jsonl` | ftrace |
| **Bundle** | SWC 编译打包后的工作流代码 | `.workflow-bundle/workflows.mjs` | `.ko` 模块 |
| **Execution Contract** | 不可变执行合同(从批准 Plan 编译) | Product Store `entities.executionContracts` | BPF verifier 验证后的程序 |
| **Approval Request** | 审批请求(等用户 approve/reject) | Product Store `entities.approvalRequests` | completion |
| **Decision** | 用户决定(approve/reject/request_revision) | Product Store `entities.decisions` | wake_up 事件 |
| **CAS 乐观锁** | Run 的 revision 字段,防止并发冲突 | Product Store `runs[...].revision` | `atomic_cmpxchg` |
| **commandId** | 幂等命令 ID,防重复提交 | Product Store `commandReceipts` | idempotent ioctl |

## 8. 模型调用架构

```
Workflow Runtime (43112)
    │
    ├── ctx.planner(planningInput)     → Planner 模型(百炼 Qwen)
    │   输入: 用户消息 + 历史 + 上下文 + 用户规则
    │   输出: 结构化 Plan JSON(objective, steps, successCriteria, ...)
    │   耗时: ~10s
    │
    └── ctx.executor(contract, step)   → Executor 模型(百炼 Qwen)
        输入: 执行合同 + step 定义 + 上下文 + 依赖结果
        输出: step 执行结果(文档/代码/分析等)
        耗时: ~35s
```

### 模型配置

`.env` 文件:
```
DASHSCOPE_API_KEY=...        # 百炼 API Key
DASHSCOPE_BASE_URL=...       # 百炼 API 端点
```

### 为什么 Planner 和 Executor 分开?

| 维度 | Planner | Executor |
|------|---------|----------|
| 职责 | 规划"做什么" | 执行"怎么做" |
| 输入 | 用户消息 + 上下文 | 执行合同(step 定义) |
| 输出 | 结构化 Plan JSON | 文档/代码/分析 |
| 耗时 | ~10s | ~35s |
| 可重试 | 可以(request_revision 回循环) | 不可以(合同不可变,maxRetries=0) |
| 用户审批 | 需要(Plan 发布后等 approve) | 不需要(按批准的合同执行) |

> 类比:Planner 是架构师(画设计图),Executor 是工程师(按图施工)。分开可以分别调优、分别计费、分别控制质量。
