## 1. 系统全景:三个独立进程

本系统是**多进程架构**,三个进程各自独立运行,通过 HTTP 通信。你可以把它想成三个独立程序(像三个 `.exe`)各自跑起来,互相用网络请求传消息,而不是一个程序里的三个函数互相调用。

```
┌─────────────────────────────────────────────────────────────┐
│ 进程 1: 前端 (apps/web, React PWA, Vite dev server)          │
│ 端口: 43110                                                  │
│ 职责: 用户交互、渲染 Plan / 执行结果、提交审批决定             │
│ 直观理解: 用户直接操作的程序(像桌面应用)                     │
└───────────────────────┬─────────────────────────────────────┘
                        ↓ HTTP (43110 Vite 代理 → 43111 API)
┌───────────────────────┴─────────────────────────────────────┐
│ 进程 2: 后端 API (apps/api, Hono)                             │
│ 端口: 43111 (公开 + 内部路由同端口)                           │
│ 职责: 产品事实管理、Outbox 派发、Application 业务逻辑         │
│ 权威存储: Product Store (.data/product/chat-product-store.v1.json) │
│ 直观理解: 存所有数据、处理所有请求的服务端程序(像带数据库的后台) │
└───────────────────────┬─────────────────────────────────────┘
                        ↓ Outbox 派发 (HTTP POST → 43112)
┌───────────────────────┴─────────────────────────────────────┐
│ 进程 3: Workflow Runtime (packages/workflows, Vercel Workflow) │
│ 端口: 43112 (运行时), 43121 (V8 Inspector 调试)              │
│ 职责: 工作流编排、耐久 checkpoint、Hook 等待/恢复、调 LLM     │
│ 数据: .data/workflow/ (checkpoint), .workflow-bundle/ (bundle) │
│ 直观理解: 后台常驻进程,专门跑耗时的工作流(像后台任务守护程序) │
└─────────────────────────────────────────────────────────────┘
```

### 为什么是多进程而不是单进程?

| 考量 | 说明 | 直观理解 |
|------|------|---------|
| **故障隔离** | Workflow Runtime 崩溃不影响后端 API 服务 | 两个独立程序互不影响,一个挂了另一个还活着(不像单进程里一个崩溃全完) |
| **独立调试** | 可以单独附加调试器到 Workflow Runtime | 每个进程有自己的调试端口,能单独断点 |
| **资源隔离** | LLM 调用耗时长,不阻塞 API 请求处理 | 耗时几十秒的模型调用放后台进程,前端请求照样秒回 |
| **生命周期独立** | Workflow 可暂停(Hook 等待)而不占内存 | 等用户审批时把等待状态存盘,进程可以该干嘛干嘛 |
| **生产一致性** | 本地和云端都是多进程,行为一致 | 开发机和线上环境跑的是同一种结构,不会"本地能跑线上炸" |

## 3. 身份层级:七层不可合并

参考 [docs/product/concept-space.md](file:///Users/xulater/Code/Chat/docs/product/concept-space.md) 和 [AGENTS.md](file:///Users/xulater/Code/Chat/AGENTS.md) §6.7。

```
Product Session    一次会话        psn_xxx    用户和 AI 的协作空间
    ↓
Product Run        一次运行        run_xxx    用户可见的一次工作记录(绑定 session)
    ↓
Run Attempt        一次尝试        att_xxx    workflow / planning / execution 各有独立 attempt
    ↓
Workflow Run       工作流运行      wrun_xxx   Vercel Workflow 的 Run(后台执行机制)
    ↓
Workflow Checkpoint 检查点         -          每个 step 后的持久化状态(耐久恢复用)
    ↓
pi Runtime Session Agent 执行会话  -          模型调用的上下文(Planner / Executor)
    ↓
Realtime Connection 实时连接       -          前端订阅(当前用轮询,未来 SSE)
```

### 为什么七层不能合并?

| 层级 | 如果合并会怎样 | 直观理解 |
|------|---------------|---------|
| Session ≠ Run | 一个会话可以有多次运行(用户发多条消息) | 一个聊天窗口里可以发很多条消息,每条是一次运行 |
| Run ≠ Attempt | 一个 Run 可以有多次尝试(Plan 修订循环) | 一次工作里可以改好几轮 Plan,每轮是一次尝试 |
| Attempt ≠ Workflow Run | Attempt 是产品概念,Workflow Run 是执行机制 | "用户看到的任务"和"后台怎么跑这个任务"是两回事 |
| Workflow Run ≠ Checkpoint | 一个 Workflow Run 有多个 Checkpoint | 一次执行过程会存好几个存档点,不是一个 |
| Checkpoint ≠ pi Session | Checkpoint 是状态快照,pi Session 是模型调用上下文 | "存档文件"和"调模型时的临时上下文"不是一回事 |
| pi Session ≠ Connection | 模型调用和前端订阅是独立的 | 后端调模型和前端等结果,是两条独立的事 |

### 关键区分:Product Run ≠ Workflow Run

> 参考 [docs/product/concept-space.md](file:///Users/xulater/Code/Chat/docs/product/concept-space.md) L51-62:
>
> Product Run 是用户可见的一次工作记录,不是 Vercel Workflow Run;Workflow 只是后台分步骤执行、等待和继续的机制,不拥有会话、消息、审批和完成事实。

- **Product Run** (`run_xxx`):用户视角的"一次工作"。状态:pending → running → waiting_human → running → succeeded/failed。存在 Product Store。
- **Workflow Run** (`wrun_xxx`):Vercel Workflow 的执行实例。状态:running → paused(Hook) → running → completed。存在 `.data/workflow/`。

一个 Product Run 对应一个 Workflow Run。Product Run 是产品事实,Workflow Run 是执行机制。用户只关心 Product Run;Workflow Run 是实现细节。

## 4. 数据流:消息原文在哪里?

这是理解系统的关键:**数据原文只在 Product Store 里,Workflow 只持引用**。就像数据库里存正文,别处只存主键 ID,要用的时候拿 ID 回数据库查。

```
用户输入"你好"
    │
    ↓ HTTP POST
后端 API 收到请求
    │
    ├──→ Product Store: 存消息原文 {text: "你好", sha256: "596b..."}
    │    (原文从此不再移动,所有后续都通过 ID + sha256 引用)
    │
    ├──→ Product Store: 创建 Run {productRunId, sourceMessageId, sourceMessageSha256}
    │                                      ↑ 引用,不是原文
    │
    └──→ Outbox: 写 workflow_start 任务 {productRunId, attemptId}
                                        ↑ 只传 ID
    
    ↓ Outbox 派发
Workflow Runtime 收到任务
    │
    │  Workflow 只持有:productRunId, attemptId
    │  Workflow 不持有:"你好" 原文
    │
    ├──→ step: beginPlanningContext(productRunId)
    │         ↓ HTTP POST 到后端
    │    后端: 用 productRunId 查 Product Store → 读"你好"原文 + 历史
    │         → 组装上下文 → 返回 contextPackageRef(引用)
    │    Workflow: 拿到 contextPackageRef(不是原文)
    │
    ├──→ step: compilePlanningInput(productRunId, contextPackageRef)
    │         ↓ HTTP POST 到后端
    │    后端: 用引用查 Product Store → 读原文 + 上下文 → 组装模型输入
    │         → 返回 planningInput(包含原文,但是后端组装的)
    │    Workflow: 拿到 planningInput → 传给 Planner 模型
    │
    ├──→ step: ctx.planner(planningInput)
    │         ↓ 调用百炼 LLM
    │    LLM: 生成 Plan(结构化 JSON)
    │    Workflow: 拿到 Plan candidate
    │
    └──→ step: publishPlanReview(productRunId, planCandidate)
              ↓ HTTP POST 到后端
         后端: 存 Plan 到 Product Store {planId, sha256, content}
         前端: 轮询拿到 Plan → 渲染给用户
```

### 为什么 Workflow 不持有原文?

| 原因 | 说明 | 直观理解 |
|------|------|---------|
| **Checkpoint 轻量** | 每个 step 后做 checkpoint。如果存原文,checkpoint 会很大 | 存档文件只记"执行到哪 + 引用的 ID",不把整本书塞进存档 |
| **权威单一来源** | 产品事实只在 Product Store 存一份,避免冗余/不一致 | 数据只在数据库存一份,别处都拿 ID 引用,改了不会各处对不上 |
| **重放安全** | 崩溃恢复时重放 step,如果持原文,原文可能已变 | 读档重放时,如果存档里存的是当时的正文副本,而正文后来被编辑过,就会用到旧数据 |
| **Trace 隐私** | Trace 只存引用 + Hash,不存正文 | 日志文件只记"操作了哪个对象",不把敏感正文写进去 |
| **引用稳定** | sha256 保证引用的内容不变,即使原文被编辑也指向原版本 | 像带版本号的指针:原文改了,旧的 sha256 仍指向旧版本,不会串 |

## 5. 设计原则

参考 [AGENTS.md](file:///Users/xulater/Code/Chat/AGENTS.md) §4 冻结架构原则。

### 原则 1:职责分离,各司其职

```
浏览器    → 只做用户交互,不直接调用 Workflow/pi
后端 API  → 只管产品事实 + Outbox 派发,不直接调用 Workflow Runtime
Workflow  → 只编排步骤顺序 + 耐久保障,不持有产品事实原文
pi        → 只调 LLM,不拥有产品事实
```

> 直观理解:每层只通过定义好的接口和下一层通信,不越层直接操作。就像你写程序时,UI 层不直接写数据库文件,业务层不直接管网络套接字——各层只暴露该暴露的函数,别的层调用它。

### 原则 2:Product Store 是唯一权威

所有产品事实(消息、Run、Plan、Decision、执行结果)只在 Product Store 里存一份。

- Workflow Run 的返回值**只用于诊断**,不是产品成功标志
- Product Store 的终态(`succeeded`/`failed`/`cancelled`)才是产品成功标志
- 直观理解:一个任务"成没成功"看权威数据库里的最终状态记录,不看后台进程的退出码

### 原则 3:Outbox 解耦提交与执行

HTTP 请求提交事实后立即返回 201,耗时工作流异步执行。

```
HTTP 请求 → Product Store 提交(同步) → 返回 201
                ↓
           Outbox 写任务(同步)
                ↓
           Dispatcher 派发(异步) → Workflow Runtime 执行(异步)
```

> 直观理解:这就是"事务发件箱"模式——先把数据和"待办任务"一起写进数据库(同一个事务),立刻给用户返回成功;后台有个派发器轮询发件箱,把任务发给工作流去跑。这样用户不用等几十秒模型调用,请求秒回。任务一定不会丢,因为已经和数据一起落库了。

### 原则 4:Hook 实现耐久等待

工作流等用户审批时,不阻塞进程,不消耗 CPU。Hook 记录持久化到磁盘,进程崩溃可恢复。

> 直观理解:工作流执行到"等用户审批"时,把"我在等这个决定"写成一个文件存到磁盘,然后这个工作流就暂停了(不占 CPU)。进程可以去做别的,甚至关掉重启都行——只要外部把决定写进来,工作流就能从存档恢复继续跑。像游戏暂停在"按 A 确认 / 按 B 取消"的对话框,状态存了盘,随时能继续。

### 原则 5:不可变执行合同

Plan 批准后编译成 Execution Contract,不可修改。Executor 必须按合同执行。

> 直观理解:用户批准的 Plan 被编译成一份不可改的"施工合同",Executor 只能照合同干活,不能自己加步骤或改顺序。这样保证"用户审批的东西"和"实际执行的东西"完全一致。

### 原则 6:模型 Step 不自动重试

`maxRetries=0`。模型调用失败后,工作流走失败收敛(`commitRunFailure`),不自动重试付费调用。

> 直观理解:调一次模型要花钱、要等几十秒。失败后不自动重试,而是直接走失败处理,把 Run 标记为失败。要重试由人决定,避免反复扣费。

## 6. 关键概念速查

| 概念 | 定义 | 存储位置 | 直观理解 |
|------|------|---------|---------|
| **Product Store** | 权威产品事实存储(JSON 文件,原子提交) | `.data/product/chat-product-store.v1.json` | 整个系统的"数据库",所有事实只在这里存一份 |
| **Product Run** | 用户可见的一次工作记录 | Product Store `entities.runs` | 一次工作任务的状态记录(像任务结构体) |
| **Outbox** | 派发任务队列(workflow_start / workflow_resume) | Product Store `outbox` | 事务发件箱:和数据一起落库的待办任务 |
| **Workflow Run** | Vercel Workflow 的执行实例 | `.data/workflow/runs/` | 后台执行这个任务的过程记录 |
| **Checkpoint** | 每个 step 后的持久化状态快照 | `.data/workflow/events/` | 存档点:执行到哪、变量值多少,存成文件 |
| **Hook** | 耐久等待点(等用户决定) | `.data/workflow/.locks/hooks/` | 暂停点:把"在等什么"存盘,不占 CPU |
| **Trace** | 结构化事件日志(JSONL,追加写) | `.data/traces/chat-trace-*.jsonl` | 日志文件:每行一个事件,按时间追加 |
| **Bundle** | SWC 编译打包后的工作流代码 | `.workflow-bundle/workflows.mjs` | 编译产物(类似把多个 .o 链接成的可执行文件) |
| **Execution Contract** | 不可变执行合同(从批准 Plan 编译) | Product Store `entities.executionContracts` | 批准后冻结的"施工合同",Executor 照此执行 |
| **Approval Request** | 审批请求(等用户 approve/reject) | Product Store `entities.approvalRequests` | 等用户拍板的请求 |
| **Decision** | 用户决定(approve/reject/request_revision) | Product Store `entities.decisions` | 用户的拍板结果 |
| **CAS 乐观锁** | Run 的 revision 字段,防止并发冲突 | Product Store `runs[...].revision` | 版本号:提交时带期望版本号,对不上就拒绝(像 git 先 pull 再 push) |
| **commandId** | 幂等命令 ID,防重复提交 | Product Store `commandReceipts` | 请求唯一编号:同一个号重发不会重复执行 |

## 7. 端口与进程速查

## 8. 模型调用架构

```
Workflow Runtime (43112)
    │
    ├── ctx.planner(planningInput)     → Planner 模型(百炼 Qwen)
    │   输入: 用户消息 + 历史 + 上下文 + 用户规则
    │   输出: 结构化 Plan JSON(objective, steps, successCriteria, ...)
    │   耗时: ~10s
    │
    └── ctx.executor(contract, step)   → Executor 模型(百炼 Qwen)
        输入: 执行合同 + step 定义 + 上下文 + 依赖结果
        输出: step 执行结果(文档/代码/分析等)
        耗时: ~35s
```

### 模型配置

`.env` 文件:
```
DASHSCOPE_API_KEY=...        # 百炼 API Key
DASHSCOPE_BASE_URL=...       # 百炼 API 端点
```

### 为什么 Planner 和 Executor 分开?

| 维度 | Planner | Executor |
|------|---------|----------|
| 职责 | 规划"做什么" | 执行"怎么做" |
| 输入 | 用户消息 + 上下文 | 执行合同(step 定义) |
| 输出 | 结构化 Plan JSON | 文档/代码/分析 |
| 耗时 | ~10s | ~35s |
| 可重试 | 可以(request_revision 回循环) | 不可以(合同不可变,maxRetries=0) |
| 用户审批 | 需要(Plan 发布后等 approve) | 不需要(按批准的合同执行) |

> 直观理解:Planner 是架构师(画设计图),Executor 是工程师(按图施工)。分开可以分别调优、分别计费、分别控制质量。
