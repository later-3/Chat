# Chat 调试技术手册

本手册面向会一点 C++、刚开始接触 TypeScript / Node.js 的开发者,把 Chat(Node.js + TypeScript + Vercel Workflow)的调试模型讲清楚。涉及编译链接的概念用 C++ 工具链类比,不依赖操作系统内核背景。

核心心智模型:启动脚本 = 拉起三个进程的"启动器",Workflow Runtime = 能自动存档 / 崩溃读档继续的工作流执行器,Product Store = 整个系统的"数据库"(只读查询),Trace = 追加写的事件日志,断点策略 = 在打进 bundle 的代码上断点不命中、在外部模块上断点才命中。

所有断言都基于仓库源码,链接指向绝对路径与行号。

## 1. 调试环境搭建

### 1.1 启动入口

调试配置在 [.vscode/launch.json](file:///Users/xulater/Code/Chat/.vscode/launch.json),唯一配置项 `"Chat：调试应用"`:

- `program` 指向 [scripts/dev/start.mjs](file:///Users/xulater/Code/Chat/scripts/dev/start.mjs),`args` 为 `["--debug"]`([launch.json L9-L10](file:///Users/xulater/Code/Chat/.vscode/launch.json#L9))。
- 对应的 npm 脚本是 `pnpm dev:debug`([package.json L11](file:///Users/xulater/Code/Chat/package.json#L11)),等价于 `node scripts/dev/start.mjs --debug`。
- 按 F5 即启动该配置。

`start.mjs` 的职责是一个"进程启动器":它先做 preflight(清理同仓库遗留进程、构建 Workflow Bundle、检查版本兼容性),再用 `AppSupervisor` 顺序拉起全部子服务,最后打印 `[chat] ready: http://127.0.0.1:43110/`([start.mjs L48-L49](file:///Users/xulater/Code/Chat/scripts/dev/start.mjs#L48))。这一行 ready 是 `serverReadyAction` 的触发信号。

### 1.2 autoAttachChildProcesses

[launch.json L11](file:///Users/xulater/Code/Chat/.vscode/launch.json#L11) 设置 `"autoAttachChildProcesses": true`。

作用:`AppSupervisor` 会 `spawn` 出 5 个子进程(Web/API/Workflow/memmy/MemoryCore),开启此项后调试器会自动把 Inspector 协议附加到每一个子进程上,于是你可以在 API、Workflow Runtime 两个进程里同时命中断点。就像调试一个会 fork 子进程的程序时,你想让断点在子进程里也生效,就得跟踪所有子进程。

### 1.3 serverReadyAction

[launch.json L15-L29](file:///Users/xulater/Code/Chat/.vscode/launch.json#L15) 定义:

- `pattern` 匹配 stdout 中的 `[chat] ready: http://127.0.0.1:43110/`;
- `action: "startDebugging"`:匹配成功后启动另一个名为 `"Chat：前端浏览器（内部）"` 的 pwa-chrome 配置,自动打开浏览器访问 `http://127.0.0.1:43110/`;
- `killOnServerStop: true`:监督器退出时连带关闭浏览器。

作用:后端 ready 后自动触发一条动作(打开浏览器),不用你手动点。

端口在 [scripts/debug/lib.mjs L25-L33](file:///Users/xulater/Code/Chat/scripts/debug/lib.mjs#L25) 的 `FROZEN_PORTS` 中冻结,全仓库共享:

|------|------|------|

| 43111 | api | Hono 后端 API（公开 + 内部 runtime 路由） |

## 2. 断点策略（核心）

### 2.1 断点命中规则

Workflow 源码经过 SWC 打包成 bundle，再由 Vercel Workflow Runtime 加载执行。打包过程不生成 sourcemap，因此源码与运行代码之间存在"映射断层"。这一点决定了断点能不能命中。

| 代码位置 | 断点是否命中 | 原因 |
|---------|-------------|------|
| `planning-execution-workflow.ts` 中 `"use workflow"` 函数体内 | **不命中** | 被 SWC 打包进 bundle，运行的是 bundle 内联字符串，源码无映射 |
| `workflow-planning-steps.ts` 中 `"use step"` 函数体内 | **不命中** | 同上，step 函数体被序列化进 bundle |
| [packages/workflows/src/api-client.ts](file:///Users/xulater/Code/Chat/packages/workflows/src/api-client.ts)（`external` 模块） | **命中** | 非 step/workflow 模块，由 tsx 直接执行，保留源码位置 |
| `packages/workflows/.workflow-bundle/workflows.mjs` | **命中** | 实际执行的代码，但无源码映射，断点只能打在生成代码行上 |

### 2.2 用 C++ 编译链接理解

用 C++ 经验理解会非常清楚:你的 `.c` 源码经过 `gcc -c` 编译、`ld` 链接成可执行文件后,如果你在 `.c` 源码某行设断点但可执行文件里没有调试信息(没加 `-g`、没有 sourcemap),调试器找不到源码行和机器码地址的对应关系,断点就不会触发。你只能在反汇编上设断点,或者用 `printf` 观察副作用。

Chat 的情况完全对应:

- 源码 ≈ `planning-execution-workflow.ts` 中的 `"use workflow"` 函数体;
- 编译链接产物 ≈ bundle 内的 `workflowCode` 字符串([workflows.mjs L5](file:///Users/xulater/Code/Chat/packages/workflows/.workflow-bundle/workflows.mjs#L5));
- `printf` 观察副作用 ≈ `api-client.ts` 的方法调用——每个 step 都会调用它发 HTTP 回后端,于是它成了观察工作流执行的侧信道。

### 2.3 断点不命中的根因

[planning-execution-workflow.ts L95](file:///Users/xulater/Code/Chat/packages/workflows/src/planning-execution-workflow.ts#L95) 的 `"use workflow";` 是 Vercel Workflow 的编译指示，标记该函数体将被序列化为可重放的耐久代码。[workflow-planning-steps.ts](file:///Users/xulater/Code/Chat/packages/workflows/src/workflow-planning-steps.ts) 中每个 `"use step";`（如 [L72](file:///Users/xulater/Code/Chat/packages/workflows/src/workflow-planning-steps.ts#L72)、[L119](file:///Users/xulater/Code/Chat/packages/workflows/src/workflow-planning-steps.ts#L119)、[L164](file:///Users/xulater/Code/Chat/packages/workflows/src/workflow-planning-steps.ts#L164)、[L223](file:///Users/xulater/Code/Chat/packages/workflows/src/workflow-planning-steps.ts#L223)、[L378](file:///Users/xulater/Code/Chat/packages/workflows/src/workflow-planning-steps.ts#L378)、[L423](file:///Users/xulater/Code/Chat/packages/workflows/src/workflow-planning-steps.ts#L423)、[L460](file:///Users/xulater/Code/Chat/packages/workflows/src/workflow-planning-steps.ts#L460)、[L528](file:///Users/xulater/Code/Chat/packages/workflows/src/workflow-planning-steps.ts#L528)、[L535](file:///Users/xulater/Code/Chat/packages/workflows/src/workflow-planning-steps.ts#L535)、[L722](file:///Users/xulater/Code/Chat/packages/workflows/src/workflow-planning-steps.ts#L722)、[L738](file:///Users/xulater/Code/Chat/packages/workflows/src/workflow-planning-steps.ts#L738)）同理。

打包产物 [workflows.mjs](file:///Users/xulater/Code/Chat/packages/workflows/.workflow-bundle/workflows.mjs) 顶部声明 `// biome-ignore-all lint: generated file`，把所有 step/workflow 源码内联成字符串常量 `workflowCode`，再交给 `workflow/runtime` 的 `workflowEntrypoint` 编译执行。源码行号信息在这一步丢失。

### 2.4 推荐策略

把断点打在 [api-client.ts](file:///Users/xulater/Code/Chat/packages/workflows/src/api-client.ts) 的方法里——它是 `external` 模块（被 `import` 进 step 函数体，而非被序列化），由 tsx 直接执行，源码位置完整保留。每个 step 在执行时都会调用这里的方法回后端，于是你可以把 `api-client.ts` 当成工作流执行的探针集合。

通用传输函数 `call` 在 [api-client.ts L112](file:///Users/xulater/Code/Chat/packages/workflows/src/api-client.ts#L112)，它在 `fetch` 前后做 Zod 校验与错误分类。如果你想观察所有出站请求，在 [L121](file:///Users/xulater/Code/Chat/packages/workflows/src/api-client.ts#L121)（`fetch` 调用处）打断点是最广角的位置。

## 4. Trace 系统使用

### 4.1 文件位置与切分

Trace 文件按 UTC 日期切分，命名规则在 [packages/realtime/src/trace-paths.ts](file:///Users/xulater/Code/Chat/packages/realtime/src/trace-paths.ts)：

- 目录解析顺序：显式参数 > `CHAT_TRACE_DIR` 环境变量 > 仓库根 `.data/traces`（[L24-L28](file:///Users/xulater/Code/Chat/packages/realtime/src/trace-paths.ts#L24)）。
- 文件名：`chat-trace-YYYY-MM-DD.jsonl`，日期取 `date.toISOString().slice(0, 10)`，即 UTC 日期（[L31-L33](file:///Users/xulater/Code/Chat/packages/realtime/src/trace-paths.ts#L31)）。

实际路径：`.data/traces/chat-trace-YYYY-MM-DD.jsonl`。`.data/` 已在 `.gitignore` 中排除。

### 4.2 写入语义

[trace-sink.ts](file:///Users/xulater/Code/Chat/packages/realtime/src/trace-sink.ts) 的 `emit`（[L42-L51](file:///Users/xulater/Code/Chat/packages/realtime/src/trace-sink.ts#L42)）：

1. 先用 `traceEventSchema.parse` 做严格判别联合校验；
2. 校验通过后 `appendFileSync` 追加一行 JSON；
3. 校验失败抛错（编程错误），不产生半行写入。

这就是往日志文件追加写一行事件，按时间顺序、不阻塞生产者。区别只在于:这是一份按天切分、追加写的文件,程序往里 `append` 一行就返回,不关心谁在读。

### 4.3 事件结构

事件合同在 [packages/contracts/src/trace.ts](file:///Users/xulater/Code/Chat/packages/contracts/src/trace.ts)，是 `z.discriminatedUnion("eventName", [...])` 判别联合（[L1425](file:///Users/xulater/Code/Chat/packages/contracts/src/trace.ts#L1425)）。

公共字段（[L338-L346](file:///Users/xulater/Code/Chat/packages/contracts/src/trace.ts#L338)）：

```
schemaVersion  Trace 合同版本，当前为 1（L56）
eventId        evt_ 前缀的 UUID
timestamp      ISO 8601
level          debug | info | warn | error
traceId        同一次请求/Run 共享
spanId         当前事件 span
parentSpanId   可选，父 span
eventName      判别字段
outcome        success | failure | rejected | unknown
```

不同事件族还携带强制的关联字段：

- Product Run 事件族：必须有 `productRunId`（[L313-L316](file:///Users/xulater/Code/Chat/packages/contracts/src/trace.ts#L313)）。
- Workflow 事件族：必须有 `productRunId + attemptId + workflowDefinitionVersion`（[L319-L322](file:///Users/xulater/Code/Chat/packages/contracts/src/trace.ts#L319)）。
- Provider/pi 事件族：必须再加 `promptTemplateVersion + modelConfigVersion`（[L325-L329](file:///Users/xulater/Code/Chat/packages/contracts/src/trace.ts#L325)）。

> Trace **只保存可观察事件和证据**，不保存模型隐藏推理、用户正文、Prompt 或 Provider 响应正文。正文只存在 Product Store，Trace 通过 `对象ID + revision + sha256` 引用（[trace.ts L37-L54](file:///Users/xulater/Code/Chat/packages/contracts/src/trace.ts#L37)）。这与 AGENTS.md §6.6 一致。

## 6. Workflow Checkpoint 查看

### 6.1 目录结构

Workflow Runtime 把 checkpoint 写在 [.data/workflow/](file:///Users/xulater/Code/Chat/.data/workflow) 下：

```
.data/workflow/
├── version.txt              # Workflow Runtime 版本
├── runs/                    # 每个 Workflow Run 的状态
│   └── wrun_xxx.json
├── events/                  # 每个 step/event 的 checkpoint 事件
│   └── wrun_xxx-evnt_yyy.json
├── steps/                   # 每个 step 的执行结果
│   └── wrun_xxx-step_zzz.json
└── .locks/                  # 并发锁
    ├── steps/               # step terminal 锁
    │   └── wrun_xxx-step_zzz.terminal
    ├── hooks/               # hook disposed 锁
    │   └── hook_xxx.disposed
    └── waits/               # wait completed 锁
        └── wrun_xxx-wait_www.completed
```

### 6.2 Run 状态文件

[runs/wrun_xxx.json](file:///Users/xulater/Code/Chat/.data/workflow/runs/wrun_01KZP1SVMAP1XRV0WT1A3N2GVP.json) 的关键字段：

- `runId` / `workflowName` / `specVersion` - Run 身份与 Workflow 定义版本
- `status` - `running` / `completed` / `failed` / `suspended` 等
- `input` / `output` - Uint8Array 编码的序列化输入输出
- `createdAt` / `startedAt` / `completedAt` / `updatedAt` - 生命周期时间戳

### 6.3 存档语义

这相当于游戏存档:每个 step 的 checkpoint 是该 step 完成时的"状态快照",Runtime 重放时直接返回缓存结果而不重新执行。`.locks/` 下的 `.terminal` / `.disposed` / `.completed` 文件是用"文件在不在"来当锁,防止 step 被重复执行或 hook 被重复恢复——比内存里的锁更持久,进程重启了文件还在。

## 8. 常见问题排查

### 8.1 Run 卡在 queued

**症状**：Product Store 里 Run 状态长时间停在 `queued`。

**原因**：
1. Workflow Runtime 进程没启动——检查 43112 端口与健康检查；
2. 断点暂停了 Workflow 进程——检查 VS Code 断点列表，是否有断点命中后未继续；
3. Bundle 未构建或版本不兼容——`start.mjs` 启动时会构建并检查，若手动绕过会出问题。

### 8.2 断点不命中

**症状**：在 `planning-execution-workflow.ts` 或 `workflow-planning-steps.ts` 里打断点，Run 执行时不停。

**原因**：见 §2。`"use workflow"` / `"use step"` 函数体被 SWC 打包进 bundle，源码行号无映射。

**对策**：把断点改打在 [api-client.ts](file:///Users/xulater/Code/Chat/packages/workflows/src/api-client.ts) 对应方法上（见 §3 断点地图）。

### 8.3 commandId 报错

**症状**：API 返回 `command_id.invalid` 或类似错误。

**原因**：`commandId` 不匹配 `^cmd_[A-Za-z0-9]+$`（[ids.ts L14](file:///Users/xulater/Code/Chat/packages/contracts/src/ids.ts#L14)）。

**对策**：去掉下划线、连字符等非法字符。注意 `cmd_` 后面的部分不能再有下划线。

### 8.4 模型调用失败

**症状**：`provider.request.failed` 事件，错误码 `provider.pre_request.*` 或 HTTP 5xx。

**原因**：检查 `.env` 中的 `DASHSCOPE_API_KEY` 与 `DASHSCOPE_BASE_URL`。Provider 固定为 bailian，模型固定为 `qwen3.7-plus`（[trace.ts L290-L291](file:///Users/xulater/Code/Chat/packages/contracts/src/trace.ts#L290)）。

**对策**：
```bash
# 检查环境变量是否加载（不打印值，只看是否存在）
node -e 'console.log(typeof process.env.DASHSCOPE_API_KEY, typeof process.env.DASHSCOPE_BASE_URL)'
```

### 8.5 Run 状态 outcome_unknown

**症状**：Run 进入 `outcome_unknown` 状态。

**原因**：网络未知错误（[api-client.ts L130-L135](file:///Users/xulater/Code/Chat/packages/workflows/src/api-client.ts#L130) 的 `dispatch.outcome_unknown`）。这是设计语义，不是 bug--外部副作用结果未知时不能假成功也不能假失败，留给人工对账。

**对策**：检查后端 API（43111）与 Workflow Runtime（43112）是否都在运行；检查 Trace 中该 Run 的最后几个事件；检查 Outbox 是否有待对账项。

### 8.6 重放时断点重复命中

**症状**：Run 恢复执行时，之前命中过的断点又命中了一次。

**原因**：这是**正常行为**。Workflow Runtime 重放时，已完成的 step 会从 checkpoint 返回缓存结果，但 `api-client.ts` 的方法调用仍会被执行（因为它是 `external` 模块，不在序列化范围内）。区分首次执行与重放：查看 Trace 中的 `workflow.step.replayed` 事件（[trace.ts L1116-L1125](file:///Users/xulater/Code/Chat/packages/contracts/src/trace.ts#L1116)），或在断点条件里检查调用栈。

## 9. 调试操作快捷键

VS Code 调试器快捷键:

| 快捷键 | 作用 | 说明 |
|--------|------|------|
| F5 | Continue | 继续执行到下一个断点 |
| F10 | Step Over | 单步，不进入函数体 |
| F11 | Step Into | 进入函数体（如进入 `call` 函数） |
| Shift+F11 | Step Out | 从当前函数跳出 |
| F9 | Toggle Breakpoint | 切换当前行断点 |

> Logpoint（日志断点）：在某行不打断执行，只输出一条日志。适合"不想暂停、只想看变量值"的场景。

### 9.1 实战建议

1. **先打 logpoint，再打条件断点**：在 [api-client.ts L121](file:///Users/xulater/Code/Chat/packages/workflows/src/api-client.ts#L121)（`fetch` 调用处）打 logpoint，输出 `path` 与 `input.commandId`，观察工作流执行轨迹，再针对性打条件断点。

2. **用 `productRunId` 做断点条件**：在 `call` 函数里打条件断点 `input.productRunId === "run_xxx"`，只跟踪目标 Run。

3. **同时观察三个数据源**：断点暂停时，同时看（a）VS Code 调用栈与变量，（b）Trace 文件中该 Run 的事件序列，（c）Product Store 中该 Run 的状态——三者交叉验证。

4. **Inspector 端口附加**：若 autoAttach 没生效，可以用 Chrome 打开 `chrome://inspect`，配置 `127.0.0.1:43120`（API）或 `127.0.0.1:43121`（Workflow）手动附加。

5. **重放调试**：Workflow Runtime 重放时不会重新执行模型调用（付费路径），但会重新执行 `external` 模块代码。这意味着你可以在重放时安全地打断点观察 step 输入输出，而不会产生新的 Provider 费用。
