# Agent 工程治理的理论基础与抽取方法

> 版本：`agent-governance-basis.v0.6`。本文件只解释经验为什么可能生效、怎样判断来源强度和何时删除；
> 规范正文见[标准](./standards.md)，当前精选经验见[标杆目录](./exemplars/README.md)。

## 1. 从文字到实际约束

```text
来源证据
→ 针对一个明确失败模式提炼经验
→ 在相关决策前选择并呈现
→ Agent产生候选方案或变更
→ 脚本、测试或检查Sub-agent比较候选与Oracle
→ 集成者或受保护门决定是否采用
→ 记录误报、漏报和成本，更新或删除经验
```

Prompt、Skill 和 Workflow 只是载体。真正效果取决于以下机制是否成立：

| 机制 | 可能生效的原因 | 常见失效 |
|---|---|---|
| 相关时点呈现 | 降低遗漏和上下文搜索成本 | 全量常驻导致过载；触发太晚 |
| 能力与写入隔离 | 让一部分错误动作不可达，缩小破坏半径 | 权限过宽；写集合仍相交；存在旁路 |
| 确定性 Oracle | 对有限、重复的约束给出稳定反馈 | 检查偶然形状；Fixture绕过生产路径 |
| 独立检查与采用 | 避免实现者直接把自身结论写成事实 | Reviewer复述摘要；采用权没有分离 |
| 版本与来源冻结 | 让本次实际使用内容可重现 | 来源漂移；旧证据证明新版本 |

“Agent 看到了规则”只证明信息送达；“检查器执行了”只证明产生了结果。只有有效结果进入采用门，才形成更强约束。

## 2. 证据强度

| 证据 | 可以证明 | 不能证明 |
|---|---|---|
| 固定 Commit 的源码/测试/配置 | 项目确实实现了该机制 | 机制长期有效或适合 Chat |
| 固定版本的维护者文档 | 维护者明确要求或解释这样做 | 要求已被所有贡献者遵守 |
| 测试或 CI 定义 | 存在可重复 Oracle | 它一定是受保护合入门 |
| 浮动产品文档 | 当前公开行为或建议 | 与某个 OSS Commit 一一对应 |
| 底层因果推论 | 为什么机制可能减少状态空间或漏检 | 实际净收益和因果效果 |

多个测试、Fork 与上游、同组织项目或同模型 Reviewer 不能机械折算为独立票数。采用判断同时考虑：来源独立性、
机制是否一致、失败与维护反证、目标项目适用性以及是否存在更直接的项目合同。用户授权和产品不变量不需要外部项目投票。

## 3. 抽取与删除门

抽取一条经验时必须依次回答：

1. 它要阻止的具体失败是什么？
2. 在什么任务和决策时点才有帮助？
3. Agent需要做什么，检查Sub-agent或脚本怎样判断？
4. 哪些固定来源证明项目确实这样做？哪些只是维护者主张或我们的推论？
5. 什么条件下它会误导、失效或不值得维护？
6. 是否已被更强来源或更短条目覆盖？

以下内容不进入常用目录或运行 Prompt：

- 只有口号、名气、Star 或未来承诺，没有可定位实践；
- 只适用于来源项目的组织、版本或社区政策；
- 不能改变方案、架构、代码、验证或协作决定；
- 与现有条目同义，只增加措辞和 Token；
- 没有适用场景、失效条件或检查方式；
- 已长期低触发、高误报或被项目硬合同替代。

治理资产同样受变更预算约束。新来源先更新固定项目附录，再由独立复核决定是否修改精选目录、规范或运行提示词；
不能在实现任务中顺手抬高标准，也不能用同一次实现静默放宽检查器。

## 4. 首次受控行为验证

2026-08-25 对两个可选组件做了一次真实 Sub-agent A/B 验证。问题不是“Agent 是否读过文字”，而是同一工程任务的最终行为是否更好。

### 4.1 条件

- 两组使用同一基线、任务、`gpt-5.6-terra`、推理强度、工具和不提交约束，并在隔离 Worktree 中实现。
- 对照组 A 只收到任务；实验组 B 先读取[方案、架构与代码变更](../../prompts/fragments/rules/controlled-project-change.md)和[工程验证与交付证据](../../prompts/fragments/requirements/engineering-evidence.md)。两组不能读取彼此实现或隐藏 Oracle。
- 任务是在无依赖 Node.js 项目中增加持久化 `TaskStore`，同时保持内存实现合同，覆盖原子更新、并发 Revision、损坏数据失败关闭、共享合同测试和交付证据。
- 完成后先运行预注册的公开测试与 13 项隐藏 Oracle，再由不知道分组身份的 `gpt-5.5` Reviewer 按 12 分量表审查最终源码、测试和证据。

### 4.2 结果

| 证据 | 对照组 A | 实验组 B |
|---|---:|---:|
| 公开测试 | 9/9 通过 | 7/7 通过 |
| 隐藏 Oracle | 13/13 通过 | 13/13 通过 |
| 新依赖、Diff 检查 | 0、通过 | 0、通过 |
| 匿名评审 | 8.1/12 | **10.4/12** |
| 相对基线净增行数 | 291 | **211** |

两组都通过预注册门，因此“测试绿”本身没有区分质量。源码审查后对两组运行了完全相同、明确标为事后诊断的两个探针：

1. 已打开的第二个句柄能否读到第一个句柄刚提交的状态：A 返回旧快照，B 通过。
2. `/dir/tasks.json` 与 `/dir/./tasks.json` 指向同一文件时，两次相同 Revision 的并发更新是否仍只有一次成功：A 两次都成功，B 通过。

B 将路径规范化，以持久文件作为读取事实源，共用校验与复制规则，写入临时文件后先同步再替换，并主动报告“没有跨进程文件锁”的剩余风险。这些行为与组件要求的事实所有权、共享合同、真实失败验证和诚实交付一致。A 的测试清理更完整；B 仍有队列键未回收、测试临时目录未清理、目录未 `fsync`，两组也都没有证明跨进程并发和掉电耐久。

### 4.3 采用判断

这次结果已经达到当前阶段的采用门：在目标场景中，加载两个相关组件的 Sub-agent 产出了更小且更稳健的实现，通过全部预注册检查，并在匿名审查和两个针对性行为探针中明确优于对照组。因此，这两个组件已经完成真实验证，可以正式用于 Codex、Chat Direct Agent 和相关 Workflow 节点。

它们保持“按场景选择”，原因是不同任务需要不同规则，而不是验证不足；文字组件也不冒充权限、Schema 或确定性测试等机器强制门。样本范围只限定结论的适用边界，不推翻本次已经验证的结果：本次没有声称每个未来任务都必然提高分数，也没有测量长期 Token 成本。

后续在自然出现的其他任务中继续记录效果，属于持续优化而不是补当前欠账。此次临时 Fixture 不进入仓库，避免为一次已经完成的采用验证建设常驻 Benchmark 平台。
