# 主题模式纠偏方案：审核后创建与完整会话

日期：2026-09-25。状态：**M1–M3 已收口；完整门禁、扩展浏览器链及真实模型 4 个场景均通过，结果与预览见收口报告。**

本轮目标是完成可正常使用的主题模式：Long Agent 整理上下文，用户审核后创建；进入任何节点后都能像普通 Session 一样工作。它不是主题管理表单加一个简化输入框。

## 0. 执行进度检查点（2026-09-25 收口）

### M1 完整会话接入

- 节点挂载公共 `ChatWindow`，发送保留节点授权入口，读取/流式/停止/草稿沿用公共机制。新节点身份来自服务端解析的 `topicNode`，不依赖首轮后才出现的旧 owner 索引。
- `work → remember` 共用执行引用与单调事件；反馈包含真实 `roundPhase`，主答案先显示，记忆处理期间可停止。公共 Session read 从耐久节点 turn 恢复 `friendExecution`，刷新后仍可观察、停止同一轮次，不重新发送正文。
- 最终答案选择排除 writer 的记忆回执，记忆过程留在可展开的过程区。下一轮 running 标记清除上一轮阶段标签，避免把新工作答案误当记忆回执。
- 输入能力读取由共享 Agent/Model Resolver 决定；无参数的 capabilities GET 返回输入能力，带 sessionId/turnId 时保留既有轮次能力审计。窄屏停止按钮直接可见。

## 2. 用户流程：创建主题 Session

```text
用户向 Long Agent 描述问题／点击新建／从已完成轮次分叉
  → 启动 topic-session-create Workflow
  → 整理 Agent：搜集相关全文、记忆与项目事实，形成上下文草稿
  → 用户审核：批准创建／提交修改意见／取消
       修改 → 同一整理 Agent 修订 → 新版本审核（可反复）
       批准 → 创建 Agent 调用受控创建工具
  → Backend 创建主题节点 Session、初始摘要/记忆、图与来源
  → 返回真实产物与“进入会话”入口
  → 用户在公共聊天界面连续工作
```

### 2.1 三个可见节点与职责

新增 `src/workflows/topic-session-create/`，manifest 声明 `agentCallable: true`、`planReview: true`，节点固定为 `collect(agent) → review(task) → create(agent)`。使用标准 Workflow/Step、注册与公共装配。

1. **整理 Agent**：读取获授权的会话记忆和全文，整理已有事实、当前问题、目标、约束、相关项目、来源以及未确定事项。根节点与分叉使用同一流程，分叉带服务器核验的父节点/轮次锚点。它可以查询但没有创建目标节点、修改来源记忆或代替用户批准的能力。
2. **用户审核**：复用现有 `planReviewDecisionHook`、版本引用、审核 API、Session 记录及审核卡片。展示的是有完整含义的上下文，不只是一句标题。用户反馈作为原生消息进入同一整理 Agent 的修订回合。信息不足时可询问并修订；未经真实用户批准不能进入创建节点。
3. **创建 Agent**：读取已批准版本，调用受控提交工具并说明工具返回的创建结果。它负责完成实际动作，不再任意改写批准内容；不能只回复“已创建”就结束成功。Step 结束时由 Backend 核对目标 Session、节点、摘要与来源确已落地。

### 2.2 审核内容与版本

一个草稿包含：名称、问题/目标、整合摘要、约束与待办、拟冻结的协作 Project（含明确无项目）、来源引用、初始记忆、根/分叉类型与父锚点。按当前能力可没有初始记忆，但必须解释无可引用条目的事实，不能伪造来源。

结构化草稿和可读预览必须来自同一版本。复用审核的 `reviewId + revision + hash` 绑定；批准指向该版结构化内容。创建工具从服务端读取批准产物，不让模型重新提交一套 title/summary/project/source 来替代它。涉及正文、来源、目标项目或父锚点的实质修改必须回到审核；创建时发现权限或来源失效则清楚失败并引导修订，不静默换内容。

存储复用准备 Session 的原生消息/CustomEntry 与现有 Workflow Run 窄记录，不再新建独立“审批数据库”。不要把模型参数中的 `approved:true` 或 `confirmedBy:"user"` 当成这次 Workflow 审核凭证。

审核卡片在此显示“主题上下文”和“批准并创建”；展示名取 Workflow 节点/审核元数据或公共组件参数，不在 ChatWindow 复制一套 `if workflowId` 专用审核实现。旧 planning-execution/planner-orchestrator 的计划审核行为必须保持可用。

### 2.3 两个 Session 的边界

- **准备 Session**：Workflow 的独立执行会话，保存搜集、草稿、用户反馈和审核，刷新可恢复；属于发起 Long Agent 的 home。等待人时由耐久 Hook 挂起，不占着日常会话的写锁，也不让父模型不停调用 wait。
- **目标 Session**：用户批准后新建的主题节点会话，属于同一 Long Agent home。只带已批准的整合上下文及明确来源；不自动复制整个准备会话或所有历史。其主题父子关系仍由 Chat DAG 表达，不能把 Workflow 子会话的 Pi parentSession 当作主题边。
- 审核时可以预留操作 ID，但不能把未创建的目标显示成可进入的 Session。取消审核保留准备记录，不创建主题壳或目标节点。

### 2.4 单一发起链与可信目标

落地一个窄的 `startTopicSessionCreation` 领域启动入口，复用现有 `callChatWorkflow` / `startChatWorkflow` 派发、子会话关系、Run 和事件机制。所有入口解析后都到这里：

- Long Agent 的 `topic_manage.request_topic` 改为薄启动适配器，实际运行 `topic-session-create`；保留名称是为了兼容，不再启动 `startFriendWork` 做建题。
- 新建按钮、分叉按钮、现有 integrations POST 也调用同一入口；返回 Workflow 执行/审核引用，最终才返回目标节点。
- 若从通用 `workflow_call` 选择该 Workflow，也必须经过同一可信目标解析，不能因为另一入口而丢失审核或来源绑定。

当前 `workflow_call` 默认以协作 Project 为子 Run 的存储项目，无项目时拒绝；它不能原样套用到本流程。**本流程是 Long Agent 自有主题管理操作，准备 Run 明确落在该 Agent home；拟冻结的业务 Project 是待审核内容，两者分开。** 在公共派发前做这一窄目标适配，其他业务 Workflow 的项目派发与显式 null 拒绝合同保持原样。不得把这个例外变成所有 Workflow 都可回退 home。

发起 Agent、来源 Session/Turn、操作 ID、home 与调用关系都由 Backend 从可信上下文解析。工具模型参数不能指定任意 owner、存储项目或审批身份。Workflow 内只获得“本次读取/批准后提交”的窄授权，不通过设置 `longAgentId = 任意 projectId` 伪造权限，也不复制整套 Long Agent 身份配置。

这份可信创建绑定作为后端内部、可序列化的 invocation 输入传到 Step 与工具上下文，并随现有 Run/Session 事实恢复；不能只放进进程内 Map。普通 HTTP/模型的自填同名字段须拒绝。准备 Session 的可读来源与目标 Session 的可写权限分开，已有 `sessionMemoryTarget` 继承不能使整理 Agent 获得修改来源记忆的权限。新增 Agent Step 沿用本仓库 `maxRetries = 0` 的显式策略，业务重试复用同一批准操作标识，而非盲目重跑模型与副作用。

创建 Workflow 等待审核时，父对话返回可操作的审核入口；用户可继续日常交流。若既有 workflow_call 的结果只表达 running，补充其已有 review 进度投影，让调用者区分等待人和执行中；不新增模型轮询器。

## 3. Backend：保留领域能力，收敛编排与工具合同

### 3.1 已有能力如何处理

| 现有部分 | 处理 |
|---|---|
| 主题图、节点身份、来源解析、锚点、防环、CAS、会话生命周期 | 保留，继续由既有领域服务拥有，Workflow 不重写这些判断 |
| `createTopicNodeWithSession` 等创建服务 | 复用，并增加批准产物的提交编排；调用方不自行拼写 Session 文件 |
| `startTopicIntegration → startFriendWork` 建题 | 新请求替换为审核 Workflow；历史 work/节点继续可读，不删数据、不重放旧请求 |
| `topic_manage` 的直接创建操作 | 新用户建题路径受服务端批准绑定约束，其他模型入口不能绕过；不能只靠 prompt 说“请先审核” |
| 节点耐久接受、Turn 绑定、已有执行队列与 relay 意图 | 保留；主题是 Session 类型与上下文组织，不另建调度器 |
| 节点会话页面的自行轮询与临时状态 | 替换为公共会话控制器及事件恢复机制 |

### 3.2 创建提交

创建 Agent 通过现有工具体系调用一个绑定本次批准版本的提交动作（可为 `topic_manage.commit_creation`）。模型无需也无权再填批准正文；工具从可信 invocation 和审核记录解析它。

提交复用节点创建的操作 ID、来源核验、Session 锁与图 CAS。根主题和根节点在最终图登记时一致发布，部分创建不能被查询为 completed；跨 Session/记忆/图的持久化沿用可恢复操作，不伪称多文件天然原子。同批准动作重试复用产物，冲突给明确错误，不遗留“成功但无根节点”。

来源语义继续分开：会话记忆引用为 smem 条目，全文引用为原生会话条目，锚点为已完成用户轮次。批准或创建都不能把三类地址混用。

旧 integrations GET 按持久记录类型解析 legacy work 或新 Workflow 引用，统一给用户可理解的状态；旧请求重放查询既有产物，不能偷偷转成另一个新建题流程。

### 3.3 节点里继续工作

节点发送仍由图解析真实 Session，保留接受与耐久队列。工作 Agent、记忆 Agent 继续用公共 Pi 装配；本批不为修 UI 推倒已有队列，也不另起一个创建 Workflow 包裹每条聊天消息。

**已有取舍必须继续说清楚**：当前节点 `work → remember` 是队列顺序编排，不是 Workflow SDK Run；前端展示其真实阶段，不能伪造 Run/Step ID。新建题必须是真实 Workflow Run。原本的 `session-memory` Workflow 定义与 writer 共用实现保留，不能复制另一套 writer。若以后迁移节点轮次载体，另作明确迁移，本批不得以此阻塞完整会话交付。

整轮 live execution 覆盖两个阶段：阶段切换更换当前 Pi session 句柄，沿用同一执行引用与单调事件序列；主答案出现即正常展示，remember 继续显示真实状态。取消必须传给当前活跃 Agent，并在阶段切换/整轮完成前核对取消意图。remember 未终态不得分叉。

记忆是普通工具调用：`purpose` 的模型 Schema 由领域层同一份白名单生成枚举，说明语义；错误返回允许值。不要增加分类 Agent 或重试系统。writer 可 list/history 按需读取，write/supersede 写有价值事实，无可写内容可以正常结束。工作答案和记忆记录均持久保留，但记忆过程默认折叠，不取代主回答。

节点消息 HTTP 接入现有文本/图片合同和有效模型能力，不再文本专用缩水；图与授权仍由后端解析。无项目节点明确显示“无协作项目”；有项目按批准值冻结。节点内不能随顶栏切项目，需换项目则整理并创建新节点。

## 4. Frontend：完整会话是主页面

### 4.1 信息结构

```text
全局导航 | 主题与节点导航 | 中央会话                      | 按需打开资料
         | 主题 A        | 节点标题 · 所属主题 · 固定项目 | 记忆／来源
         |   根节点      | 用户消息                      | 主题关系图
         |   └ 分支 B    | Agent 答案、工具、工作过程     | 节点资料
         | 主题 C        | 当前阶段/停止                 |
         |               | 公共多行输入框与附件          |
```

中央复用 `ChatWindow`、`useAgentSession`、`MessageView`、`RunStatus`、公共输入/草稿/滚动机制。为公共控制器增加 topicNode 目标适配；适配层只承担定位、接受、读取、订阅和能力差异。发送必须走节点入口，不能误走每日会话或直接绕过节点轮次执行链。

`LongAgentTopicsView/Panel` 收敛为主题/节点导航与辅助面板，不再拥有第二个聊天循环。保留原组件名称与否不是验收依据，完整行为与公共机制才是。

### 4.2 每个主要动作应如何呈现

| 用户动作 | 必须看到的行为 |
|---|---|
| 发起新建 | 打开准备会话，看到搜集信息、工具过程与整理结果；使用现有 Workflow 过程视图 |
| 审核 | 正文展示完整上下文，提供“批准并创建”“提出修改”和取消；修改可多轮；等待状态不假装模型仍在运算 |
| 创建完成 | 明确的创建结果卡片与“进入会话”，真实 Session 链接；不展示预留 ID 假装可进入 |
| 打开已有节点 | 中央立即读回历史；项目、身份、标题明确；不会先铺一页管理表单 |
| 聊天 | 受理后看到自己的消息、流式回答和工具进展；多行输入、附件按能力、停止、失败提示、草稿与刷新恢复同普通 Session |
| 分叉 | 在已完成轮次的消息操作处“从此分叉”，带用户选中的锚点进入同一整理/审核/创建流程；父会话保持原样 |
| 查看图 | 左侧有可读的层级/关系导航；多父边如实展示；需要全图时展开辅助图视图，不让大图挤占日常聊天 |
| 查看/改记忆 | 工具栏打开抽屉/资料面板，分类使用中文名称；编辑沿用 CAS，冲突保留草稿；关闭回到聊天 |
| 补充整合 | 在节点操作中打开已有功能的抽屉/对话框，展示来源与目标、预览产物，再由用户确认；不要常驻“R4”技术表单 |
| relay | 在目标会话中显示来源徽章与普通用户轮次，执行反馈沿用公共会话；无另一个 relay 聊天窗口 |

本轮新增的多轮审核循环明确适用于根节点和分叉创建。补充整合保留既有“预览后用户确认”合同，不擅自再扩一个补充整合 Workflow。UI 不向用户暴露 R4、CAS、schema、raw turnId 等实现术语；技术 ID 放可展开详情。

### 4.3 视觉与交互的可检验标准

数值直接沿用 UI/UX 规范 §15，不另造页面样式：桌面导航 64px，列表默认 280px（224–360），中央最小宽 480px；资料默认折叠。顶栏 48px，消息正文 16px/27px，输入 16px/24px，正文内容列上限 880px。宽度不足先收辅助资料和列表；Compact 单主任务面。

- 会话填满可用高度，消息区独立滚动，输入锚定底部；移除管理面板的 520px/消息 280px 硬上限及使消息归零的收缩关系。
- 使用既有语义 Token、图标、按钮、Dialog/Sheet、字体与间距；减少重复标题、粗边框和整屏表单。
- 初次进入和新活动跟随最新消息；阅读历史时普通刷新不抢滚动；输入不随页面整体上下跑。
- waiting review、运行中、停止中、断线/未知、失败、完成分别真实呈现；读取消息不依赖记忆/锚点接口同时成功。
- 按 Session 隔离草稿与订阅，切节点取消旧观察、忽略旧响应；重新进入从服务端恢复当前执行。
- 390px 窄屏、768px 中屏、1440px 桌面均可完成主链；150%/200% 缩放下正文和输入可见，无页面整体横向滚动；明暗主题清晰，键盘焦点和触控目标遵守既有规范。

## 5. 实施顺序与文件范围

三个工作包属于**同一次完整交付**，按依赖推进；不是每个小修都停下来要求用户再次批准。发现影响主链的新缺陷并入本批；无关重构与极端边界记录到尾项。

| 顺序 | 工作包与具体范围 | 包内证明 |
|---|---|---|
| A | `frontend/hooks/useAgentSession.ts`、公共 ChatWindow/输入/执行适配，topics 导航；`topics-browser` 与节点 messages/feedback/control 接线；修 purpose 与 remember 控制 | 现有节点真实可见地多轮聊天、工具、停止、刷新恢复；不依赖建题流程完成才验证页面 |
| B | `src/workflows/topic-session-create/**` + catalog/registry；`topic-integration.ts` 启动入口替换；公共派发可信绑定、审核复用、批准提交；前端复用审核卡片 | Long Agent 发起 → 审核 → 两次修改 → 批准 → 唯一节点 → 进入 A 的会话；根与 fork |

Backend 的实现前读取 backend/coding/testing 指南与 Long Agent 工程基线；Frontend 读取其 AGENTS、开发指南及 UI/UX 全文。跨模块接口变更同时更新 Parser、相关模块合同与测试。现有文档中“完整 ChatWindow 接入是可选重构”等声明须在实际落地时修正，不能只改文档把当前缺口合理化。

本轮范围不含动态 Workflow 热加载、另一个任务引擎、全局 UI 改版、重写 Pi/NanoClaw 或全部历史数据迁移。
