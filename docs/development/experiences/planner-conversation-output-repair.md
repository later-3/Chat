# Planner续聊中的阶段与输出协议

2026-09-08，审核型Workflow完成一次任务后，用户在同一Session追加修订需求。Planner直接交付修订稿，缺少`chat-planner-output`首行，正文保存后Run报失败。另一项独立问题是Project持久Tool覆盖只选择Memory搜索，取消了默认`read`；默认配置存在工具不等于本轮已启用。

直接失败点是Planner输出解析，不是审核批准或Executor执行。历史角色与任务交接可能影响续聊行为，不能仅凭该模型输出断定唯一心理原因。系统应从机制保证阶段边界和失败恢复。

原有测试覆盖首次规划、审核修订和切回直接执行，但假模型始终返回合法协议；没有覆盖完成一次审核型Workflow后再次进入同一Planner，也没有验证格式错误后的恢复。这使首次成功掩盖了续聊失败。

修复使用公共Workflow装配标明本轮身份；旧内部交接只从模型输入中排除，不删除Pi历史，不裁掉原始对话。规划执行与规划协调共享新轮次Planner提示和一次有界格式修正。修正由CustomMessage触发，原回答保留，工具关闭；模型错误、取消不按格式问题重试。第二次仍失败则保留可见原因，不自动补就绪状态或绕过审核。Project配置通过原有加锁配置服务修复，不能通过全局迁移强加`read`给所有用户。

回归门禁：`scripts/planner-conversation-fixture.mjs`同时接入生产Built Server与Nitro开发链，覆盖两个审核Workflow在同一Session中正常完成、第二轮格式修正、连续格式失败、失败后继续交互；校验新Invocation、批准前无下游执行、修正时无工具、历史消息与JSONL原始行前缀不变。单元测试覆盖公共阶段上下文和不同Workflow之间的旧交接隔离。原有直接执行、Memory、Rule、配置覆盖、人工修订与子Workflow测试继续运行。

2026-09-08验证：225项Backend测试、112项Frontend测试、28项Built Server测试及真实Nitro开发链通过；包含上述连续交互和切换到直接执行、Memory、Rule的回归。生产构建在独立源码快照目录进行，不替换正在运行的服务产物；使用隔离Chat Home和本地假模型。

诊断顺序：按Session与Invocation关联Run日志→核对最后阶段→确认模型是否完成→核对协议错误→通过配置Resolve区分默认能力和实际启用能力。不能让用户反复复制任务书碰运气，也不能只改提示词而不补失败分支测试。原始用户对话、私有配置和日志不提交Git。
