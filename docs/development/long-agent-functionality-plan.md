## 最终目标与范围

同一 Friend 保持身份、Workspace 和能力定义，能够同时日常交流、独立做任务、参与多个群聊；任务和讨论各有隔离的上下文。Workflow 组织执行，所有模型交互仍经公共装配进入 Pi。Web 与渠道读取相同的持久事实，Nano 保留触发、路由和投递职责。

代表性验收：小思持续学习《天道》《道德经》《金刚经》，有资料依据、进度、产物和下一步；每天早/中/晚各发一条站内动态，每晚在自己的 Workspace 写一篇笔记，格式由它选择；这些工作不阻塞用户日常交流。书目是配置和资源，不进入调度器枚举。具体时间、时区、资料授权与受众在配置任务时确定，本计划不自动启用任务或发布内容。

合同只保存在对应模块：[机制与生命周期](../modules/long-agents/chat-long-agent-mechanism-contract.md#9-la0交互任务与调度的实施合同)、[Session 映射](../modules/sessions/chat-session-architecture.md#11-la0独立工作与群聊的原生-session-合同)、[Workflow 接入](../modules/workflows/chat-subworkflow-design.md#la0friend-执行绑定与后台返回目标)。本文件只管理实施顺序与验收，不另定义一份 Schema。

## LA3 用户与 Agent 共同管理的交付清单

2026-09-20 补充确认：以下内容属于 LA3，不延后到 LA6。2026-09-20 已完成实施与验收，技术合同见 [Friend 长期职责](../modules/long-agents/duties.md)，证据见 [LA3 验收](../history/reviews/2026-09-20-long-agent-la3.md)。机制和数据归属沿用[机制合同 §9.4](../modules/long-agents/chat-long-agent-mechanism-contract.md#94-长期职责任务与触发)，本节只明确入口、场景和验收，不另建 Schema 或运行时。

职责管理持续目标，关联任务复用 LA2，单次执行沿用 LA1 的独立 Session 和公共聊天展示。用户在 Friend 现有管理区域查看“长期职责”和“任务”，也可以通过聊天管理；Agent Tool 与 Web 必须调用同一 Backend 服务，不能只在 Prompt、Memory 或浏览器内存维护职责。

| 交付项 | 用户与 Agent 的共同管理行为 | 必须验收 |
|---|---|---|
| 创建与修改 | 表单或自然语言设置目标、材料、项目/授权范围、成果要求、推进节奏、允许时段、预算与提醒偏好；内部 ID 自动生成。Agent 在已授权范围安排下一步，扩大目标或授权边界需用户确认 | Web 创建后 Tool 可查；聊天修改后 Web 可见；信息不足明确缺口；目标修改保留 revision，旧计划不误启动 |
| 进度与查询 | 展示已处理材料/章节/里程碑、成果链接、当前工作、下一步、下次检查时间、阻塞原因与消耗；支持用户纠错及 Agent 更新，保留依据与修改历史 | 三项学习职责各自推进；引用真实存在；有明确总量才显示百分比，不将模型自评当掌握程度；刷新和重启可恢复 |
| 推进与生命周期 | 支持立即推进一次、暂停、恢复、结束职责；暂停阻止未来自动推进，已接受任务提供独立停止入口；完成子任务不自动结束职责 | 手动与自动触发去重；暂停/结束不继续派发；在途与迟到结果按冻结版本处理；主聊始终可继续 |
| 心跳与等待 | 用户配置工作节奏而非底层心跳参数；展示本次推进或未推进的原因。无变化不制造模型调用、空 Session、动态或通知 | 缺资料、未到期、预算耗尽、失败和重启均有准确状态与后续动作；只在需要时推进，不以重复同一 Prompt 冒充学习 |
| 双向维护与一致性 | 用户和 Agent 共享权限校验、持久化、修订冲突处理、关联任务与结果查询；沿用前端统一风格和实时更新机制 | 并发修改不静默覆盖；用户暂停后 Tool 和调度器读到同一状态；配置、执行和页面事实一致 |

LA3 完成门槛：以上入口必须在真实浏览器和真实模型下联合验证，并覆盖用户创建→Agent 分解推进→页面查询成果→用户修正/暂停→恢复继续的完整链。自检逐项记录通过、失败或未测及证据；只有后台心跳、只有 Tool 或只有静态管理页均不算完成。笔记/动态可靠发布仍由 LA4 验收，群聊仍由 LA5 验收。

## LA3 执行交接任务书

本节与上方 LA3 交付清单共同作为执行 Agent 的任务输入。目的：让用户和 Friend 共同维护有依据、可暂停、可恢复的长期工作，在不阻塞日常聊天的情况下持续推进；不是增加一个定时重复 Prompt 的按钮。只实施 LA3，不顺带开发 LA4–LA6。

### 开始前恢复上下文

1. 阅读根 `AGENTS.md`、`.chat/skills/chat-architecture/SKILL.md`、[贡献方法](./agent-contribution.md)和本计划。按修改范围继续阅读配置、Backend、编码和测试规范；前端遵守 `frontend/AGENTS.md`；修改 Nano/Pi 前分别阅读其规则。
2. 核对[机制合同 §9](../modules/long-agents/chat-long-agent-mechanism-contract.md#9-la0交互任务与调度的实施合同)、[工程基线](../modules/long-agents/chat-long-agent-engineering-baseline.md)、[LA2 任务合同](../modules/long-agents/tasks.md)和 [LA2 验收](../history/reviews/2026-09-20-long-agent-la2.md)。配置/资源和项目归属沿用公共装配与模块合同，不从旧聊天描述另造规则。
3. LA0–LA2 已完成的依据是当前工作区和验收记录，并不代表已提交或部署。先记录父仓库及各 Submodule 的状态，保留已有改动；独立 checkout 必须包含这些未提交依赖，不能仅检出父仓库旧 Commit 就认为具备 LA2。
4. 测试使用独立 `CHAT_HOME`、Nano 数据和端口。不要覆盖常驻服务构建、停正式进程、发布动态、提交或部署。旧 `36145` 演示页不是生产验收入口；重新确认实际启动链。LA2 临时验收服务已清理，需按文档重新启动。

这是接入方向，不指定必须复用某个内部函数。实施者先核对真实签名和边界，避免为复用强行耦合。具体字段、端点、存储版本和 UI 组织由实施者在既有边界内设计，并同步权威模块文档，不另建第二套 Agent Runtime。

### 编码前必须落实的技术细节

先在职责所属模块文档形成短技术合同，再编码；普通实现选择不必逐项请求用户确认。下面每项必须有明确答案，不能留到验收时补猜测：

- 区分职责启停/结束与等待资料、预算不足、执行失败等推进条件；定义结束后恢复或另建的语义，保留历史。
- 职责、目标 revision、下一步、Task、Occurrence、work/turn、进度证据之间用稳定 ID 关联；定义推进键和进度提交去重键。任务创建或结果提交中途崩溃后可恢复，不能重复派发或重复累计进度。
- 明确允许时段/时区、预算单位与周期、计量来源、检查时机及未知消耗的处理。若不能承诺精确 Token 硬上限，界面和文档必须说明实际控制能力；不显示无法兑现的预算限制。
- 自动执行启动前和推进结果提交时核对目标版本及权限；改目标后旧结果可保留为历史，但不能直接当新目标进度。一次性推进、暂停、恢复与已接受执行的关系必须一致。
- 心跳跳过原因与下一次检查持久可查；规划没有产生有效下一步时等待，不能无限自触发。资料内容属于输入，不能获得系统权限或覆盖职责定义。
- 进度纠错与 Agent 更新使用修订冲突保护，证据校验遵守授权路径。新增职责默认不自动打开正式任务；执行范围和数值策略在用户配置时明确。
- 完整职责合同纳入现有模块文档导航；若实现必须改变已确认的所有权、授权或执行架构，先明确提出影响并交用户审核，不先旁路实现。

### 验证与交付要求

自动化至少覆盖上方交付清单，加上：同触发重复到达、执行后进度提交前崩溃、目标修改后的迟到结果、并发预算竞争、暂停后待派发项、撤权与越界引用、无有效下一步停止。不同 Session 并行不等于共享文件安全，复用已有资源冲突保护。

真实验收必须走实际产品入口：

1. 浏览器创建小思的三项学习职责，提供合法可读取的测试资料，检查列表、编辑、刷新恢复和窄屏操作；Agent 通过实际管理 Tool 查询相同事实。
2. 真实模型完成至少两次连续推进，第二次使用第一次的进度和证据而非重读同一段；三项职责进度独立，产物可打开、引用可核对。小样本证明链路，不宣称完整学完三部作品。
3. 浏览器修正目标、暂停、恢复、立即推进和停止单次执行；Agent 更新与页面一致；后台运行期间主聊流式交流正常。
4. 验证无资料等待、重复触发不重复执行、预算不足不启动、重启恢复、过时结果不覆盖新目标。跨日可用可控时钟作自动化验证，明确不等于实际跨日运行；至少 24h 联合验收仍归 LA6。
5. 运行 `pnpm verify`、`pnpm check:architecture`、父仓库和 Frontend 的 `git diff --check`；改 Nano 则补其类型、测试、构建和 diff 检查。Agent 装配/Workflow 改动按根规则覆盖开发 Step、生产构建与 `pnpm test:dev`，不能用相邻链路代替。

交付时更新职责用法、阶段状态及 `docs/history/reviews/` 下 LA3 验收记录，附变更文件范围、实际命令、真实浏览器/模型证据、失败与重测、未验证项。逐项填写本计划自审，任何必验场景未过都标记未完成，不能缩范围换取完成。运行日志/截图使用隔离验收目录，不提交认证或正式数据。不要自动提交、推送、部署或开展 LA4。

### 实现方案与编码前合同

沿用“Task/Occurrence → 独立 Pi 执行 → 产物校验与提交 → 发布或文件结果 → 状态查询/通知”。只有内容生成需要模型；校验、幂等、存储和重试由 Backend 负责。先在对应模块文档明确以下合同，再落代码；常规实现选择自行完成，不反复申请权限。

1. **产物身份与幂等**：由服务端从执行上下文解析 Friend、Task revision、Occurrence/work，组合产物类型和明确槽位/目标形成稳定身份。同一发生重试不新建帖子或第二篇笔记；不同早/中/晚槽位必须各自保留；同日其他自主动态也不能被按日期合并。
2. **内容冻结与提交**：生成结果先耐久保存，再提交至文件或 Social；产物内容版本与执行尝试分别记录。同键异内容拒绝或显式修订，不能静默覆盖。若一次运行可产生多产物，槽位需明确、不可靠重新随机 ID 绕过去重。
3. **恢复与未知结果**：覆盖文件/帖子写入后但回执未保存、投递前后崩溃、重复并发提交。能根据稳定身份查到已有产物则补记回执，不能重调模型。确实未知的外部副作用显示待核查，不承诺无法保证的 exactly-once。
4. **真实完成状态**：模型完成、笔记落盘、站内发布、通知送达分开。只有实际文件及内容引用存在才显示笔记完成，只有 Social 可读取到对应帖子才显示发布完成；通知失败不把产物改成生成失败或再次生成。
5. **来源与隐私**：关联已授权的职责进度、材料、work 或用户指令；LA3 未应用/未核验历史不能自动作为已学事实。发布前校验有效授权/受众；私有日终交接与 Memory 不自动复制成公开内容。模型选择文本/格式，不替代服务端权限判断。
6. **时间与取消**：使用 Task 的 IANA 时区和既有 missed/overlap 策略；过期社交内容默认不自动补发，用户可明确补跑。暂停阻止后续运行，停止单次不删除已有产物；目标/授权改变后的迟到结果保留历史，不能用旧授权发布。有限重试和清晰的等待/失败原因，不无限堆积。
7. **升级兼容**：旧帖子/评论/任务可读，新增关联不可编造来源；确定存储版本、迁移标记、锁及原子性，不读 Nano 数据库，不引入第二份可写任务定义。不得从字段相似推断旧记录曾被发布或已授权。

### 用户与 Agent 的管理入口

- 配置/查询/修改/暂停/恢复 3+1 安排和单独时段；使用相同 Backend 服务，刷新后可恢复。已有任务的调整保持 revision 冲突保护，主聊和 Web 的不同入口不能绕过版本检查。
- 查询今天及指定日期哪些已完成、哪些缺资料/失败、下次安排、对应笔记/动态、来源和执行详情；实际聊天过程继续使用公共实时 Session 展示。
- 明确区分“重新生成内容”“补交已有产物”“补发通知”与“修改产物”；UI 不用一个重试按钮混淆副作用。Agent 能调用同一管理动作，权限不因自然语言入口扩大。
