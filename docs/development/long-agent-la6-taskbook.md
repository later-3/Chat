## 1. 完成后用户获得什么

小思等 Friend 保持自己的身份与 Workspace，用户可持续私聊、安排后台工作、参与多个群；每位 Friend 记住自己的协作项目。三项学习职责持续推进，早/中/晚动态和夜间笔记按用户配置自然发生。Web 与已验收的真实渠道呈现同一工作事实；断线、重启、跨日和升级不会串项目、重复执行或伪造完成。

LA6 既包含两个明确功能交付，也包含对 LA0–LA5 的联合验收：

1. **按 Friend 持久化协作项目**，修复当前全局选择影响其他 Friend 的问题。
2. **实际渠道闭环**，包括一个明确选定平台的私聊和群场景接入/验证；复用 Nano 窄合同和 Chat Conversation，不把外部群当另一个 Agent Runtime。
3. **升级、恢复与至少 24h 自然联合运行**，补齐用户真正使用时的组合证据。

不新增登录体系、多租户、第二套 Session/调度器/模型循环；不重做 UI，不引入全平台 IM 适配；Docker 隔离环境和分布式多 Backend 不属于本阶段。未支持的平台继续明确拒绝，不能默认为已支持。

## 3. 必须先落定的合同

### 3.1 Friend 与项目关联

- 稳定 `longAgentId` 为关联主体，关联属于当前本地用户与该 Friend；不改变 Friend 身份、专属 Workspace、每日 Session 的存储归属或历史。
- A/P→B/Q→A 恢复 P，返回 B 恢复 Q。普通 Project Session 和群各自保持选择，不反写 Friend 私聊关联。
- Backend 是权威事实源；Web 与 Agent 授权动作使用同一读写服务。持久对象具备版本和预期 revision；慢响应、双标签页及 Agent/Web 交错不能覆盖更新值。
- 区分“从未设置”“显式无项目”“关联项目已不可用”。**首次默认无协作项目**；若迁移已有明确的单 Friend 关联则保留。不得从最近访问的其他 Friend/全局导航推测默认关联。
- 页面标题、文件浏览器、发送目标、实际模型请求中的项目及 AGENTS.md 来源一致。消息接受时冻结 Friend、关联 revision 和项目；发送后切页不更改已接受轮次。对过期关联采用明确冲突/重新确认语义，不悄悄换项目执行。
- 修改项目只改变后续轮次输入，不主动给模型发送“切换”消息，不重建日常 Session；显式无项目仍有 Friend 自身身份和资源。
- 关联不等于授权。失效/撤权显示不可用并阻止错误项目执行，用户可明确清空/重选，不能静默回退 Friend Workspace 或 Daily。
- Agent 经授权改变协作目标也更新同一服务；群成员不能借此修改私聊选择。旧 Task/Occurrence/Discussion 保持原冻结目标。
- 渠道 binding、群协作目标、私聊偏好分别归属：群使用群记录；已接受事件沿用其冻结目标；新私聊事件的 binding 与偏好如何一致，必须在 A 包给出明确规则与迁移依据，不能让两个入口各自猜测。

### 3.1.1 A 包设计决策（纳入本任务书评审，不另设四次用户审批）

这些是实施方案，由实施者在短设计中落实和核对；不是现有代码已支持的事实。用户批准 A 包或 LA6 后即可据此实施，无需再逐项申请普通存储/接口选择的许可。

| 决策 | 采用方案 |
|---|---|
| 存储 | 使用既有 `longAgentConfigRoot` 下独立 `interaction.json`，不扩写身份 definition，不在 registry 或 Nano 保存第二份。由本地 Chat Home 确定用户范围，稳定 longAgentId 确定 Friend；路径授权、原子写和 revision CAS 沿用现有持久化原语。文件迁移/删除纳入 Friend 生命周期。 |
| 三态 | 无记录是 unset（读取时有效项目为 null，不暗中写入）；有记录的 `projectId:null` 是显式清空；非 null 项目失效是 unavailable（保留原值及 revision，解析结果带原因）。记录包含 schemaVersion、projectId、revision、updatedAt；读取有效状态由 Backend 计算。 |
| 首次默认 | 无协作项目。不得用 agent.defaultProjectId、最近一条历史、全局导航或 Agent Home 推断协作项目。显式改选才写入。 |
| Web/Agent 私聊选择 | 写入共同关联服务并带 expectedRevision；普通发送携带关联版本校验值，在接受时原子核对/冻结。旧页面不一致返回明确冲突，不默默采用当前值，也不让每轮 projectId 成为绕过持久关联的隐式覆盖。 |
| 其他执行对象 | 已接受 turn/work/occurrence/discussion 的冻结目标优先且不可变；新 Task/Duty/群配置使用其自身明确目标，**不在每次触发时重新读 Friend 私聊偏好**。普通 Project Session/TUI 项目会话仍用自身项目；未来 TUI Friend 私聊入口使用共同关联服务。 |
| 渠道 | 旧 binding 的显式协作目标保留为该渠道的固定目标，不能反向迁移成所有入口共享的偏好。新的可信本地 owner 私聊绑定可明确采用 follow-friend；非 owner 或身份未核验的来源不得继承 owner 的私有项目，沿用已授权目标或 null。绑定模式/来源的版本化变更在 A 短设计中列明，B 按合同接线。已接受事件重试永远使用接受时冻结值。 |
| 迁移 | 不从 defaultProjectId/历史轮次猜测。若找到独立、明确且唯一的旧 per-Friend 用户选择来源，可迁移其原值并记录来源；当前代码没有该事实时保持 unset。旧渠道固定绑定、群、任务、Session 不改属；冲突来源不得用“最新一个”覆盖。 |

接受消息时的 CAS 与冻结必须解决检查/接受的竞态，不能先锁外读偏好、隔一段 I/O 后当成仍然有效。Agent 修改偏好须来自可信私聊 owner 作用域；项目关联不授予新的资源权限。

上述渠道区分不是新增全系统账号/登录体系：只复用现有可信绑定；没有可靠 owner 身份证据就拒绝继承，不为了通过测试信任请求自报身份。

### 3.2 外部渠道

选 **1 个现有 Nano 已支持且有测试账号的平台** 作为 LA6 真机基线，优先可用的 Telegram；不先承诺所有平台。先核实该适配器的私聊、群消息、发送者身份、消息 ID、发送回执和 bot 权限。

- 外部 conversation/destination 到 Chat Conversation 的绑定由受权管理入口建立，带版本与群成员/受众规则；普通外部消息不能创建 owner、扩大授权或指定任意源 Session。
- 入站依靠 instance/channel/conversation/message/event 稳定身份去重；出站依靠 publication/delivery 关联。禁止按正文、昵称或显示名判断身份。
- 外部人类发言必须保留实际发送者标识和来源；不能全部伪装成本地 owner 的指令。工具和模型请求按该群的可信 scope 裁剪。
- 选人、@、圆桌等继续由已有 Workflow 组织；外部平台消息只是入口。对自己刚发出的 bot 消息防回环，Webhook/轮询重送不能再次执行。
- 默认只向绑定且批准的测试目标投递公开内容；不发送私有 thinking、工具输出、参与 Session 全文或未发布草稿。
- 平台支持稳定幂等键则使用；平台对发送结果不确定且无法查证时，显示“待核查”，保留关联，不自动重发以假装 exactly-once。Delivery/Ack 重试不重新生成答案。
- 渠道未配置/缺权限/离线、服务认证失败、群解绑/撤权时明确失败或等待；界面不能假报送达。

如果选定平台尚无群适配：先在 B 的短设计中列出最小适配范围与原生证据，依托现有 Gateway/Management 合同实施。若涉及本任务书之外的平台或权限模型扩展，再提交具体差异评审；不能用“私聊发送成功”代替外部群验收。

### 3.3 联合运行与交付

学习材料使用用户提供或合法可用且授权的版本；《天道》《道德经》《金刚经》是职责配置，不能硬编码为任务类型。缺资料应进入等待，不能制造学习进度。3 条动态与 1 篇笔记由既有任务/职责/产物合同承载。

笔记沿用 LA4 不可变版本与当前引用；工作区用户文件不被自动覆盖。不能为验收观感恢复覆盖文件或将模型生成当作笔记落盘。成本、并发、时长、重试均有明确有限配置；测试记录实际用量，不默认无限运行。

## 6. 24h 运行规程

1. 固定候选版本（含子仓库指纹和工作区变更摘要），独立 Chat Home/Nano 数据、测试 Project/素材、时区、模型、测试 destination、有限预算。不得复用正式动态空间发布验收内容。
2. 先跑短期预演：创建职责/3+1计划→触发→执行→产物→页面/渠道可见；短期预演与24h证据分别存档。
3. 观察窗口需同时满足自然经过24h、跨日、覆盖四个真实配置时间点；若起始时刻导致未覆盖完整窗口就延长，不能裁剪成“等价一天”。
4. 开始时登记预计发生账本。持续记录任务状态、投递回执、模型用量、进程重启、队列积压、磁盘/内存和错误；对账业务结果，而不只看进程 uptime。
5. 窗口内进行受控主聊/群聊/后台工作和至少一次有记录的重启/断线演练。受控中断是测试事件，不伪称进程连续在线；观察与记录仍必须连续，所有到期事件有可解释处理。
6. 不依赖一个 Agent 会话或终端一直活着；用既有常驻服务及可重入验收收集脚本保存进度。跨会话先读取账本继续，不因上下文接近上限声称无法继续；24h尚未经过就保持该包未完成。
7. 运行中改动影响行为的代码/配置后，前后证据分开；最终通过版本重新跑完整窗口。采集缺口无法还原时不得拼接通过。
8. 结束时冻结账本，对每个应发生项判断成功/已批准跳过/失败/待核查，说明差异并修复。停止并清理本次测试服务和临时账号绑定，不删除验收证据与用户数据。

## 7. 环境、授权与阻塞边界

A/C 的设计与代码验证不依赖真实渠道账号或24h运行预算。B 可先实现适配与本地故障门禁；外部实际发送才受测试目标授权限制。D 的常驻环境、账本和预算配置可先准备；启动长时间真实模型运行前明确本次预算上限及观察窗口。24h 是验收证据门槛，不是阻止整个 LA6 开工的通用前置。任务书获批后，对已经覆盖在批准范围内的步骤不重复请求许可。

- 本任务书不授权发送真实外部消息。B 开始前应提供具体测试账号、平台、群/收件人和预计消息范围，取得用户对这些目标的明确授权；沿用既有明确授权时不重复询问。只缺平台凭据时，先完成可独立进行的代码、故障测试和本地验收。
- 使用已授权模型配置，密钥不写日志/截图/文档；调用预算耗尽或认证失败如实记录，不临时换未获授权的账号或偷偷扩大预算。
- 24h 需要真实等待与常驻环境；这是最低观察时间，不承诺一轮对话结束即完成。需要自动回访/监控时使用环境提供的正式机制，不假装回复后仍在持续运行。
- 不默认获得生产部署、Git 提交/推送、系统安装、破坏性迁移授权。先给可审阅的候选与回退方案，再按用户实际授权执行。
- macOS 可作为主要联合验收环境；Linux/WSL 从零安装的真实验证沿用部署文档边界。若没有相应主机，必须列为未测平台，不把 macOS 的 shell 测试写成 Linux/WSL 真机验收；不得扩大已发布平台声明。

## 8. 质量门槛与自审

代码改动运行 `pnpm verify`、`pnpm check:architecture`、根/Frontend `git diff --check`；修改 Nano/Pi 则加其规定的测试与 diff 检查。涉及 Workflow/公共装配须覆盖 Builder、Nitro 开发 Step、生产构建及 `pnpm test:dev` 的真实执行链。参考既有 `group-*.test.mjs`、`long-agent-live-smoke.mjs` 扩展验收，不再建产品执行旁路。

每包退出前必须回答并附证据：

- **有没有只实现容易的一半？** 管理、实际执行、查看、失败/恢复均有入口；新增偏好不是只存 React，外部渠道不是只收到202。
- **有没有错误更换对象？** 身份、Workspace、存储 Project、协作 Project、每日 Session、群参与、Task、Occurrence、Delivery 没混在一起。
- **是否检查所有写入口？** Web/Tool/渠道/维护/恢复使用同一授权、版本、幂等与提交仲裁；锁从获取到交接/释放覆盖所有异常，等待模型/网络不持提交锁。
- **有没有异步逃逸？** 用量/权限/回执写入失败不能被吞掉后继续；旧快照不能覆盖新关联；新增测试必须证明实际模型输入、请求数、磁盘和公开投影，而非只断言字段。
- **是否倒退已有覆盖？** 保留 LA3/LA4/LA5 故障探针、浏览器刷新门禁与旧配置兼容；扩展测试不能删除原断言。
- **是否偏离最终目标？** 三项职责、3+1、主聊/多群/任务并行与真实渠道共享持久事实；不恢复 Nano 原生模型 Loop，不通过屏蔽必要能力让测试变绿。
- **是否诚实披露限制？** 本地模拟、真实模型、浏览器、平台收件、自然24h分别写；环境阻塞写明具体缺项和继续条件，不能把未测改成通过。

发现同范围问题直接修复，补可复现的永久门禁后重验。只有涉及新增平台/授权范围或推翻已批准合同才提出具体差异评审；不要把每次测试失败变成一次“是否继续”的提问。
