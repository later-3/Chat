# 公共 Agent 装配与 Friend 交互开发计划

状态：P1–P5 代码与本地验收完成；P5 无损迁移演练、586 项完整门禁和真实 Chrome＋DeepSeek 通过。真实 Telegram 外部收发与用户最终审核待完成，P5 最终验收保持开放。日期：2026-09-20。

本计划承接用户最新定义；只管理本轮施工顺序、场景和验收，不替代架构事实源。阶段完成后更新对应模块规范，不能把本计划中的目标写成已发布能力。

## 1. 最终目标与范围

完成后，Workflow Agent 与 Friend 通过同一个公共 Pi 装配入口获得有效身份、能力与本轮上下文；Web 与 Nano 渠道复用同一 Friend 执行和每日 Session 定位，前端复用普通 Session 的消息、工具、阶段、收尾和恢复机制。

必须达到：

1. Friend 有稳定身份、专属 Workspace、Tool、Skill 和 Memory；用户项目是本轮协作上下文，不能冒充其专属空间。
2. 每个 Friend 每天一个原生交流 Session；切项目不拆 Session、不换 Friend、不移动既有历史。普通项目 Session 保留原有归属与创建方式。
3. 每条消息接受时，由 Backend 解析并冻结项目、项目根规则、协作说明及有效资源；不要求用户手动通知模型“切项目”。在途执行不受之后的页面选择影响。
4. Session 存储归属、Agent Workspace、本轮协作项目分别建模；提示内容、工具默认工作目录与项目资源/Memory 作用域一致，授权仍由服务端执行。
5. 每日总结与交接可以恢复、重试；长上下文使用 Pi 原生压缩，不把压缩、总结和长期 Memory 混为一套存储。
6. 同一 Friend 的已授权 Web/渠道消息按同一每日 Session 有序执行，保留来源和回复目的地；投递重试不重复模型执行。
7. 普通 Session 与 Friend 共用聊天展示与实时消费，操作可用性来自真实后端能力；断线、停止等待与取消执行分别处理。
8. 旧历史可读、迁移可重复且有恢复依据；开发/生产链均有证据，未验证外部渠道明确列出。

不包含新群聊/多用户共享、朋友圈写入、Docker 工具环境、新通道、新模型运行时或全面重做布局。Workflow 原生委派子 Session 不冒充 Friend 的第二个直接交流 Session；其关系与记录在阶段 1 明确。

## 3. 阶段、依赖与工作量

顺序：P1 → P2 → P3 → 第一轮审核 → P4 → P5 → 最终审核。

估算是单人专注工程时间，包含实现与针对性测试，不是交付日期承诺；外部渠道凭据准备及用户审核等待另计。若原生 Pi 接口或历史迁移复杂度超出假设，先说明差异并更新剩余估算。

| 阶段 | 目标 | 预计工作量 | 完成标志 |
|---|---|---:|---|
| P1 合同与原生接缝 | 对象、填充区域、所有权、生命周期无歧义 | 1 人日 | 合同与场景评审通过，关键接缝有可执行证据 |
| P2 公共装配 | 所有 Agent 使用同一套有效输入解析 | 2–3 人日 | 模型实际输入和工具行为与本轮项目一致 |
| P3 Friend 每日生命周期 | 多入口共享每日 Session、可靠换日交接 | 2–3 人日 | 跨日/并发/重启/压缩用例通过，第一轮审核 |
| P4 公共聊天交互 | 实时过程、操作、终态和恢复统一 | 2–3 人日 | 普通与 Friend 场景对照验收通过 |
| P5 迁移与全链验收 | 原始入口到真实持久记录形成闭环 | 1–2 人日 | 全量门禁、迁移演练、可用渠道实测及最终审核 |
| 合计 | 两轮审核、五个阶段 | 8–12 人日 | 第 6 节全部必选条件满足 |

### P1：合同与原生接缝

目标：把模型输入和程序保障分别定义，确定后续实现的唯一输入。

交付：

- 分层调用图：入口适配 → Chat 生命周期 → 公共装配 → Pi → 公共反馈/渠道投递。
- 字段与填充表：身份、自定义要求、Workspace、项目规则、协作说明、Tool/Skill、交接、历史、装配元数据；注明事实源、权限、注入点、冻结时机和恢复方式。
- 明确本轮工作目录与 Session 存储根分离；检查 Pi 工具创建、SettingsManager、ResourceLoader、SessionManager 和压缩恢复是否支持，先做最小接缝验证。
- 每日日期使用的时区、跨午夜消息归日、正在运行旧日任务的处理、无消息时的换日/总结触发、总结失败后的降级/重试、取消与排队规则。
- Web 显式项目、通道会话绑定项目、未选择项目三种输入；不得共享“最后一个浏览器选择”作为所有入口隐式全局项目。
- 请求身份、可信发送者、回复目的地、幂等标识；私有渠道共享每日历史的适用边界。
- 盘点旧合同冲突与迁移清单。具体策略尚未确认的，必须在本阶段标注并完成审核，不埋进代码。

覆盖场景：S01–S12 的输入/输出均可从合同推导，特别是同一 Friend 连续处理项目 A/B、无项目闲聊、Web 与 Telegram 同时发消息。

验证：评审逐场景列出实际 Session、项目、cwd、加载规则和回复目的地；本地假模型最小实验确认 Pi 同一 Session 在重新装配后能使用不同协作目录且不改历史归属。不能只用类型定义或文档链接检查证明可行。

退出条件：无未决的身份/授权/Session 核心合同；任何需改 Pi 的接缝有必要性证据。未通过不进入依赖该合同的实现。

### P2：公共装配与本轮上下文

目标：Workflow 与 Friend 复用公共解析和装配；项目选择实际影响本轮输入与工具默认目标。

交付：

- 在公共入口引入明确的 Agent 定义、Session 引用、本轮协作上下文；禁止入口自行拼另一套系统提示。
- 每轮读取并冻结规则正文和版本；保留现有 AGENTS.override.md 等优先级，不继承无授权父/子目录。规则缺失与读取失败分别处理，真实错误不能伪装成无规则。
- 自身规则和项目规则分区；A 切 B 时 A 不再是有效指令，历史对话仍保留；长历史中的旧规则不能重新获得当前规则地位。
- 工具默认 cwd、项目 Memory 目标、资源策略与当前项目一致；Agent 自有资源始终绑定其身份。inherit/explicit 规则不因本次改造被绕过。
- 版本化装配元数据支持检查与恢复；检查页面和执行使用同一有效结果，不复制另一套 resolver。

覆盖场景：S01、S02、S03、S04、S10。

验证：本地假模型捕获真实请求正文和 Tool Schema；实际读写隔离测试目录，检查写入项目、Memory 目标及 Agent 专属资源；规则在运行中被修改或页面切项目时，本轮保持冻结、下一轮采用新内容。Workflow 的 explicit/继承与普通 Session 回归必须通过。

退出条件：不仅模型“说对项目名”，实际输入、工具行为、记录中的目标也一致；旧项目规则无重复注入；失效项目失败明确且不静默回退。

### P3：每日 Session、总结与跨入口生命周期

目标：每日唯一性是 Backend 合同，不依赖 Web 页面打开顺序；总结、交接和压缩可靠衔接。

交付：

- Web、Nano 消息、已支持调度入口统一定位每日 Session；同 Session 排序，重复请求只产生一次有效接受/执行。
- 固化 P1 确认的日期/时区规则，正确处理跨午夜在途任务和旧链接；保留旧 Session 只读历史/兼容读取，不拼接历史文件。
- 每日初始化可幂等执行：先开页面后发消息、进程重建、多轮重新装配都不丢交接。
- 每日总结记录原 Session/截止范围和状态，原子写入、重试不重复；重启补偿及无模型凭据/总结失败时明确暴露未完成状态。
- Pi 原生压缩、Session 恢复和每日总结各有职责；压缩后仍能判断每段历史的项目归属。
- Nano 耐久接收、Delivery/Ack 继续复用；模型完成但投递失败时只重试投递。

覆盖场景：S05、S06、S07、S08、S09、S11。

验证：可控时钟跨日/时区；同时提交 Web 和模拟 Nano 事件；重复事件、Backend 重启、总结写入故障和投递故障注入；实际 Pi 压缩后恢复并继续调用工具。断言 Session 唯一、消息顺序、项目快照、来源、终态和投递次数。

退出条件／第一轮审核：演示“Friend 在同一天协作 A/B → 跨日总结交接 → 刷新/重启后继续”；普通 Session/Workflow 不回归。用户审核通过后进入第二步交互收敛。

### P4：公共实时聊天和能力适配

目标：普通 Session 与 Friend 共用事件、展示和交互逻辑；入口差异只留在执行适配。

交付：

- 从现有 Workflow Pi 事件投影抽取公共协议；保留 Workflow 阶段/审核等附加信息，不让 Friend 冒充 Workflow。
- Friend 接受请求后返回稳定执行引用；执行与浏览器连接解耦。事件序号、快照/增量边界、补订阅与去重有明确合同，Pi 历史仍是消息事实源。
- 共用文字/工具增量、阶段、耗时、统计、自动跟随、正常完成与异常收尾。
- 同一组件恢复正在运行的任务；切 Friend/页面只离开观察，不隐式取消或重发。
- 后端返回真实操作能力；取消、停止等待、引导、后续消息逐项核对。未实现队列的按钮不伪装成可用，不能为一致性发明假完成状态。若移除现有入口须列出变化供审核。
- URL/恢复状态分清交流归属与浏览项目，兼容既有链接；资料面板继续跟随用户选择。

覆盖场景：S01、S04、S07、S08、S10、S12。

验证：真实浏览器对照普通/Friend 执行；首 Token、工具参数、工具执行、重试、压缩和终态；流中断/重连/重复事件/切页/刷新；长内容与滚动、明暗主题。验证断开等待不误报取消、失败不误报完成、刷新不重发。

退出条件：聊天核心状态与渲染无两套分叉实现；有能力差异表；仅有轮询或最终全文刷新不能视为实时交互验收通过。

### P5：数据兼容与全链交付

目标：真实用户入口和既有数据均可使用，文档、代码与发布版本一致。

交付：

- 在数据副本上验证旧项目绑定、旧 Friend Session、渠道映射和旧 URL 的迁移；迁移有标记、可重试、恢复步骤，不删除原历史。
- 全量场景矩阵、自动化结果及人工验收证据；旧机制移除清单、剩余限制与运维排障说明。
- 所有相关规范同步；关闭本计划时只保留执行结果与权威文档链接，不再复制完整架构。

覆盖场景：S01–S12 全部。

验证：执行第 5 节门禁，生产构建使用隔离 CHAT_HOME；具备已授权测试账号时完成 Telegram → Nano → Backend → Pi → Nano → Telegram，Web 可观察同一每日历史；真实外部发送单独获得明确授权，没有条件时保持该项未验收，不能以模拟事件代替。

退出条件：第 6 节必选项全部完成；不能把提交/推送或部署当作本计划隐含授权。
