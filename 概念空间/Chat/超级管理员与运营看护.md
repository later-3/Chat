# 超级管理员与运营看护

## 文档治理信息

| 项目 | 内容 |
|---|---|
| 目的 | 定义超级管理员如何在不制造第二事实源、不越权读取敏感内容的前提下，看见用户登录、使用、工作与作品进度。 |
| 概念状态 | 有效；2026-07-24用户确认这是Chat必须具备的超级管理员能力。 |
| 实现状态 | 未实现：当前没有真实身份登录、超级管理员角色、活动采集、运营投影或管理控制台。 |
| 事实所有者 | 身份事实归Identity；使用活动与管理员审计归Super Admin Operations；项目/工作进度归Product Harness；作品与证据归Evidence。 |
| 维护责任 | Identity、Super Admin Operations、Product Harness、Evidence和Super Admin Console共同维护。 |

## 一句话理解

**超级管理员看护是一个受授权、可审计的运营视角：它汇总“谁登录了、怎样使用、工作和作品推进到哪里、哪里需要关注”，但不复制业务事实，也不默认赋予读取所有对话与秘密内容的权限。**

## 为什么需要

Chat是独立运营的产品。只有个人主页、Run监控或系统日志，运营者仍不能回答：

1. 哪些真实用户登录并使用了产品。
2. 用户停留多久、真正发生了多少有效协作，而不是一次请求耗时多少。
3. 用户的Project、Work、Plan和Artifact推进到哪里。
4. 哪些用户长期没有进展、遇到失败、等待批准或存在交付阻塞。
5. 管理员查看了什么、执行了什么治理动作，是否发生越权。

因此它既不是个人主页，也不是开发运维仪表盘，而是建立在权威产品事实之上的超级管理员运营能力。

## 定义与边界

| 概念 | 定义 | 不是什么 |
|---|---|---|
| Super Administrator / 超级管理员 | 由服务端Role与Grant授权、可访问跨用户运营查询和限定治理动作的Principal | 不是配置文件里的固定用户名，也不是能绕过审计直接读数据库的人 |
| Authentication Session / 登录会话 | 一次经认证建立、续期、撤销和结束的服务端身份会话 | 不是Product Session、浏览器标签页或MAF Session |
| User Activity Event / 用户活动事件 | 用户在产品中发生的、经过分类和最小化记录的可审计行为 | 不是完整Prompt、消息正文、键盘鼠标原始轨迹或隐藏推理 |
| Activity Window / 活跃窗口 | 根据前台心跳、空闲阈值和服务器时间，从活动事件推导出的可解释使用区间 | 不是登录会话时长，也不是简单用最后事件减第一个事件 |
| Meaningful Collaboration / 有效协作 | 发送、审批、修正、创建或推进Work、采纳Memory、提交Artifact等有产品意义的动作 | 不是页面一直打开，也不是模型或Worker的计算时间 |
| Usage Aggregate / 使用聚合 | 可从活动事件重建的按用户、时间和入口汇总的运营读模型 | 不是Principal、Project、Work或Artifact的权威记录 |
| Work Progress Projection / 工作进度投影 | 从Product Harness权威Project、Work、Plan状态生成的管理员查询视图 | 不是管理员维护的第二套进度 |
| Artifact Progress Projection / 作品进度投影 | 从Evidence/Artifact生命周期、版本、验证和交付状态生成的管理员查询视图 | 不是从Assistant文本猜测的“作品完成百分比” |
| Super Admin Audit Event / 管理员审计事件 | 记录管理员查询敏感范围、导出或治理动作的主体、目标、时间、理由和结果 | 不是一般开发日志，也不能被管理员自行删除 |

## 概念关系

```text
Principal + Role/Grant
-> Authentication Session
-> Super Admin Console
-> Super Admin Query API
-> Super Admin Authorization Guard

Identity事实 --------------------┐
User Activity Event ------------|
Product Harness的Project/Work ---|-> 可重建Operations Projection
Evidence的Artifact/Evidence -----|              |
Run/Delivery的异常与等待 --------┘              v
                                        超级管理员看护界面

所有跨用户查询/导出/治理动作
-> Super Admin Audit Event
```

Identity、Product Harness、Evidence、Run和Delivery仍拥有各自事实。Super Admin Operations只拥有活动事实、管理员审计和可重建投影，不反向修改源状态。

## 人和系统怎样使用

1. 服务端认证用户，创建可撤销的Authentication Session；浏览器Cookie或Token只用于证明该会话，不能自行声明管理员Role。
2. 前端只在可信RequestContext具有相应Grant时加载Super Admin Console和跨用户查询。
3. 页面活动通过最小事件与前台心跳形成Activity Window；服务端同时保留事件来源、计算版本和未知区间。
4. Product Harness提供Project、Work、Plan权威进度；Evidence提供Artifact、Evidence、验证与交付状态；运营投影只做跨用户查询优化。
5. 管理员可查看身份、时间、进度、等待审批、失败和长期停滞等必要元数据；查看消息正文、Artifact正文或导出数据需要单独Grant和审计理由。
6. 来源事实变化后，投影通过Outbox/Event或重建任务更新；投影延迟或不一致时展示`stale`或`unknown`，不能猜测完成。
7. 管理员所有跨用户读取、导出和治理动作写入不可抵赖的Super Admin Audit Event。

## 四种时间必须分开

1. **登录会话时长**：认证会话从建立到撤销、过期或结束的时间，表示凭据有效期，不等于用户一直使用。
2. **前台活跃时长**：浏览器可见、收到心跳且未超过空闲阈值的区间，允许网络缺口和`unknown`。
3. **有效协作时长/次数**：由有意义产品动作构成的工作量信号，主要用于理解采用与阻塞，不冒充精确劳动工时。
4. **Run/Provider/Tool耗时**：机器执行和外部调用的技术耗时，用于运行性能，不能算作人的使用时长。

每个指标必须公开口径、时间窗、时区、空闲阈值、去重规则和数据新鲜度。

## 正例与反例

正例：超级管理员查看“最近7天已登录用户、前台活跃区间、有效协作次数、活动Project、阻塞Work和待验证Artifact”，每个数字都能回到对应权威来源与更新时间。

正例：某用户页面一直打开8小时但只活跃20分钟，系统分别显示登录会话、前台活跃和有效协作，不把8小时写成使用时长。

正例：作品缺少验证Evidence时显示“待验证”，而不是根据Assistant说“完成了”自动标记100%。

反例：复用`/api/diagnostics/operations`，把Worker队列、Provider耗时和Run统计包装成用户运营看护。

反例：管理员前端直接联表查询Product DB，自己计算Project进度并回写“完成度”。

反例：只要Role名叫`super_admin`就可以读取全部对话正文、Provider Payload、密钥或模型隐藏推理。

反例：用登录时间减退出时间作为用户有效使用时长，忽略多标签、后台页面、断网和空闲。

## 当前状态与未知

当前只有固定`local-user` Scope、Product Harness中的Project/Work/Plan事实，以及Run/Provider/Tool技术耗时；尚无真实认证、Authentication Session、超级管理员Role/Grant、Activity Event、运营投影、管理员审计或Super Admin Console。

详细设计仍需审核：

1. 登录与活跃会话的失效、续期和多设备语义。
2. 前台心跳、空闲阈值、有效协作事件清单和时间聚合版本。
3. 管理员可见字段、消息/Artifact内容的额外授权、隐私告知和数据保留期限。
4. Project、Work和Artifact进度投影的状态映射、延迟目标与重建策略。
5. 查询、导出、治理动作的审计保留和不可篡改边界。
