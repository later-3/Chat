# 身份与外部入口

## 文档治理信息

| 项目 | 内容 |
|---|---|
| 目的 | 区分Principal、权限Scope、可信RequestContext、Channel、Adapter、Binding和外部会话身份。 |
| 概念状态 | 有效。 |
| 实现状态 | 局部实现：当前使用固定本地Scope；真实Principal、Channel Binding、Telegram Adapter和OPC-OS Bridge合同未完成。 |
| 事实所有者 | 产品边界见[项目上下文第2节](../../PROJECT_CONTEXT.md#2-产品边界与外部关系)，当前实现见[项目状态](../../PROJECT_STATE.md)。 |
| 维护责任 | Identity、Channel Binding、Interaction Ingress、Channel Adapter和Delivery共同维护。 |

## 一句话理解

**Principal说明谁在行动，Scope说明允许什么，Channel说明从哪里来，Binding说明外部身份如何被授权映射到Product Session；任何协议ID都不能单独充当权限。**

## 为什么需要

如果把Telegram chat ID、AG-UI threadId、Product Session ID或Agent名称当成身份和授权，外部消息就可能越权进入产品核心。把Chat Web、终端平台、Channel Adapter和OPC-OS Bridge都叫“入口”，也会让认证、幂等、能力降级和交付责任无法落地。

## 定义与边界

| 概念 | 定义 | 不是什么 |
|---|---|---|
| Principal / 主体 | 用户、服务或外部系统的稳定身份 | 不是Session、Agent Profile、Provider或外部chat ID |
| Scope / Grant / 权限范围 | Principal在一定条件下可读、可写或可执行的能力范围 | 不是模型Instructions或Tool Definition |
| RequestContext / 请求上下文 | 服务端验证凭据、来源和Binding后生成的单次可信身份/权限快照 | 不能由浏览器或外部Adapter自行声明为可信 |
| Channel / 交互通道 | 某类交互入口的协议、能力、限制和来源身份边界 | 不是Product Session或具体平台消息 |
| Chat Web / 产品Web客户端 | Chat自带客户端，通过自己的REST/AG-UI后端访问产品核心 | 不是一个通用外部Channel Adapter |
| Channel Adapter / 通道适配器 | 终止某个平台协议、验证来源、映射能力并调用Interaction Ingress的受信组件 | 不是Telegram等平台本身，也不能直写Product DB |
| Bridge Adapter / 系统桥接适配器 | Chat与OPC-OS Chat等对等外部系统之间的版本化合同适配器 | 不是父系统控制Chat的层级关系 |
| Channel Binding / 通道绑定 | 外部身份/会话与Principal、Product Session之间可撤销且可授权的映射 | 不是简单ID相等或永久绑定 |
| External Channel Conversation / 外部平台会话 | Telegram或其他平台拥有的会话对象和消息ID空间 | 不是Chat Product Session事实源 |
| Interaction Ingress / 交互接纳入口 | 统一验证幂等、可信RequestContext和产品接纳合同的应用边界 | 不是直接暴露MAF、Run或数据库给外部平台 |

## 概念关系

```text
Chat Web -> Web/API Adapter -> Interaction Ingress

终端平台 -> Channel Adapter -> Channel Adapter Host -> Interaction Ingress

OPC-OS Chat -> Bridge Adapter -> Channel Adapter Host -> Interaction Ingress

凭据 + 来源声明 + Channel Binding
-> Identity验证
-> RequestContext(Principal, Scope, Channel)
-> Product Session / Interaction接纳
```

外部系统与Chat各自拥有自己的事实；Binding和合同只建立受控关联，不形成双重事实源。

## 人和系统怎样使用

1. 所有外部请求先在Adapter终止协议和验证来源，再进入统一Interaction Ingress。
2. 服务端根据凭据与Binding创建RequestContext；客户端只能提交声明，不能自行授予Scope。
3. Product Session ID、AG-UI threadId、MAF Session ID和外部chat ID分别保存并显式映射。
4. Binding可撤销、有范围和版本；撤销后必须传播到后续上下文、执行和Delivery权限。
5. Agent Profile和模型Provider用于执行配置，不是Principal，也不能获得用户权限。

## 正例与反例

正例：Telegram Adapter验证Webhook来源和外部消息ID，经Binding找到已授权Product Session，再以可信RequestContext调用Interaction Ingress。

反例：Telegram平台直接调用Conversation Repository并把chat ID写成Product Session ID。

反例：前端只要知道AG-UI `threadId`就可以恢复别人的运行。

反例：把OPC-OS Chat画成Chat的上位产品并让它成为Work、Run或Evidence事实源。

反例：把Agent名称`planner`当成执行该Agent的权限主体。

## 当前状态与未知

当前只使用固定本地Scope支撑单机产品纵向切片，尚无完整Principal/Grant、Channel Binding、外部身份撤销、Telegram Adapter或OPC-OS Bridge正式合同。具体部署形态、跨入口并发和外部能力降级仍待设计审核。
