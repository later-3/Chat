# 运行与恢复

## 文档治理信息

| 项目 | 内容 |
|---|---|
| 目的 | 统一Product Run、各种Attempt/Job和Retry、Restart、Resume、Cancel、Follow-up、Steer等动作。 |
| 概念状态 | 有效。 |
| 实现状态 | 局部实现并验证：Product Run/Attempt、用户可见Retry/Restart和精确Cancel已存在；Runtime Job、活动Resume、Steer和Worker接管未完成。 |

## 一句话理解

**Product Run是用户长期看到的一次执行；Attempt和Job是实际执行机制；Retry、Restart和Resume分别表示原输入再试、修改后新跑和从安全点继续。**

## 为什么需要

用户说“继续”“重来”“再试一次”时可能表达完全不同的意图。如果系统不区分，会重复发送Provider请求、重做外部副作用、丢失失败血缘，或用一次新Run冒充从Checkpoint恢复。

## 定义与边界

| 概念 | 定义 | 不是什么 |
|---|---|---|
| Product Run / 产品运行 | 一次Agent、Workflow或Runtime执行的长期产品事实 | 不是整段Interaction，也不是HTTP连接 |
| Run Attempt / 运行尝试 | Product Run的一次实际执行尝试、Worker所有权和恢复血缘 | 不是用户看到的完整任务，也不覆盖旧Attempt |
| Runtime Job / 运行任务 | 等待Worker领取、续租和执行的调度对象 | 不是Product Run；Job清理不删除产品事实 |
| Model Call Attempt / 模型调用尝试 | 一份已批准ModelCallDraft的一次Provider发送尝试 | 不是Run Attempt，也不自动重试 |
| Tool Execution / 工具执行 | 一次具体Tool副作用及其账本 | 不是模型调用或Run本身 |
| Delivery Attempt / 交付尝试 | 把已生成结果发送到某个接收方的一次尝试 | 不决定Product Run是否执行成功 |
| Retry / 原样重试 | 当前用户语义：以相同输入创建有血缘的新Product Run并重新经过审批 | 不是修改Prompt，也不是Checkpoint Resume |
| Restart / 修改后重启 | 取回原输入，用户修改后创建有血缘的新Product Run | 不是继续旧Run |
| Resume / 恢复运行 | 从已验证的活动状态、Checkpoint或安全点继续同一个长期Product Run | 不是重新发送原Prompt；当前完整能力未实现 |
| Cancel / 取消请求 | 对精确Run发出的停止意图；结果取决于外部请求是否已发送 | 不是一定能够撤销已发生副作用 |
| Follow-up / 后续消息 | 在已有结果之后创建新的Interaction继续协作 | 不是修改正在执行的Run |
| Steer / 运行中引导 | 向仍在活动的Run提交版本化控制输入 | 不是普通Follow-up；当前未实现 |
| Outcome Unknown / 结果未知 | 外部请求已可能发生，但系统无法确认最终结果 | 不是失败，也不能盲目重试 |

## 概念关系

```text
Interaction -> Product Run -> Run Attempt -> Runtime Job
                         ├── Model Call Attempt
                         ├── Tool Execution
                         └── Runtime Event / Checkpoint

失败后：
相同输入 -> Retry -> 新Product Run（保留血缘）
修改输入 -> Restart -> 新Product Run（保留血缘）
有安全恢复点 -> Resume -> 同一Product Run继续
已完成后再说话 -> Follow-up -> 新Interaction
运行中改变方向 -> Steer -> 同一活动Run的控制输入
```

## 人和系统怎样使用

1. UI只在满足语义和安全前提时显示对应动作，不提供含糊的“重来”。
2. Retry必须验证输入未变；一旦用户修改，动作转为Restart并重新审批。
3. Resume必须说明从哪个Checkpoint或事件游标继续，并验证图版本、权限和Tool副作用。
4. Cancel绑定精确AG-UI `runId`到Product Run映射；旧runId不能取消后续Run。
5. Provider发送后取消或超时可能进入Outcome Unknown，不能产生Assistant假成功或自动重放。

## 正例与反例

正例：Provider明确失败后，用户点击Retry，系统创建新Run、保持原输入、排除重复祖先Prompt并重新审批。

正例：用户取回失败Prompt并修改，按钮和Trace明确显示Restart，而不是Retry。

反例：Worker崩溃后直接创建新Tool Execution，假定上一次外部操作没有发生。

反例：把“重新打开已完成会话”称为Resume Run。

反例：浏览器SSE断开时自动Cancel Product Run。

## 当前状态与未知

当前已验证Product Run/Attempt持久化、Retry/Restart血缘、Provider发送前/后精确取消和Outcome Unknown保守终态。活动流游标、Runtime Job/Lease、Worker恢复、Tool对账、Checkpoint Resume和Steer仍未完成。
