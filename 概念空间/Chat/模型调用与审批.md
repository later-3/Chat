## 一句话理解

**用户Prompt只是完整模型请求的一部分；真正被授权的是绑定Provider、协议、规范Body、版本和Hash的ModelCallDraft，授权可以来自本次人工批准或有效策略的有界自动决定，发送时不得再改写。**

## 为什么需要

模型行为同时受Instructions、消息角色、历史、知识、Tools、模型和参数影响。只审核最后一段Prompt，会让用户看不见真正决定行为的内容；两个视图或Transport各自拼请求，则会形成“看见的不是实际发送的”。

## 定义与边界

| 概念 | 定义 | 不是什么 |
|---|---|---|
| User Prompt / 用户Prompt | 用户本轮明确表达的自然语言目标或要求 | 不是完整Provider请求，也不包含系统自动装配的所有上下文 |
| Instructions / 行为指令 | 系统、产品或Agent对模型行为、角色、限制和输出的指令内容 | 不是用户身份、授权策略或隐藏规则；进入请求就必须可审核 |
| Message Role / 消息角色 | Provider协议用来表达消息来源、顺序或指令优先级的枚举语义 | 不是昵称、Agent名称、Principal身份或权限；可选值由协议能力限制 |
| ContextPackage / 上下文包 | 本次被选择、排除、裁剪和引用的版本化上下文快照 | 不是Provider JSON本身；要先物化成目标协议内容 |
| ModelCallDraft / 模型调用草稿 | 某一次Provider调用的完整规范请求、路由、版本、Canonical bytes和Hash | 不是整个ExecutionDraft，也不是已经发送的Attempt |
| Provider Request / Provider请求 | `Provider + protocol + canonical body + 安全路由`确定的实际外部请求 | 不包含暴露给浏览器的API Key；审批后不能暗中转换协议或补消息 |
| Readable Review / 可读审核视图 | 从同一Draft投影出的固定Key、类型化Value编辑界面 | 不是另一份简化请求 |
| Provider JSON / 高级核对视图 | 同一Draft的目标协议Body结构化视图 | 不是独立草稿，也不能绕过Tool和Provider能力校验 |
| Model Call Authorization / 模型调用授权 | 人工或有效策略对特定Draft版本、Binding Hash、权限范围和后果的决定 | 不是对后续所有模型调用的永久同意 |
| Model Call Approval / 模型调用批准 | Model Call Authorization中的人工授权记录 | 不是唯一可能的授权来源，也不是产品默认以外的永久规则 |
| Model Call Attempt / 模型调用尝试 | 原子消费有效授权后，对已授权bytes的一次实际发送 | 不是Product Run或Run Attempt |
| Model Response Candidate / 模型响应候选 | Provider返回并经协议解码的文本、Tool Call或结构化内容 | 不是已接受Memory、Evidence、Work或产品成功终态 |

## 概念关系

```text
User Prompt
+ Instructions
+ ContextPackage物化内容
+ Tool Definitions
+ Provider / Model / Parameters
-> ModelCallDraft vN
-> Readable Review 与 Provider JSON（同一对象的两个投影）
-> Model Call Authorization Evaluation(binding hash)
-> Human Approval 或 Policy Auto Decision
-> Model Call Attempt
-> Exact Provider Request bytes
-> Model Response Candidate
-> 产品候选校验和提交
```

一个Product Run可以产生多份ModelCallDraft；Tool结果进入下一次模型调用时必须生成新的Draft和独立授权判断。当前产品默认每次请求人工批准，但目标HITL策略可以在不可放宽下限内配置自动推进；无论哪种模式都不能复用上一份Draft的决定。

## 人和系统怎样使用

1. 可读视图的Key不可改名，Value用文字、数字、布尔、枚举或受约束列表编辑。
2. Provider先选，模型只能从该Provider能力目录选择；协议切换同时转换最终Body并重新审批。
3. 所有进入Body的内容可修改，但修改必须生成新版本和Hash，使旧授权决定失效。
4. Message Role只允许当前协议支持的角色；修改Role会改变语义，因此必须重新进行授权判断。
5. `store=False`且不使用Continuation引用，保证完整显式上下文可见；自动Tool循环关闭。
6. 点击放弃不创建Attempt，原输入返回编辑框；只有显式清空才删除Input Draft。

## 正例与反例

正例：用户把一条历史消息从`user`改成`assistant`，系统生成Draft v2和新Hash，再次解析有效HITL策略；若当前模式要求人工，则请求再次批准。

反例：前端允许把Role改成任意姓名，例如`reviewer`，然后把它当权限或Agent身份。

反例：审批页展示Responses格式，Transport在批准后转换成Chat Completions `messages`再发送。

反例：第一次批准后，Tool结果触发的第二次模型调用复用旧批准直接发送，且没有为新Draft解析策略和记录决定。

反例：Provider JSON新增不存在的Tool后，服务端只检查JSON格式就允许发送。
