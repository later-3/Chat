## 一句话理解

**用户进入的是一条可跨天继续的协作时间线：主页负责重新定位，协作日历负责按天导航，对话日组织当天内容，灵感花园承接还没有必要升级为Project或Work的想法。**

## 为什么需要

传统“每次新建一个会话、从会话侧栏找历史”的交互，会迫使用户先理解系统怎样切割会话，再决定去哪里继续事情。Chat的目标恰好相反：用户只需要继续表达，系统负责按时间、事项和来源维护连续性。

但“连续”不能被错误实现为无限模型上下文。完整历史是可追溯证据，真正发送给模型的仍是经过意图识别、渐进召回和用户控制后形成的有界ContextPackage。

## 定义

| 概念 | 定义 | 不是什么 |
|---|---|---|
| Continuous Chat Stream / 连续对话流 | 用户可持续输入、跨天浏览和继续推进的主对话界面；按时间展示已提交Message、运行结果和公开协作事件 | 不是单个Product Session，不是发给模型的完整历史，也不是一个永不结束的Product Run |
| Conversation Day / 对话日 | 按用户时区把连续对话流投影到一个自然日的阅读与导航单位 | 不是Product Session、项目边界、事务边界或自动归档边界 |
| Personal Home + Activity Calendar / 个人主页与协作日历 | Chat的默认入口与时间导航：主页呈现今天、继续推进、活动、近期产物和灵感；日历按天显示有意义的协作活动并进入对应Conversation Day | 不是第二套工作台、绩效仪表盘或权威工作状态；Token消耗不能冒充成果 |
| Idea Garden / 灵感花园 | 对`Note(kind=idea)`及其状态、来源和关联的友好投影，让想法先被保存、培育、连接，再由用户决定是否升级为Project、Work、Note或规则 | 不是自动创建Project的收件箱，也不是只有标签而没有来源和生命周期的便签墙 |

## 边界

1. 连续对话流、Conversation Day、主页、日历和灵感花园都是Product Harness事实的服务端或前端投影，不新建第二事实源。
2. Product Session继续拥有交互、恢复和访问控制边界；目标界面只是默认不再用Session列表导航。
3. 完整历史继续作为证据保存，模型调用仍只能采用有界ContextPackage。
4. 日历活动是透明的协作活动表达，不是生产力评分；Token和成本始终属于二级用量信息。
5. Idea在用户接受前是候选，接受后可以保持为Idea；关联或升级不能静默创建Project、Work或Memory。

## 相关派生视图

### 每日日记

每日日记是Conversation Day的可编辑、可追源总结，至少可以包含：

1. 今天真正推进了什么。
2. 产生或修改了哪些Project、Work、Note、Artifact和Decision。
3. 哪些想法仍未归类。
4. 下一次最值得继续的事项。
5. 对应Message、Run、Evidence和资源来源。

系统生成的日记只是派生候选。用户编辑或接受前，它不能静默改写Project、Work、Memory或完成事实。它最终落为Note、Artifact还是二者的组合，应在Artifact详细设计中决定，当前概念不提前冻结存储Schema。

### 活动强度

协作日历的第一层只表达“这一天是否发生了有意义的协作”。强度可以综合有效Interaction、完成或推进的Work、接受的知识、产生的Artifact和用户主动停留，但必须满足：

1. Token、模型调用数和停留时长只作为可展开的成本或使用数据。
2. 强度不是生产力评分，不用颜色暗示用户做得好或不好。
3. 每个格子都能展开到可核验的当天来源，而不是只给一个神秘分数。

## 概念关系

```text
Personal Home
├── Continue / Today -> Continuous Chat Stream
├── Activity Calendar -> Conversation Day
├── Active Work -> Project / Work / Plan
├── Recent Outputs -> Note / Artifact / Evidence
└── Idea Garden -> Note(kind=idea)

Continuous Chat Stream
├── 按Conversation Day分组
├── 展示Message与公开Run结果
├── 关联一个或多个内部Product Session
└── 每次模型调用只采用有界ContextPackage

Conversation Day
└── 可生成Daily Journal候选 -> 用户审核 -> Note / Artifact（对象映射待详细设计）
```

Product Session仍是交互、恢复和访问控制容器。连续对话流可以在服务端依据权限与时间把多个Product Session投影成一条阅读流，但不能抹掉原始Session、Message、Run和来源关系。

## 人和系统怎样使用

1. 用户打开Chat默认进入个人主页，不需要先从会话列表选择入口。
2. 用户点“继续”进入连续对话流；输入区保持当前工作Context和显式选择的规则、文件、经验或事项。
3. 用户点击日历某天进入Conversation Day，可查看原始对话、当日推进、产物、成本和每日日记。
4. 用户捕获一句还不成熟的想法时，系统保存为Idea候选；只有用户接受后才进入正式灵感花园。
5. Idea可以关联Project、Work、Note、Artifact和来源，也可以长期保持未归类；升级为正式事项必须显式决定。
6. 主页、日历和灵感花园都是Product Harness事实的投影，不拥有第二份权威状态。

## 正例与反例

正例：用户周三点击日历，看到当天围绕英语学习和书签API发生的两段协作；系统分别链接到各自Project和Work，没有把它们合并成一个Session主题。

正例：用户说“记一个灵感：把学习复盘做成卡片”，系统先保存Idea候选；用户以后把它关联到学习系统Project，再决定是否创建Work。

反例：绿格越深就表示用户当天越高效，实际只是Token消耗更多。

反例：用户点进某一天后，前端把当天全部Message默认拼进下一次模型请求。

反例：系统为了移除Session侧栏，直接删除Product Session及其恢复、授权和Trace关系。

反例：把`#贪吃蛇`标签同时当作Project归属、Context采用授权和Workflow路由条件。

## 当前状态与未知

现有系统已经具备Product Session、Interaction、Message、Run、TurnDigest、Project、Work、Note、Memory和显式资源关联，可支持目标视图的事实基础。个人主页信息架构、Material 3 Expressive影响下的视觉基线，以及主页问候、关键动作反馈、公开AI运行状态和可追源协作日历4项轻量情绪层已经用户审核通过；生产主页、连续对话流、协作日历、每日日记和灵感花园均尚未实现。

还需在详细设计中确认：

1. Conversation Day按哪个用户时区切分，以及跨时区旅行如何显示。
2. 活动强度的透明计算和无障碍表达。
3. Product Session到连续对话流的服务端查询、分页和权限投影。
4. 每日日记最终采用Note、Artifact还是组合对象。
5. Idea的候选、接受、升级、合并和归档操作合同。
