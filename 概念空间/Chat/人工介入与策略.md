## 一句话理解

**HITL不是固定弹窗，而是在明确决策点上，用有效策略判断“禁止、必须由人决定、满足条件时暂停，还是可自动推进”，并把人工或自动决定都绑定到当前对象版本和后果。**

## 为什么需要

用户既希望在意图、上下文、计划、模型请求、Tool执行、状态提交和记忆接受等位置介入，也不希望每轮都被相同弹窗打断。系统因此必须把“哪里可能暂停”“当前是否真的暂停”和“谁作出了什么决定”分开，既允许配置自动化，又不能让低层配置绕过安全、权限和实际运行风险。

## 定义与边界

| 概念 | 定义 | 不是什么 |
|---|---|---|
| Decision Point Definition / 决策点定义 | 某类流程在何时、针对什么对象、可能产生什么后果的稳定定义 | 不是某次弹窗或MAF节点 |
| HITL Policy Rule / 人工介入策略规则 | 在一个作用域内，为某类决策点配置模式、条件和边界 | 不是用户已经作出的批准 |
| Policy Evaluation / 策略解析结果 | 系统对当前对象、风险、权限和所有适用规则计算出的本次处理方式及依据 | 不是长期事实本身 |
| Human Decision Request / 人工决定请求 | 当有效模式要求人工时，交给用户审核的版本化问题和可见后果 | 不是Provider Request或隐藏推理 |
| Decision Record / 决定记录 | 人或策略对一个具体决策点和对象版本作出的接受、拒绝、修改后重审、自动推进或禁止记录 | 不是可复用于任意后续执行的全局同意 |
| Approval / 批准 | Decision Record中允许特定对象、权限和后果继续执行的授权子类型 | 不是模型输出、按钮点击日志或永久授权 |

MAF `request_info`、Pending Request和AG-UI Interrupt/Resume是HITL运行时与协议投影；产品Decision Record才是长期授权和审计事实。二者需要映射，不能互相替代。

`Clarification Request`虽然也可以借MAF `request_info`或AG-UI交互实现，但它是在索取新的User Input，不是Human Decision Request：前者必须允许用户回答并触发Intent重判，后者才使用接受、拒绝、修改后重审等决定动作。若澄清通过普通聊天完成，当前Interaction提交问题后结束，下一条User Message携带回答；不能为了复用弹窗把它伪装成Approval。

## 概念关系

```text
Decision Point Definition
+ 当前被决定对象的revision / hash
+ System / Identity / Capability / Runtime约束
+ 各作用域HITL Policy Rule
-> Policy Evaluation
-> deny
   或 Human Decision Request -> 人工作出Decision Record
   或 Auto Decision -> 策略作出Decision Record
-> 有效授权时继续Workflow / Run
```

Decision Record回答“这一次为何可以、不能或需要修改后再继续”；HITL Policy回答“同类决策通常怎样判断”。策略本身不能替代具体决定记录。

## 固定决策点类型

当前目标闭环固定12类决策点：意图确认、项目关联、上下文审核、计划审核、ExecutionDraft执行授权、单次模型调用授权、Tool授权、Work状态提交、Memory接受、结果接受、运行中干预，以及结果未知处置。

`not_applicable`表示本次流程根本没有该决策点；`auto_continue`表示决策点真实存在，但策略在边界内自动作出了继续决定。两者不能混写。

## 模式顺序

```text
deny（禁止）
> require_human（必须人工）
> conditional（命中条件时人工，否则自动）
> auto_continue（有界自动推进）
```

`inherit`只表示本层不覆盖，由更广作用域继续解析；它不是最终执行模式。产品不提供“删除HITL”的模式，只能声明不适用或在有效边界内自动推进。

`conditional`也是配置模式，不是最终执行动作。系统必须先依据本次风险和事实求值为`deny`、`require_human`或`auto_continue`；求值所需信息缺失、过期或解析失败时按`require_human`处理。`not_applicable`只用于决策点确实不存在的场景。

## 作用域与优先级

策略必须分两阶段解析，不能简单采用“最后保存的配置覆盖一切”。

第一阶段计算不可放宽下限：

1. System Safety Floor：密钥、破坏性动作、合规和结果未知等系统边界。
2. Identity / Scope Policy：当前Principal、组织、项目和资源授权。
3. Capability Policy：Agent、Tool、Provider和Runtime实际允许的能力。
4. Runtime Facts：本次风险、成本、数据敏感度、能力扩张和外部状态。

这一阶段按更严格结果合并：模式取最高限制，允许集取交集，预算取最小值，风险条件取并集。任何用户配置都不能把这一阶段放宽。

第二阶段解析用户可配置偏好，作用域从具体到一般：

1. 当前Decision Instance。
2. 当前Product Run。
3. 当前Interaction。
4. 当前Product Session。
5. 当前Project / WorkItem / TaskPlan。
6. 当前Workflow Definition + Version；指定Node/Decision Point时比整图更具体。
7. 当前Scenario / Execution Pattern。
8. 当前Agent / Tool / Model Profile及revision。
9. 当前Channel / Surface偏好；Channel实际能力仍属于不可放宽下限。
10. 当前Principal默认值。
11. 产品默认值。

系统先选择最具体且命中的用户偏好作用域；更具体偏好可以放宽或收紧更广作用域的用户偏好，但不能突破不可放宽下限。同一作用域冲突时先把条件求值，再取更严格最终动作，然后取条件更具体的规则，最后才比较策略Revision。最终有效动作是“不可放宽下限”和“用户偏好结果”中更严格者。

## 人和系统怎样使用

1. 用户可以配置某个Workflow的上下文审核为“有歧义才问”，但不能让它绕过项目权限或把高风险Tool自动放行。
2. 用户可以仅对当前Run临时要求每次模型调用人工确认；该设置不应永久改变Project或Principal默认值。
3. 系统自动推进时仍保存命中的规则、风险快照、对象版本、Hash、决定者和结果，前端可显示“已按策略自动通过”。
4. 任何影响语义、能力、成本、权限或后果的变化都使旧决定失效并重新解析。
5. 用户直接说“请记住这个偏好”可以构成当前Memory候选的人工决定，但不能变成对未来所有Memory候选的自动授权。

## 正例与反例

正例：用户把“项目A的代码阅读Workflow”配置为模型调用自动推进；当前请求临时增加Shell写权限后，Capability Policy把Tool授权提升为必须人工，模型调用本身仍按各自策略判断。

正例：简单知识问答没有Project关联，项目关联决策点记为`not_applicable`；模型调用决策点仍存在，可记录策略自动通过。

反例：用户在全局设置“全部跳过”后，系统自动执行删除文件、发送邮件或结果未知重试。

反例：前端不弹窗就不创建Decision Record，导致无法解释为什么本次自动发送。

反例：Workflow设置比Principal默认更具体，于是无条件覆盖系统安全下限。

反例：澄清问题显示在Human Decision Request卡片里，却只有“接受并继续”；用户没有输入答案，系统也不能把接受按钮解释成答案。

## 当前状态与未知

当前产品默认仍让每次模型调用询问用户；配置中心已经能在Principal、Web、当前Session、当前Workflow和只读系统规则作用域查看12行矩阵并激活不可变Policy revision。Resolver已经验证`inherit`不会误覆盖产品默认、Conditional事实缺失会失败关闭、用户`auto_continue`不能放宽未知结果系统下限；持续协作主Workflow会为不适用、自动推进和人工审批分别保存Evaluation/Decision事实。

Web在线交互仍可以由同一个AG-UI调用提交Human Decision并继续；决定也可以先与Outbox原子提交，再由独立Worker从Product绑定的MAF Checkpoint恢复。后者已经通过新OS进程接管、竞争Lease、退避与死信测试。当前保证只覆盖持续协作主Workflow的无外部Tool副作用审批安全点；活动流重新订阅、批量Tool决定、子Workflow和结果未知对账不能据此类推。组织级策略、完整16种scope入口和具体风险评分仍需后续交付。
