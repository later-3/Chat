## 一句话理解

**历史保存发生过什么；ContextPackage说明本次用了什么；Memory是获准跨会话复用的信息；Evidence证明结果；Artifact是产物；Trace记录过程；Delivery说明是否送达。**

## 为什么需要

如果把聊天历史全部当上下文，会无限膨胀；把模型总结当Memory，会把猜测长期化；把Assistant回答当Evidence或把Run成功当送达，会产生假事实和假成功。用户必须能回答“这次采用了什么、为什么采用、结果凭什么成立、是否真的送达”。

## 定义与边界

| 概念 | 定义 | 不是什么 |
|---|---|---|
| Conversation History / 完整历史 | Product Store保存的Message、分支和关联事实记录 | 不是每轮默认模型上下文 |
| Context Source / 上下文来源 | 可能被本轮选用的History、Work、Memory、Evidence、附件或知识引用 | 不是已经采用的内容 |
| Knowledge Source / 知识来源 | 外部文档、仓库、数据库或服务中的可引用信息源 | 不是Accepted Memory，也不因被检索就自动可信 |
| ContextPackage / 上下文包 | 某次Interaction或Run实际纳入、排除、裁剪和引用的版本化快照 | 不是完整历史或MAF AgentSession |
| Context Item / 上下文项 | ContextPackage中的一条来源引用、内容投影和采用原因 | 不是无来源复制文本 |
| Compaction / Summary / 压缩摘要 | 为Token预算生成的派生表达 | 不删除原始事实，也不冒充原始Evidence |
| Memory Candidate / 记忆候选 | 模型或规则建议跨会话复用的信息 | 尚未生效，不应默认进入后续上下文 |
| Accepted Memory / 已接受记忆 | 经用户或明确规则确认、带来源、范围、版本和有效性的信息 | 不是整个Conversation History |
| Result Candidate / 结果候选 | Agent、模型或Tool产生的待校验内容 | 不是已提交Message、Evidence或工作完成事实 |
| Evidence / 证据 | 对结果、状态或外部操作的可验证材料及来源关系 | 不是隐藏推理，也不只是Assistant自述 |
| Artifact / 产物 | 文件、报告、白板、代码或其他可保存、版本化和交付的内容对象 | 不是Evidence本身，也不是临时前端视图 |
| Trace / 轨迹 | 可观察步骤、状态变化、错误、时间、关联和审计记录 | 不保存或展示模型隐藏推理 |
| Delivery / 交付 | 将结果或Artifact发送给用户或下游的状态、Attempt和回执 | 不是Product Run执行成功本身 |

## 概念关系

```text
History / Work / Accepted Memory / Evidence / Knowledge Source
-> 候选Context Sources
-> 选择与裁剪
-> ContextPackage(version, reasons, exclusions)
-> ModelCallDraft
-> Result Candidate
-> 校验和产品提交
   ├── Message
   ├── Evidence
   ├── Artifact
   ├── Trace
   ├── Memory Candidate
   └── Delivery
```

Run成功、Evidence有效、Artifact存在和Delivery成功是四个不同判断。

## 人和系统怎样使用

1. 审批页展示每个Context Item的来源和采用原因，而不是只显示一大段合并文本。
2. 完整历史作为证据保留；上下文装配器按相关性、预算和有效性选择本轮内容。
3. Memory Candidate必须等待接受；来源删除、权限撤销或事实变化时触发失效传播。
4. 模型输出先是Result Candidate，经解析、校验和提交门后才成为产品Message或其他事实。
5. Trace只记录可观察过程；用户需要解释时提供依据、来源和结果，不伪造Chain-of-Thought。
6. Delivery失败不能反向把已成功生成的Artifact改成Run失败。

## 正例与反例

正例：ContextPackage显示采用3条历史和1份Evidence，另有2条因Token预算被排除，并给出原因。

反例：系统把整个Product Session消息树全部复制给模型，却显示“采用了完整上下文”而没有Token和来源说明。

反例：模型说“用户喜欢简洁回答”，系统未经确认写入Accepted Memory。

反例：Assistant回答“文件已写入”就被当成Evidence，而没有文件哈希或Tool回执。

反例：Telegram发送失败后，把已经完成的报告Product Run标为失败。

## 当前状态与未知

当前已实现服务端唯一历史装配、产品消息恢复、基础脱敏Trace和每轮TurnSummary持久化。阶段A从最近摘要与Product Harness正式Project目录召回轻量候选；阶段B只装配已绑定Project的Work、Plan、Action、Note和Accepted Memory，并把每个Context Item的来源、revision、采用/排除原因、Token预算与Hash持久化。Note与Memory严格分离；Memory Candidate经拒绝或接受后才改变长期上下文，Note失效会使关联的Accepted Memory和候选失效。21天/28天长测证明Context不会无界叠加完整历史。当前来源失效只覆盖已实现关联类型；独立Evidence/Provenance、Artifact Store和Delivery Outbox仍未实现。
