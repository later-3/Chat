## 一句话理解

**Product Session是长期协作的内部交互与恢复容器；用户主要看到的是跨天连续对话流；Interaction是一次完整交互；Message是已提交消息；AG-UI Thread、MAF AgentSession和Workflow Checkpoint分别只服务协议、Agent上下文和控制流恢复。**

## 为什么需要

“Session”在产品、协议、模型运行时和外部平台中都存在。如果只说“恢复Session”，系统无法判断是在重新打开历史、接回事件流、恢复模型上下文，还是从Workflow暂停点继续。错误合并会导致权限越界、重复历史、错误恢复和用户输入丢失。

## 定义与边界

| 概念 | 定义 | 不是什么 |
|---|---|---|
| Input Draft / 输入草稿 | 用户尚未提交的文字、附件选择和当前编辑状态 | 不是正式Message，清空它不能删除已提交事实 |
| Product Session / 产品会话 | 用户可创建、打开、归档和恢复的长期协作容器 | 不是MAF对象、AG-UI Thread或用户身份 |
| Continuous Chat Stream / 连续对话流 | 面向用户跨Product Session、按时间连续浏览与输入的服务端投影 | 不是新的消息事实源，也不是模型默认读取的无限历史 |
| Conversation Day / 对话日 | 连续对话流按用户时区形成的自然日阅读单位 | 不是Product Session、Project或事务边界 |
| Interaction / 一次交互 | 用户与系统围绕一次输入发生的完整协作；可触发0到多个Product Run | 不是一条Message，也不必对应一次模型调用 |
| Message / 产品消息 | 用户、Assistant、Agent或Tool产生并经产品提交的可见消息 | 不是MAF Message、流式Delta或输入框草稿 |
| Message Branch / 消息分支 | 由Message父子关系形成的一条可阅读路径 | 不是模型默认应读取的全部历史 |
| AG-UI Thread / 协议线程 | `threadId`关联一次或一组实时请求、事件、State和Interrupt投影 | 不是产品事实源、身份或授权令牌 |
| MAF AgentSession / Agent运行会话 | MAF保存Agent运行上下文、服务侧Session引用和Context Provider状态的对象 | 不拥有标题、归档、Work、Evidence和产品消息树 |
| Workflow Checkpoint / 工作流检查点 | Workflow控制流在特定图版本和执行位置上的可恢复状态 | 不是Product Session，也不能证明Tool副作用结果 |

## 概念关系

```text
Product Session
├── 包含多次 Interaction
├── 包含或关联多条 Message / Message Branch
└── 关联多个 Product Run

某次 Product Run
├── 通过服务端映射关联 AG-UI Thread
├── 可以使用一个或多个 MAF AgentSession
└── 可以关联 Workflow Checkpoint

一个Continuous Chat Stream
├── 可投影多个有权限的Product Session
├── 按Conversation Day组织已提交Message与公开结果
└── 不改变原始Message、Run和Session来源

同一Principal / Harness Scope
├── 可同时打开多个独立Product Session
├── 共享Project、Work、Plan、Note、Memory与协议等权威事实
├── 各自保留Message、Interaction、Run与ContextPackage
└── 通过revision、CAS与来源Trace收敛同一资源冲突
```

这些ID即使当前碰巧同值，也只能标识各自对象，不能合并责任或作为授权。

## 人和系统怎样使用

1. 面向用户优先使用“连续对话”和“对话日”；只有恢复、诊断、归档和权限场景才显式展示Product Session及稳定定位码。
2. 点击发送前是Input Draft；接纳成功后才有正式User Message。
3. 前端以REST/Product Store恢复长期消息，以AG-UI补充活动Run投影；二者不能互相替代。
4. 模型上下文只能从选定的ContextPackage物化，不能把Product Session全部历史无边界发送。
5. 任何“恢复”操作必须进一步说明恢复的是历史、事件流、AgentSession还是Checkpoint。
6. 多个Product Session可以并行推进不同事项；相关资源被另一Session更新时，系统必须显示来源与
   冲突，不得靠最后写入者覆盖，也不得在模型或Tool外部调用期间持有全局长锁。

## 正例与反例

正例：浏览器刷新后重新打开Product Session，从Product Store看到已提交User Message；活动Run则按独立事件游标重连。

反例：前端拿AG-UI `threadId`直接判断用户是否有权打开某个Product Session。

反例：用户清空Input Draft时，后端同步删除已经接纳的User Message。

反例：Product History、MAF History和客户端消息全集同时默认进入模型，造成重复上下文。
