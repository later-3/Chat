# 意图与工作

## 一句话理解

**Intent说明系统认为用户想达成什么；WorkItem承载跨回合事项；TaskPlan描述怎样推进；ActionItem明确下一步由谁负责。**

## 为什么需要

如果把模型回答中的“你应该做X”直接当成任务，AI会替用户创建长期事实；如果把一次澄清、长期目标、计划步骤和下一动作都叫“任务”，用户无法判断系统理解了什么、已经接受了什么以及谁应该行动。

## 定义与边界

| 概念 | 定义 | 成为正式事实的条件 | 不是什么 |
|---|---|---|---|
| Intent / 意图 | 系统从输入和上下文观察到的目标、依据和不确定性 | 用户确认或明确产品规则接受某一版本 | 不是已执行命令或长期Work |
| Intent Candidate / 意图候选 | 模型或规则提出、等待检查的Intent版本 | 尚未正式生效 | 不是系统已经“知道”的事实 |
| WorkItem / 工作项 | 需要跨回合持续推进的工作或学习事项 | 经产品命令创建或采纳 | 不是聊天标题、单条Prompt或Run |
| TaskPlan / 任务计划 | 为一个或多个WorkItem组织的步骤、顺序、依赖和检查点 | 用户或策略接受某一版本 | 不是Workflow Definition或Runtime Job |
| Plan Node / 计划节点 | TaskPlan中的工作步骤或检查点 | 随所属TaskPlan版本生效 | 不是MAF Workflow Node |
| ActionItem / 行动项 | 明确由用户、AI或系统承担的下一行动 | 进入Work生命周期并具有责任人 | 不是泛泛建议或模型Tool Call |

## 概念关系

```text
一次 Interaction
-> 产生零到多个 Intent Candidate
-> 确认后可创建或更新 WorkItem
-> WorkItem 可关联版本化 TaskPlan
-> TaskPlan 包含 Plan Node
-> 当前可执行责任形成 ActionItem
-> 需要运行时再生成 ExecutionDraft / Product Run
```

TaskPlan是用户工作结构；Executable Workflow是系统执行图。两者可以映射，但不能因为节点名称相似就合并。

## 人和系统怎样使用

1. AI表达“我的理解”时展示Intent、依据和不确定性，不写成已经确认的目标。
2. 用户说“把它列为长期事项”才通过产品命令创建或采纳WorkItem。
3. 计划修改产生新版本；旧版本的执行批准不能自动覆盖新计划。
4. ActionItem必须显示责任人和完成判断，避免“我们下一步”这种无所有者表达。
5. 前端分别呈现意图审核、Work状态、计划和下一动作，不用一个聊天气泡代替全部对象。

## 正例与反例

正例：系统显示“我理解你要完成Session恢复设计，信心0.8；是否作为长期WorkItem？”用户确认后才创建。

反例：模型说“下一步应修改数据库”，系统立即把WorkItem标记为进行中并启动Tool。

反例：把TaskPlan里的“审批模型请求”节点直接当成MAF Workflow节点ID，导致计划编辑改变运行图。

反例：用一条Assistant Message的存在证明ActionItem已经完成。

## 当前状态与未知

Intent、WorkItem、TaskPlan和ActionItem是有效目标概念，但正式Schema、状态机、权限、并发和前端审核尚未实现。后续详细设计仍需决定多Intent关系、计划版本接受、责任转移和完成证据。
