**归档日期**：2026-07-30  
**分类**：调试实战  
**机器清单**：[scenario-manifest.json](./scenario-manifest.json)  
**关联源码**：[主Workflow目录](../../backend/app/workflows/catalog.py)、[图接线](../../backend/app/workflows/continuous_chat_factory.py)、[双Trace投影](../../backend/app/product_sessions/trace_reports.py)

## 问题

我不想照抄一条固定Prompt。我希望随意输入，再根据文档提前判断Chat应该怎样反应；运行时逐节点看代码和
数据；运行后用Product Store、治理记录和Trace判断它是否符合预期。应该怎样使用这套材料？

## 结论

从本页开始，调试实战不再以“把一篇课文读完”为完成，而以一个场景是否通过为完成：

```text
选择用户目的和前置状态
-> 写下运行前预言机
-> 用同一输入族内自己的Prompt发送
-> 在关键边界停断点
-> 用工作台、REST、只读SQL和双Trace对账
-> 判定通过/偏差/缺口
-> 清理本轮验证数据
```

你可以自由输入，但“自由”不等于系统的每个字都能预先固定。必须区分4种断言强度：

| 等级 | 能否精确预测 | 例子 |
|---|---|---|
| `精确 exact` | 必须相同，否则就是合同偏差 | 0次Provider Attempt、旧Hash失效、Run终态、节点选择、表行数 |
| `语义 semantic` | 文字可变，结构和产品含义必须相同 | 模型怎样解释递归；但必须是回答候选、不能创建Work |
| `观察 observe` | 只记录本轮实际值，不预设固定数字 | Token、耗时、Provider请求ID、首字节时间 |
| `缺口 gap` | 当前没有该保证 | 真实Identity、Delivery、Super Admin、任意Tool跨进程恢复 |

如果一个Prompt横跨两个输入族，例如“列出项目并修改Chat代码”，它不再属于SC01的确定性目录查询。
预期应切到多Intent/规划/执行治理场景；若系统无法稳定拆分，正确反应是澄清或失败关闭，不是强行套用
SC01的0模型结论。

第一次进场景前，先按自己的基础读4份公共底座：

1. 若不熟悉前端，先读[TypeScript与React基础](../00-从这里开始/TypeScript-React与Chat前端基础.md)。
2. 再读[Vite与浏览器API基础](../00-从这里开始/Vite-浏览器API与Chat网络调试基础.md)，看懂Network/Sources/Application。
3. [从断点停住到知道来路和下一跳](./从断点停住到知道来路和下一跳.md)：建立目录→文件→函数→调用者→下一跳的地图。
4. [一句Prompt如何逐层变成Chat对象](./一句Prompt如何逐层变成Chat对象.md)：看同一句真实输入怎样逐层增加ID、引用、状态和决策。

场景卡采用“公共主干 + 本场景分叉”，不会在15张卡里各复制一遍React、HTTP接纳、Worker和最终提交。
先走公共主干，再从卡片的“本场景在公共主干哪里分叉”进入业务差异。

## 1. 三种实验方式

### 1.1 手动调试：你亲自输入

适合学习产品实际体验。启动`Chat Full Stack`，在浏览器输入自己的Prompt；在场景卡指定的符号处下断点。
模型自然语言和耗时允许变化，确定性状态必须符合预言机。

### 1.2 自动场景：固定外部变量，验证产品合同

每张场景卡都绑定已有pytest用例。测试用受控Provider/Runtime替身固定模型返回，只为验证路由、审批、
状态机、事务、失败和恢复，不冒充真实Provider效果。

运行单场景：

```bash
.venv/bin/python -m pytest -q \
  backend/tests/test_continuous_chat.py::test_explicit_project_catalog_query_cannot_be_rewritten_as_create_or_clarify
```

### 1.3 Run复盘：给一个真实Product Run ID还原当时发生了什么

适合真实模型运行后排查。终态Run必有同源的`diagnostic`和`human`报告；旧字段缺失会写
`historical_not_recorded`，不能用当前代码猜旧Run。

```bash
.venv/bin/python -m backend.app.diagnostics_cli --run-id '<Product Run ID>'
```

也可以调用：

```text
GET /api/sessions/{product_session_id}/runs/{product_run_id}/trace
GET /api/sessions/{product_session_id}/runs/{product_run_id}/trace-reports
GET /api/runs/{product_run_id}/governance
GET /api/diagnostics/runs/{product_run_id}/timeline
GET /api/runs/{product_run_id}/step-inputs
```

对SC01–SC10这类主Workflow场景，可以直接让检查器只读human Trace并对比场景清单中的必经/禁止节点：

```bash
.venv/bin/python scripts/inspect-debug-scenario.py \
  --scenario SC01 \
  --session-id '<Product Session ID>' \
  --run-id '<Product Run ID>'
```

它只输出ID、状态、数量和节点名，不输出Prompt、Context正文或模型结果。SC11–SC15的核心预言机主要是
故障/恢复状态，不只由主Workflow节点路径决定，仍须按各场景卡的SQL/自动测试核对。

## 2. 所有场景共用的对象链

一次主Workflow请求至少要分清下面对象。ID偶尔同值也不能合并职责：

| 顺序 | 对象 | 创建者/所有者 | 主要Store | 你用它回答什么 |
|---:|---|---|---|---|
| 1 | AG-UI请求 | React `useChatAgent.send` | HTTP请求；不是事实源 | 浏览器提交了哪个threadId、runId、Workflow |
| 2 | Product Message/Interaction | `prepare_agui_run` | `messages`、`interactions` | 用户输入是否先于执行保存 |
| 3 | Product Run/Run Attempt | Product Session服务 | `product_runs`、`run_attempts` | 这次产品执行和第几次尝试是什么状态 |
| 4 | Runtime Job/Event | Runtime Execution服务 | `runtime_jobs`、`runtime_event_records` | 谁领取执行、断线后从哪里回放 |
| 5 | CollaborationState | MAF Workflow节点 | Checkpoint中的运行投影 | 当前节点下一步需要哪些引用；它不是Product Store |
| 6 | ContextPackage/Intent Set | Harness/Intent服务 | `context_packages`及Intent表 | 本轮采用了什么、系统理解了什么 |
| 7 | ExecutionDraft/RunSpec | Governance/Dispatch | 执行治理表 | 准备怎样做、用户最终授权了哪个不可变合同 |
| 8 | ModelCallDraft/Attempt | Model治理边界 | `model_call_*`表 | 实际发给Provider的版本/Hash和传输结果 |
| 9 | ToolExecution/Operation | pi/Tool治理边界 | Tool/Workspace表 | 提议、授权、执行了什么副作用 |
| 10 | Claim/Evidence/ResultCommit | Evidence模块 | Evidence 15表与Artifact Store | 为什么结果可以或不可以改变Work/Action状态 |
| 11 | Trace报告 | Product终态事务 | `trace_events`、`run_trace_reports` | 实际路径、选择原因、未走分支和限制 |

一个脱敏的AG-UI输入形态：

```json
{
  "threadId": "<Product Session ID映射>",
  "runId": "<AG-UI runId>",
  "messages": [{"id": "<AG-UI message id>", "role": "user", "content": "<你的Prompt>"}],
  "forwardedProps": {
    "workflow": {"id": "continuous-collaboration", "version": "1.8.0"}
  }
}
```

接纳门通过后返回到内部执行链的是`AcceptedRun`，关键字段是：

```text
session_id / product_run_id / interaction_id / user_message_id /
agui_run_id / provider_id / model / is_resume
```

它只保存ID映射和运行选择，不保存全部产品事实；Worker凭这些稳定引用重新读取权威状态。

## 3. 每个步骤怎样记录

每张场景卡使用同一套节点账。你调试时建议自己加一列“本轮实际值”：

| 列 | 必须回答的问题 |
|---|---|
| 目录/文件/符号 | 它属于哪个进程、架构层和产品模块；名字是文件、类还是函数？ |
| 调用者 | 同一调用栈是谁直接调用；若跨HTTP/Job/进程，用哪个ID从上一段接过来？ |
| 节点/边界 | 当前停在稳定符号还是易漂移行号？ |
| 输入对象 | 它来自`[USER]`、`[FE]`、`[AGUI]`、`[CHAT]`、`[MAF]`、`[MODEL]`还是`[DECISION]`？ |
| 选择依据 | 确定性规则、版本化Policy、用户Decision、外部证据还是模型候选？ |
| 输出对象 | 新对象、旧对象新revision、运行投影还是用户可见文本？ |
| Store变化 | 哪张表新增/更新；哪些表必须保持0变化？ |
| Trace | `executor_id`、事件、Reason Code和Sequence是什么？ |
| 用户可见 | 页面出现回答、审批、等待、失败、结果未知还是恢复入口？ |
| 失败恢复 | 能否Retry、Restart、Checkpoint Resume、Cursor Replay或只能人工处置？ |
| 责任来源 | 是框架原生、Chat适配、Chat产品治理还是尚未实现？ |
| 下一跳/按键 | 下一符号是什么；应该Step Into、Step Over还是Continue？ |

## 4. 通用断点：先用8个边界看懂全链

不要第一轮就启用全部代码级断点或给39个节点都下红点。先在8个责任边界停住；每个断点的调用者、数据、
下一跳和按键见[来路与下一跳总表](./从断点停住到知道来路和下一跳.md#3-一次发送的动态调用与下一跳)：

| # | 符号 | 观察 |
|---:|---|---|
| 1 | `App.submit` | 原始Prompt、已选Workflow |
| 2 | `useChatAgent.send` | AG-UI runId、endpoint、forwardedProps |
| 3 | `durable_agent_endpoint` | 接纳、入队和SSE订阅是3件事 |
| 4 | `ProductSessionService.prepare_agui_run` | Product Message/Interaction/Run先落库；历史/幂等/互斥门 |
| 5 | `ExecutionWorker._execute_claim` | Job、lease epoch、事件先入Journal后投影；不要用空闲也命中的`run_once` |
| 6 | `ProductAwareWorkflow.run` | Product Run/Attempt如何包住MAF Workflow与恢复 |
| 7 | 当前场景卡指定的Workflow Executor | 输入State、路由/策略、输出对象 |
| 8 | `ProductSessionService.complete_active_run` | 图完成不等于产品成功；最终Message、Run和双Trace同事务物化 |

第二轮再按场景卡逐节点走。行号只做辅助，符号名和节点ID才是稳定入口。

源码里的`breakpoint()`与`debugger;`是真正会暂停的代码，不等于IDE红点，不能靠右键“Disable Breakpoint”
关掉。普通测试应使用`PYTHONBREAKPOINT=0`，具体启停和热点断点风险看
[断点清单与调试配置](./断点清单与调试配置.md)。

## 5. 通用只读查询

默认数据库为`backend/.data/chat.db`；私有配置可能覆盖路径。只在本机确认实际路径，不读取或打印
`backend/config.json`。

```bash
sqlite3 -readonly backend/.data/chat.db
```

```sql
.headers on
.mode box

-- 1. Product Run、Attempt与重试血缘
SELECT id, status, retry_of_run_id, retry_mode, failure_code
FROM product_runs
WHERE session_id = '<Product Session ID>'
ORDER BY created_at DESC;

-- 2. Runtime Job所有权和回放边界
SELECT id, product_run_id, status, recoverability, lease_epoch,
       last_event_sequence, external_dispatch_state, failure_code
FROM runtime_jobs
WHERE product_run_id = '<Product Run ID>';

-- 3. 本轮实际有公开内容的Workflow节点
SELECT sequence,
       json_extract(payload, '$.executor_id') AS node,
       json_extract(payload, '$.content_type') AS content_type
FROM trace_events
WHERE run_id = '<Product Run ID>'
  AND event_type = 'workflow.node.content'
ORDER BY sequence;

-- 4. 模型调用只查身份、状态和Hash，不查正文
SELECT d.workflow_node_id, r.revision, substr(r.binding_hash, 1, 12) AS hash12,
       a.status, a.http_status, a.output_disposition
FROM model_call_drafts d
JOIN model_call_draft_revisions r ON r.model_call_draft_id = d.id
LEFT JOIN model_call_attempts a ON a.model_call_draft_revision_id = r.id
WHERE d.run_id = '<Product Run ID>'
ORDER BY d.call_ordinal, r.revision;

-- 5. 双Trace是否已物化
SELECT report_kind, schema_version, source_event_count, substr(content_hash, 1, 12) AS hash12
FROM run_trace_reports
WHERE run_id = '<Product Run ID>'
ORDER BY report_kind;
```

查询完整Prompt、Provider Body、Context正文、密钥或隐藏推理不属于学习实验。

## 7. 怎样判定一个场景通过

一次手动实验至少留下6项临时记录：

```text
场景ID / 自己的Prompt / Product Session ID / Product Run ID /
运行前预言机 / 实际偏差
```

满足以下条件才算通过：

1. 所有`exact`断言成立。
2. `semantic`输出没有违反来源、权限、长期事实和完成语义。
3. 实际节点路径能由同版本Workflow Definition和Reason Code解释。
4. 工作台、REST、只读SQL、human报告至少3方能对上同一Product Run。
5. 没有把测试会话、受管Workspace或临时文件长期留在正式数据中。

若不一致，先归类：文档过期、测试缺口、Trace缺字段、代码Bug、配置/前置状态不同、模型语义波动或当前
功能缺口。不要先改文档迁就运行结果，也不要先把模型文本不同判成Bug。

## 掌握验收

1. 为什么允许自由输入，却不能承诺每个Prompt固定走同一路径？
2. 对普通问答，哪些内容必须精确，哪些只能做语义断言？
3. 给一个Product Run ID，怎样证明浏览器断线没有创建第二个Provider Attempt？
4. 为什么`CollaborationState`和ContextPackage不能当成同一个对象？
5. 实际路径与场景预言机不同，你会先核对哪5类事实？
