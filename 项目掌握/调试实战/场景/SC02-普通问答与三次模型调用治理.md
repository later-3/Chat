## 1. 自由输入范围

可用：`用一句话解释递归`、`什么是幂等？只回答，不创建事项。`、`解释闭包的核心含义。`

若你要求“制定学习计划”“读取仓库证明”“修改文件”，就分别进入规划、pi只读或Workspace场景，不能再
预期恰好3次模型调用。

## 4. 三份ModelCall对象

| 调用 | `workflow_node_id` | 允许变化 | 必须固定 |
|---:|---|---|---|
| 1 | `intent_agent` | 模型对目标的自然语言摘要 | 独立revision/hash；采用去向`accepted_as_intent` |
| 2 | `response_agent` | 回答措辞 | 独立revision/hash；采用去向`accepted_as_response` |
| 3 | `turn_summary_agent` | 主题摘要表达 | 候选去向；不能自动成为Work/Accepted Memory |

每次调用的数据链：

```text
StepInputProjection
-> Provider协议专用ModelCallDraft revision
-> Policy Evaluation
-> Human/Auto Decision
-> 一次性Grant Consumption
-> Provider Attempt + transport events
-> output disposition
```

在`GovernedSemanticAgentExecutor._advance`看Draft/Policy/Interrupt；在`_deliver`看输出解析和
`output_disposition`。不要在调试器展开鉴权Header、完整Provider Body或私密Context正文。

## 5. 为什么只回答也需要ExecutionDraft/RunSpec

更简单的做法是“只回答就直接调Response Agent”。项目没有这样做，因为系统必须先确定：

1. 本轮目标、Context、协议和能力范围是什么。
2. 是否真的不需要Tool、副作用或额外权限。
3. `answer_only`是谁基于哪一版授权合同决定的。

代价是多4个确定性节点；收益是以后把同一输入升级到pi只读或写执行时，不会绕过统一授权边界。

## 6. 亲手验证

在3张模型审批卡分别记下：`workflow_node_id`、revision、binding hash前12位。批准后到治理视图确认
3个Attempt各自有`dispatch/receive/decode`里程碑和采用去向。

```sql
SELECT d.workflow_node_id, r.revision, substr(r.binding_hash,1,12),
       a.status, a.output_disposition
FROM model_call_drafts d
JOIN model_call_draft_revisions r ON r.model_call_draft_id=d.id
LEFT JOIN model_call_attempts a ON a.model_call_draft_revision_id=r.id
WHERE d.run_id='<Product Run ID>'
ORDER BY d.call_ordinal, r.revision;
```

应有3行Attempt。再核对`tool_executions`和`execution_workspaces`没有本Run新增记录。

## 7. 通过/失败

- 通过：模型正文可变，但3次独立治理、`answer_only`、0 Tool/Workspace、候选提交边界全部成立。
- 失败：3次调用共用一份Hash；摘要直接创建长期Memory；模型成功就跳过Product Finalization Gate。
