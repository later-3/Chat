# 15个场景教材深度审计与升级顺序

**审计日期**：2026-07-30  
**目的**：如实说明哪些场景已经能带小白走实值全链，哪些还只是合同卡，避免“有文档”等于“已经讲懂”

## 结论

当前15张场景已经统一补齐成熟度、证据类型、数据图、断点来路/下一跳、源码入口和安全修改边界，但仍诚实保留
不同证据等级：

- SC01为L2+；SC02、SC08、SC09为L2。
- SC03第一轮澄清和SC06来源失效失败链已有当前Workflow 1.8.0真实Run，分别是“局部L2”和“失败链L2”。
- SC04、SC05、SC07、SC11–SC15为L1+：有具体受控数据和真实组件合同，但缺同版本人工Run。
- SC10是L1+完整合同＋真实缺口样本：受控测试证明完整Evidence链，真实Run反而显示0 Artifact/Claim/Commit，
  所以不能升级为L2成功教材。

所有场景复用2个公共底座：

1. [从断点停住到知道来路和下一跳](./从断点停住到知道来路和下一跳.md)。
2. [一句Prompt如何逐层变成Chat对象](./一句Prompt如何逐层变成Chat对象.md)。

这使SC02–SC15不必各复制SC01的一千多行；每张场景只需讲清它从公共主干何处分叉、增加什么对象和决策。

## 1. 教材深度标准

| 级别 | 必须包含 |
|---|---|
| L1合同卡 | 输入族、前置状态、预言机、关键节点、通过/失败、自动测试 |
| L2实值教材 | L1 + 同一真实Run ID总账 + 每跳实际值 + Store/Trace对账 + 来路/下一跳 |
| L3开发教材 | L2 + 框架/Chat边界 + 失败恢复 + 安全修改入口 + 应补测试与影响面 |

没有真实运行证据的场景不能标为L2；自动测试替身证明产品合同，不冒充真实Provider/进程/文件系统效果。

## 3. 为什么按这个顺序升级

原升级顺序仍解释学习依赖，但不再代表“文档还没写”：

1. SC02：看懂模型不是直接调用，而是Draft→Policy→Decision→Grant→Attempt。
2. SC09：看懂Chat核心进程怎样受控地调用pi子进程和Tool。
3. SC12：看懂HTTP连接、Worker执行和恢复为什么必须分开。

学完这3张，才适合进入Context失效、Evidence、取消和跨进程HITL等组合风险。SC12已补真实Runtime组件的受控
断线数据，但还不是浏览器人工Run。以后从L1+升级L2前仍必须产生可安全公开的同版本真实Run。

## 4. 每张场景以后统一增加的7块

1. 小白前置概念：本场景出现的新名词。
2. 公共主干分叉点：从哪个Executor开始与SC01不同。
3. 业务推导：用户想达成什么、若不治理会失败什么、因此为什么新增对象。
4. 同一Run数据血缘：输入→新增字段→输出→Store，所有ID来自同一轮。
5. 框架与项目边界：MAF/AG-UI/pi原生做什么，Chat增加什么。
6. 断点导航：调用者、当前符号、下一跳、调试按键和观察字段。
7. 开发入口：改需求时从哪个模块开始、必须守什么不变量、补哪些测试。

## 5. 本轮没有冒充完成的内容

1. 文档优化不等于Identity、Delivery、Super Admin、通用Tool对账或跨进程活动pi恢复已经实现。
2. SC04/05/07/11–15仍没有当前版本人工真实Run，所以保持L1+。
3. SC10真实缺口没有用受控测试覆盖掉；修复产品链前不能标L2。
4. `scenario-manifest.json`现在记录每张卡的`maturity/evidence_kind/current_run_id`，检查器强制字段与人读成熟度存在；
   它只能防口径漂移，不能代替用户亲手调试。

## 掌握验收

4. SC02升级后下一批仍缺哪两个核心场景，它们分别建立什么能力？
