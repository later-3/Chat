# 断点清单与调试配置

本文档是调试实战的配套参考。面向不熟悉 VS Code debugpy 和 Chrome DevTools 的开发者，从基础知识开始，覆盖项目调试配置、30个断点的位置与触发时机、以及调试操作指南。

---

## 1. 调试基础知识

### 1.1 什么是断点

断点是程序执行到某个位置时自动暂停的标记。暂停后你可以查看当前变量的值、调用栈、内存状态，然后逐行执行观察程序行为。

本项目使用两种断点机制：

| 机制 | 语言 | 原理 | 显示位置 |
|---|---|---|---|
| `breakpoint()` 函数 | Python | Python 3.7+ 内置函数，调用后触发调试器暂停 | 不在 VS Code Breakpoints 面板显示，暂停时在编辑器高亮 |
| `debugger;` 语句 | TypeScript/JavaScript | JS 语言关键字，执行到该语句时触发调试器暂停 | 不在 VS Code Breakpoints 面板显示，暂停时在 Chrome Sources 面板高亮 |

**与 VS Code 红点断点的区别**：VS Code 的红点断点存在 IDE 的 workspace state 中，显示在 Breakpoints 面板。我们的 `breakpoint()`/`debugger;` 直接写在源码里，不走 VS Code 断点管理，但效果相同——执行到该行时暂停。

### 1.2 后端 Python 调试（VS Code + debugpy）

#### debugpy 是什么

debugpy 是 VS Code Python 扩展自带的调试器。当你通过 VS Code 的 "Run and Debug" 启动 Python 程序时，debugpy 会附加到 Python 进程上，拦截 `breakpoint()` 调用并在 VS Code 中暂停。

#### breakpoint() 的工作流程

```
程序执行到 breakpoint()
  → debugpy 检测到调用
  → 向 VS Code 发送暂停信号
  → VS Code 在编辑器中高亮当前行
  → 程序暂停，等待你的操作
```

关键点：
- **只有 debugpy 附加时才会被 VS Code 拦截**。如果直接在终端运行 `python -m uvicorn ...`（不通过 VS Code 调试启动），`breakpoint()` 会进入 pdb 命令行模式（终端交互式调试器），而不是 VS Code 暂停。
- **非调试运行时需要禁用**：运行测试或直接 uvicorn 前，执行 `export PYTHONBREAKPOINT=0`，这样 `breakpoint()` 会被完全跳过，不会阻塞程序。

#### VS Code 调试时的操作

暂停后，你可以用以下操作（菜单栏有对应按钮，括号是快捷键）：

| 操作 | 快捷键 | 说明 |
|---|---|---|
| 继续 | F5 | 从当前暂停位置继续执行，直到下一个断点 |
| 步过 | F10 | 执行下一行，不进入函数内部 |
| 步入 | F11 | 执行下一行，如果是函数调用则进入函数内部 |
| 步出 | Shift+F11 | 执行完当前函数，回到调用处 |
| 重启 | Ctrl+Shift+F5 | 重启调试会话 |
| 停止 | Shift+F5 | 停止调试 |

#### 查看变量

暂停后，VS Code 左侧 Run and Debug 面板显示：

- **Variables**：当前作用域的所有变量。展开对象查看属性。
- **Watch**：你可以添加表达式，持续监控某个值。比如添加 `state.collaboration_context` 来观察状态变化。
- **Call Stack**：调用栈，显示从程序入口到当前暂停位置的完整调用链。点击任意一层跳转到对应代码。
- **Breakpoints**：VS Code 红点断点列表（我们的 `breakpoint()` 不在这里显示）。

### 1.3 前端 TypeScript 调试（Chrome DevTools）

#### debugger 语句的工作流程

前端代码经过 Vite 编译后运行在浏览器中。`debugger;` 语句是 JavaScript 原生的调试关键字：

```
浏览器执行到 debugger 语句
  → 如果 Chrome DevTools 已打开，暂停执行
  → 在 Sources 面板高亮当前行
  → 如果 DevTools 未打开，该语句被忽略（不暂停）
```

关键点：
- **必须打开 Chrome DevTools**。用 F12 或右键 → "检查" 打开。如果 DevTools 未打开，`debugger;` 不起作用，程序正常执行。
- **Source Maps**：Vite 开发模式自动生成 Source Maps，让 Chrome 显示原始 TypeScript 代码而不是编译后的 JavaScript。你在 Sources 面板看到的是 `.ts` 源文件。

#### Chrome DevTools Sources 面板

当 `debugger;` 触发时，Chrome 会显示 "Paused in debugger" 提示（页面顶部黄色条）。右侧 Sources 面板显示：

- **代码区域**：当前暂停的 TypeScript 源码，高亮暂停行。
- **Scope**：当前作用域的变量（类似 VS Code 的 Variables）。
- **Call Stack**：调用栈（类似 VS Code 的 Call Stack）。
- **Watch**：表达式监控。
- **Breakpoints**：断点列表（包含 `debugger;` 语句和手动设置的断点）。

#### Chrome DevTools 调试操作

暂停后，Sources 面板右侧有按钮栏：

| 按钮 | 快捷键 | 说明 |
|---|---|---|
| Resume（播放） | F8 | 继续执行到下一个断点 |
| Step over（箭头跨过） | F10 | 执行下一行，不进入函数 |
| Step into（箭头向下） | F11 | 进入函数内部 |
| Step out（箭头向上） | Shift+F11 | 执行完当前函数 |

#### 你看到的 "Paused in debugger"

当你在前端发消息时，如果 `debugger;` 语句已注入，Chrome 会在执行到该语句时暂停。页面顶部显示 "Paused in debugger"，右侧 Sources 面板显示暂停位置的 TypeScript 代码。点击 Resume（F8）继续执行。

### 1.4 前后端同时调试

本项目支持前后端同时调试：

- **后端**：VS Code debugpy 附加到 Python 进程，`breakpoint()` 在 VS Code 中暂停。
- **前端**：Chrome DevTools 打开，`debugger;` 在 Chrome 中暂停。

两者独立工作：后端暂停不影响前端，前端暂停不影响后端。当后端暂停时，前端的 AG-UI 流式请求会等待后端响应（HTTP 连接保持）。当前端暂停时，后端正常执行但前端不显示更新。

典型调试流程：
1. VS Code 启动 `Chat Full Stack`（后端 + 前端）
2. Chrome 打开 `http://127.0.0.1:15073`，按 F12 打开 DevTools
3. 在前端发消息
4. 后端 `breakpoint()` 在 VS Code 暂停 → 检查后端变量 → F5 继续
5. 前端 `debugger;` 在 Chrome 暂停 → 检查前端变量 → F8 继续
6. 前端收到 AG-UI 事件，`onRunFinishedEvent` 的 `debugger;` 在 Chrome 暂停

## 2. 项目调试配置

### 2.1 配置文件总览

| 文件 | 职责 |
|---|---|
| `.vscode/launch.json` | 调试启动配置（单服务 + compound 组合） |
| `.vscode/tasks.json` | 清理任务（端口释放、进程终止） |
| `.vscode/settings.json` | 端口、主机、解释器等设置 |
| `scripts/cleanup-dev.sh` | 端口和进程清理脚本 |
| `scripts/setup-debug-breakpoints.py` | 断点注入/清理工具 |
| `scripts/debug-breakpoints.json` | 30个断点的配置清单 |

### 2.2 端口配置

| 服务 | 端口 | 说明 |
|---|---|---|
| 后端 FastAPI/Uvicorn | **18030** | 调试和开发统一使用，从 `.vscode/settings.json` 的 `chat.backendPort` 读取 |
| 前端 Vite | **15073** | 调试和开发统一使用，从 `chat.frontendPort` 读取 |
| pi 调试端口 | 9230 | Node.js Inspector，仅在 pi External Source Debug 模式使用 |

端口选择原则：使用高位非标准端口（18030/15073），避免与其他开发工具冲突。

### 2.3 调试启动配置（launch.json）

#### 单服务配置

| 配置名 | 类型 | 说明 |
|---|---|---|
| Chat Backend (MAF + FastAPI) | debugpy | 后端主服务，`--reload` 热重载 |
| Chat Backend (pi External Source Debug) | debugpy | 后端 + pi 源码调试模式 |
| Chat Frontend (React + Vite) | node-terminal | 前端 Vite 开发服务器 |
| Chat Backend API (External Workers) | debugpy | 仅 API 服务，Worker 独立启动 |
| Chat Execution Worker | debugpy | 独立 Execution Worker |
| Chat Outbox Worker | debugpy | 独立 Outbox Worker |

#### 组合配置（compound）

| 配置名 | 包含 | 说明 |
|---|---|---|
| **Chat Full Stack** | Backend + Frontend | 最常用，一键启动前后端 |
| Chat Full Stack (pi External Debug) | Backend(pi调试) + Frontend | 需要调试 pi 源码时使用 |
| Chat Distributed Stack | API + Execution Worker + Outbox Worker + Frontend | 分布式模式，各服务独立进程 |

每个 compound 都有：
- `preLaunchTask: "chat: prepare normal full stack"` → 启动前清理端口和残留进程
- `postDebugTask: "chat: cleanup all"` → 结束后清理端口
- `stopAll: true` → 停止时同时停止所有子配置

### 2.4 清理机制

每次调试启动前和结束后，VS Code 自动执行清理任务：

```
启动调试
  → preLaunchTask: chat: cleanup all
    → scripts/cleanup-dev.sh all 18030 15073
      → 释放端口 18030（后端）和 15073（前端）
      → 终止残留的 Uvicorn、Vite、pi 进程
      → 等待端口完全释放（含 TIME_WAIT 处理）
  → 启动后端 debugpy
  → 启动前端 Vite

停止调试
  → postDebugTask: chat: cleanup all
    → 同上，确保下次启动干净
```

清理脚本只终止属于本项目的进程（通过路径匹配），不会影响其他应用。

### 2.5 断点注入工具

#### 使用方法

```bash
# 注入全部30个断点到源码
.venv/bin/python scripts/setup-debug-breakpoints.py

# 清理全部断点，恢复源码
.venv/bin/python scripts/setup-debug-breakpoints.py --clean

# 查看注入状态（哪些已注入，哪些未注入）
.venv/bin/python scripts/setup-debug-breakpoints.py --status

# 列出所有断点及其触发时机
.venv/bin/python scripts/setup-debug-breakpoints.py --list
```

#### 工作原理

1. 读取 `scripts/debug-breakpoints.json` 配置
2. 对于 Python 断点：用 `ast` 模块解析源码，找到函数定义，在函数体首行（跳过 docstring）插入 `breakpoint()`
3. 对于 TypeScript 断点：用文本搜索定位函数定义，在函数体首行插入 `debugger;`
4. 每个断点带唯一标记注释（`# DEBUG-BREAKPOINT: BP-XX`），确保注入和清理幂等

#### 注意事项

- **注入后修改了源码文件**：后端 uvicorn `--reload` 会检测到文件变化并自动重载，这是正常的
- **非调试运行前必须禁用**：`export PYTHONBREAKPOINT=0`，否则 `breakpoint()` 会进入 pdb 阻塞程序
- **前端 `debugger;` 无需特殊处理**：DevTools 未打开时自动忽略
- **调试结束后建议清理**：`--clean` 恢复源码，避免提交到 Git

> **前端调试前提**：必须在 Chrome 中打开 DevTools（F12），否则 `debugger;` 语句被忽略。暂停时页面顶部显示 "Paused in debugger"，Sources 面板显示暂停位置的 TypeScript 源码。

### 3.3 频率分类速查

| 频率 | 断点 | 调试建议 |
|---|---|---|
| **频繁触发** | BP-02（Worker空转）、BP-08（Trace写入） | 调试时如干扰可暂时禁用 |
| **每条消息1次** | BP-01、04、09、10、11、16、20、21 | 适合观察单次消息处理流程 |
| **每个Run 1次** | BP-06、07、19、22 | 适合观察Run生命周期 |
| **每次模型调用1次** | BP-13、14、15 | 适合观察模型调用审批流程 |
| **条件性** | BP-05、12、17、30 | 只在特定场景触发 |
| **仅pi启用时** | BP-24、25、26 | 未启用pi时不会触发 |

## 4. 调试操作指南

### 4.1 启动调试

#### 后端 + 前端（最常用）

1. 确保 `debugger;` 和 `breakpoint()` 已注入：
   ```bash
   .venv/bin/python scripts/setup-debug-breakpoints.py --status
   # 如果全部"未注入"，运行：
   .venv/bin/python scripts/setup-debug-breakpoints.py
   ```

2. 在 VS Code 左侧 Run and Debug 面板，选择 **Chat Full Stack**，按 F5 启动。

3. VS Code 自动执行：
   - 清理端口 18030/15073
   - 启动后端 debugpy（`uvicorn ... --port 18030 --reload`）
   - 启动前端 Vite（`npm run dev -- --port 15073`）

4. 用 Chrome 打开 `http://127.0.0.1:15073`，按 F12 打开 DevTools。

5. 在前端发消息，程序会在注入的断点处暂停。

#### 仅后端

选择 **Chat Backend (MAF + FastAPI)**，按 F5。前端不启动。

#### 分布式模式

选择 **Chat Distributed Stack**，按 F5。API、Execution Worker、Outbox Worker、Frontend 分别在独立进程启动。

### 4.2 调试时的操作

#### 后端暂停时（VS Code）

- **查看变量**：左侧 Variables 面板，展开对象查看属性。
- **查看调用栈**：左侧 Call Stack 面板，点击任意层跳转到对应代码。
- **添加 Watch**：在 Watch 面板点击 `+`，输入表达式如 `state.collaboration_context`。
- **继续执行**：F5（继续到下一个断点）。
- **步过**：F10（执行下一行，不进入函数）。
- **步入**：F11（进入函数内部）。
- **停止调试**：Shift+F5（会自动触发清理任务释放端口）。

#### 前端暂停时（Chrome DevTools）

- **查看变量**：右侧 Scope 面板。
- **查看调用栈**：右侧 Call Stack 面板。
- **继续执行**：F8 或点击播放按钮。
- **步过**：F10。
- **步入**：F11。
- **取消暂停**：点击 "Deactivate breakpoints" 按钮（类似暂停图标），临时禁用所有 `debugger;` 语句。

#### 同时调试前后端

后端在 VS Code 暂停时，前端的 HTTP 请求会等待（连接保持）。你可以在 VS Code 检查后端状态后 F5 继续，然后到 Chrome 检查前端状态。两端独立操作。

### 4.3 模型调用审批流程与断点

用户发消息后看到的"模型调用审批"是产品功能（不是断点暂停），对应以下断点链路：

```
BP-13 prepare     ← 构造 ModelCallDraft（此时前端显示审批卡片）
  ↓ [用户在前端点击"批准"]
BP-14 _advance    ← 发送 Provider 请求
  ↓ [Provider 返回结果]
BP-15 _deliver    ← 交付结果到产品层
```

如果你在 BP-13 暂停时查看变量，可以看到 ModelCallDraft 的内容（Provider 请求候选）。在 BP-14 暂停时可以看到审批已通过、即将发送请求。在 BP-15 暂停时可以看到 Provider 返回的结果。

### 4.4 停止调试

按 Shift+F5 停止。VS Code 会：
1. 终止 debugpy 进程
2. 执行 `postDebugTask: chat: cleanup all`
3. 释放端口 18030/15073
4. 终止残留的 Uvicorn、Vite、pi 进程

下次启动时 `preLaunchTask` 会再次清理，确保干净启动。

### 4.5 清理断点

调试结束后，恢复源码：

```bash
.venv/bin/python scripts/setup-debug-breakpoints.py --clean
```

这会删除所有 `breakpoint()` 和 `debugger;` 行，源码完全恢复。

### 4.6 常见问题

#### Q: 程序启动后立即进入 pdb 模式（终端显示 `> ... (Pdb)`）

原因：直接在终端运行了 `python -m uvicorn ...`，没有通过 VS Code 调试启动，`breakpoint()` 进入了 pdb。

解决：
- 临时禁用：`export PYTHONBREAKPOINT=0` 然后重新运行
- 或清理断点：`python scripts/setup-debug-breakpoints.py --clean`

#### Q: 后端断点不触发

检查清单：
1. 断点是否已注入：`python scripts/setup-debug-breakpoints.py --status`
2. 是否通过 VS Code 调试启动（不是终端直接运行）
3. `PYTHONBREAKPOINT` 环境变量是否设为 `0`（如果是，取消设置：`unset PYTHONBREAKPOINT`）

#### Q: 前端断点不触发

检查清单：
1. Chrome DevTools 是否已打开（F12）
2. 断点是否已注入：检查 `frontend/src/App.tsx` 中是否有 `debugger;` 语句
3. 是否在正确的端口打开页面（`http://127.0.0.1:15073`）

#### Q: 端口被占用（Address already in use）

```bash
# 手动清理
.venv/bin/python scripts/cleanup-dev.sh all 18030 15073

# 或直接清理端口
lsof -tiTCP:18030 -sTCP:LISTEN | xargs kill -9
lsof -tiTCP:15073 -sTCP:LISTEN | xargs kill -9
```

#### Q: `--reload` 导致断点失效

uvicorn `--reload` 模式下，修改源码会触发重载。断点注入修改了源码，可能触发重载。这是正常的——重载后 debugpy 仍然附加，断点继续生效。如果重载后断点不触发，尝试停止调试（Shift+F5）后重新启动（F5）。

#### Q: BP-02 频繁暂停

BP-02 `ExecutionWorker.run_once` 是 Worker 心跳循环，空闲时也触发。调试时如干扰：
- 方案1：在 VS Code 中右键该行 → Disable Breakpoint
- 方案2：注释掉该行的 `breakpoint()`
- 方案3：用 BP-03 `_execute_claim` 替代（只在有 Job 时暂停）
