## 这课解决什么

第2课给了断点清单，但只告诉你“在哪停”。本课回答更深的问题：**每个函数为什么存在、
它在守哪条产品规则、停在那里应该看到什么**。所有“实测值”都来自2026-07-29真实运行的
落库数据（Run ID可查），不是示意。

先读第1节建立分层心智，再按第2节逐个函数精读，第3节用7个场景把不同分支走全，
第4节是实测中发现的4个真实行为（含1个已修复的配置回归）。

## 2. 逐层函数精读：为什么、看什么、实测值

### 第1层：前端（只投影，不拥有状态）

**`App.submit` → `useChatAgent.send`**（frontend/src/use-chat-agent.ts）

- **为什么**：产品规则“发送前可见”——发送时必须把Workflow选择、控制字段随请求固化，
  不允许运行中切换。所以`send`先把`workflow`塞进`forwardedProps`再发。
- **断点看**：`runId`（本次AG-UI关联ID）、`agent.url`（本轮回路端点）。
- **失败模式**：`agent.isRunning || pendingReview`时直接return——前端互斥只是体验层，
  真正的互斥在第2层服务端。

**`subscribe`的`onRunFinishedEvent`**（同文件）

- **为什么**：AG-UI把“中断”和“结束”都装在RUN_FINISHED里，靠`result.outcome`区分。
  前端必须把interrupt翻译成审批卡，否则用户不知道系统在等他。
- **断点看**：`result.outcome.type`——`"interrupt"`时取
  `interrupt.metadata.agent_framework.data.review_kind`（实测3种：
  `model_call`/`product_decision`/tool类），**注意不在`interrupt.value`里**
  （我第一版脚本就踩了这个坑，value是空的）。

### 第2层：接纳门 `prepare_agui_run`（service.py:619）——HTTP终止处

这是全系统最重要的函数之一。**为什么每道检查都存在**（按执行顺序）：

| 检查 | 守的产品规则 | 断点观察 | 实测 |
|---|---|---|---|
| threadId/runId必填 | 无关联ID不能落库 | `input_data`键 | — |
| resume分流 | 恢复与新建是两种入口 | `input_data.get("resume")` | B-G每次批准都走这 |
| 相同runId幂等回放 | 双击/网络重试不产生两次执行 | `existing_protocol` | — |
| 归档会话拒绝 | 归档=冻结 | `session.status` | — |
| 单活动Run互斥 | 状态机可恢复的前提 | `session.active_run_id` | — |
| **历史前缀+恰好1条新User消息** | 浏览器历史只是投影，服务端才是权威 | `incoming` vs `persisted`逐条比对id+role+**内容Hash** | 我伪造历史时被拒2次：`SESSION_HISTORY_CONFLICT`；水合必须用服务端返回的`agui_message_id`，不是产品消息ID |
| 同事务落库Interaction+Message+Run | **输入先于执行持久化**，Worker崩了也能对账 | 事务内4张表 | A轮`request_hash=a19d7cc9…` |

- **断点**：`service.py` `prepare_agui_run`，逐行看这6道门。返回值`AcceptedRun`
  里有`product_run_id`——**这是之后查Trace/SQL的钥匙**，先抄下来。

### 第3层：Worker `_execute_claim`（runtime_execution/worker.py）

- **为什么存在**：执行权与HTTP连接解耦（架构规则：SSE断开≠取消Run）。
  所以每个事件先写Journal再转发，浏览器只是“其中一个订阅者”。
- **断点看**：
  - `payload.type`逐事件——你会看到B轮中断后Worker并不退出，而是把Run置为
    `waiting_human`挂起（`_is_interrupt`：interrupt是**伪装成终态的等待**）；
  - `_require_product_terminal`——**没有产品终态事件就不算完成**，防止MAF正常
    结束但产品提交失败时被误标succeeded。

### 第4层：Workflow外层 `ProductAwareWorkflow.run`（workflows/runtime.py:120）

- **为什么Product要包住MAF**：MAF知道怎么跑图，但不知道“这算哪次产品运行、
  什么时候算成功、失败了历史怎么办”。产品生命周期（Run/Attempt/提交/历史关联）
  必须由产品层持有（架构规则5：四对象不混用）。
- **断点看**：`input_data`里的`resume`——B-G轮每次批准都从这里恢复MAF图。

### 第5层：39节点内部（4个必须读懂的函数）

**① `GovernedSemanticAgentExecutor.prepare`**（continuous_chat.py）——短路判定

- **为什么**：目录查询这类问题有权威数据源（Product Harness），问模型只会更慢、
  更贵、还可能编。确定性护栏`is_project_catalog_query`（contracts.py:310）命中时
  直接产出意图，**0次模型调用**。
- **断点看**：A轮命中→`execution_mode:"deterministic_guard", model_call_count:0`（Trace seq20）；
  B-G轮不命中→进入`_advance`。

**② `GovernedSemanticAgentExecutor._advance`**——每次模型调用的治理链

- **为什么**：产品规则“每次模型调用发送前审批”。所以链是：
  `新鲜度核验 → 构造ModelCallDraft(含绑定Hash) → register_model_call(策略评估) →
  deny关闭 / auto消费Grant发送 / require_human发interrupt`。
- **断点看**（B轮seq20-21实测）：`policy_action="require_human"`、
  `model_call_revision_id=263fed56…`。批准后Resume进`_deliver`：
  **模型输出只是候选**，`output_disposition`记录采用去向——B轮3次实测：
  `accepted_as_intent`（1634+347 tok）、`accepted_as_response`（1712+70）、
  `accepted_as_summary`（860+217）。
- **新鲜度核验的实测**：D轮第一次失败就是因为`_require_fresh_context`发现我当天
  改了仓库治理文档（`ContextSourceStale: 仓库治理文档大小已变化`）——
  **上下文过期时拒绝用旧快照回答，而不是假装最新**。刷新端点：
  `POST /api/harness/repositories/{binding_id}/refresh`（快照13→14后重跑成功）。

**③ `ScenarioRouterExecutor.route`**（节点16）——可解释路由

- **为什么**：产品要求“未走的边也要有原因”（反例043）。所以不是返回一个分支名，
  而是对4条Case全量求值并记录。
- **断点看**：`route_decision.options`——A轮实测Case#1命中（`matched:true, selected:true`，
  其余3条`matched:false`+原因）；B轮4条都没命中→Default（`前三条Case均未命中，MAF执行Default分支`）。

**④ `route_from_run_spec`**（execution_dispatch/contracts.py:129）——防注入升级

- **为什么只看批准的RunSpec、绝不回看用户原文**：注释原话“Routing after approval must
  not reinterpret text”——用户在执行阶段说句话不能把只读请求升级成写入。
  所以`recommends_pi_workspace_edit`（drafts.py:161）用词表确定性判定，**词表不命中
  就fail closed到answer_only，绝不猜**。
- **实测**：F轮第一次“创建hello.txt”不命中词表（词表有“编辑文件/修改代码”但没有
  “创建文件”）→`answer_only`；改成“请编辑文件：…”后命中→走通pi_workspace整条链
  （seq101工作区准备→120装配→123/125 Claim）。

### 第6层：图外提交门 `complete_active_run` + SSE回流

- **为什么提交在图外**：MAF的图正常结束≠产品成功。节点39只`yield`候选；
  真正写Assistant Message、置Run终态、生成双Trace报告的是产品层——**这是用户看到的
  “成功”的唯一定义点**（A轮seq72：`assistant_message_id=3a2278ad…`）。
- **断点看**：`committed`返回值。若为None，Run会被置failed而非succeeded。

## 3. 七个场景的分支全景（每条链路学到了什么）

### A：确定性目录查询（0.64s，72条Trace）

```text
S1(1-5) → 节点6短路 → S2(7-15) → 节点16 Case#1 → 节点17权威查询 → 34-39提交链
```
- 跳过：18澄清、19规划、20-31执行、32答复Agent、33摘要Agent（答复由节点17直接产出）。
- **学到**：确定性问题的完整骨架；human Trace实际为23节点经过/16节点未访问，全部有reason code。

### B：简单问答（19.1s，120条Trace）

```text
S1 → 节点6完整治理链(中断#1) → S2 → 节点16 Default → 20-23执行准备 → answer_only
→ 节点32答复(中断#2) → 节点33摘要(中断#3) → 34-39
```
- **学到**：Default分支也要先编译ExecutionDraft/RunSpec再决定动不动执行；
  `execution_route=answer_only`是RunSpec的确定性结论，不是省略。

### C：澄清（1次模型调用）

```text
S1 → 节点6(中断#1) → S2 → 节点16 Case#2 → 节点18直接产澄清问题 → 38-39
```
- 实测答复：“‘那个事’是指哪个项目？当前有两个活跃项目：1) SD3… 2) Chat…请直接回答。”
- **学到**：澄清分支不经过答复Agent，节点18自己产出问题；代价最低（1次模型）。

### D：规划（4次模型+2次人工决定）

```text
S1 → 节点6(中断#1意图) → S2 → 节点11项目绑定(中断#2 product_decision→accept)
→ 节点16 Case#3 → 节点19规划Agent(中断#3) → plan_acceptance自动 → 20-23 → answer_only
→ 节点32(中断#4) → 33(中断#5) → 节点36 Memory提交(中断#6 product_decision→commit)
```
- **学到**：①product_decision的允许动作**按决定点不同**（绑定=`accept`、提交类=`commit`，
  我脚本因发错action被拒两次：`GovernanceValidationError: 请求项不允许该决定`）；
  ②模型产的Memory候选（FTS5技术选型）必须人工`commit`才进长期Memory——
  **模型输出只是候选**规则的直接体现。

### E：pi只读执行（7次模型，其中6次是pi自己的）

```text
…Default → 20-23 → execution_route=pi_readonly → 节点24/26 pi只读派发
（pi内部：6次模型边界审批 + ls/find只读工具）→ 27/31装配 → 32-33 → 提交链
```
- 实测答复带证据：“已通过工具实际读取仓库快照（snapshot id: 8601c70a…），
  ls实际输出，find交叉验证”。只读工具**策略自动批准**（无tool中断），
  但pi的**每次模型调用仍逐一审批**（中断#3-#8）。
- **学到**：Chat对pi的治理是逐次模型调用级别的，不是“放行整个pi”。

### F：pi工作区编辑（链走通，pi拒绝编辑，系统诚实收场）

```text
…Case#3规划 → 20-23 → pi_workspace → 节点25/28工作区准备+派发（2模型+2只读工具）
→ 30装配{model_call_count:2, tool_call_count:2} → 31 Claim准备
→ Claim决定: not_applicable(no_committed_edit_operation) → 33-39
```
- pi检查工作区后**拒绝创建文件**（治理edit工具只对已存在文件做精确替换，不支持新建），
  最终答复如实说明“无法继续执行的原因”。
- **学到**：没有编辑产物时Claim链诚实落`not_applicable`，**不产生假成功**（产品规则6）。

### G：放弃（<1s，0次Provider发送）

```text
S1 → 节点6 Draft+中断 → abandon → seq29 run.abandoned → Run置abandoned
```
- SQL实测：`model_call_attempts`=**0**，Revision保持`reviewable`（从未发送）。
- **学到**：abandon=零Provider接触，Draft留在库中可审计。

## 4. 实测发现的4个真实行为

1. **【已修复】ark配置回归**：protocol=`openai_responses`但capabilities是chat风格
   （`text`），所有模型调用挂在节点6。修复21处内容类型（选“修能力表”因为昨天的
   Attempt全HTTP 200证明协议可用、`max_output_tokens`等参数本就是Responses风格）。
   **教训：config.json变更必须重启后端，`--reload`不监听它。**
2. **新鲜度门真实生效**：我当天改仓库文档→D轮被拒`ContextSourceStale`→
   刷新快照后放行。过期上下文宁可拒答不用旧快照。
3. **词表覆盖缺口**：`PI_WORKSPACE_EDIT_TERMS`（drafts.py:49）没有“创建文件/新建”，
   创建类请求会fail closed到answer_only。行为安全（不猜），但覆盖面可以考虑补——
   **这是一个可讨论的候选改进，不是bug**。
4. **pi编辑工具能力边界**：edit=对已存在文件的精确替换，不支持新建文件；
   pi正确识别并拒绝，系统诚实落`not_applicable`。

## 5. 手动复现与断点对照

复现步骤同第2课第6节（curl建会话→POST→SQL查Trace）。打断点时对照本课第2节：
每个函数都给了“停在哪、看什么、实测值是多少”——**你的单步值和第2节的实测值
对上了，就说明你读懂了这一层**。推荐顺序：先在`prepare_agui_run`看6道门（A轮），
再在`_advance`看治理链（B轮），最后在`route`看4条Case求值（任意轮）。
