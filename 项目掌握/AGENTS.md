# 项目掌握知识库 — AI Agent 协作规则

## 1. 目录职责

本目录是**用户掌握整个 Chat 项目的个人知识库**。每个与用户交流的 AI Agent 都必须：

1. 在回答问题前，先检查本目录是否已有相关归档。
2. 回答完成后，按本文件规定的结构归档到对应文档。
3. 如果已有文档覆盖了当前问题，直接引用并补充新发现，不重复创建。

## 2. 目录结构

```
项目掌握/
├── AGENTS.md          ← 本文件：Agent 协作规则
├── INDEX.md           ← 全局索引：按分类列出所有已归档问题
├── <分类文件夹>/
│   ├── <问题文档>.md  ← 一个问题一个文档
│   └── ...
└── ...
```

## 3. 命名规则

| 对象 | 规则 | 示例 |
|------|------|------|
| 分类文件夹 | 简短中文短语，描述问题领域 | `执行层与pi运行时` |
| 问题文档 | 简短中文问句或主题名 | `pi子进程在哪里启动.md` |

## 4. 问题文档格式

每个问题文档必须包含：

```markdown
# <问题标题>

**归档日期**：YYYY-MM-DD
**分类**：<分类文件夹名>
**关联源码**：<关键文件路径列表>

## 问题

<用户原始问题或精炼后的问题>

## 回答

<结构化的回答内容>

## 关键文件

| 文件 | 职责 |
|------|------|
| ... | ... |

## 补充记录

<后续对话中的补充、修正或新发现，按日期追加>
```

## 4.1 面向小白的强制解释顺序

只写“节点、类、字段和阶段”不算讲懂。每篇实质性学习文档必须按以下顺序组织；某项确实不适用时，
要写明原因，不能静默省略：

1. **一个具体场景**：先固定一条用户输入和可见结果，不从术语表开场。
2. **要解决的问题**：说明如果没有这层设计，用户会遇到什么真实错误。
3. **一句人话定义**：首次出现英文名时同时给出中文含义和“它不是什么”。
4. **一个具体对象样本**：用脱敏的JSON、表格或数据库行展示本轮真实形态。
5. **对象生命周期**：谁创建、从哪里读取、存在内存还是数据库、谁修改、谁消费、何时结束。
6. **为什么这样设计**：至少比较当前方案与1个看似更简单的替代方案，说明取舍。
7. **代码链**：按实际执行时间列出符号名和可点击源码；行号只能辅助，符号名才是稳定入口。
8. **亲手验证**：给出断点、应观察的变量、无敏感正文的数据库/Trace查询和预期现象。
9. **掌握验收**：给出3到5个复述或小改动问题；能回答才算完成，不以“文档读完”为完成。

首次解释`Session`、`Run`、`Workflow`、`Context`、`Agent`、`Tool`、`Approval`或`Canvas`时，必须使用
限定名并说明相邻对象，不能把同名对象合并。

## 4.2 三层材料必须分开

同一主题按用途分为3层，避免一篇文档同时承担全部责任：

1. **总地图**回答系统有什么、为什么存在、一次操作如何穿过系统。
2. **专题文档**回答一个概念或能力的对象、状态、代码和设计取舍。
3. **调试实验**让用户通过断点、数据库和Trace亲眼验证。

项目交付阶段、Workflow节点阶段和学习顺序是3套不同维度。不得用“阶段A/节点3”替代产品架构，
也不得把学习顺序写成新的产品实现事实。

## 4.3 全盘覆盖是硬门，不是写作感觉

任何Agent声称“全面、完整、全盘”前，必须同时维护4本账：目标能力、当前实现、学习单元和显式缺口。

1. 先读取`00-从这里开始/全盘掌握范围与覆盖审计.md`与`coverage-manifest.json`。
2. 运行`.venv/bin/python scripts/check-project-mastery.py`，不得留下未映射的后端/前端源码面、Workflow或节点。
3. 新增顶层源码面、前端Feature、Workflow、主Workflow节点或目标模块时，同步更新机器清单和人读总账。
4. 代码塞进已有目录但产生新对象、状态所有权、协议、进程或质量责任时，也要人工新增/调整学习单元。
5. “已映射”不等于“已掌握”。没有小白专题、调试实验和掌握验收时，状态必须保留为`待补`。
6. 当前未实现的Identity、Delivery、Super Admin和非功能保证不能从总账删除，必须标为目标或缺口。

## 4.4 先讲“源码怎样成为正在运行的系统”

面向只掌握少量C/C++基础的读者，不得从“启动Vite和FastAPI”开始并把它们当作已知黑盒。

1. 先对照C++的“源码→编译/链接→可执行文件→进程”，说清TypeScript/TSX由Vite转换后在浏览器执行，Python模块由CPython/Uvicorn加载后成为Web服务。
2. 第一次实质使用前解释Runtime、进程、IP、端口、客户端/服务端、HTTP、JSON、DTO、SSE、环境变量和依赖锁；每个词要指向当前项目实例。
3. 启动说明必须展开为“命令→配置→进程→端口→入口模块→用户可见结果”，并给出`lsof`、健康探针和浏览器Network的亲手观察。
4. 必须区分架构模块、逻辑运行角色、OS进程和部署选择；不得因为API/Execution/Outbox在开发模式共进程，就把它们写成同一责任。
5. 架构、对象和SC文档可以链接统一运行基础课，但首次使用关键概念仍须就地提醒边界，不能只丢文件名让用户自行搜索。

## 5. Agent 执行流程

1. **定位**：先从 `INDEX.md` 判断问题属于总地图、专题还是调试实验。
2. **查重**：检查是否已有同类问题；已有文档必须先读取。
3. **补前提**：如果用户卡在某个术语，先补其来源和具体样本，再继续解释下游节点。
4. **核代码**：以当前源码、测试和Schema为准；明确区分当前实现与目标设计。
5. **归档**：创建新文档；补充新发现时可追加记录，发现与当前代码冲突的旧事实时必须直接改正正文，
   不能让读者先读一遍错误说法再去文末找纠正。
6. **可验证**：提供断点/查询/Trace路径和掌握验收题。
7. **更新索引**：新增文档或改变掌握状态时，同步更新 `INDEX.md`。

## 6. 禁止事项

1. 不得把多个不相关问题合并到一个文档。
2. 不得在回答后忘记归档。
3. 不得为了保留写作历史而保留已经被代码推翻的口径；Git历史负责保存旧版本，当前正文只表达当前代码事实。
4. 不得用字段名的英文拆词或同义改写冒充第一性原理解释。
5. 不得只给调用链而不说明每一步拿到的具体对象和为什么需要它。
6. 不得把模型候选、运行时状态、协议投影或前端状态写成Product Store权威事实。
7. 不得让用户通过输出密钥、完整Prompt、Provider Payload或私密正文来完成调试实验。
8. 不得用一个详细案例、一个Workflow或一组数据库表冒充整个Chat的覆盖范围。

## 7. Workflow口径的唯一来源

持续协作主Workflow的教学分组由
`backend/app/continuous_workflow_learning.py::CONTINUOUS_WORKFLOW_LEARNING_STAGES`唯一拥有。所有教材、
Trace人读标签和代码注释统一使用`S1`到`S7`，并由`backend/tests/test_continuous_workflow_learning_comments.py`
与`scripts/check-project-mastery.py`反向核对真实Workflow Definition。

必须同时区分5种数量：

1. 项目交付阶段：`PROJECT_PLAN.md`中的阶段0到8，共9个。
2. 主Workflow学习阶段：S1到S7，共7个。
3. Context装配步骤：`directory/detail`共2步；历史材料中的“阶段A/B”只能作为旧别名出现。
4. 单模型审批Workflow的代码阶段：仅`chat-model-call-approval`使用，共12个。
5. 主Workflow可达路径：按两个Switch分支形成8种典型路径，不是8个阶段。

文档不得自行重新发明阶段名、节点范围或数量。主Workflow版本、节点和边来自
`backend/app/workflows/catalog.py`；学习阶段来自上述唯一模块；实际接线来自
`backend/app/workflows/continuous_chat_factory.py`。
